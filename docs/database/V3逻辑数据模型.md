
# V3逻辑数据模型

生成日期：2026-07-23

## 1. 建模结论

阶段2先交付可审查、可迁移、可测试的PostgreSQL 16数据底座资产，不接入现有运行服务，不修改任何SQLite样本库和业务代码。

本模型采用“模块化单体 + 关系型强约束 + 迁移暂存追溯”的设计：

- 业务主键统一使用 `uuid`，V2原始编号保存在 `v2_source_id` 或迁移映射表中。
- 金额字段使用 `numeric(18,2)`，数量使用 `numeric(18,4)`，比例使用 `numeric(9,4)`，不使用浮点数。
- 关键业务对象保留当前状态列，同时建立事件或历史表，禁止把全部生命周期塞进一个万能状态字段。
- 当前功能之外的公海池、营销自动化、通用SaaS租户表不进入阶段2模型。
- 正式表只保存业务必要字段；不确定、低频、历史兼容字段先进入迁移暂存或明确 `jsonb` 扩展列，后续由产品签字再固化。
- 本地密码和开放接口密钥在迁移装载时转换为散列，正式表和中间导出文件都不输出明文。

## 2. 逻辑分区

| 逻辑域 | PostgreSQL schema | 覆盖对象 | 阶段2目标 |
| --- | --- | --- | --- |
| 迁移框架 | `migration` | 迁移版本、批次、原始记录、错误、校验 | 可重复导出、导入、清洗、装载、校验 |
| 账号权限 | `iam` | 用户、密码凭据、外部身份、角色、权限 | 服务端权限底座前置模型 |
| 组织区域 | `org` | 大区、区域、组织节点、员工画像 | 数据范围和查询索引基础 |
| 渠道 | `channel` | 渠道主档、上下级关系、成员、画像 | 支持几百到几千渠道商 |
| 产品目录 | `catalog` | 大类、模块、功能、硬件、套餐、价格、工作量 | 报价和订单计算底座 |
| CRM主链路 | `crm` | 客户、报备、商机、跟进、报价、订单 | 支持百万客户和高增长业务数据 |
| 运营任务 | `ops` | 通知、审批、文件、导入导出任务、幂等、发件箱 | Redis任务化前的数据基础 |
| 开放接口 | `integration` | 客户端、密钥、权限、访问日志 | 保持当前开放接口兼容和审计 |
| 审计 | `audit` | 操作审计分区表 | 高增长审计可归档、可查询 |

## 3. 核心实体关系

账号通过 `iam.user_roles` 获得角色，通过 `org.regions`、`org.org_units`、`channel.partner_members` 获得数据范围。渠道关系由 `channel.partner_relations` 记录，避免只在渠道主档上写一个上级编号导致历史不可追溯。

客户主档 `crm.customers` 从报备、商机、报价、订单中的客户字段归一化生成。报备、商机、报价、订单各自保留业务主表和历史事件表，支持后续权限校验、状态回放和迁移差异排查。

产品目录、价格规则和工作量规则进入 `catalog` 域，报价单通过 `crm.quote_snapshots` 保存生成时快照，避免后续产品价格调整影响历史报价。

## 5. 当前状态与历史事件

| 业务对象 | 当前值字段 | 历史表 | 说明 |
| --- | --- | --- | --- |
| 用户 | `iam.users.status_code` | 后续阶段3接入审计 | 当前只迁移现状，变更由审计记录 |
| 渠道 | `channel.partners.status_code`、`partner_level_code` | `channel.partner_relations` | 上下级变化必须留历史 |
| 报备 | `crm.registrations.status_code` | `crm.registration_events` | 审核、驳回、复制、转商机均进入事件表 |
| 商机 | `crm.opportunities.stage_code`、`status_code` | `crm.opportunity_stage_history` | 历史中文阶段原值保留在 `raw_stage_name` |
| 报价 | `crm.quotes.status_code` | `crm.quote_status_history` | 转订单和审批必须可回放 |
| 订单 | `crm.orders.status_code` | `crm.order_status_history` | 一级确认、驳回、取消留痕 |
| 审批 | `ops.approvals.status_code` | `ops.approval_events` | 当前审批与历史处理拆分 |

## 6. `jsonb`使用边界

允许使用 `jsonb` 的场景：

- 迁移暂存表保存原始JSON。
- 报价快照保存历史产品结构、计算输入和输出。
- 审计日志保存前后差异和额外上下文。
- 低频且待产品确认的渠道画像扩展属性。

禁止使用 `jsonb` 替代以下字段：用户、角色、渠道编号、客户名称、报备编号、商机编号、报价编号、订单编号、金额、状态、时间、数据范围字段。
