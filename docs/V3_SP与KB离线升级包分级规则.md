# V3 SP 与 KB 离线升级包分级规则

文档版本：1.1  
制定日期：2026-08-14  
最近修订：2026-08-18（同步生产升级失败防复发门禁）  
适用系统：联软 CRM V3  
适用环境：完全内网、无外网访问权限的 openEuler x86_64 单机服务器  
默认安装目录：`/opt/lianruan-crm-v3`

## 一、目标与适用范围

本文统一 V3 后续安装包、整体升级包和定向补丁包的名称、选型、内容、离线限制、停启、验证和回退规则。

本文只适用于以下 V3 资产：

- 前端：`apps/web`
- 后端：`apps/api`
- 后台任务进程：`apps/worker`
- 共享包：`packages/*`
- 数据库迁移：`database/migrations`
- 单机部署：`deploy/single-server`

不得把根目录历史 V2 静态目录、旧后端、旧启动脚本或旧升级包模式重新引入 V3。

本文是 SP 与 KB 包型选择的统一入口；具体脚本结构、校验清单和生产执行细节继续遵守《V3 生产升级包制作规范》。两份文档冲突时，以本文的包型、离线约束和选型规则为准。

## 二、统一术语

### 2.1 SP

SP 是 V3 服务包，用于完整应用版本交付、较大范围整体升级或新服务器安装。

SP 分为：

| 编号      | 名称           | 用途                                                                                                              |
| --------- | -------------- | ----------------------------------------------------------------------------------------------------------------- |
| `SP-APP`  | 应用服务包     | 整体升级 API、Worker、Web、配置、运维脚本和数据库迁移，复用服务器已有 PostgreSQL、Redis、Docker 和 Docker Compose |
| `SP-FULL` | 完整离线服务包 | 新服务器安装、基础运行时升级或完全离线重装，携带应用、PostgreSQL、Redis、Docker、Docker Compose 和全部部署资产    |

### 2.2 KB

KB 是 V3 补丁包，也称补丁 KB 或 KB 升级包，用于从明确的源版本修复一个问题或一组强相关问题。

KB 分为：

| 编号       | 名称               | 用途                                                                     |
| ---------- | ------------------ | ------------------------------------------------------------------------ |
| `KB-FILE`  | 文件补丁           | 只更新宿主机挂载的配置、Nginx 配置或运维脚本                             |
| `KB-LAYER` | 离线差量镜像层补丁 | 依赖和运行时不变，只替换经过本地构建与验证的 API、Worker 或 Web 编译产物 |
| `KB-IMAGE` | 组件完整镜像补丁   | 依赖、Dockerfile、运行目录或组件结构变化时，携带受影响组件的完整镜像     |
| `KB-DB`    | 数据库兼容补丁     | 包含兼容性结构扩展或小范围数据修复，并携带必要的应用补丁                 |

KB 默认不得包含破坏性数据库迁移。删除字段、改变既有字段语义、覆盖历史业务数据或无法证明可回退的数据变更，必须升级为 SP 并进入维护窗口。

## 三、不可放宽的环境约束

### 3.1 完全离线

目标服务器没有外网和公网访问权限。服务器升级脚本禁止执行：

- `docker pull`
- `npm install`、`npm ci`、`npx`
- `pnpm install`、`yarn install`
- `apt`、`yum`、`dnf`
- `pip`、`pip3`
- 访问公网地址的 `curl`、`wget`
- 访问外部镜像仓库、软件源、代码仓库或对象存储

所有源码编译、依赖安装、类型检查、单元测试和前端构建必须在本地构建机完成。服务器只负责校验、解压、备份、复制文件、离线构建差量镜像、加载完整镜像、迁移、停启和验证。

### 3.2 只使用 ZIP 与 UNZIP

服务器只承诺提供 `zip` 和 `unzip` 相关能力。

强制要求：

- SP、KB 外层包只允许使用 `.zip`。
- 必须同时提供外层 `.zip.sha256`。
- 包内必须提供 `manifest/SHA256SUMS`。
- 业务目录备份必须使用 ZIP。
- PostgreSQL 逻辑备份使用普通 `.sql` 文件。
- 禁止升级脚本调用 `tar`、`gzip`、`gunzip`、`7z`、`rar`。
- 禁止最终交付包内出现 `.tar`、`.tar.gz`、`.tgz`、`.7z`、`.rar` 文件。
- Docker 镜像归档统一使用 `.docker-image` 后缀，通过 `docker load -i` 读取，不依赖服务器的 TAR 命令。
- `SP-FULL` 中的 Docker 和 Docker Compose 必须以预先展开的可执行文件形式放入 ZIP。

构建机允许下载和预处理官方运行时源文件，但不得把需要二次解包的运行时源压缩文件交付给服务器。

### 3.3 不直接修改运行容器

禁止使用以下方式升级业务代码：

- 使用 `docker cp` 把代码复制进正在运行的容器。
- 在容器可写层直接编辑文件。
- 只覆盖容器中的单个 JavaScript 文件后继续沿用旧镜像标签。
- 让运行容器内容、镜像摘要和部署版本不一致。

应用代码变更必须形成新的目标镜像。差量 KB 也必须生成新的不可变镜像和唯一目标版本。

## 四、包型选择规则

### 4.1 决策顺序

每次出包先按以下顺序判断：

1. 是否改变 PostgreSQL、Redis、Docker、Docker Compose 或主机运行时。
2. 是否改变 Dockerfile、依赖锁文件、启动命令、系统库或运行目录。
3. 是否改变数据库结构或业务数据。
4. 是否改变共享包，并同时影响 API 与 Worker。
5. 是否只改变一个组件的编译产物。
6. 是否只改变宿主机挂载的配置或脚本。

选择满足安全条件的最小包型，不得为了减小体积降低校验、回退或可追溯性。

### 4.2 场景矩阵

| 变更场景                           | 默认包型                 | 必须携带                                                               | 不应携带                              |
| ---------------------------------- | ------------------------ | ---------------------------------------------------------------------- | ------------------------------------- |
| 只改运维脚本                       | `KB-FILE`                | 目标脚本、旧文件摘要、回退副本、验证脚本                               | API、Worker、Nginx、PG、Redis、Docker |
| 只改 Nginx 配置                    | `KB-FILE`                | 完整 Nginx 配置、配置语法检查、回退副本                                | 无关业务镜像和基础镜像                |
| 只改 API 代码，依赖不变            | `KB-LAYER`               | `apps/api/dist`、受影响共享包 `dist`、差量 Dockerfile、基线镜像摘要    | Worker、Nginx、PG、Redis、Docker      |
| 只改 Worker 代码，依赖不变         | `KB-LAYER`               | `apps/worker/dist`、受影响共享包 `dist`、差量 Dockerfile、基线镜像摘要 | API、Nginx、PG、Redis、Docker         |
| 只改 Web 页面或 `apps/web/public`  | `KB-LAYER`               | 完整 `apps/web/dist`、差量 Dockerfile、基线镜像摘要                    | 单个哈希资源文件、无关镜像            |
| 改共享包且 API、Worker 均受影响    | `KB-LAYER` 或 `KB-IMAGE` | API 与 Worker 两个目标产物或完整镜像                                   | 只更新其中一个组件                    |
| 改依赖、锁文件或 Dockerfile        | `KB-IMAGE`               | 受影响组件完整镜像                                                     | 原始源码差量、在线依赖安装命令        |
| 新增兼容字段、索引或小范围数据修复 | `KB-DB`                  | SQL、数据库备份、数量校验、必要应用补丁                                | 破坏性迁移、自动数据库恢复            |
| API、Worker、Web 和迁移整体升级    | `SP-APP`                 | 三类业务镜像、配置、脚本、迁移、自检                                   | 已满足版本门禁的 PG、Redis、Docker    |
| 新服务器或基础运行时变化           | `SP-FULL`                | 所有业务与基础设施资产                                                 | 任何在线下载步骤                      |

### 4.3 自动提升包型

出现以下任一情况时，必须提高包型，不得继续制作较小的 KB：

- 无法确认服务器精确源版本。
- 无法确认源镜像摘要。
- `package.json` 或 `package-lock.json` 变化。
- Node、Nginx 基础镜像变化。
- Dockerfile、Compose、启动命令、运行用户或文件权限变化。
- 新增 Node 原生模块或系统库。
- 编译产物依赖关系无法完整确定。
- 数据库变更不可逆或旧应用不能兼容新结构。
- 需要跨越多个未经验证的历史版本。
- 目标服务器缺少差量构建所需的精确基线镜像。

## 五、代码差量的安全边界

### 5.1 只交付编译产物

`KB-LAYER` 只允许携带本地构建完成的运行产物，不允许把 TypeScript、Vue 源码或未安装依赖的源目录复制到服务器运行。

各组件最小完整单元：

- API：完整 `apps/api/dist`，以及所有受影响的 `packages/*/dist`。
- Worker：完整 `apps/worker/dist`，以及所有受影响的 `packages/*/dist`。
- Web：完整 `apps/web/dist`，不得只交付某个 Vite 哈希资源文件。

如果无法证明只替换上述运行产物即可保持依赖完整，必须使用 `KB-IMAGE`。

### 5.2 离线差量镜像构建

服务器执行差量镜像构建时必须：

1. 校验源版本与允许版本清单完全匹配。
2. 校验源镜像名称、架构和摘要完全匹配。
3. 校验差量文件 SHA-256。
4. 使用 `docker build --pull=false --network=none`。
5. Dockerfile 只能基于已存在的精确源镜像执行本地 `COPY`、权限调整和标签写入。
6. 禁止在差量 Dockerfile 中执行依赖安装、软件安装或联网命令。
7. 生成新的目标镜像标签，不得覆盖源镜像标签。
8. 在停止现有服务前完成目标镜像构建和静态校验。

差量镜像示意：

```dockerfile
FROM lianruan-crm-v3-api:精确源版本
COPY apps/api/dist /app/apps/api/dist
COPY packages/config/dist /app/packages/config/dist
LABEL org.opencontainers.image.version="目标版本"
```

实际包必须同时记录源镜像摘要，并在升级前使用 `docker image inspect` 校验；仅匹配标签不够。

### 5.3 文件补丁

`KB-FILE` 只能更新宿主机已有、被 Compose 挂载或由运维直接调用的文件。

每个目标文件必须记录：

- 目标绝对路径。
- 升级前 SHA-256。
- 升级后 SHA-256。
- 文件权限和属主。
- 是否需要停止或重载服务。
- 回退文件和回退动作。

升级前文件摘要不匹配时必须中止，禁止强制覆盖服务器上的未知修改。

## 六、SP 内容规则

### 6.1 SP-APP

`SP-APP` 用于现有 V3 服务器的完整应用升级，默认包含：

- API、Worker、Nginx 三类业务镜像。
- Compose 目标版本或经过审查的 Compose 变更文件。
- V3 配置模板及配置差异说明。
- 数据库正向迁移。
- 运维、健康检查、备份和回退脚本。
- 业务冒烟测试和人工验收清单。
- 包内完整校验清单。

满足以下条件时不携带 PostgreSQL、Redis、Docker 和 Docker Compose：

- 目标服务器已经安装并运行。
- 版本与允许版本清单一致。
- 镜像或可执行文件摘要满足门禁。
- 本次变更不涉及这些基础设施。

### 6.2 SP-FULL

`SP-FULL` 用于：

- 新服务器首次部署。
- 新服务器部署后导入经批准的数据包或数据库备份。
- Docker、Docker Compose、PostgreSQL 或 Redis 版本变化。
- 目标服务器无法证明具备所需基础资产。
- 完全离线重建或灾难恢复。

`SP-FULL` 必须包含：

- API、Worker、Nginx 镜像。
- PostgreSQL 与 Redis 镜像。
- 预先展开的 Docker x86_64 可执行文件。
- Docker Compose x86_64 可执行文件。
- Compose、配置模板、迁移、安装、备份、验证和诊断脚本。
- 外层与包内 SHA-256 校验。

SP 只负责提供可安装环境。历史数据导入必须使用明确的数据迁移包、PostgreSQL 备份恢复流程或经过批准的暂存装载资产，不能把来源不明的数据静默带入 SP。

## 七、统一包目录与元数据

### 7.1 公共目录

所有 SP 和 KB 解压后必须只有一个顶层目录，并至少包含：

```text
包名/
├── README.md
├── 变更说明.md
├── manifest/
│   ├── 包元数据.env
│   ├── 文件清单.tsv
│   └── SHA256SUMS
├── scripts/
│   ├── precheck.sh
│   ├── upgrade.sh 或 install.sh
│   ├── verify.sh
│   └── rollback.sh
└── tests/
    ├── smoke.sh
    └── 验证清单.md
```

按包型选择性增加：

```text
├── images/
├── layers/
├── files/
├── database/migrations/
├── runtime/
├── compose/
└── config/
```

### 7.2 元数据

`manifest/包元数据.env` 至少包含：

```bash
PACKAGE_ID=唯一编号
PACKAGE_FAMILY=KB
PACKAGE_MODE=KB-IMAGE
SOURCE_VERSION=精确源版本
ALLOWED_FROM_VERSIONS=允许的精确版本清单
TARGET_VERSION=唯一目标版本
AFFECTED_COMPONENTS=api,nginx
REQUIRES_DB_MIGRATION=false
DATABASE_CHANGE_MODE=none
AUTO_ROLLBACK_SCOPE=app
REQUIRES_MAINTENANCE_WINDOW=false
BUILD_COMMIT=构建提交
BUILD_TIME=构建时间
DEFAULT_INSTALL_ROOT=/opt/lianruan-crm-v3
```

`PACKAGE_FAMILY` 只允许 `SP` 或 `KB`；`PACKAGE_MODE` 必须使用本文定义的六种包型之一。`SP-FULL` 用于新服务器首次安装时，`SOURCE_VERSION` 使用明确值 `none`，不得留空。

差量镜像包还必须记录各源镜像和目标镜像的完整摘要。文件补丁还必须在文件清单中记录升级前后摘要。

不得使用“最低版本”推断任意较高版本都兼容。必须使用精确 `SOURCE_VERSION` 或经过实际验证的 `ALLOWED_FROM_VERSIONS` 清单。

## 八、升级执行顺序

### 8.1 预检查

`precheck.sh` 必须只读，不得创建生产目录、修改配置、加载镜像、停止服务或执行数据库写入。

至少检查：

1. openEuler/Euler 标识和 x86_64 架构。
2. 只使用承诺的基础命令。
3. V3 安装目录和关键配置存在。
4. 当前版本在允许版本清单内。
5. 当前镜像摘要或文件摘要匹配。
6. Docker、Docker Compose、PostgreSQL、Redis 的现状满足本包要求。
7. 包内完整性校验通过。
8. 磁盘空间能同时保留源版本、目标版本、备份和日志。
9. 数据库迁移状态与包内迁移起点一致。
10. 包型与实际携带内容一致。

### 8.2 准备目标资产

在停止服务前尽可能完成：

- 校验并加载完整镜像。
- 离线构建差量目标镜像。
- 校验 Nginx 配置。
- 校验 Compose 展开结果。
- 校验 SQL 语法和迁移前置条件。
- 生成配置和应用快照。
- 执行 PostgreSQL、上传文件和导出文件备份。

### 8.3 停止影响范围

| 影响范围                           | 默认停启范围                                                     |
| ---------------------------------- | ---------------------------------------------------------------- |
| 运维脚本                           | 通常不停服务                                                     |
| Nginx 配置或 Web                   | 只处理 Nginx                                                     |
| API                                | 处理 Nginx、API-1、API-2；只有滚动切换经过专项验证后才能减少停机 |
| Worker                             | 只处理受影响 Worker 角色                                         |
| 数据库迁移                         | 停止所有可能写库的 API 和 Worker，保留 PostgreSQL、Redis         |
| PostgreSQL、Redis、Docker、Compose | 进入维护窗口并执行 SP 完整停启                                   |

不得宣称零停机，除非该包已经实际完成滚动切换、连接排空、会话保持和失败回切测试。

### 8.4 切换与验证

目标资产准备完成后，按以下顺序执行：

1. 停止受影响服务。
2. 应用配置或文件变更。
3. 执行允许的数据库迁移。
4. 更新目标镜像和构建版本。
5. 启动受影响服务。
6. 执行容器状态、健康接口和依赖检查。
7. 执行与本次变更一致的业务冒烟。
8. 验证版本、镜像摘要、迁移版本和配置摘要。
9. 成功后记录升级结果，保留源镜像和升级前快照。

## 九、失败处理与回退边界

### 9.1 自动应用回退

以下包型应支持升级失败后自动恢复旧镜像引用、配置和文件，再重新启动并执行旧版本健康检查：

- `KB-FILE`
- 不含数据库迁移的 `KB-LAYER`
- 不含数据库迁移的 `KB-IMAGE`
- 不含数据库迁移的 `SP-APP`

自动应用回退的触发条件至少包括：

- 目标镜像构建或加载失败。
- Compose 解析失败。
- 服务未在规定时间内启动。
- `/health/live` 或 `/health/ready` 失败。
- 目标容器镜像、版本或摘要不匹配。
- 本次业务冒烟失败。

如果仅自检脚本断言错误，但镜像、健康检查和真实业务流程均已通过，应停止自动回退并进入人工复核，避免把健康服务误回退。

### 9.2 数据库回退

数据库变更分为：

| 类型          | 允许自动处理 | 失败策略                                                             |
| ------------- | ------------ | -------------------------------------------------------------------- |
| `none`        | 是           | 自动恢复旧应用                                                       |
| `expand`      | 有条件允许   | 保留向后兼容的新表、新字段或新索引，自动恢复旧应用，不自动删除新结构 |
| `data-fix`    | 默认否       | 迁移事务失败则数据库自动回滚；迁移提交后需要补偿脚本或人工恢复       |
| `destructive` | 否           | 禁止自动升级，必须维护窗口、人工审批和恢复演练                       |

任何 SP 或 KB 都不得在失败处理函数中自动恢复 PostgreSQL 备份。数据库恢复会覆盖升级后产生的新写入，必须由负责人确认恢复点、影响数据和停机范围后执行。

### 9.3 不影响业务和数据的成立条件

只有同时满足以下条件，才能声明“失败回退不影响业务数据”：

- 升级期间已停止或阻断受影响写入。
- 数据库没有迁移，或只有旧应用完全兼容的扩展式迁移。
- 旧镜像、旧配置和旧文件快照完整存在。
- 自动回退已经在等价测试环境实际演练。
- 回退后的健康检查和核心业务查询通过。

如果升级窗口内允许业务继续写入，或者包含不可逆数据修复，不能承诺恢复到升级前完全相同状态。

## 十、制包与验收门禁

### 10.1 本地构建门禁

至少执行：

```bash
npm ci
npm run verify
```

还必须按包型执行：

- `KB-FILE`：新旧文件语法检查和摘要验证。
- `KB-LAYER`：源镜像摘要验证、离线差量构建、目标镜像启动验证。
- `KB-IMAGE`：受影响组件完整镜像构建和启动验证。
- `KB-DB`：数据库备份、正向迁移、重复执行、数量守恒和业务样本验证。
- `SP-APP`：完整应用升级和应用回退演练。
- `SP-FULL`：外层 ZIP、新服务器解压、包内校验、安装、迁移、健康检查和备份演练。

所有包含 Shell 脚本的包还必须完成运行级验证，不能只执行 `bash -n`。至少覆盖允许源版本到目标版本的升级、目标版本重复复核、失败回退，以及瞬时 `502` 重试；HTTP 健康检查必须使用真实 `/health/live`、`/health/ready` 路径并校验 API JSON，能够拒绝前端 HTML 假健康。详细失败案例和执行方法见《V3 生产升级包制作规范》第十四章。

### 10.2 包内容门禁

交付前必须确认：

- 包型与目录内容一致。
- 只携带受影响组件；未受影响组件不得为了方便被默认加入 KB。
- 所有脚本通过 `bash -n`。
- Shell 变量名符合 ASCII 标识符规则，已扫描非 ASCII 变量赋值和展开。
- 升级、复核和回退脚本已经实际执行，不以 `bash -n` 代替运行验证。
- 元数据可以被 Bash 正确读取。
- 外层 `.zip.sha256` 实际校验通过。
- ZIP 实际解压通过。
- 包内 `manifest/SHA256SUMS` 实际校验通过。
- 所有自检关键字已在本地构建产物或真实接口等价响应中确认。
- 已分别等待所有目标 API 实例达到 `healthy`，所有 HTTP 自检使用统一重试机制。
- 健康检查使用 `/health/live`、`/health/ready`，同时校验 API JSON，禁止只看 HTTP `200`。
- 源镜像摘要严格匹配生产实际运行镜像；目标镜像不强制比较构建机和生产的镜像 ID。
- 目标环境基线与制包源版本或源镜像摘要不一致时必须停止，禁止放宽旧包版本门禁；确需升级时必须基于目标环境实际镜像重制新修订包，并验证后续能力未被覆盖。
- 最终 ZIP 已在独立目录解压，并从解压后的文件重新执行包内校验和关键自检。
- 升级失败后会核对当前版本和实际容器镜像，能够区分“目标版本仍在运行但自检误判”和“已经自动回退”。
- 前端自检不写死 Vite 哈希文件名。
- 脚本不包含联网安装、在线拉取或目标环境不支持的解包命令。
- 包内不存在禁止的压缩格式和明文密钥。

## 十一、版本与命名规则

```text
lianruan-crm-v3-sp-app-目标版本.zip
lianruan-crm-v3-sp-full-目标版本.zip
```

```text
lianruan-crm-v3-kb-YYYYMMDD-编号-模式-问题名.zip
```

## 十二、当前实现状态与过渡规则

本文定义目标规则，不代表当前所有自动化脚本已经实现。

当前状态：

- `deploy/single-server/scripts/package-offline.sh` 主要对应 `SP-FULL`。
- 现有 KB 包以人工组织目录和完整组件镜像为主，主要对应 `KB-IMAGE`。
- 当前 KB 失败处理通常只输出回退命令，尚未统一实现安全条件下的自动应用回退。
- 当前尚无统一的 `KB-LAYER` 制包器、基线摘要门禁和离线差量镜像模板。
- 当前 SP 安装脚本尚未完整区分 `SP-APP` 与 `SP-FULL`。

在配套脚本和自动测试落地前：

1. 不得直接在生产使用手工制作的 `KB-LAYER`。
2. 不得宣称现有 SP 或 KB 已实现失败自动回退。
3. 继续使用已验证的完整镜像 KB 或完整离线 SP。
4. 每次出包仍须遵守现有生产升级包自检规则。

后续实现顺序建议：

1. 统一包元数据和包型校验。
2. 实现 `KB-FILE` 制包、旧文件摘要门禁和自动回退。
3. 实现 `KB-IMAGE` 按组件制包，禁止默认携带三类镜像。
4. 实现 `KB-LAYER` 离线差量构建与基线镜像摘要门禁。
5. 实现 `SP-APP` 与 `SP-FULL` 分离。
6. 实现安全条件下的自动应用回退和故障演练。

## 十三、最终原则

1. 包越小不代表越安全，最小包型必须建立在可验证影响范围之上。
2. 可以交付编译产物差量，但不得直接修改运行容器或绕过镜像版本。
3. 未变更的 API、Worker、Nginx、PostgreSQL、Redis、Docker 不应被无条件放入 KB。
4. 服务器完全离线，任何运行时依赖都必须提前准备或由 SP-FULL 携带。
5. 只允许 ZIP/UNZIP 交付和备份流程。
6. 应用失败可以在满足条件时自动回退；数据库恢复必须人工确认。
7. 所有包都必须可校验、可追溯、可验证、可说明回退边界。
