# 账号归档清理与泛微身份接管设计

## 目标

解决两个已确认问题：

1. 已完成停用交接的历史账号无法释放登录名，无法重新创建同名账号。
2. 停用账号仍保留有效泛微 OA userid，导致新账号无法接管该 userid。

## 业务规则

- 不物理删除 `iam.users`，保留用户主键、订单/审批/审计引用和历史外部身份。
- “删除账号”继续表示“停用并交接”；只有交接状态为 `completed` 或 `closed` 且账号状态为 `disabled`、不存在未处理交接项时，才允许执行“归档清理”。
- 归档清理在事务中保存原登录名历史，生成不可登录的归档登录名并更新 `iam.users.username`，从而释放原登录名。原姓名、手机号、邮箱和业务事实不改写。
- 泛微 userid 仍保持有效映射全局唯一；同一账号最多一条有效泛微映射。
- 仅超级管理员可执行泛微身份接管。只有来源账号已停用且目标账号已启用、目标账号没有有效泛微映射时，才允许在单事务内停用来源映射并把 userid 绑定给目标账号。
- 接管必须填写原因、二次确认来源账号和目标账号；不自动修改订单、审批、OA 发起历史、企微映射或角色。
- 来源映射改为 `disabled`，不删除；新映射写入 `active`。数据库部分唯一索引继续兜底并发唯一性。

## 接口

- `GET /api/org/users/:userId/archive-preview`
- `POST /api/org/users/:userId/archive`
- `GET /api/org/users/:userId/eteams-identity/takeover-preview`
- `POST /api/org/users/:userId/eteams-identity/takeover`

所有写接口沿用组织写入开关、超级管理员鉴权、幂等键和行版本校验。泛微身份接管还必须输入来源账号与目标账号的登录名进行双重确认。

## 回退

代码回退只下线新入口和接口；已完成归档及身份接管不自动反转。必要时由超级管理员通过既有账号恢复/身份候选流程人工处理，并保留审计。
