# 客户报备业务编号迁移覆盖缺陷修复设计

## 问题与根因

生产排查确认：`20260812_S9_023_客户报备业务编号统一` 已执行，但后续补执行的 `20260811_S9_020`、`S9_021`、`S9_022` 通过 `CREATE OR REPLACE FUNCTION` 覆盖了 `crm.next_business_number`。最终函数不再支持 `registration`，导致客户报备提交失败。

## 范围

- 新增一份正向数据库迁移，恢复 `registration`、`quote`、`order`、`opportunity` 四类业务编号生成能力。
- 新增回归测试，模拟旧函数在正确迁移后被覆盖的历史顺序，并验证新迁移可恢复客户报备编号生成。
- 不修改历史迁移、不修改客户报备状态机、接口契约、权限、数据范围或已有业务数据。

## 实现方案

1. 新增 `20260907_S10_018_客户报备业务编号函数补齐.sql`，仅重新定义 `crm.next_business_number(text, text)`。
2. 函数规则保持既有 `S9_023` 约定：客户报备编号为 `BB-提报账号-YYYYMMDD-日流水`，按提报账号和自然日递增；报价、订单和商机规则保持不变。
3. 在 API 集成测试中开启事务，先执行旧 `S9_022` 函数定义模拟覆盖，再执行新迁移；断言客户报备编号可生成，并在事务回滚后不污染测试库。

## 验收标准

- 模拟旧函数覆盖后，调用 `crm.next_business_number('registration', ...)` 明确失败。
- 执行本次新迁移后，同一事务内可生成符合 `BB-提报账号-YYYYMMDD-四位流水` 的编号。
- 报价、订单、商机仍可由现有测试链路生成业务编号。
- 数据库迁移文件语法可通过 PostgreSQL 本地测试库执行。

## 风险与回退

- 风险：数据库函数是共享底座，定义错误会影响四类单据编号。
- 缓解：函数体复用已验证的 `S9_023` 规则，并在同一事务内覆盖客户报备恢复场景。
- 回退：代码无需回退；若必须撤销已发布迁移，只能另发受控正向迁移恢复到发布前函数定义，禁止删除迁移记录或直接改写历史迁移。
