# 全量备份离线恢复修复设计

## 目标

修复 V3 单机全量备份在无国际网络生产环境中的镜像恢复问题，保证生产当前 API、Nginx 与 Worker 镜像标签不一致时仍能生成可验证、可离线恢复的备份，并且不改变数据库、业务接口和正常启动流程。

## 已确认事实

- 生产环境不能访问国际网络。
- 生产 `compose/.env` 声明的 Worker 标签可能与实际运行容器不同。
- 旧脚本在备份后通过 `docker compose up` 恢复业务服务，会按声明标签尝试拉取不存在的镜像。
- 用户会自行把修复后的脚本或文件上传到生产执行；本任务不直接修改生产环境。

## 方案

1. 备份前读取所有已存在容器的服务名、容器名、容器 ID、声明镜像、实际镜像摘要、运行状态和健康状态。
2. 以实际容器声明镜像生成 `metadata/docker-images-actual.txt`、`metadata/actual-images.override.yml` 和镜像对账清单；Compose 声明与实际镜像不一致时明确记录。
3. Docker 镜像在停止业务前导出，避免延长业务暂停时间；缺少实际镜像时直接失败并给出中文原因。
4. 备份期间恢复原业务状态时只执行 `docker start`，不重建容器、不访问镜像仓库。
5. 跨机器还原时加载备份镜像，使用实际镜像覆盖文件，并对所有可能创建容器的 Compose `up` 调用传入 `--pull never`。
6. 还原不再调用 `start.sh`，避免读取生产中可能冲突的 `config/deploy.env`；按备份快照启动业务服务，不主动执行数据库迁移。
7. 保留 v1 备份校验和还原兼容性；v1 没有容器快照时按原有核心四个业务服务启动，但同样强制 `--pull never`。

## 非目标与边界

- 不修改 `docker-compose.yml`、生产配置、数据库结构、Redis 数据格式和业务容器代码。
- 不执行生产备份、部署、重启或数据迁移。
- 不把不存在的 Worker 镜像错误地改标签为其他版本。
- 不引入新的外网依赖。

## 回退

生产替换前保留旧脚本副本；若新脚本未通过本地验证或现场检查，可恢复旧脚本。新脚本本身不会删除原安装目录或数据库，恢复操作仍保留带时间戳的回退目录。
