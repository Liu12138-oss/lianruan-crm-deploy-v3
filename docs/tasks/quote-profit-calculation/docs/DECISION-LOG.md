## 2026-09-15：公式与金额口径

### 决策

采用以下服务端公式：

```text
合同额（产品） = 软件折后价 + 硬件报价
合同额（服务） = 维保及服务报价
硬件内部成本 = Σ（数量 × 内部销售成本）
产品税费 =（产品合同额 - 硬件内部成本）× 5%
服务税费 = 服务合同额 × 7%
质保成本 =（硬件年度质保/维保成本合计 + 软件公开报价 × 0.5%）×（质保年限 - 1）
采购维保成本 =（硬件年度质保/维保成本合计 + 软件公开报价 × 0.5%）× 采购维保年限
合同有效收入 =（产品合同额 - 硬件内部成本）× 95% + 服务合同额 × 93%
项目收益 = 合同有效收入 - 质保成本
```

### 取舍与原因

- 软件公开报价使用报价时同区域、同数量下“未应用渠道级比例或渠道专属价”的公开原价，不使用渠道折后价；服务端在输入快照中固化目录版本和命中阶梯，避免目录改价后历史快照漂移。
- Excel 只有一列年度质保/维保成本，V1 用同一规则值分别供质保和采购维保公式使用；收益表保留两个汇总字段，为未来业务拆分保留空间。
- 计算中间值不提前按分取整，使用数据库定点数；接口展示按人民币分四舍五入，避免大量硬件数量累计产生误差。
- 项目收益允许为负，禁止静默归零或取绝对值，因为负值本身是报价风险信号。
- 采购维保成本只展示，不从项目收益再次扣减；这是用户确认的 Excel 口径，避免重复扣减。
- 正式冻结使用订单最终总额。由于现有总价调价没有金额分摊字段，V1 保持硬件和服务明细不变，并将“订单总额减硬件、减服务”的剩余金额作为软件折后价；剩余金额为负或明细无法明确归类时不猜测分摊，标记收益不完整。
- 草稿使用计算时点的成本规则，正式快照使用订单进入 `confirmed` 的事件时间所对应的成本规则，避免 Worker 延迟导致结果漂移。

## 2026-09-15：数据模型与兼容

### 决策

1. 新增版本化成本规则表 `catalog.hardware_profit_cost_rules`，历史版本不可覆盖；超管维护，所有变更审计。
2. 新增收益计算表 `crm.quote_profit_calculations`，保存输入快照、计算快照、公式版本、缺失规则、行版本和冻结信息；冻结记录只读。
3. `crm.quote_items` 增加结构化项目归类和扩展快照字段；硬件数量使用应用层正整数校验并增加数据库约束。
4. `crm.quotes` 增加正式 `region_id`，从商机或渠道商正式区域补齐；无法唯一确定时收益不完整，禁止名称兜底。
5. 新请求使用 `hardwareItems: [{productId, quantity}]`；旧 `hardwareIds` 继续接受并转换为每型号 1 台。相同型号重复提交直接报参数错误。
6. 为产品分类增加结构化 `profit_scope_code`；套餐必须展开 `package_items` 后再计算软件、硬件和公开价。报价包含 XCAD 或未分类软件时整单不适用本期核算，不能只算其中一部分。

### 未采用方案

- 不把内部成本直接写回 `catalog.hardware_products.list_price`：公开销售价和内部成本是不同业务事实，混写会破坏既有报价。
- 不把收益金额塞入 `crm.quotes.extra_json` 作为唯一来源：无法满足版本化、冻结不可覆盖和并发幂等要求。
- 不用前端计算结果作为正式收益：浏览器可被篡改，且与目录/成本版本不一致。
- 不用名称正则判断服务：名称变更会导致税费和合同额错误；未知归类必须标记不完整。

## 2026-09-15：冻结与主链解耦

### 决策

1. 订单从超管待确认进入 `confirmed` 时，同事务写入收益冻结请求发件箱事件。
2. `apps/worker` 异步读取最新订单、报价、目录和成本规则，成功后冻结 `weidun-v1` 快照。
3. 成本缺失时记录 `incomplete` 和具体缺失型号，不回滚订单确认；超管补齐规则后可重算冻结，规则变更事件可触发重试。
4. 同订单重复事件、Worker 重试和并发请求使用事件租约、输入指纹和数据库唯一约束幂等处理。
5. 收益失败不改变订单状态、不关闭审批待办、不影响 OA/企微流程。

### 风险接受

- 异步冻结存在短暂延迟，页面必须区分“实时预估”和“已冻结”，不能把草稿显示成正式收益。
- 成本规则缺失会导致订单已确认但收益仍不完整；这是为保护订单主链而接受的可见风险，页面和审计必须明确提示。

## 2026-09-15：权限与展示

### 决策

- 敏感接口每次复核启用账号、有效角色和正式区域；仅依赖会话摘要被否决。
- 角色判定以有效 `superadmin`/`region_manager` 为准；只有在预检确认 `admin` 是历史区管别名时，才可带正式区域做显式兼容，不得把所有 `admin` 角色默认视为区管。
- 区管越权详情返回保护性 404；区域为空、区域名称重复或正式区域不存在时不放行。
- 收益区块直接放在正式报价详情；首版不新建独立收益审批页、不提供导出、不增加渠道端入口。
- 超管专属硬件成本维护能力放在管理员端现有“产品目录 → 硬件管理”的型号操作中；区管只看到收益参数和明细，不看到成本配置操作。

## 2026-09-16：成本维护入口与数据边界

### 用户提出的问题

用户希望确认硬件成本能否直接加到现有功能模块中维护，并要求将明确方案更新到交付文档，方便其他代理实施。

### 已核对事实

1. V3 管理端已有“产品目录 → 硬件管理”列表和硬件编辑弹窗，前端位于 `apps/web/public/admin-app.js`。
2. 对外硬件产品当前保存在 `catalog.hardware_products`，其中 `list_price` 是报价使用的对外销售单价；`/api/v2/hardware` 会返回该目录数据。
3. 现有硬件目录接口还承担渠道报价读取，直接把内部成本字段加入硬件表或 `extra_json` 会产生内部成本泄露风险。

### 最终决策

采用“页面合并、数据分离”：

- 页面上不新增独立的成本管理菜单，直接在现有“产品目录 → 硬件管理”的每个硬件型号上增加“成本配置”按钮和弹窗。
- 数据上继续使用独立的 `catalog.hardware_profit_cost_rules` 版本表，内部销售成本和年度质保/维保成本不写入 `catalog.hardware_products.list_price`，也不通过 `/api/v2/hardware` 返回。
- 硬件基本资料编辑与成本规则维护是两个独立提交动作；成本规则只能新增版本，历史版本只读。
- 只有超管显示和调用成本配置；区管不读取成本规则列表，只在收益区块填写年限并查看核算结果。

### 取舍原因

页面合并可以复用现有硬件维护习惯，降低培训和实施成本；数据分离可以保持报价目录与内部成本的事实边界，支持历史版本、订单冻结、审计和权限隔离。该决策不改变已确认的收益公式、冻结流程、角色范围和对外不暴露原则。

### 本轮新增工程决策

- 纯计算函数的 `complete` 是计算结果状态，持久化时映射为 `draft`；接口可根据报价版本和草稿状态显示 `estimated` 或 `draft`，不得向 `crm.quote_profit_calculations.status_code` 写入 `complete`。
- 正式页面需要原始有效角色列表。`/api/v2/auth/login` 和 `/api/v2/auth/me` 必须返回稳定 `roleCodes` 数组，前端不得从展示角色 `admin` 反推区管身份。
- `hardwareProductId` 接口接受数据库 UUID、`hardware_code` 或 `v2_source_id`，服务端必须解析为唯一数据库 UUID 后保存；匹配 0 条或多条均拒绝。
- 事件流程统一为：订单确认事务内直接写入 `crm.quote.profit.freeze.requested`，不由前端另行投递，也不要求再消费 `crm.order.confirmed` 二次转换。

### 报价调整边界补充确认

用户进一步确认：同一硬件型号在真实报价中可能出现两台。

最终决策：

1. 报价计价规则不变，包括软件阶梯价、区域价格覆盖、渠道价格比例、渠道专属价和服务价格。
