# V3 新 UI 开发手册

更新日期：2026-09-22

## 1. 手册目的

本手册规定 V3 UI 重构期间的新 UI 开发方式，确保：

- 老 UI 继续稳定承载生产和业务热修。
- 新 UI 可以并行开发、预览、测试和按模块交付。
- 新旧 UI 共用一套后端业务逻辑、权限、状态机和数据。
- 新 UI 不修改、不影响当前生产页面的运行。
- 每个模块都有明确的灰度、回退和旧 UI 清理门禁。

本手册适用于参与新 UI 开发、后端兼容、测试、部署和评审的所有 Agent。

## 2. 开发基线

开发前必须阅读：

- `ARCHITECTURE-OPTIMIZATION-BLUEPRINT.md`
- `IMPLEMENTATION-SPEC.md`
- `VISUAL-RULES.md`
- `DESIGN.md`
- `FEATURE-COVERAGE-MATRIX.md`
- `index.html` 和 `PROTOTYPE-EVIDENCE.json`

生产基线是当前 V3 正式页面。新 UI 开发不得把原型 HTML 直接复制成正式业务工程，也不得修改老 UI 的业务规则。

## 3. 硬性规则

1. 老 UI 文件只允许生产热修，不允许因为新 UI 开发而重构。
2. 新 UI 必须使用独立入口、独立资源目录和独立路由前缀。
3. 新旧 UI 共用同一 API、认证、权限、数据范围、状态机和后台任务。
4. 新 UI 不得复制金额、折扣、税费、工作量、收益和状态流转规则。
5. 后端接口只做向后兼容扩展，不因新 UI 删除或重命名旧字段。
6. 新 UI 没有通过完整验收前，不得接管正式入口。
7. 新 UI 出问题时必须能按模块回退，不能影响老 UI。
8. 所有业务动作必须支持幂等、版本校验和审计。
9. 新 UI 开发期间，生产热修优先级高于重构排期。
10. 旧 UI 清理必须按模块执行，禁止最后一次性删除。

## 4. 代码边界

### 4.1 老 UI 保护区

以下文件和由它们直接加载的历史资源属于老 UI 保护区：

- `apps/web/public/admin.html`
- `apps/web/public/admin-app.js`
- `apps/web/public/partner.html`
- `apps/web/public/partner-app.js`
- `apps/web/public/app.js`
- `apps/web/public/mobile.html`
- `apps/web/public/mobile-app.js`
- `apps/web/public/mobile-v2-app.js`
- 老 UI 独占的样式、接口封装和静态资源

规则：

- 新 UI Agent 默认不得修改这些文件。
- 生产热修可以修改这些文件，但必须走独立热修流程。
- 热修完成后必须同步到 `main`，并合并到 `ui-next`。
- 合并 `ui-next` 时，如果冲突发生在老 UI 保护区，保留 `main` 的生产版本，不能为了新 UI 干扰老行为。

### 4.2 新 UI 开发区

建议的新 UI 逻辑边界：

```text
apps/web/src/next/
  app/                 应用启动、全局装配和错误边界
  router/              新 UI 路由
  layouts/             页面壳和导航
  components/          通用组件
  domains/             按业务域拆分的页面、状态和动作
  api/                 新 UI 统一 API 客户端
  stores/              跨页面状态
  styles/              设计令牌和主题
  mocks/               仅开发环境使用的演示数据
  tests/               单元和组件测试

apps/web/public/
  admin-next.html      管理端新 UI 预览入口
  partner-next.html    渠道端新 UI 预览入口
  admin-mobile-next.html
  partner-mobile-next.html
```

最终正式入口仍然保持 `/admin.html`、`/partner.html`、`/admin-mobile.html`、`/partner-mobile.html`。开发期使用 `*-next.html` 是为了隔离，不是永久增加四套业务入口。

## 5. 分支与合并策略

### 5.1 分支职责

| 分支                         | 用途           | 规则                                      |
| ---------------------------- | -------------- | ----------------------------------------- |
| `main`                       | 生产稳定轨     | 只接收经过验证的生产热修和稳定发布        |
| `ui-next`                    | 新 UI 集成轨   | 汇总新 UI 功能，定期同步 `main`           |
| `ui-feature/<domain>-<task>` | 新 UI 功能分支 | 从 `ui-next` 创建，完成后合并回 `ui-next` |
| `hotfix/<issue>`             | 生产热点分支   | 从 `main` 创建，修复后合回 `main`         |

### 5.2 同步规则

- 每个新 UI 功能分支开始前先同步一次 `ui-next`。
- `ui-next` 至少每天同步一次 `main`。
- 生产热修合并后立即同步到 `ui-next`。
- 不允许长期保留完全隔离的 UI 分支。
- 不允许把 `main` 与 `ui-next` 合并冲突留给最后统一处理。

### 5.3 冲突处理

- 老 UI 保护区冲突：以 `main` 的生产版本为准。
- 新 UI 目录冲突：由新 UI 模块负责人处理。
- 共享接口契约冲突：由后端负责人和架构负责人共同确认。
- 争议未解决前不得绕过门禁合并。

## 6. 环境与入口

| 环境   | 老 UI    | 新 UI         | 用途                         |
| ------ | -------- | ------------- | ---------------------------- |
| 生产   | 正式入口 | 默认不可见    | 稳定业务和生产热修           |
| 预发布 | 正式入口 | `*-next.html` | 全量回归和业务验收           |
| 测试   | 正式入口 | `*-next.html` | 接口、权限、状态机和任务测试 |
| 开发   | 只读参考 | 独立入口      | 页面开发和局部联调           |

新 UI 不得在生产中偷偷替换老入口。正式入口切换必须由单独发布任务、功能开关和回退方案控制。

## 7. 业务域开发顺序

推荐按以下模块逐步迁移：

1. 应用壳、设计系统、登录态和导航。
2. 工作台、业务全景和系统架构页。
3. 客户、报备、商机和跟进。
4. 报价、订单、审批、履约和收益。
5. 渠道、成员、证书、产品和价格。
6. 消息、提醒、组织、账号和权限。
7. 审计、导入导出、OpenAPI 和运维。
8. 移动端一期和二期。

每个模块必须独立完成开发、回归和验收，不得等待全量 UI 完成后再一起测试。

## 8. 架构约定

### 8.1 前端分层

```text
页面 Page
→ 领域组件 Domain Component
→ 领域 Store / Composable
→ API Client
→ 服务端接口
```

约束：

- 页面不直接拼接接口 URL。
- 页面不直接读写数据库字段或推断业务状态。
- 状态机、权限和数据范围以服务端返回为准。
- 通用操作使用统一组件；领域动作放在对应域内。
- 不允许在组件内复制旧 UI 的业务计算。

### 8.2 状态管理

- 页面局部状态留在组件内。
- 跨页面业务状态使用 Pinia。
- 服务端数据缓存必须能按权限和数据范围隔离。
- 退出登录、切换账号和会话过期时必须清理新 UI 的缓存和页面状态。
- 不把服务端权威状态改成前端永久本地状态。

### 8.3 API 客户端

- 新 UI 使用 `apps/web/src/next/api` 的统一客户端。
- 自动携带统一登录态和请求标识。
- 401、403、409、429 和 5xx 统一转换为中文业务错误。
- 写操作必须支持幂等键或版本号。
- 新接口字段只做加法扩展；旧字段删除必须等老 UI 下线后执行。

## 9. UI 与交互约定

- 使用固定 1440px 业务画板。
- 浏览器窗口变化时不得自动换行、折叠列或改变页面结构。
- 顶部业务导航、内容标题、六项指标和三栏结构的尺寸按 `VISUAL-RULES.md` 执行。
- 管理配置采用“业务板块 / 配置列表与编辑 / 状态和影响”三栏。
- 订单必须显示来源报价、商品价格快照、价差和审批上下文。
- 高风险动作使用独立确认窗口，并填写原因。
- 页面必须实现加载、空、错误、无权限、冲突和成功状态。
- 不得用隐藏入口代替导航；一级业务能力必须可直接发现。

## 10. 权限与数据范围

- 身份、权限和数据范围全部由服务端解析。
- 前端隐藏按钮只是体验优化，不能作为鉴权。
- 区域筛选只对超级管理员展示。
- 渠道端和 OpenAPI 不返回内部成本、收益和系统配置。
- 组织内部域与渠道域不得简单取并集。
- 用户级权限覆盖必须单独审计，不允许静默继承。

## 11. 状态机与数据一致性

- 每个业务对象只有一个服务端状态机。
- 状态变化写入状态历史、操作人、时间和原因。
- 订单确认后商品与价格快照只读。
- 报价转订单后保留原报价版本和订单快照。
- 回退修订必须同步更新关联报价和订单，并重新进入审批。
- 外部 OA、企微、IAM 和消息投递失败不回滚已经提交的主业务状态。

## 12. 异步任务约定

- 导入、导出、消息、订单预审、收益冻结和审计任务不得阻塞主请求。
- 任务必须具备幂等键、重试次数、最后错误和补偿状态。
- 任务失败会在消息中心或审计运维页面显示。
- 前端不得自行重算失败任务的结果。

## 13. 模块迁移状态

每个模块必须维护以下状态：

```text
Legacy       只使用旧 UI
Preview      新 UI 内部预览
Canary       按账号、角色或区域灰度
Default      新 UI 默认，旧 UI 可回退
Frozen       旧 UI 冻结，只接受生产热修
Removed      旧 UI 已清理
```

模块迁移台账至少记录：

- 模块名称。
- 新 UI 路由。
- 旧 UI 路由。
- 当前状态。
- 灰度范围。
- 回退开关。
- 负责人。
- 功能覆盖。
- 预计清理时间。

## 14. 测试与验收

### 14.1 每个模块必须覆盖

- 正常、空、加载、错误、无权限和冲突状态。
- 超级管理员、区域管理员、企业管理员和员工角色。
- 区域和外层渠道数据范围。
- 页面刷新、会话过期和重新登录。
- 列表筛选、分页、排序和导出。
- 所有写操作的幂等、版本和审计。
- 高分辨率桌面和固定画板横向滚动。

### 14.2 跨 UI 一致性

- 老 UI 和新 UI 对同一业务对象必须读取同一事实。
- 两个 UI 不得显示不同的最终状态或金额。
- 新 UI 写操作完成后，老 UI 刷新必须看到相同结果。
- 新 UI 的权限结果必须与老 UI 一致。

## 15. 发布与回退

1. 新 UI 先发布到预发布环境的 `*-next.html`。
2. 通过模块验收后，按角色、账号或区域灰度。
3. 灰度期间保留老 UI 入口和回退开关。
4. 新 UI 默认后，老 UI 继续保留生产热修能力。
5. 只有达到清理门禁后，才允许删除旧模块。

不得使用“整站一次性替换”方式上线。

## 16. 老 UI 清理门禁

一个模块只有同时满足以下条件，才允许删除旧 UI：

- 新 UI 已覆盖该模块全部页面和动作。
- 连续两个发布周期无 P0/P1 问题。
- 权限、数据范围、状态机和审计回归通过。
- 外部任务和消息链路正常。
- 没有页面或菜单继续链接旧 UI。
- 回退开关没有实际回退需求。
- 监控数据达到稳定标准。
- 代码、路由、兼容接口、测试和静态资源有独立清理回归。

清理顺序：

```text
停止新功能
→ 冻结旧 UI
→ 隐藏旧入口
→ 观察使用量
→ 删除旧页面和路由
→ 删除旧接口字段
→ 删除旧测试和静态资源
```

## 17. Agent 协作规则

新 UI 开发 Agent：

- 只修改 `ui-next` 和新 UI 目录。
- 不修改老 UI 保护区文件。
- 发现后端契约缺失时先提接口需求，不绕过后端写业务规则。

后端 Agent：

- 先保证老 UI 行为不变。
- 新接口使用加法扩展。
- 所有权限和状态从服务端解析。
- 为兼容旧 UI 保留必要字段和错误码。

测试 Agent：

- 同时验证老 UI 和新 UI。
- 验证跨 UI 数据一致性和回退开关。
- 验证模块清理前没有遗留链接和接口依赖。

发布与运维 Agent：

- 保持正式入口稳定。
- 新 UI 预览和灰度单独发布。
- 任何生产热修都不等待新 UI 排期。

## 18. 任务与 PR 门禁

每个新 UI 任务开始前必须写清：

- 目标页面和业务域。
- 对应原型截图。
- 旧 UI 是否受影响。
- 所需接口和权限范围。
- 状态机和审计要求。
- 回退方式。
- 验收标准。

每个 PR 合并前必须确认：

- 没有修改老 UI 保护区。
- 没有复制业务计算。
- 没有新增未授权接口。
- 有正常、异常和权限测试。
- 有截图或交互证据。
- 有回退方案。
- 已同步最新 `main`。

满足以上规则后，才可以认为新 UI 开发可以与生产修复、业务迭代和旧 UI 运行并行推进。
