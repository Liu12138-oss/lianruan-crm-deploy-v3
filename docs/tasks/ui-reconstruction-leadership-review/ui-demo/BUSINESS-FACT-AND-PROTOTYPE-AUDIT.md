# V3 业务事实、状态流程与原型核对

更新日期：2026-09-22

## 1. 事实来源

本文以当前 V3 代码和已确认业务文档为准，原型、截图和演示数据只能表达这些事实，不能反向定义业务规则。

主要事实来源：

- `apps/api/src/business-store.ts`：客户报备、商机、报价、订单状态和迁移规则。
- `apps/api/src/message-platform-store.ts`：消息渠道、测试投递和状态。
- `apps/worker/src/message-store.ts`：消息消费、重试和到期提醒。
- `packages/shared/src/message-catalog.ts`：事件和到期数据源单一事实来源。
- `docs/V3业务平台底座与业务扩展实施交付方案.md`：未来模块业务边界。
- `docs/H5移动端二期业务决策确认单.md`：移动二期业务范围。
- `docs/tasks/ui-reconstruction-leadership-review/ui-demo/DECISION-LOG.md`：已确认的 UI 重构决策。

## 2. 重要原则

1. 持久化状态、派生展示状态和业务动作名称必须分开。
2. 原型中的数字默认是演示值，不代表生产实时值；接口字段、状态代码、动作和权限必须准确。
3. 服务端状态机是唯一事实来源，前端不能根据日期或按钮自行推进状态。
4. 一个状态可以对应多个业务动作，但动作名称不能伪装成持久化状态。
5. 历史兼容状态和当前正式状态必须分开描述。

## 3. 客户报备状态与流程

### 3.1 持久化状态

| 状态代码    | 中文名   | 说明                               |
| ----------- | -------- | ---------------------------------- |
| `draft`     | 草稿     | 尚未提交审核                       |
| `pending`   | 待审核   | 已提交，等待管理端处理             |
| `approved`  | 已通过   | 审核通过，允许计算保护期和创建商机 |
| `rejected`  | 已驳回   | 审核驳回，必须保留原因             |
| `cancelled` | 已取消   | 业务取消，保留历史                 |
| `converted` | 已转商机 | 已关联创建商机                     |

### 3.2 关键规则

- 当前正式代码没有独立的 `reviewing` 持久化状态。
- 当前正式代码没有独立的 `expired` 报备状态；保护期到期是依据 `approvedAt + protectDays` 计算的派生结果。
- 渠道员工和渠道管理账号提交报备时，初始状态强制为 `pending`。
- 通过时设置 `approvedAt` 并计算保护期到期日。
- 代码兼容 `已过期` 的旧展示，但新 UI 应表达为“保护期已到期”，不能写成独立业务状态。

## 4. 商机阶段与结案状态

### 4.1 新 UI 推进阶段

自 2026-09-22 起，商机原型和 UI 重构统一使用七个推进阶段。阶段名称和进度区间是业务确认值：

| 顺序 | UI 阶段         | 进度区间 | 退出条件摘要                                   |
| ---- | --------------- | -------- | ---------------------------------------------- |
| 1    | 客户建联        | 10%      | 已联系到有效客户联系人，客户主体和初步意向明确 |
| 2    | 需求挖掘        | 20%-30%  | 已识别业务痛点、终端规模、预算方向和技术要求   |
| 3    | 客户方案        | 40%      | 已形成可评审的客户方案，并完成主要技术交流     |
| 4    | POC 试用        | 50%      | 已进入或完成产品验证，客户对关键能力形成结论   |
| 5    | 立项推进        | 60%-70%  | 客户内部进入立项、预算或采购流程推进阶段       |
| 6    | 招投标          | 80%-90%  | 已进入招标、竞争性谈判或商务定标阶段           |
| 7    | 成单            | 100%     | 已确认成交，后续进入报价转订单或订单生成       |
| 终止 | 输单 / 项目取消 | 不参与   | 作为终止结果展示，不占用七阶段主进度           |

### 4.2 现有代码阶段兼容

现有后端阶段代码尚未按七阶段落库，不能直接删除历史代码。接口和迁移必须按下表建立稳定映射，原型只依赖 UI 阶段，不把旧代码名称暴露给用户：

| 现有阶段代码  | 现有关键词 | 新 UI 阶段落位      | 兼容要求                                         |
| ------------- | ---------- | ------------------- | ------------------------------------------------ |
| `contacted`   | 已联系     | 客户建联（10%）     | 直接映射                                         |
| `registered`  | 已报备     | 需求挖掘（20%-30%） | 映射后保留原阶段历史                             |
| `quoted`      | 已报价     | 需求挖掘（20%-30%） | 报价仍为独立实体，不因阶段合并而删除报价状态     |
| `budget`      | 明确预算   | 需求挖掘（20%-30%） | 与需求明确度一起归入需求阶段，保留金额和预算审计 |
| `design`      | 方案设计   | 客户方案（40%）     | 直接映射                                         |
| `testing`     | 产品测试   | POC 试用（50%）     | 产品测试语义统一展示为 POC 试用                  |
| `negotiation` | 商务谈判   | 招投标（80%-90%）   | 商务谈判是子活动，阶段展示统一为招投标           |
| `won`         | 赢单       | 成单（100%）        | 成交概率字段继续兼容，显示名称改为成单概率       |
| `lost`        | 输单       | 输单（终止）        | 保留结案原因和审计                               |
| `cancelled`   | 项目取消   | 项目取消（终止）    | 保留结案原因和审计                               |

“立项推进（60%-70%）”当前没有独立的现有阶段代码。它不是前端可以静默推断的状态；后端需要在不破坏历史数据的前提下新增阶段代码或明确派生规则，并在接口层返回统一的七阶段值。

### 4.3 结案状态代码

- `active`：推进中。
- `won`：已赢单。
- `lost`：已丢单。
- `cancelled`：已取消。

结案状态与推进阶段分开：`active` 表示仍在七阶段中推进，`won`、`lost`、`cancelled` 表示已结束。结案原因、最后阶段和操作人必须保留在状态历史中。

## 5. 报价状态与流程

### 5.1 持久化状态

| 状态代码    | 中文名   | 业务含义                   |
| ----------- | -------- | -------------------------- |
| `draft`     | 草稿     | 可修改、可删除             |
| `submitted` | 已提交   | 已提交给客户或进入确认流程 |
| `approved`  | 已确认   | 客户确认，可转订单         |
| `rejected`  | 已驳回   | 报价被驳回                 |
| `converted` | 已转订单 | 已生成订单，报价只读       |
| `cancelled` | 已取消   | 历史保留                   |

### 5.2 派生展示

- “待客户确认”是 `submitted` 的业务展示，不是独立持久化状态。
- “折扣待审”是审批任务或风险提示，不是报价主状态。
- “报价有效期已到”由有效期日期计算，不能直接写入正式状态字段。
- 当前正式代码将旧 `confirmed` 归一化为 `approved`。

## 6. 订单状态与流程

### 6.1 持久化状态

| 状态代码                     | 中文名               |
| ---------------------------- | -------------------- |
| `draft`                      | 草稿                 |
| `pending_primary_confirm`    | 待一级确认           |
| `primary_confirmed`          | 一级已确认           |
| `primary_rejected`           | 一级已驳回           |
| `pending_superadmin_confirm` | 待超管确认           |
| `returned_to_region`         | 已退回区管修改       |
| `returned_to_primary`        | 已退回一级渠道商修改 |
| `returned_to_secondary`      | 已退回二级渠道商修改 |
| `revision_requested`         | 待回退修改审核       |
| `confirmed`                  | 已确认               |
| `processing`                 | 处理中               |
| `shipped`                    | 已发货               |
| `completed`                  | 已完成               |
| `rejected`                   | 已驳回               |
| `cancelled`                  | 已取消               |
| `replaced`                   | 已替换               |

### 6.2 主审批链

```text
草稿
→ 待一级确认
→ 一级已确认
→ 待超管确认
→ 已确认
→ 处理中
→ 已发货
→ 已完成
```

### 6.3 例外链

```text
一级已驳回 / 已驳回
退回区管 / 一级 / 二级修改
待回退修改审核
已取消
已替换
```

### 6.4 关键规则

- 当前没有独立的 `pending_region_confirm` 持久化状态；“待区管处理”是 `primary_confirmed` 上的当前动作提示。
- 一级渠道商确认的正式状态是 `primary_confirmed`。
- 区管确认后进入 `pending_superadmin_confirm`。
- 区管调价直接进入 `pending_superadmin_confirm`，并保留调价记录。
- 超管确认后进入 `confirmed`。
- 回退修订申请把订单置为 `revision_requested`。
- 批准修订会保留旧订单，创建版本递增的新报价和新订单；旧订单最终表现为 `replaced`。
- 报价转订单时订单复制报价明细，不能重新从前端提交金额。

## 7. 渠道状态

持久化审核状态只有四种：

| 状态代码   | 中文名          |
| ---------- | --------------- |
| `pending`  | 待审核          |
| `active`   | 已启用 / 合作中 |
| `rejected` | 已驳回          |
| `disabled` | 已停用          |

“待续签、即将到期、协议到期”是协议有效期计算的业务风险，不是渠道主状态。

### 7.1 渠道核心档案字段和维护入口

渠道核心档案必须从渠道商列表、渠道详情和渠道画像页都能发现，入口统一为“编辑渠道商信息”或“维护核心档案”。成员、证书和登录账号仍分开维护：

| 档案分组       | 字段                                                                                                     | 维护位置                  | UI 展示要求                                |
| -------------- | -------------------------------------------------------------------------------------------------------- | ------------------------- | ------------------------------------------ |
| 工商主体       | 企业名称、统一社会信用代码、法定代表人、成立时间、经营状态、开票能力                                     | 编辑渠道商信息            | 详情只读展示，编辑弹窗可维护               |
| 经营规模       | 注册资本、实缴资本、年营收额、企业员工数量、社保参保人数、注册地址、经营范围、数据来源、资料核验状态     | 编辑渠道商信息            | 空值显示待补充，不自动伪造                 |
| 联系人         | 企业管理员、渠道负责人、联系电话、企业邮箱、地市区号、老板及老板联系方式                                 | 编辑渠道商信息 / 成员     | 敏感号码按权限脱敏                         |
| 合作与渠道关系 | 渠道等级、所属区域、所在城市、协议编号、合作状态、上级渠道、分销层级、技术服务商类型、服务区域、回款周期 | 编辑渠道商信息 / 层级管理 | 层级变更保留有效期历史                     |
| 经营画像       | 主要行业、主要代理品牌、授权产品线、资质认证、典型客户、渠道定位、合作背景                               | 编辑渠道商信息            | 用于渠道画像和筛选，不替代成员证书         |
| 能力与提醒     | 产品能力矩阵、销售覆盖评分、交付能力评分、回款稳定评分、授权到期提醒、风险敏感字段                       | 渠道画像 / 资质维护       | 评分和矩阵由服务端持久化，渠道端按权限展示 |

渠道核心档案保存后必须写审计。渠道企业管理员可维护本企业档案，区域管理员只可维护绑定区域，超级管理员可维护全量；查看和编辑权限分开校验。

## 8. 组织与账号状态

- 账号基础状态：`active`、`disabled`。
- 离职状态：`active`、`offboarding`、`offboarded`、`reactivated`。
- 归档后账号释放原登录名，但保留主键、业务引用和审计。
- 恢复账号只按本次提交的新角色和任职授权，不自动恢复历史角色。
- 证书变化不自动修改业务角色、系统权限或数据范围。

## 9. 审批、任务和消息状态

### 9.1 审批

持久化状态：`pending`、`approved`、`rejected`、`cancelled`。

### 9.2 后台任务

统一后台任务状态：`queued`、`running`、`succeeded`、`failed`。

### 9.3 消息投递

消息投递状态包括：`pending`、`sending`、`retry_wait`、`success`、`failed`、`dead`、`ignored`。

- `retry_wait` 与 `failed` 必须区分。
- `dead` 表示重试耗尽，等待人工补偿。
- 消息失败不得回滚已提交的业务事实。

## 10. 消息事件和到期数据源

`packages/shared/src/message-catalog.ts` 当前定义：

- 15 类业务事件。
- 5 类到期数据源。
- 合计 20 类提醒来源。

业务事件包括订单待审批、订单状态变更、订单已确认、报备待审批、报备通过、报备驳回、员工账号待审核、渠道商待审核、报价待审批、报价通过、报价驳回、商机赢单、商机输单、商机阶段变更、消息任务连续失败。

到期数据源包括报备保护期、商机预计成交日、报价有效期、订单交付日期、商机下次跟进计划。

### 11.1 线索管理的原型边界

线索管理属于本轮新增原型，不是当前代码已经实现的正式业务能力。原型只定义以下边界：

- 外部公告由独立爬虫和归一化模块采集，UI 不直接访问目标网站。
- 线索只读，第一版允许关注、忽略、备注和导出，不建立客户或商机关联。
- 采集来源状态、公告生命周期和业务处理状态分开，不合并为单一状态。
- 公告不会自动创建客户、商机，也不会自动推进商机七阶段。
- `立项推进` 和 `招投标` 仍按商机七阶段口径处理，线索不会改变商机状态。
- 线索详情预留客户与商机关联位置，但第一版不提供正式动作和写接口。

## 12. 数值使用规则

原型中的客户数、订单数、金额、增长率和趋势图仍属于演示数据，不能作为业务事实或生产实时值。前端开发必须使用服务端响应；后端不得把原型数字写入种子数据或验收断言。

状态代码、中文名、顺序、终态、异常态、审批角色和动作规则必须按本文核对。

## 13. 原型核对结论

本轮原型已按本文修正交互和状态显示。后续新增页面必须同时更新：

- 页面、路由与权限矩阵。
- 动作、接口、幂等与错误契约。
- 测试和回退矩阵。
- 本事实核对文档。
