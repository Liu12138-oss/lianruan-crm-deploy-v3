## 3. 事实核查

### 3.1 官方规范和主流实践

2026-09-18 对 GitHub 主线进行只读核查，结论如下：

1. MCP `2026-07-28` 是当前正式稳定版，服务端必须实现 `server/discover`。
2. 该版本取消协议级会话和 `initialize` 握手，每次请求通过 `_meta` 携带协议版本、客户端信息和客户端能力。
3. Streamable HTTP 使用单一 POST 端点，不再提供旧版 GET/SSE 会话；要求校验 `Origin`、`MCP-Protocol-Version`、`Mcp-Method` 和 `Mcp-Name`。
4. 工具可声明 `annotations`、`outputSchema`，结构化结果通过 `structuredContent` 返回。
5. `server/discover`、`tools/list` 等可缓存结果在 `2026-07-28` 必须携带 `ttlMs` 和 `cacheScope`；TypeScript SDK v2 会提供安全默认值。
6. 远程授权推荐 OAuth 2.1 和受保护资源元数据。客户端注册优先使用预注册或 Client ID Metadata Documents，Dynamic Client Registration 已废弃但仍保留兼容。
7. GitHub 官方 MCP Server 通过 GitHub API 和用户令牌执行权限判断，不直接连接 GitHub 数据库；官方参考数据库 Server 属于参考实现，不作为本项目生产依赖。

### 3.2 当前仓库事实

1. 当前不存在 `apps/mcp`、MCP 契约、MCP 内部路由、MCP 配置或 `mcp_net`。
2. 当前业务接口仍存在兼容身份、空用户上下文全量条件、OpenAPI 未传入绑定用户和数据范围 `*` 回退等前置风险。
3. 当前业务事实、权限、数据范围、字段策略和审计来源仍是 V3 API 和 PostgreSQL。
4. 当前单机部署只有 `app_net`、`data_net` 和 `maintenance_net`，没有 MCP 独立网络。
5. 当前生产远程 MCP 不存在，因此方案修订不会影响现有业务运行。

## 4. 已确认范围

1. 三阶段全部实施：协议骨架与 RedClaw 模拟验收、可信授权与真实只读工具、隔离部署与生产灰度。
2. 首期只读，不上线任何创建、修改、审批、收款、领取、分配、导出、附件下载或任意 SQL 能力。
3. 内部人员和渠道人员同时支持，每次调用必须解析唯一有效主身份。
4. 默认以赤兔支持 MCP `2026-07-28` 为实施前提；阶段一仍执行真实协议探测，不通过的按客户端兼容阻断处理。
5. 先完成 MCP 规范细节修订和任务级验收固化，再修改代码；修订不得改变当前 V3 页面、API、Worker 和业务流程。

## 5. 标准细节修订决策

1. 十个工具全部显式声明 `readOnlyHint: true`、`destructiveHint: false`、`idempotentHint: true`、`openWorldHint: false`。
2. 每个工具定义版本化 `inputSchema` 和 `outputSchema`，结构化业务结果同时放入 `structuredContent`，并保留序列化 TextContent 兼容内容。
3. 协议结果层的 `resultType: "complete"` 由 SDK v2 生成并纳入协议测试；业务结果不得自行伪造协议信封。
4. `server/discover` 与 `tools/list` 的 `ttlMs`、`cacheScope` 必须显式验收。工具列表依赖用户授权时只允许 `ttlMs: 0` 或 `cacheScope: "private"`，不得使用公共缓存。
5. 工具执行错误使用 `isError: true`；未知工具、请求结构错误、协议版本不支持和未授权仍分别使用标准 JSON-RPC 或 HTTP 错误。
6. 不实现 Resources、Prompts、Roots、Tasks、MCP Apps 和旧 HTTP+SSE 传输。

## 6. 授权和权限决策

允许一次 MCP 工具调用仍按以下链路计算：

```text
MCP总开关与客户端有效
+ 用户账号有效且主身份唯一
+ MCP接入和工具权限默认开放
+ V3原业务读取权限通过
+ 对象位于用户数据范围
+ 字段通过现有角色字段权限
+ 限流、分页、超时和审计允许
```

最终决策：

1. “默认全授权”仅表示 MCP 接入权限和十个评审通过的工具不额外要求逐人、逐工具白名单。
2. MCP 权限不替代 V3 原业务权限，不扩大数据范围，不绕过字段权限。
3. 所有有效 V3 账号默认具备 MCP 接入和十个工具的 MCP 层权限；是否实际看到和调用工具，仍按原业务权限、数据范围和字段策略过滤与复核。
4. 权限代码和管理能力继续保留，支持总开关、工具停用、客户端停用、账号停用和紧急撤权。
5. 新增 `V3_MCP_DENIED_USERS` 作为紧急用户禁用清单，优先级高于默认开放，用于快速撤销 MCP 调用。
6. 超级管理员没有隐藏的业务全量绕过，仍必须具备显式业务读取权限和显式数据范围。
7. 账号存在多个有效身份、多个渠道成员关系或主身份无法唯一解析时，拒绝业务工具调用。
8. 新增加的工具默认关闭，必须完成契约、权限、数据范围、脱敏、审计和测试后才能加入默认开放集合。

## 7. 字段和敏感数据决策

1. 不建立独立的 MCP 业务涉密字段分类，直接复用 V3 现有角色字段权限。
2. 无字段权限时默认隐藏或脱敏，不降级返回明文。
3. Token、密码、私钥、服务密钥、数据库密码、Session Secret、API Key、OAuth 授权码、Refresh Token 和客户端密钥对任何角色均禁止读取。
4. 上述凭据不得进入模型上下文、工具参数回显、工具返回、普通日志、调试日志、错误详情和审计正文。
5. 审计最多保存令牌指纹、`jti`、哈希、结果状态和非敏感元数据，不保存凭据原文。

## 8. 数据访问决策

1. MCP 不直接连接业务主库，也不直接连接业务库、分析库或其他数据库。
2. 数据访问链路固定为 `MCP -> apps/api 内部只读接口 -> 领域服务或受控只读视图 -> PostgreSQL`。
3. API 负责可信身份、权限、数据范围、字段脱敏、保护性 404、V3 链接和审计落库。
4. MCP 只负责协议、工具注册、输入输出校验、限流、错误转换和调用内部接口。
5. MCP 容器不注入 `DATABASE_URL`、数据库密码、Docker 套接字和其他业务主库凭据。

## 9. HTTP 与 HTTPS 决策

1. 本机 stdio 是阶段一首要验收传输，不依赖 HTTPS。
2. 本机 Streamable HTTP 只允许绑定 `127.0.0.1`，仅开发和测试使用。
3. 容器内部由 Nginx 到 `apps/mcp` 可以使用 HTTP，但必须位于独立 `mcp_net`，不得直接发布到宿主机公网。
4. 外部远程 MCP 在证书就绪前保持关闭，不使用公网或跨网明文 HTTP 开放 OAuth 令牌和业务数据。
5. 实现阶段同步完成 HTTPS-ready 配置：证书挂载、443 服务、80 跳转或拒绝、MCP 稳定路径和健康检查。
6. 证书和域名就绪后，只需启用 443 MCP 路径并切换配置，不修改 MCP 工具或鉴权协议。

## 10. 未采用方案

1. 不让 MCP 直接连接业务主库或使用共享数据库超级账号。
2. 不把所有 OpenAPI 自动转换为 MCP 工具。
3. 不使用共享业务账号、匿名账号、固定管理员令牌或模型自报身份。
4. 不在外部无 TLS 场景下开放远程 MCP。
5. 不在 MCP 文档中另建一套业务字段权限、角色体系或 V3 业务状态机。
6. 不把 P0 身份权限修复和 MCP 业务工具混为一个不可回退升级包。

## 11. 回退与风险

1. MCP 总开关默认关闭，停止 MCP 后 V3 登录、四套正式页面、API、Worker 和数据库事务继续运行。
2. 出现越权、字段泄露、身份映射错误、异常负载或审计失败时，关闭总开关、关闭 Nginx MCP 路径并停止 MCP 容器。
3. 不因 MCP 回退业务数据、业务状态或既有 API 镜像。
4. 远程 HTTPS 尚未启用是阶段三的生产门禁，不影响阶段一、阶段二的本地和测试实施及验收。
5. 赤兔协议探测、真实数据库前置修复、HTTPS 证书、试点人员和性能基线可能影响对应阶段退出，任何一项未完成都不得宣称生产完成。
