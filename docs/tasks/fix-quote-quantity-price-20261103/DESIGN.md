# 报价逐项数量与价格计算修复方案

> 由 hgrill-bug 访谈自动生成，来源：docs/tasks/fix-quote-quantity-price-20261103/docs/DECISION-LOG.md。术语表见仓库 docs/CONTEXT.md。

## Problem Statement（问题陈述）

生产旧 UI 报价页允许逐模块调整数量，但固定价与部分阶梯价行金额没有乘以逐项数量，导致用户修改数量后行金额和报价总额不变。旧 UI 创建、更新报价时只提交 featurePointOverrides，而服务端缺少逐项数量解析和持久化，保存或再次编辑后数量可能回退；非端点产品还会错误继承整单端点数。该问题同时影响旧管理端、旧渠道端及其商机内嵌报价入口。

复现场景：访客管理模块单位为“套”，数量由 1 改为 100；标准虚拟镜像按固定价计价，数量由 1 改为 10。预期行小计和报价总额随数量变化，保存刷新后数量与金额保持。

## Solution（解决方案）

- 旧 UI 统一按产品主档单位确定默认数量：端点类产品默认取整单端点数，非端点产品默认取 1，标准维保默认按 12 个月。
- 行金额统一为“有效单价 × 逐项数量”，固定价和阶梯价均遵循同一公式；行金额展示采用产品主档单位。
- 创建、更新、试算报价时优先使用完整逐项数量快照 itemQuantities，并兼容旧页面的 featurePointOverrides；保存后持久化数量快照，刷新和再次编辑不丢失。
- 报价详情返回真实产品单位作为数量标签，不再硬编码“点”。
- 合并已验收的 KB029 渠道员工审批、企微提醒与审计修复，生产继续使用旧 UI。

## 涉及模块（Implementation Impact）

- 数据层：不新增表结构、不迁移报价历史数据；报价扩展字段保存规范化逐项数量快照。
- 接口层：试算、创建、更新报价统一解析逐项数量；兼容 itemQuantities、quantities、逐项数量、itemQuantitiesList、featurePointOverrides；既有调用字段保持可用。
- 前端：旧管理端与旧渠道端的报价创建、编辑、汇总、商机内嵌报价、报价详情统一数量和单位口径；脚本缓存版本同步更新。
- 逻辑：固定价、阶梯价、渠道等级价、区域覆盖价、维保计算均以逐项数量为输入；不改产品价格配置和订单编号规则。

## Compatibility（兼容性分析）

- 存量报价记录保持原数量和金额，不做批量重算；再次编辑时按现有明细恢复数量。
- 尚未刷新浏览器的旧页面仍可只发 featurePointOverrides，服务端兼容读取，避免升级过程中丢数量。
- 硬件数量继续由 hardwareItems 控制，维保月数继续由标准维保逻辑控制，订单编号和审批状态机不变。
- 接口新增字段为可选字段，不破坏重构 UI 现有 itemQuantities 调用。

## Acceptance Criteria（验收标准）

- [ ] 旧管理端固定价产品数量 10、100 时，行小计与报价总额均等于单价乘数量。
- [ ] 旧管理端与旧渠道端阶梯价产品数量变化时，命中正确档位且行小计、总额同步变化。
- [ ] 访客管理模块数量 100 保存、刷新、再次编辑后仍为 100，金额不回退。
- [ ] 只发送 featurePointOverrides 的旧载荷仍能按逐项数量保存和计价。
- [ ] 报价详情数量标签使用产品主档单位，不把“套”“端点”等统一显示为“点”。
- [ ] 硬件数量、维保月数、订单金额、订单编号与审批规则不回归。
- [ ] KB029 员工首次加入审批、四名提醒接收人、企微投递渠道和成员审计动作继续通过。
- [ ] 生产旧 UI 页面正常，未引入重构 UI 的 Vite 资源入口。

## Regression Scope（回归范围）

- 旧管理端和旧渠道端：报价创建、编辑、详情、商机内嵌报价、转订单。

- KB029：渠道成员新增/编辑/导入审批、员工审批提醒、企微应用投递、渠道成员审计。
- 基础运行：API 双实例、Nginx、Worker、PostgreSQL、Redis 健康检查。
