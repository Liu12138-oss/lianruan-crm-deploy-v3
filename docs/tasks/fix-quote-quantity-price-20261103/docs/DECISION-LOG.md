# 报价修改数量后价格未变化 — 决策日志

## 2026-11-03 — 首轮只读排查

- 问了什么：用户反馈“联软安略安全管控平台标准虚拟镜像、访客管理模块”修改数量后价格没有变化；当前尚未确认页面、修改字段和价格未变化的准确位置。
- 定了什么：本次按缺陷处理；生产继续使用旧 UI，不部署重构 UI；在未确认现象和影响范围前不修改代码、不写生产数据、不制作或部署升级包。
- 否了什么：暂不直接按“价格没有变化”编码；单价、行小计、报价总额和产品目录维护价是不同口径，需先区分。
- 权衡了什么：优先只读核查代码与生产数据，避免因产品编码、UI 版本或计价口径不一致造成误修。

### 已核实事实

- 用户明确生产使用旧 UI。
- 生产产品目录中的 `UA-NAC-G-1` 为“访客管理模块”，单位为“套”，价格类型为阶梯计价；全国 1–500 档的阶梯单价均为 2000 元，江苏区、安徽区、上海区（非金）、浙赣区覆盖价均为 3000 元。因此数量变化后“单价不变”符合当前价格配置，但行小计应按“单价 × 数量”变化。
- 当前可访问的生产库中未检索到精确的 `LV-VM-1` 或“联软安略安全管控平台标准虚拟镜像”产品记录；只检索到名称相近但价格不同的 `Q-DSS-Base-VM-V1` 和 `Q-DSS-Base-VM-CNOS-V1`。
- 旧 UI 报价页支持逐模块数量输入，并以 `featurePointOverrides` 保存本地选择；报价试算、创建和更新接口当前读取的逐项数量字段为 `itemQuantities` / `itemQuantitiesList`，两者口径存在不一致风险，尚需用实际请求或复现确认。
- 该不一致可能导致：界面本地按单项数量重算，但服务端保存后按端点数或默认数量 1 重算，从而出现金额回退或不变。

### 待确认

- 具体操作页面是报价单创建/编辑页、产品维护页，还是订单退回修改页。
- 修改的是整单“端点数量”、单个模块数量，还是硬件数量。
- “价格没有变化”指最终单价、行小计、报价总额还是目录维护价。
- 报价单号、修改前后数量与金额，或对应截图。
- “联软安略安全管控平台标准虚拟镜像”在页面中的产品编码、所属分类和选择入口；当前生产库未找到同名记录。

## 2026-11-03 — 第二轮：截图确认

- 问了什么：请用户补充总价未变化的准确位置和截图。
- 定了什么：结合截图确认操作为旧 UI 报价页“第三步：报价汇总—自选功能”；用户修改了单模块数量，访客管理模块由 1 改为 100，虚拟镜像数量为 10。
- 否了什么：排除“整单端点数量输入”问题；截图中的整单端点数量保持 100。
- 权衡了什么：截图行尾金额显示的是计价结果而非明确标注的“小计”，需同时核对“行尾金额口径”和“整单报价总额口径”，不能用一处展示正常掩盖另一处计算或保存错误。

### 代码核查补充

- 旧管理端 `apps/web/public/admin-app.js` 的 `getFeaturePrice` 在固定价和阶梯价分支没有乘以单项数量：固定价直接返回 `priceFixed`，阶梯价直接返回档位单价；这会让汇总行金额看起来不随数量变化。
- 同一文件的 `calculateBaseFeatureTotal` 在阶梯价分支会乘以数量，但固定价分支仍不乘以数量；因此固定价产品即使整单总额重新计算，也不会随数量变化。
- 旧 UI 创建和更新报价提交的是 `featurePointOverrides`，服务端试算、创建和更新读取的是 `itemQuantities` / `itemQuantitiesList`；单项数量在保存链路中可能丢失，服务端会按“端点数”或默认 1 重新取数。
- 重构 UI `QuoteCreatePage.vue` 已按“数量、最终单价、小计”分列，并在试算和保存时提交 `itemQuantities`，具备同一修复的对照口径。

## 2026-11-03 — 订单编号补充排查

- 问了什么：用户要求“区管提交的订单编号也要和渠道商提交的订单编号规则一致，自动带订单对应合作伙伴的协议编号”，需要确认正式编号的生成时机。
- 定了什么：正式编号规则仍只读核对，未改代码、生产数据或发布包。
- 否了什么：不能未经确认把正式编号生成时机从“区管确认或调价”提前到“首次提交订单”，否则会改变现有审批编号规则，并可能影响渠道商、一级渠道、区管和超管的状态流转。
- 权衡了什么：需要区分“首次提交时看到前置编号”与“区管确认后仍未生成正式编号”两种现象，前者是业务规则取舍，后者才是缺陷。

### 已核实事实

- 正式规则见 `docs/V3业务平台底座与业务扩展实施交付方案.md`：订单在区管确认前使用 `LS-提报登录账号-YYYYMMDD-日流水` 前置编号；区管确认或区管调价时保留前置编号并生成 `协议编号-smb-区管邮箱前缀-地市区号-合同流水号` 正式编号。
- 服务端 `apps/api/src/business-store.ts` 已实现该规则：区管确认或调价时，从订单关联渠道商主档读取协议编号、地市区号，并以已登录区管身份取流水号；协议编号缺失时阻止确认并返回明确错误。
- 旧管理端 `apps/web/public/admin-app.js` 的区管确认按钮虽未显式提交 `action: "region_confirm"`，但会提交目标状态 `pending_superadmin_confirm`；服务端以订单原状态和目标状态判断是否取正式编号，因此理论上仍会触发。
- 生产复核：近期由江苏区管确认的订单已生成 `LP-2505018-H-smb-liuchengzhou-0512-*` 正式编号，并保留 `LS-liuchengzhou-*` 前置编号。存量有 3 笔仍为 `LS` 编号的确认/完成订单，创建时间分别为 2026-08-06、2026-08-25、2026-09-01，均早于正式编号功能投产，属于历史订单，不在本次重编范围。
- 生产存在 1 笔 `LS-liuchengzhou-20261028-0003`，状态为 `pending_primary_confirm`，其渠道商协议编号为空；按现有规则后续区管确认会被服务端阻止，需由业务补齐渠道商主档，不能擅自补写生产数据。

### 待确认

- 用户所说“区管提交的订单编号”是要求区管首次提报订单时立即显示正式编号，还是指区管确认后仍显示前置编号或未带协议编号。选择后者时只修复缺陷；选择前者时属于正式编号生成时机调整，需要单独确认对现有审批规则的影响。
