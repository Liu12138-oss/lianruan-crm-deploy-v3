# 客户商机情报与智能分析平台需求总结与建设建议

## 文档定位

- 文档角色：产品负责人需求总结与建设建议
- 依据材料：`客户商机情报与智能分析平台建设建议书.md`、V3 业务平台底座与业务扩展实施交付方案、V3 现有代码和数据库资产
- 适用范围：V3 工程化应用（`apps/web`、`apps/api`、`apps/worker`、`packages/*`、`deploy/single-server`）
- 当前结论：建议立项，但必须采用小范围试点、人工确认、证据可追溯和分期交付方式
- 重要说明：本文中的“建议”“待确认”不等于已经批准的业务规则；未确认内容不得直接写死到代码或生产配置

## 一、产品负责人结论

### 1.1 是否建设

建议建设。该平台对现有 V3 的价值不是增加一个搜索页面，而是把外部公开信息、内部客户商机、产品资料和销售动作连接起来，形成：

```text
发现信号 → 识别客户 → 归并项目 → 提炼需求 → 匹配产品资料 → 人工确认 → 回到CRM推进
```

它能够补足现有 CRM “已经发生的业务记录”，但不能替代 CRM 的客户主数据、报备审批、商机阶段、报价和订单主流程。

### 1.2 建设原则

1. **V3 仍是业务事实主系统。** 情报平台保存发现、分析和证据；客户、报备、商机、报价、订单仍由 V3 正式流程管理。
2. **先建立数据和证据基础，再扩大模型能力。** 客户识别、项目归并、资料标签、证据回链比“接入更强模型”更优先。
3. **外部信息只做合规接入。** 优先使用开放接口、授权数据服务和人工导入，不模拟登录、不绕过验证码、不抓取受限页面。
4. **人工确认是第一版的业务闸门。** 情报可以自动发现和分析，但不能自动创建正式商机、修改客户主档或提交投标文件。
5. **所有智能结论必须可解释。** 报告明确区分已确认事实、基于资料的推断、待确认问题和暂无结论，并回链原文证据。
6. **权限先于智能。** 服务端必须按 V3 身份、组织、区域、渠道、客户归属、字段权限和资料密级执行授权。
7. **第一版控制范围。** 建议选择一个产品线、两个重点行业、一个或两个区域和一批真实客户开展试点。

### 1.3 建议的产品形态

不是另建一套 CRM，也不是把大模型直接接到生产数据库，而是 V3 内的三个协同层：

| 层次         | 主要职责                                                   | 是否写入CRM业务事实        |
| ------------ | ---------------------------------------------------------- | -------------------------- |
| 情报中台     | 采集、清洗、客户识别、项目归并、文件解析、证据管理         | 否                         |
| 智能分析应用 | 客户画像、需求分析、风险识别、资料推荐、商机评分、行动建议 | 否                         |
| CRM协同      | 人工确认、转报备草稿、关联既有商机、跟进反馈、结果回流     | 仅经人工确认后进入既有流程 |

## 二、需求总结

### 2.1 业务问题

销售人员目前需要在公开网络、招采来源、历史商机、产品资料和案例文件之间反复查找，主要痛点是：

- 外部采购信号发现晚，无法持续跟踪客户建设动态；
- 企业名称、集团关系和别名不统一，难以判断公告是否对应已有客户；
- 同一项目的采购意向、招标、更正和中标公告容易重复计数；
- 招标文件、扫描件、表格和历史方案中的关键信息提取成本高；
- 客户需求、预算、时间、联系人、竞争情况分散在多个记录中；
- 产品资料和成功案例缺少统一标签，推荐依赖个人经验；
- AI 如果没有权限、证据和反馈约束，容易产生客户混淆、日期误读、无依据推断和越权泄露。

### 2.2 总体目标

用户输入客户名称、选择已有客户或选择情报项目后，平台能够在授权范围内汇总内部 CRM 数据、合规公开信息和内部资料，生成一份带证据、可解释、可确认、可执行的客户商机分析报告，并把确认结果安全地带回 V3 业务流程。

### 2.3 目标用户

| 用户                | 主要诉求                                 | 首期权限建议                         |
| ------------------- | ---------------------------------------- | ------------------------------------ |
| 销售人员/商机负责人 | 查客户动态、看报告、确认行动、关联商机   | 本人或授权客户、商机和资料范围       |
| 区域管理员          | 查看区域商机情报、审核高价值项目、看转化 | 绑定区域及下级范围                   |
| 渠道管理员          | 查看本渠道关联客户、项目和资料           | 当前渠道及授权成员范围               |
| 产品/售前人员       | 维护产品能力、案例标签、方案资料         | 产品资料编辑；业务数据只读范围       |
| 情报审核人员        | 审核客户匹配、项目归并和报告结论         | 受控审核范围，不自动获得全量业务数据 |
| 平台管理员          | 配置数据源、模型、规则、权限、审计和任务 | 平台配置权限与业务数据权限分离       |
| 管理层              | 查看汇总、重点项目、风险和趋势           | 只读指标和脱敏摘要，按组织范围       |

### 2.4 核心业务场景

1. **客户主动分析**：选择 CRM 客户，查看客户画像、历史合作、公开动态、现有商机和下一步建议。
2. **外部信号发现**：系统按来源和规则采集招采公告、采购意向、项目预告、企业建设动态，形成待审核情报。
3. **项目归并**：将同一项目的采购意向、招标公告、更正公告、中标公告和附件归并为项目时间线。
4. **招标文件分析**：解析网页、PDF、扫描件、Word、演示文稿、表格和图片，提取需求、预算、日期、资格条件、技术参数和竞争风险。
5. **资料推荐**：按行业、区域、客户规模、场景、产品线和资料密级推荐产品资料、成功案例和历史应答材料。
6. **销售行动辅助**：生成优先级、建议负责人、首次沟通问题、建议联系时间和推进/观察/暂缓/放弃理由。
7. **CRM 协同**：人工确认后转为报备草稿、关联既有商机或写入跟进记录；失败可重试、可对账、可人工补偿。
8. **反馈闭环**：记录销售采纳、忽略、纠错、赢单、输单和资料使用结果，用于规则和推荐评测。

### 2.5 范围边界

#### 本期建议纳入

- 客户检索、企业标准化、别名和集团关系确认；
- 合规公开情报接入与采集任务；
- 情报去重、项目归并、公告版本和时间线；
- 多格式文件解析、文本切片、资料标签和证据定位；
- 客户画像、需求摘要、风险提示、商机评分和行动建议；
- 人工审核队列、报告版本和反馈；
- 与 V3 客户、报备、商机、产品和跟进的只读关联；
- 人工确认后的“转报备草稿”“关联商机”“新增跟进”协同；
- 任务、审计、权限、限流、失败重试和数据保留。

#### 第一版明确不纳入

- 自动向客户发送邮件、文件、营销消息或外部营销短信；
- 未经授权抓取登录后页面、绕过验证码或访问控制；
- 自动修改客户主档、自动创建正式商机、自动推进商机阶段；
- 自动生成并提交完整投标文件或承诺中标；
- 直接让模型访问生产主库、执行任意查询或调用写接口；
- 未经评测上线复杂预测模型；
- 把企微群聊作为默认的敏感明细出口。

## 三、与 V3 项目的结合评估

### 3.1 可复用能力与缺口

| 能力             | V3 现有资产                                                                         | 当前成熟度判断           | 本需求处理建议                                                                         |
| ---------------- | ----------------------------------------------------------------------------------- | ------------------------ | -------------------------------------------------------------------------------------- |
| 客户主档         | `crm.customers`、`crm.customer_aliases`，含统一社会信用代码、区域、负责人、渠道归属 | 二级，可用但需收口       | 复用主档；扩展别名来源、集团关系和匹配证据，不在扩展字段中堆项目主数据                 |
| 客户报备         | `crm.registrations`、报备事件和审批链路                                             | 二级                     | 情报只生成“报备草稿建议”，由既有报备审批流程办理                                       |
| 商机与跟进       | `crm.opportunities`、`crm.opportunity_followups`、阶段历史                          | 二级                     | 复用商机和跟进；情报项目与正式商机建立可追溯关联                                       |
| 产品与报价       | 产品目录、价格、工作量、报价快照                                                    | 二级                     | 复用产品元数据和资料标签；不让模型直接计算或修改报价                                   |
| 组织、渠道和权限 | `iam`、`org`、`channel`、数据范围和角色权限设计                                     | 二级至三级               | 作为强制前置门禁；分析、详情、下载、异步任务共用同一范围策略                           |
| 审计             | `audit.audit_logs`、请求编号和结构化日志                                            | 二级                     | 扩展情报查看、下载、确认、同步、模型调用和拒绝审计                                     |
| 文件与任务       | `ops.files`、`ops.import_export_tasks`、`ops.outbox_events`、`apps/worker`          | 三级                     | 扩展文件扫描与保留；新增独立情报任务池，不能与关键业务事件争抢并发                     |
| 消息提醒         | 统一消息平台和多渠道投递设计                                                        | 四级至三级               | 后续将高价值项目、待审核和截止时间接入提醒；不在情报模块内直调供应商                   |
| OpenAPI          | `/api/open/v1` 核心资源、统计和产品只读接口                                         | 二级但存在生产前置阻断项 | 不直接依赖现状全量接口；先完成可信身份、绑定用户范围和默认拒绝，再建设专用只读分析接口 |
| 分析与智能       | 设计文档已有指标、AI、模型网关、评测和企微边界                                      | 四级，尚无生产闭环       | 本需求作为分析智能域的一个业务场景落地，复用统一模型网关、分析库、评测和审计           |
| 前端入口         | `apps/web` 工程化工作区、四套正式业务页面                                           | 二级                     | 新模块进入 `/workspace/*`；正式页面只增加最小导航，不替换现有页面                      |
| 部署             | `deploy/single-server` 单机容器、数据库、Redis                                      | 可复用                   | 采集、解析、分析任务纳入同一升级包，但使用独立进程池、开关和回退方案                   |

### 3.2 必须先完成的 V3 前置门禁

1. 所有业务接口使用服务端可信身份，不再让 `operatorId`、`username`、`x-v3-delivery-user` 或页面自报字段参与授权和审计主体判断。
2. OpenAPI 绑定用户必须进入实际数据范围计算；资源未配置时默认拒绝，不得回退为全量。
3. 客户、报备、商机、产品和文件详情、下载、导出、异步任务统一执行功能权限、数据范围和字段权限。
4. AI 和分析默认查询只读分析视图、物化视图或指标宽表，不直接查询生产主库。
5. `apps/worker` 按关键事件、外部投递、批量规则、分析智能划分进程池，情报解析和模型调用不得阻塞报备、商机、审批和消息任务。
6. 统一入口和四套正式页面保持不变，新页面通过 `/workspace/*` 显式路由、权限菜单和整页导航进入。

## 四、目标业务流程与状态机

### 4.1 目标流程

```mermaid
flowchart LR
    A[选择客户或订阅规则] --> B[采集合规公开信息]
    B --> C[清洗去重与来源校验]
    C --> D[客户主体匹配]
    D --> E[项目归并与公告版本]
    E --> F[文件解析与证据提取]
    F --> G[内部CRM和资料检索]
    G --> H[生成客户商机分析报告]
    H --> I[人工审核和确认]
    I --> J[转报备草稿或关联商机]
    J --> K[进入V3正式流程]
    K --> L[回收销售反馈和结果]
    L --> H
```

### 4.2 情报条目状态

```text
已发现 → 抓取中 → 已获取 → 已解析 → 待匹配 → 已匹配 → 已审核
                                      ↘ 解析失败/来源失效/已归档
```

要求：每次抓取保留来源、抓取时间、内容摘要、版本指纹和失败原因；重复条目不得重复触发分析和提醒。

### 4.3 情报项目状态

```text
候选项目 → 已确认 → 跟进中 → 已转报备 → 已转商机 → 赢单/输单/关闭
                 ↘ 暂缓/放弃
```

“已转报备”只表示已生成或关联报备，不代表报备审批通过；“已转商机”只表示进入 V3 商机流程，不改变既有商机阶段规则。

### 4.4 分析报告状态

```text
排队 → 生成中 → 草稿 → 人工审核 → 已发布 → 已过期/被新版本替代
                 ↘ 生成失败
```

报告必须保存数据快照、口径版本、模型、提示词、工具版本、证据集合、生成时间和降级原因。

### 4.5 CRM 协同状态

```text
待确认 → 待同步 → 同步中 → 已同步
                   ↘ 同步失败 → 人工重试/人工补偿
```

同步使用幂等键和事务发件箱；不得通过前端双写客户或商机。

## 五、功能需求建议

### 5.1 情报源与采集管理

**功能要求**

- 配置来源名称、来源类型、授权状态、区域、行业、访问频率、抓取范围、保留期限和启停状态；
- 支持开放接口、授权数据服务、人工文件导入和公开网页四类来源，第一版优先前两类与人工导入；
- 采集任务支持定时、手工触发、增量检测、失败重试、暂停、恢复和死信；
- 保存原始链接、来源平台、发布时间、抓取时间、版本指纹、附件列表和删除期限；
- 对同一来源执行频率、并发、下载大小、文件类型和超时限制；
- 来源授权到期、接口变更、连续失败和异常增量进入平台告警。

**产品约束**

- 采集器只负责获取公开内容，不能自行判断客户归属或直接创建业务记录；
- 外部来源中的文字、网页和附件均视为不可信输入，不能改变系统权限、触发写操作或执行命令；
- 个人信息按最小必要原则处理，手机号、邮箱和联系人只在业务授权且确有必要时保存。

### 5.2 客户主体识别与集团关系

**匹配顺序建议**

```text
统一社会信用代码 → 标准企业名称 → 企业别名 → 地址和官网
→ 联系人和电话 → 集团关系 → 模糊匹配 → 人工确认
```

**功能要求**

- 企业名称规范化：全称、简称、括号、地区前后缀、历史名称和常见错别字；
- 维护别名、来源、有效期、确认人和确认时间；
- 支持集团、子公司、分支机构和项目业主关系；
- 为每次匹配保存候选客户、匹配依据、算法版本、置信度和审核结果；
- 高置信度可以进入待审核队列，不能在第一版自动覆盖客户主档；
- 当无法确认时显示“待人工确认”，不能把不确定匹配当成事实。

### 5.3 项目归并与公告版本

**归并依据建议**

- 客户主体、项目名称、项目地点、采购单位、预算、发布时间和公告编号联合判断；
- 采购意向、招标公告、更正公告、延期公告、中标公告和附件作为同一项目的事件版本；
- 不能只按标题相似度归并，也不能把同一项目重复计为多个商机；
- 人工拆分、合并和纠错必须保留前后关系、操作者、原因和时间。

**项目主档至少包括**

- 项目名称、项目类型、客户、集团关系、区域、行业、项目地点；
- 预算、币种、发布时间、投标截止时间、预计采购/签约时间；
- 当前阶段、来源数量、最新来源、竞争品牌、项目负责人建议；
- 关联 CRM 客户、报备、商机和销售跟进；
- 归并置信度、人工确认状态、最后更新时间和数据质量状态。

### 5.4 文件解析与资料知识库

**文件处理要求**

- 支持网页、PDF、扫描件、Word、演示文稿、表格和图片；
- 文件进入解析前校验类型、大小、扩展名、病毒扫描和存储权限；
- 解析服务隔离运行，设置资源上限、超时、失败重试和人工下载兜底；
- 复杂表格、扫描件和技术参数建立专项测试样本，不以纯文本抽取成功作为验收；
- 文本切片必须保留文件编号、页码、段落、表格位置和版本；
- 文档、案例和产品资料维护行业、区域、客户规模、产品线、场景、项目规模、实施周期、对外等级、审核状态和有效期标签。

**知识库边界**

- 内部案例、方案和产品资料按资料密级、产品线和组织范围授权；
- 外部公开资料与内部资料分区管理，不能混淆来源和可信度；
- 资料推荐只能返回用户有权查看的内容，敏感附件通过 V3 受控页面链接访问。

### 5.5 客户画像与商机分析报告

报告首屏建议包含：

1. 客户标准名称、统一社会信用代码、集团关系、行业、区域、规模和数据更新时间；
2. 历史合作、已有产品、联系人、报备、商机、报价和跟进摘要；
3. 外部采购信号、项目时间线、预算、截止时间、来源和版本；
4. 需求摘要、部署方式、容量、性能、兼容性、服务和资质要求；
5. 竞争情况、品牌倾向、时间风险、资格风险、废标风险和数据质量风险；
6. 综合优先级、评分构成、建议负责人、建议联系时间和首轮沟通问题；
7. 推荐产品、案例、方案和历史应答材料；
8. 已确认事实、推断结论、待确认问题、暂无结论；
9. 每条关键结论对应原文链接、文件编号、页码或原文片段。

**报告生成规则**

- 先通过确定性规则和受控工具获取数据，再由模型归纳和表达；
- 模型不得自行补齐预算、日期、联系人、竞争品牌和中标概率；
- 关键字段缺失时必须显示“未发现”或“待确认”；
- 生成失败、数据过期、证据不足和模型降级必须在报告中明确标记；
- 报告版本不可覆盖，重新分析生成新版本并保留差异。

### 5.6 商机评分与行动建议

建议采用“可解释基础分 + 风险扣分”的方式，初始维度可包括：

| 维度       | 建议含义                                   | 权重是否已定 |
| ---------- | ------------------------------------------ | ------------ |
| 客户价值   | 客户规模、行业战略价值、历史合作和区域价值 | 待试点确认   |
| 需求明确度 | 采购阶段、技术参数、预算和时间是否明确     | 待试点确认   |
| 产品匹配度 | 产品能力、案例和服务条件匹配程度           | 待试点确认   |
| 紧迫度     | 截止时间、项目窗口和客户行动信号           | 待试点确认   |
| 数据可信度 | 来源权威性、更新时间、字段证据完整度       | 待试点确认   |
| 风险扣分   | 竞争强度、资格缺口、时间不足、数据冲突等   | 待试点确认   |

输出必须同时展示总分、分项得分、加分依据、扣分依据、证据和缺失信息。第一版不输出“必然中标概率”，只输出“建议推进、重点跟进、持续观察、暂缓/放弃”的建议及原因。

### 5.7 人工审核与确认

审核队列至少覆盖：客户匹配、集团关系、项目合并/拆分、关键字段、风险判断、资料推荐和 CRM 同步内容。

审核动作：通过、驳回、修改、合并、拆分、标记无关、转人工、暂缓。每次动作记录操作者、权限、范围摘要、原因、前后值和请求编号。

### 5.8 CRM 协同建议

第一版采用以下安全路径：

1. 情报项目确认后，可生成“客户报备草稿建议”，带入客户、项目、行业、联系人和证据链接；
2. 报备仍由现有 V3 报备接口和审批状态机办理，不能绕过审批直接生成正式商机；
3. 对已存在的商机，只新增情报关联和跟进建议，不自动改变阶段、金额、负责人或状态；
4. 销售确认后，可新增一条商机跟进记录，内容包含来源和报告链接；
5. 后续如需自动转正式商机，必须另行确认状态机、负责人、重复判断和回退策略。

### 5.9 反馈闭环

记录以下反馈：报告有用/无用、客户匹配正确/错误、项目归并正确/错误、推荐资料采用/忽略、行动建议采纳、赢单/输单及原因、销售纠错文本。

反馈只用于规则和模型评测，不得未经审批自动训练生产模型。线上错误应能一键转为评测用例。

## 六、建议数据模型

### 6.1 领域划分

建议新增 `intelligence` 逻辑域保存外部情报和分析过程；`analytics` 逻辑域只保存指标口径、快照、分析视图和大屏数据。不要把项目主档、证据和报告长期堆入 `crm.*.extra_json`。

### 6.2 核心实体建议

| 实体                            | 主要内容                               | 关键约束                            |
| ------------------------------- | -------------------------------------- | ----------------------------------- |
| `intelligence.sources`          | 来源、授权、频率、范围和启停           | 来源代码唯一；凭据只存密文引用      |
| `intelligence.collection_tasks` | 采集任务、进度、重试和失败             | 任务幂等；按来源限流                |
| `intelligence.raw_items`        | 原始公告、网页、附件和版本指纹         | 来源+外部编号/指纹去重              |
| `intelligence.customer_matches` | 情报与 CRM 客户候选及证据              | 保留算法版本和人工结果              |
| `intelligence.projects`         | 统一项目主档和当前状态                 | 项目不能重复归并；支持拆分/合并历史 |
| `intelligence.project_events`   | 采购意向、招标、更正、中标等时间线     | 外部事件编号和版本唯一              |
| `intelligence.documents`        | 文件元数据、扫描、解析状态和密级       | 下载再次校验数据范围                |
| `intelligence.document_chunks`  | 文本片段、页码、表格位置和向量索引引用 | 保留来源定位，不保存无来源片段      |
| `intelligence.evidences`        | 结论与原文的关联                       | 关键结论证据覆盖率可统计            |
| `intelligence.analysis_reports` | 报告版本、口径、模型和状态             | 不覆盖历史版本                      |
| `intelligence.analysis_scores`  | 分项评分、依据和风险扣分               | 规则版本化                          |
| `intelligence.recommendations`  | 产品、案例、方案及推荐原因             | 推荐结果受资料权限过滤              |
| `intelligence.review_tasks`     | 人工审核项和处理记录                   | 审核人必须来自服务端身份            |
| `intelligence.crm_links`        | 情报项目与客户/报备/商机关联           | 关联类型和唯一性明确                |
| `intelligence.sync_records`     | 同步预览、结果、重试和对账             | 幂等键唯一；失败不改变主业务状态    |
| `intelligence.feedback`         | 错误、采纳、赢单/输单和评价            | 可转评测用例                        |

### 6.3 数据保留建议

- 原始页面和附件按来源授权及业务价值设置保留期限；
- 报告、证据、审核和同步审计按 V3 高风险审计规则保留，普通不少于三年，高风险不少于五年；
- 个人联系方式默认不复制到情报域，确需使用时只保存受控引用和必要摘要；
- 删除和过期采用逻辑归档、来源失效标记和审计记录，不物理删除影响追溯的业务证据。

## 七、技术与接口建议

### 7.1 架构落点

```text
合规来源/人工导入
        ↓
apps/api 情报接口与权限校验
        ↓
intelligence 数据域 + ops.files + 审计
        ↓
apps/worker 情报采集、解析、归并、分析独立任务池
        ↓
只读分析视图/物化视图 + 模型网关 + 受控检索工具
        ↓
apps/web /workspace 情报工作台、报告、审核和协同
        ↓
经确认的 V3 报备、商机和跟进接口
```

### 7.2 建议接口（先入 `packages/contracts`）

以下仅为需求阶段的接口方向，最终字段、权限、错误码、幂等和状态前置条件必须在契约评审后确定：

- `GET /api/intelligence/sources`
- `POST /api/intelligence/collection-tasks`
- `GET /api/intelligence/signals`
- `GET /api/intelligence/projects`
- `GET /api/intelligence/projects/:id`
- `POST /api/intelligence/projects/:id/match-review`
- `POST /api/intelligence/projects/:id/analyze`
- `GET /api/intelligence/reports/:id`
- `POST /api/intelligence/reports/:id/review`
- `POST /api/intelligence/projects/:id/sync-preview`
- `POST /api/intelligence/projects/:id/sync`
- `POST /api/intelligence/feedback`
- `GET /api/analytics/intelligence-overview`

接口共性要求：服务端身份、功能权限、数据范围、字段密级、分页、超时、行数上限、请求编号、审计和幂等均必须明确；普通页面接口不允许前端指定模型供应商、密钥、任意数据库连接或原始查询语句。

### 7.3 前端入口

建议新增以下工程化工作区页面：

- `/workspace/admin/intelligence/workbench`：情报工作台和待审核队列；
- `/workspace/admin/intelligence/projects/:id`：项目时间线、证据、报告和 CRM 关联；
- `/workspace/admin/intelligence/reports/:id`：报告阅读、证据回链、审核和反馈；
- `/workspace/admin/intelligence/knowledge`：产品资料、案例和标签维护；
- `/workspace/admin/platform-admin/intelligence`：来源、采集任务、保留策略和数据质量；
- `/workspace/admin/platform-admin/ai`：模型网关、提示词、路由、评测、成本和审计；
- `/workspace/admin/analytics/intelligence-overview`：情报量、有效项目、转化和质量指标。

渠道端是否开放情报工作台、可见到什么粒度，必须按渠道业务规则另行确认；不能因“渠道有客户”就默认可查看全部外部情报和内部资料。

## 八、智能分析治理要求

### 8.1 模型与工具

- 模型只能通过统一模型网关调用，模型名称、供应商密钥和敏感数据许可不写入业务模块；
- 工具只允许调用固定的情报查询、资料检索和指标查询能力，不开放任意 SQL、任意文件读取和命令执行；
- 内部 CRM 问题默认不联网；确需结合公开信息时先脱敏和泛化关键词；
- 查询结果必须经过表、字段、范围、行数、超时和成本审查；
- 高敏数据只进入已审批的模型、区域和账号，不满足条件时拒答或返回 V3 链接；
- 企微机器人后续接入时，私聊按用户权限返回精准结果，群聊默认只返回汇总和链接。

### 8.2 评测集

首期至少建立一百条结构化评测用例，覆盖：

- 客户识别、项目归并、关键字段抽取；
- 报告事实、证据回链、评分和资料推荐；
- 歧义、空数据、过期数据和解析失败；
- 越权查询、提示注入、内部信息外发和敏感附件；
- 模型超时、限流、降级和重复任务。

固定回归集与盲测集分开管理。模型、提示词、工具说明和路由变更必须通过评测后再灰度；核心数字、关键字段和权限结果以确定性工具结果为准，越权信息泄漏和越权工具执行零容忍。

## 九、分期实施建议

### 阶段零：V3 前置收口

**目标**：完成可信身份、权限、数据范围、审计、幂等和分析查询门禁。

**退出条件**：现有管理员、渠道、桌面、移动端主链路回归通过；OpenAPI 绑定用户范围正确；情报功能开关默认关闭。

### 阶段一：内部数据与资料验证

**建议范围**：不接全国外部采集，导入一批真实客户、历史商机、本地案例、方案和产品资料。

**交付**：客户检索、客户画像、资料检索、报告草稿、证据回链、人工评价和首批评测集。

**目的**：先验证“报告准确、推荐有用、行动可执行”，确认客户识别和资料标签质量。

### 阶段二：小范围外部情报接入

**建议范围**：一个或两个合规来源、一个或两个区域、一个产品线、两个重点行业。

**交付**：采集任务、来源治理、客户匹配、项目归并、公告版本、截止时间和待审核队列。

### 阶段三：CRM 协同与提醒

**交付**：报备草稿建议、既有商机关联、跟进建议、同步预览、幂等同步、失败补偿和高价值项目提醒。

**边界**：仍不绕过报备审批，不自动改变商机阶段、金额、负责人和正式状态。

### 阶段四：规模化与经营分析

**交付**：多区域、多产品线、情报转化漏斗、质量看板、模型路由优化、资料推荐排序、管理层大屏。

### 阶段五：企微智能入口（后续单独准入）

**前置条件**：企微身份映射、群成员范围、消息底座、只读分析库、查询审查、回答审计和评测门禁全部通过。

**首期边界**：只读问答、风险摘要、到期提醒和 V3 链接，不提供创建、修改、审批、领取、分配、导出和附件正文。

## 十、验收指标建议

以下为试点建议门槛，需用真实样本校准后由业务负责人签字确认：

| 指标               | 建议目标                                                 | 验收方式                                       |
| ------------------ | -------------------------------------------------------- | ---------------------------------------------- |
| 客户主体匹配准确率 | 高置信自动进入审核的准确率不低于95%                      | 抽样核验统一社会信用代码、名称、集团关系和证据 |
| 项目归并准确率     | 不低于90%                                                | 核验采购意向、招标、更正和中标事件是否正确归并 |
| 关键字段准确率     | 预算、日期、联系人、技术参数不低于90%                    | 与原文逐项比对                                 |
| 关键结论证据覆盖率 | 100%                                                     | 每条关键结论回链原文链接、页码或片段           |
| 重复项目率         | 不高于5%                                                 | 对同项目多公告和多版本抽样核验                 |
| 报告可用率         | 销售评价“有用”不低于70%                                  | 试点用户评价和复核记录                         |
| 资料推荐有效率     | 相关且可使用评价不低于70%                                | 推荐资料点击、采用和人工评价                   |
| 同步可靠性         | 幂等成功率100%，失败可重试可对账                         | 重复提交、超时、回调乱序和人工补偿测试         |
| 权限正确性         | 越权信息泄漏为零                                         | 跨区域、跨渠道、跨人员和敏感字段负向测试       |
| 外部检索安全       | 内部客户、合同、金额、联系人和附件正文不出现在外部关键词 | 日志审计与敏感样本测试                         |
| 分析性能           | 普通客户分析建议异步十分钟内完成，复杂文件按任务进度展示 | 固定数据量和硬件条件下压测                     |
| 主业务影响         | 报备、商机、报价、订单主链路无新增阻断                   | 发布前后端到端回归                             |

## 十一、主要风险与应对

| 风险           | 具体表现                               | 应对建议                                         |
| -------------- | -------------------------------------- | ------------------------------------------------ |
| 数据源授权不清 | 采集被投诉、接口被封或资料不能商用     | 来源台账、授权状态、频率限制、删除机制和法务确认 |
| 客户误匹配     | 外部公告归到错误客户或集团             | 多字段匹配、置信度、人工审核和纠错闭环           |
| 项目重复计算   | 一个项目被统计为多个商机               | 项目主档、事件版本、唯一指纹和合并审计           |
| 模型幻觉       | 编造预算、日期、联系人、竞争情况和建议 | 确定性抽取、证据回链、事实/推断分层、低置信拒答  |
| 内部数据外泄   | 敏感内容进入联网检索、模型或群聊       | 脱敏拦截、敏感级别路由、群聊只给汇总和链接       |
| 主库性能受影响 | 大屏、向量检索和批量分析拖慢 CRM       | 分析库、物化视图、缓存、限流和独立任务池         |
| 自动写入失控   | 错误报告覆盖客户、商机或状态           | 首期只读，人工确认，预览、幂等和状态机           |
| 资料过期       | 案例、产品和方案不再适用               | 有效期、审核状态、版本和过期禁止推荐             |
| 反馈不足       | 无法证明推荐和评分有价值               | 试点绑定反馈动作，赢单/输单和采用结果入评测      |
| 范围持续扩大   | 同时接全国来源、全产品和机器人导致延期 | 设定试点边界和阶段退出条件，变更进入评审         |

## 十二、必须在立项评审时确认的决策

1. 首期产品线、行业、区域、客户样本和试点销售团队。
2. 外部情报来源清单、授权主体、数据用途、访问频率、附件保留和费用预算。
3. “情报项目”与“正式商机”的业务定义，以及转报备草稿、关联商机和新增跟进的具体路径。
4. 客户匹配、集团关系和项目归并的自动进入审核阈值及审核责任人。
5. 商机评分维度、权重、风险扣分项和“推进/观察/暂缓/放弃”判定口径。
6. 客户、项目、预算、联系人、竞争信息和报告结论的字段权威来源与修改责任。
7. 内部资料密级、可见组织、对外等级、有效期和失效后的处理方式。
8. 报告、原文附件、模型调用、提示词和审计日志的保留期限。
9. 是否允许渠道侧使用情报功能，以及渠道之间的客户、资料和项目隔离规则。
10. 首期是否接入企微提醒；如接入，确认接收人、强制级别、群聊边界和成本。
11. 模型供应商、数据处理区域、高敏数据许可、预算和降级方案。
12. 试点验收目标是否采用本文建议值，以及业务负责人、产品、技术、测试、数据、法务和安全的签字人。

## 十三、分层实施与情报中心详细方案

本章回答“每个层次怎么搭建、由谁负责、先后顺序是什么、依据在哪里”。其中涉及外部数据来源、阈值和保留期限的内容属于产品建议，必须在试点样本、法务审查和业务负责人签字后固化。

### 13.1 三层业务结构总览

本项目按三层业务结构建设，六个技术工作面是三层内部的实施分工，不能把技术工作面误认为三套独立产品。

| 业务层               | 业务目标                                                     | 内部技术工作面                   | 输入                                      | 输出                                                       | 第一责任角色        |
| -------------------- | ------------------------------------------------------------ | -------------------------------- | ----------------------------------------- | ---------------------------------------------------------- | ------------------- |
| 第一层：情报中台     | 把分散、异构、未经确认的信息变成可追溯的客户和项目情报       | 情报源与采集、数据治理、内容处理 | 官方/授权来源、人工资料、V3客户与产品数据 | 原始条目、标准客户候选、项目事件、文件片段、证据和质量状态 | 数据工程 + 情报审核 |
| 第二层：智能分析应用 | 在授权数据和证据基础上形成画像、需求、风险、评分、推荐和报告 | 检索与分析                       | 情报项目、V3只读分析视图、知识库、证据    | 分析报告、评分、行动建议、资料推荐                         | 产品 + 智能分析工程 |
| 第三层：CRM协同      | 把确认后的结果安全地交给销售流程，并回收反馈改进前两层       | 业务应用、协同与反馈             | 报告、审核结果、销售确认和业务结果        | 报备草稿、商机关联、跟进、提醒、反馈和评测用例             | 产品 + 销售运营     |

三层之间只有一条受控主链路：

```text
情报中台形成候选事实
  → 智能分析应用基于证据形成建议
  → 人工确认
  → CRM协同进入既有V3流程
  → 销售结果和纠错反馈回到情报中台与分析应用
```

所有层次共用 V3 的身份、权限、组织、渠道、数据范围、审计、任务和部署底座，不单独建立账号、客户主档或第二套业务权限。

### 13.2 第一层：情报中台具体建设方式

#### 13.2.1 情报中心的职责边界

情报中心只负责“发现、整理、分析和提交建议”，不负责以下事实的最终写入：

- 不直接修改 `crm.customers` 的客户名称、统一社会信用代码、负责人或渠道归属；
- 不直接把外部信息变成正式客户报备或正式商机；
- 不直接推进商机阶段、修改预计金额或替换销售负责人；
- 不直接向外部客户发送材料；
- 不以模型结论代替销售、法务或管理审批。

情报中心向 V3 提供三类结果：

1. **情报事实**：来源、发布时间、原文、附件、版本和抽取字段。
2. **分析建议**：客户匹配候选、项目归并候选、需求、风险、资料推荐和优先级。
3. **协同草稿**：报备草稿建议、既有商机关联建议和跟进内容草稿。

#### 13.2.2 推荐采集来源分级

第一版不追求“全国所有网站”，而是按权威性、授权清晰度、更新稳定性、覆盖价值和接入成本筛选来源。

| 来源类别     | 优先寻找的平台                                                               | 建议采集方式                                               | 可采集内容                                             | 关键核实项                                     |
| ------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------- |
| 政府采购     | 中国政府采购网、全国公共资源交易平台、目标省市公共资源交易平台及政府采购子站 | 平台开放接口、数据下载或书面授权；无明确授权时只做人工导入 | 采购意向、招标公告、更正公告、中标公告、预算和截止时间 | 使用条款、接口权限、访问频率、附件下载限制     |
| 地方交易     | 重点区域的公共资源交易中心、财政采购平台、行业主管部门采购栏目               | 官方数据接口、公开下载、经授权的聚合服务                   | 区域项目、采购单位、交易阶段、公告附件                 | 是否允许批量获取、历史数据范围、站点结构变更   |
| 央国企采购   | 目标行业央企、地方国企官网及其电子采购平台                                   | 采购平台授权接口、数据服务或人工导入                       | 企业采购公告、供应商征集、项目预告                     | 平台账号授权、供应商协议、数据商用范围         |
| 企业公开信息 | 国家企业信用信息公示系统、客户官网“新闻/采购/招投标/建设”栏目                | 官方查询、授权数据服务、低频公开页面采集                   | 企业主体、名称变更、分支机构、建设动态                 | 查询限制、个人信息最小化、来源留痕             |
| 商业数据服务 | 具有正式数据服务和商用授权的企业信息、招采信息服务商                         | 合同约定的接口或数据文件                                   | 标准企业主体、公告索引、集团关系辅助信息               | 数据来源可追溯、许可证、转授权、费用和停服机制 |
| 行业与政策   | 工信、财政、行业协会、标准组织等官方栏目                                     | 公开接口、公开下载或人工收藏                               | 政策、行业趋势、技术标准和公开市场信号                 | 仅用于公开背景，不把政策内容当成客户项目事实   |
| 内部资料     | V3客户、报备、商机、跟进、产品、报价、案例和历史应答材料                     | V3只读接口、受控文件上传、批量导入                         | 内部客户关系、历史项目、产品能力和案例                 | 组织范围、资料密级、对外等级、有效期           |
| 客户提供资料 | 销售上传的招标文件、会议纪要、客户邮件导出件                                 | 受控上传和人工确认                                         | 项目原文、需求、联系人和客户确认信息                   | 上传授权、敏感信息、文件保留期和下载权限       |

**来源选择顺序**：内部资料和人工上传 → 官方接口或数据下载 → 有合同的商业数据服务 → 条款允许的公开网页低频采集。没有授权、无法留痕或需要模拟登录、绕过验证码、突破访问控制的来源不进入生产。

#### 13.2.3 采集器如何实现

情报中心采用“来源适配器 + 统一采集任务 + 原始内容存储”的方式，不为每个网站单独写一套业务流程。

每个来源适配器至少实现以下能力：

1. 读取来源配置：来源编号、授权状态、区域、关键词、时间窗口、频率和文件大小限制。
2. 按游标或时间窗口获取列表，记录请求编号、来源响应状态和最后成功游标。
3. 将来源内容转换为统一原始条目：外部编号、标题、采购单位、发布时间、公告类型、链接、附件清单和原始摘要。
4. 对网页正文和附件计算内容指纹；同一来源、外部编号或指纹不重复入库。
5. 将原始内容保存到受控文件存储，数据库只保存元数据、摘要、指纹、授权状态和存储引用。
6. 生成后续任务：清洗、附件扫描、文件解析、客户匹配和项目归并。
7. 记录限流、超时、解析失败、来源结构变化、授权到期和连续失败告警。

推荐任务链：

```text
采集任务排队 → 获取列表 → 获取详情/附件 → 原始入库 → 指纹去重
→ 清洗标准化 → 客户匹配 → 项目归并 → 文件解析 → 报告分析
```

采集、解析和分析必须进入 `apps/worker` 的分析智能进程池；不能在浏览器请求中同步执行，也不能与合同、审批和消息投递共用并发池。

#### 13.2.4 采集频率建议

频率不能按“越快越好”设计，而应由来源条款、业务时效和服务器承载共同决定：

- 采购意向和招标公告：试点可每日一次；临近投标截止时间的重点来源可在授权允许时提高频率。
- 更正、延期和中标公告：每日增量检查；发现原公告版本变化时只新增版本，不覆盖旧版本。
- 企业官网和行业政策：每日或每周检查，按栏目和更新时间增量获取。
- 商业数据服务：按合同约定的推送、批量或接口频率执行。
- 内部资料：上传即触发解析，资料更新后生成新版本。

以上频率是试点初始值，不是写死规则。每个来源必须有单独的频率、并发、失败重试和暂停配置。

### 13.3 采集后如何清洗和治理

#### 13.3.1 五步清洗流水线

| 步骤       | 处理内容                                             | 产物                | 是否允许覆盖原文       |
| ---------- | ---------------------------------------------------- | ------------------- | ---------------------- |
| 原始保全   | 保存原始页面、文件、链接、时间和指纹                 | 原始条目            | 不允许                 |
| 格式清洗   | 去除网页导航、脚本、重复页眉页脚，保留正文和表格位置 | 可解析正文          | 不覆盖原始内容         |
| 字段标准化 | 名称、日期、金额、地址、公告类型和编码统一           | 标准字段 + 原始字段 | 不覆盖原始字段         |
| 去重与版本 | 外部编号、链接、指纹、标题和关键字段联合判断         | 版本关系            | 不删除历史版本         |
| 质量评估   | 权威性、完整性、新鲜度、冲突和解析状态评分           | 质量等级、待复核项  | 不将低质量伪装为已确认 |

#### 13.3.2 重点清洗规则

- **企业名称**：保留原名称；另存标准名称、去空格名称、简称和历史名称。括号、地区前缀、有限公司后缀只能作为辅助处理，不能直接删除导致主体混淆。
- **统一社会信用代码**：去除空格和不可见字符，校验长度与校验位；校验失败只标记异常，不自行修正。
- **时间**：统一保存原始时间文本与标准时间，标准时间使用中国时区；“报名截止”“投标截止”“开标时间”分字段保存，禁止混为一个日期。
- **金额**：保存金额数值、币种、含税/不含税、单位（元/万元）和原文片段；无法确认单位时标记待确认。
- **公告类型**：统一为采购意向、招标、竞争性磋商、询价、更正、延期、中标、废标、终止等字典值，同时保留来源原类型。
- **附件**：按文件哈希去重，保存原文件名、文件类型、页数、扫描状态、解析状态和来源版本；禁止仅按文件名覆盖。
- **联系人**：只保存业务确需的联系人信息；电话号码和邮箱默认脱敏展示，来源、授权和用途必须可追溯。
- **冲突字段**：不同来源的预算、日期和采购单位不强行取一个值，保留多来源值并创建冲突复核项。

#### 13.3.3 数据质量等级

建议使用以下状态，不把质量分数直接当成商机分数：

- `A`：权威来源、主体明确、关键字段有证据、更新时间在有效窗口内；
- `B`：来源可信但缺少部分字段，适合进入人工审核；
- `C`：主体或项目存在冲突，需要销售或情报审核；
- `D`：来源失效、解析失败、疑似重复或无法证明与业务相关，只保留待处理记录。

数据质量等级由规则计算，最终是否纳入报告由人工审核和证据完整度决定。

### 13.4 客户识别怎么做、谁来做

#### 13.4.1 识别顺序

```text
统一社会信用代码精确匹配
→ 标准企业名称精确匹配
→ 已确认别名匹配
→ 官网、地址、注册地和采购单位联合匹配
→ 联系人和电话辅助匹配
→ 集团/子公司关系辅助判断
→ 模糊候选排序
→ 人工确认或标记无法确认
```

不建议第一版仅依赖大模型或标题相似度识别客户。模型可以解释候选原因，但候选集合和最终确认必须由确定性规则、数据范围和人工动作共同完成。

#### 13.4.2 建议的候选阈值

阈值只能作为试点初始配置，必须用已确认样本校准：

| 候选结果                                         | 建议处理                         | 是否写入客户主档 |
| ------------------------------------------------ | -------------------------------- | ---------------- |
| 高置信度且统一社会信用代码一致                   | 自动标记“推荐匹配”，进入审核队列 | 否               |
| 名称、地址、官网等多字段一致但无统一社会信用代码 | 推荐前两至三个候选               | 否               |
| 名称相似但集团关系、地区或项目不一致             | 标记冲突，要求人工选择           | 否               |
| 无法形成可靠候选                                 | 标记“待人工确认”或“未识别主体”   | 否               |

建议试点阶段先采用“高置信只推荐、不自动确认”的保守模式。客户负责人或情报审核人员确认后，才写入别名或建立集团关系；修改客户主档仍走 V3 原有权限和审计。

#### 13.4.3 角色分工

| 角色            | 责任                                                 |
| --------------- | ---------------------------------------------------- |
| 数据工程人员    | 名称标准化、候选算法、匹配日志、阈值评测和异常修复   |
| 情报审核人员    | 处理低置信、冲突、集团关系和项目业主疑难匹配         |
| 客户负责人/销售 | 确认“是不是我的客户”“是否属于本项目”和下一步业务关系 |
| 产品负责人      | 定义匹配状态、审核动作、升级规则和验收口径           |
| 法务与安全人员  | 审核个人信息、来源授权、保留期限和对外展示边界       |
| 平台管理员      | 配置来源、权限、任务和审计，不代替业务确认           |

#### 13.4.4 客户识别操作流程

1. 采集器生成情报条目，保存原始来源。
2. 规则引擎生成候选客户和匹配依据。
3. 系统按照数据范围过滤候选，只展示当前用户有权查看的客户。
4. 高置信候选进入待审核队列；中低置信候选要求人工选择、标记无关或暂不处理。
5. 审核人确认后，建立 `情报条目—V3客户` 关联；若要新增别名或集团关系，调用 V3 受控接口。
6. 识别结果进入项目归并和报告分析；后续发现错误时可撤销关联并保留审计。

### 13.5 项目归并怎么做

项目归并是情报中心最容易产生业务误判的环节。建议建立“项目主档 + 公告事件版本”两层结构：

- 项目主档保存一个潜在采购项目的稳定身份；
- 事件版本保存采购意向、招标、更正、延期、中标、废标等阶段事实；
- 每个事件保留来源编号、发布时间、链接、附件、内容指纹和与前一版本的关系。

归并判断依次使用：采购单位、统一社会信用代码、项目名称、项目地点、预算区间、公告编号、联系人、时间窗口和附件内容。标题相似只能产生候选，不能单独触发合并。

归并结果建议分为“自动推荐合并、待人工确认、明确拆分”三类。合并、拆分、撤销和重新关联均记录前后项目、理由、操作者和时间。

### 13.6 文件解析和证据链如何实现

文件处理建议分成“安全检查—格式解析—文本切片—字段抽取—证据绑定”五个任务：

1. 安全检查：类型白名单、大小限制、病毒扫描、存储权限和超时。
2. 格式解析：网页、PDF、扫描件、Word、演示文稿、表格和图片分别处理；扫描件需要文字识别。
3. 文本切片：每个片段保存文件编号、页码、段落、表格位置和版本。
4. 字段抽取：预算、日期、联系人、技术参数、资质条件和竞争要求使用结构化字段保存。
5. 证据绑定：每个关键字段和报告结论必须绑定原文链接、文件页码或原文片段。

抽取失败时保留失败原因并提供人工查看原文入口，不用模型补齐缺失事实。内部案例和产品资料必须有审核状态、有效期、密级和可见范围；过期或未审核资料不进入默认推荐。

### 13.7 第二层：智能分析应用怎么搭建

采用“三种检索联合”的方式：

- **条件检索**：按客户、区域、行业、产品、时间、公告类型和状态筛选；
- **全文检索**：在已授权文本中检索原词、技术参数、资质条件和项目名称；
- **语义检索**：在已授权文本片段和案例向量中查找相近需求。

模型只负责意图识别、分析计划、摘要、解释和推荐表达；客户、项目、预算、日期、金额和权限结果由规则和受控查询工具提供。报告生成顺序为：

```text
确定性取数 → 证据筛选 → 规则评分 → 模型归纳 → 结果校验 → 人工审核 → 发布报告
```

分析服务必须使用只读分析视图、物化视图或指标宽表；模型网关负责供应商、模型、敏感级别、成本、超时、降级和版本审计。该做法与 V3 既定的“分析智能域只读、模型网关统一路由、查询审查和评测门禁”一致。

#### 13.7.1 输入、输出和责任人

| 项目       | 规定                                                                                    |
| ---------- | --------------------------------------------------------------------------------------- |
| 输入       | 已确认或待确认的客户/项目、V3授权范围、情报事件、文档片段、产品资料、历史商机和时间范围 |
| 输出       | 客户画像、需求字段、风险项、评分、资料推荐、行动建议、证据集合和报告版本                |
| 确定性责任 | 数据查询、金额/日期、状态、权限、评分规则和证据覆盖由规则或受控工具负责                 |
| 模型责任   | 意图分类、信息归纳、风险解释、推荐理由和自然语言表达，不得创造业务事实                  |
| 人工责任   | 销售或审核人员确认客户关系、项目相关性、风险和行动建议                                  |

#### 13.7.2 报告生成流程

1. 读取用户服务端身份、组织、渠道、区域、角色、字段权限和数据范围。
2. 检查问题或分析目标是否明确；“业绩”“重点客户”等歧义词先追问口径。
3. 生成固定的分析计划，只能选择已注册的客户、项目、资料和指标工具。
4. 从分析视图、全文索引和语义索引取得结果，所有查询带范围、行数和超时限制。
5. 对预算、日期、联系人、技术参数和阶段等关键字段绑定证据片段。
6. 按版本化规则计算优先级和风险扣分，展示分项依据。
7. 由模型生成事实、推断、待确认问题和行动建议四个分区。
8. 结果校验器检查数字、日期、权限、空结果、冲突和证据覆盖；不通过则降级为“待人工查看”。
9. 保存数据快照、指标口径、模型、提示词、工具版本、成本、耗时和报告版本。
10. 报告进入人工审核，审核通过后才能展示为“已发布”或进入第三层协同。

#### 13.7.3 分阶段实现方式

- **第一步先做结构化和全文检索**：使用客户、项目、公告类型、时间、产品标签和关键词，优先保证结果可解释。
- **第二步再做语义检索**：在文档片段和案例完成标签、密级、有效期和权限过滤后，再引入向量索引；向量只做候选召回，不能绕过权限。
- **第三步做模型编排**：意图识别、分析计划、摘要、推荐和风险解释走模型网关；关键字段仍由规则抽取和原文证据约束。
- **第四步做评分和推荐优化**：先用可解释规则和销售反馈调权重，样本和反馈不足时不训练复杂预测模型。

### 13.8 第三层：CRM协同怎么搭建

工作台先做四个核心页面：

1. **情报待办**：待匹配、待归并、待解析、待审核、截止时间临近和同步失败。
2. **项目详情**：客户候选、项目时间线、公告版本、附件、证据和质量状态。
3. **分析报告**：事实、推断、待确认问题、评分、推荐资料、证据回链和反馈。
4. **CRM协同**：报备草稿预览、既有商机关联、跟进草稿、同步结果和人工补偿。

所有按钮按查看、下载、审核、关联、同步和资料维护分别授权。渠道端是否可见、可见哪些资料和是否允许查看外部情报，必须单独确认，不能从管理员权限自动推导。

#### 13.8.1 协同处理流程

```text
报告审核通过
  → 选择协同动作
  → 展示客户/报备/商机重复和权限校验结果
  → 生成报备草稿、商机关联或跟进草稿预览
  → 用户确认
  → V3服务端再次校验身份、权限、范围、状态和幂等键
  → 本地事务写协同记录并写事务发件箱
  → Worker异步执行跨模块或外部同步
  → 返回成功、失败或待人工对账
  → 销售反馈和业务结果回流
```

#### 13.8.2 三类协同动作

| 动作         | 第一版做法                                                                    | 明确禁止                                 |
| ------------ | ----------------------------------------------------------------------------- | ---------------------------------------- |
| 转报备草稿   | 复制已确认客户、项目、行业、联系人、预算和证据链接，进入现有报备创建/审批流程 | 直接生成已通过报备或绕过报备审批         |
| 关联既有商机 | 建立情报项目与商机的关联，记录关联理由和证据                                  | 自动修改商机阶段、金额、负责人和赢输状态 |
| 新增跟进草稿 | 由销售确认后调用既有商机跟进能力，保留来源和报告链接                          | 模型自动代表销售提交关键承诺或客户结论   |

#### 13.8.3 实现方式

- 协同页面只提交“动作、目标对象、报告版本和幂等键”，不提交服务端操作者、角色或权限。
- 服务端在确认时重新读取客户、报备、商机和当前状态，重新执行重复判断、数据范围和业务状态校验。
- 本地业务写入与协同记录在同一事务中完成；跨系统通知、提醒和对账通过 `ops.outbox_events` 与独立 Worker 执行。
- 同一报告、目标对象、动作和操作者只能成功一次；超时不能盲目重试，必须先查询本地同步记录和外部结果。
- 同步失败只把协同记录置为失败或待人工处理，不回滚已经合法完成的 V3 主业务，也不擅自修改主业务状态。
- 任何下载、导出和附件查看都在协同页面重新校验权限；链接使用短期、受控、可撤销的 V3 页面地址。

### 13.10 情报中心的主要难点

#### 13.10.1 第一层：情报中台难点

- 来源授权、页面结构变化、访问频率和附件下载限制不一致；
- 企业简称、历史名称、分支机构、集团关系和同名主体导致误匹配；
- 同一项目的采购意向、招标、更正、延期和中标公告存在标题变化和多来源重复；
- 扫描件、复杂表格和技术参数的文字识别、版面恢复和页码定位容易出错；
- 数据时效和冲突字段无法简单取最新值，必须保留版本和人工复核。

控制方式：来源台账和授权审批、适配器隔离、原始保全、指纹去重、项目主档、候选匹配、人工确认、版本事件和质量等级。

#### 13.10.2 第二层：智能分析应用难点

- 内外部数据的口径、时间范围和可信度不同，容易把推断写成事实；
- 资料标签不完整时，语义检索会推荐行业、区域或版本不适用的案例；
- 模型可能误读预算、日期、联系人、品牌和竞争信息，或受到文档提示注入影响；
- 只读分析查询、向量检索和大模型调用可能带来主库压力、延迟和成本失控；
- 没有结构化评测集时，无法判断报告是真的有用还是文字看起来合理。

控制方式：确定性取数、证据回链、事实/推断分层、资料密级和有效期、查询审查、模型网关、独立分析任务池、评测集、降级和人工审核。

#### 13.10.3 第三层：CRM协同难点

- 情报结论与 CRM 正式业务状态不是一回事，自动写入容易越过报备、商机和权限规则；
- 同一项目可能被多个销售或多个来源重复提交，必须防止重复报备、重复跟进和重复提醒；
- 接口超时不能确定外部是否成功，盲目重试会产生重复业务；
- 渠道、区域、销售和情报审核人员的责任边界不同，错误分配会造成撞单或越权；
- 销售若不反馈纠错和结果，平台无法形成推荐质量和转化效果闭环。

控制方式：预览确认、服务端二次授权、既有状态机、幂等键、事务发件箱、同步对账、人工补偿、分配规则、反馈必填和采用率指标。

#### 13.10.4 跨层共性难点

| 难点             | 为什么难                             | 解决策略                                          |
| ---------------- | ------------------------------------ | ------------------------------------------------- |
| 来源授权和稳定性 | 平台条款、接口、频率和附件政策不同   | 来源台账、合同/授权、适配器隔离、限流和可暂停     |
| 客户主体混淆     | 简称、分支、集团和历史名称多         | 统一社会信用代码优先、别名、集团关系、人工确认    |
| 项目重复和错并   | 同一项目多公告、名称变化、跨地区同名 | 项目主档、事件版本、多字段候选、人工拆分/合并     |
| 扫描件和复杂表格 | 文字识别、表格结构和技术参数容易错   | 专项样本、页码证据、人工复核、失败降级            |
| 数据时效         | 更正、延期和中标会改变项目判断       | 增量版本、截止时间任务、过期标记和提醒            |
| 模型幻觉         | 预算、日期、竞争品牌可能被编造       | 结构化取数、证据绑定、事实/推断分层、低置信拒答   |
| 权限泄露         | 外部情报与内部客户、资料权限叠加     | V3范围过滤、字段密级、下载复核和审计              |
| 主库性能         | 文本检索、向量检索和批量分析耗时     | 分析库、物化视图、缓存、行数/超时限制、独立进程池 |
| 业务采用率       | 报告正确但销售不行动                 | 首期围绕截止时间、首次沟通问题和资料推荐设计反馈  |

## 十四、最终建设建议

### 推荐方案

采用“V3 内集成、模块化单体、分析旁路、任务异步、人工确认、证据驱动”的建设方式：

- 情报和报告作为 V3 新增业务域，不建立第二套客户、账号和权限体系；
- 新增 `intelligence` 数据域，`analytics` 只负责指标和分析快照；
- 公开数据、内部 CRM 数据和内部资料分区治理；
- 采集、解析、向量化和模型调用全部任务化，使用独立并发池；
- AI 只读 V3 授权后的分析资产，所有结果可回溯到数据快照、证据和模型版本；
- 通过“情报项目 → 报备草稿建议 → 既有报备审批 → 商机跟进”进入 CRM，而不是直接写入正式商机；
- 先以真实样本验证客户匹配、项目归并、关键字段和报告价值，再扩大来源和模型能力。

### 不推荐方案

- 直接采购一个通用大模型平台，要求它自动读写 CRM；
- 先做全国范围爬虫，再补授权、去重、客户匹配和权限；
- 把外部公告、报告正文和证据全部塞进 `crm` 扩展字段；
- 先开放企微群机器人，再补身份映射和数据范围；
- 用模型生成的中标概率替代销售判断和正式商机流程。

### 产品负责人建议的立项口径

本项目首期验收不是“能不能生成一段像样的 AI 文字”，而是：

```text
客户找得准、项目并得对、关键事实有证据、推荐资料能使用、
销售知道下一步做什么、结果能安全回到 V3、错误能够被纠正和复盘。
```

只有满足上述条件，才进入全国化、多产品线、经营大屏和企微智能机器人阶段。
