### 0.1 当前实现与验收边界

- 已实现：站内消息、订单与报备事件桥接、任务连续失败告警、四端通知入口、企微群机器人、企微自建应用、短信通用适配、SMTP 邮箱适配、报备保护期与商机预计成交日提醒、超管消息渠道配置页、运行前置检查、脱敏投递状态、脱敏诊断、运行观测和默认只读的数据保留脚本。
- 默认关闭：消息工作进程、企微群机器人、企微自建应用、短信和邮箱都必须由部署配置或超管配置页显式开启；保存通道参数不会启用正式业务投递，也不会发起外部请求。
- 尚未通过真实验收：退订、退信/投诉回调、12 类事件全量接入、告警接入与监控管理页面仍属于后续验收范围。外部渠道的业务投递仍须以目标环境的投递成功事实和接收端实际到达为准。
- 普通渠道用户：报备审核结果投递创建人和当前负责人；到期提醒仅投递当前负责人。协作人尚无权威、可审计的授权关系表，当前不会擅自投递。
- R3-002 到期规则保存修正：更新语句必须绑定全部十个参数，并返回规则页回显所需的模板、数据源、系统标记和最后更新人字段；事务在审计写入完成后才提交。该修正不改变规则策略、渠道、接收人或既有提醒事实。

### 0.2 超管外部通道配置与验收

企业微信外部渠道同时支持两种独立形态：企业微信群机器人以用户提供的[群机器人消息推送说明](https://developer.work.weixin.qq.com/document/path/99110)为准，仅发送不含敏感业务数据的团队汇总；企业微信自建应用使用企业 ID、应用 AgentId 和应用 Secret 向指定成员 UserId 点对点试发。超级管理员可在 `admin.html#/message-platform` 维护两种企微通道、短信和 SMTP 邮箱参数。该入口仅在服务端会话角色为 `superadmin` 时可访问；普通管理员、渠道管理员和渠道用户均无权读取或修改。

首次启用前，实施人员必须在部署环境生成并持久保存 `MESSAGE_CHANNEL_CONFIG_ENCRYPTION_KEY`（执行 `openssl rand -base64 32`）；它只存在于部署密钥文件或环境变量中，不入库、不回显、不写日志。配置页将 Webhook、短信密钥和 SMTP 密码以 AES-256-GCM 密文保存；读取接口只返回掩码、状态、版本和最近测试结果。保存时留空的敏感字段表示保持原值。

真实验收应使用专用测试群、测试成员 UserId、测试手机号和测试邮箱，并按以下顺序执行：保存参数 → 配置不可变的 `MESSAGE_EVENT_CUTOVER_AT` 并启动消息投递角色 → 查看页面“运行前置检查”已通过 → 在配置页发送不含业务数据的测试消息 → 等待投递进程处理并刷新脱敏投递状态 → 成功后填写二次确认启用正式投递。企微机器人测试消息不得含客户名称、合同、金额、报价、货币、手机或邮箱；企微自建应用测试应同时核对应用可见范围与指定成员 UserId；邮箱试发可由超管临时填写合法收件地址。临时邮箱和临时 UserId 仅 AES-256-GCM 密文暂存，最终投递状态为成功、失败或忽略后立即清除，且不回显、不写普通日志、不出现在投递状态中。测试成功前接口拒绝启用，任一通道可随时在配置页停用。验收完成后立即停用测试 Webhook 或轮换密钥；不得把真实参数写入文档、代码、截图或测试数据。

### 0.3 提醒规则管理实施基线（已确认）

提醒规则管理与渠道配置分离：渠道配置回答“怎样发送”，规则管理回答“何时提醒、提醒何人、采用哪些已启用渠道”。首期只允许超级管理员在管理桌面端维护；普通管理员和渠道用户只能查看自己的通知，并维护个人渠道偏好。

### 0.4 八类业务提醒通道基线（M10-002）

订单待审批、订单确认完成、订单状态变化、客户报备审批待办、客户报备通过、客户报备驳回、客户报备保护期到期、商机预计成交提醒的已启用规则，统一配置为 `in_app`、`wecom_app`、`email` 三个通道。迁移只修改通道组合并递增规则版本，不改变接收人、规则启停、到期提前天数、执行时点、模板、渠道凭据和历史投递事实；企业微信群机器人不在这八类规则中使用，严禁发送业务明细。

正式投递仍取决于三个独立门禁：企微自建应用通道启用且接收人有权威企微 UserId 映射、邮件通道启用且接收人已开启邮件偏好并具有有效邮箱、消息外部投递角色健康运行。任一门禁未满足时，业务主事务和站内提醒不受影响，未创建的外部投递不会被伪造为成功。

首期规则目录冻结如下：订单待审批、订单状态变化、订单确认、报备通过、报备驳回、消息任务连续失败、报备保护期临近、商机预计成交日临近。其中订单待审批、报备通过/驳回、消息任务连续失败为系统保护规则，不允许停用、删除、改为无接收人或关闭站内渠道。报备和商机到期默认提前 30、7、1 天，于中国标准时间工作日 09:00 生成提醒；当前负责人是唯一默认接收人。

### 0.5 业务字段与超管审核待办基线（M11-001）

- 订单待审批、确认完成、状态变化和交付到期提醒固定包含“订单号、订单名称、订单渠道商、提交人”。订单名称按订单 `extra_json.projectName`、订单 `extra_json.project`、报价项目名称、商机名称顺序取值；均为空时显示“未填写订单名称”。
- 客户报备审批待办、通过、驳回和保护期到期提醒固定包含“客户名称、报备编号、提报渠道商、提交人”。渠道商和提交人由服务端从 `channel.partners`、`iam.users` 的权威关联读取，缺失时显示明确占位，禁止采用请求体字段。
- 新增员工账号待审核 `iam.account.approval.pending` 与渠道商待审核 `channel.partner.approval.pending`。前者显示员工姓名、渠道商名称和提交人；后者显示渠道商名称和提交人。渠道商或员工提交、驳回后重提时，在审批待办事务中写入发件箱事件。
- 两类超管审核规则初始均为“指定用户：`liulonghai`”，不是全部超管广播。超级管理员可在规则详情添加或移除指定用户；保存至少保留一名启用接收人，并保留二次确认、乐观锁和审计。
- 本轮仅完成本地隔离库迁移和自动化验证，未在测试服务器执行迁移、写入凭据或触发真实外部投递。

## 1. 建设目标与范围

统一消息提醒平台规划覆盖站内通知、企微自建应用、企微群机器人、短信和邮箱五类渠道。本轮企业微信外部渠道同时实现群机器人 Webhook 与自建应用的配置、受控试发、启停和投递状态；自建应用的正式业务自动投递仍须等待 IAM 用户与企微 UserId 的权威映射及规则审批。平台为合同、应收、审批、公海、报备、证书和系统任务提供统一事件订阅、接收人解析、模板、偏好、频控、投递记录、补偿与审计能力。

消息不是业务事实。合同、审批、收款等业务事务先成功并写入事务发件箱，消息平台异步消费；消息失败不得回滚已经成功的业务事务。

实施分为五个切片：

| 切片 | 交付内容 | 进入条件 |
| --- | --- | --- |
| M0 | 架构、状态机、UI、权限、参数和验收口径收口 | 本文档及决策记录完成复核 |
| M1 | 事件消费底座、站内通知、四套正式页面入口 | M0 全部确认 |
| M2 | 企微群机器人 Webhook、企微自建应用试发、短信、模板管理和渠道配置 | M1 稳定运行 |
| M3 | 邮箱、提醒计划、合并和失败补偿 | M2 渠道与合规验证通过 |
| M4 | 企微群汇总、12 类事件、监控、升级与排障文档 | M3 稳定运行 |

## 2. 实施硬约束

1. 统一入口仍为 `/`，登录后只能落到四套正式 `.html` 页面，不新增根路径 `/messages`。
2. 桌面和移动通知中心必须嵌入正式页面内部，不能跳向 `/admin/dashboard`、`/partner/dashboard` 等未替换页面。
3. 复用 `ops.outbox_events` 作为事件来源，但消息消费者不改写其既有状态语义。
4. 消息消费事实、投递事实和失败事实必须落在 PostgreSQL；Redis 只承担排队、延迟和协作。
5. 生产环境按关键事件、外部投递和维护补偿拆分进程角色，不能由一个全能进程处理全部消息任务。
6. 外部渠道默认关闭；站内渠道验收通过后再逐项启用企微、短信和邮箱。
7. 手机号、邮箱、凭据和敏感业务变量不得进入普通日志、队列载荷或未脱敏页面。
8. 业务规则、接收人规则和强制提醒范围未确认时，不得在代码中静默补默认行为。
9. 规则页面不能创建任意事件、任意模板、任意跳转或任意群发；事件、字段、接收人策略、业务目标和渠道均由服务端白名单控制。
10. 规则变更只影响变更后领取的事件和尚未投递的到期计划；已生成通知不撤回、不重发，避免重复或漏发。

## 3. 整体架构

```text
业务事务
  └─ 同一数据库事务写业务表和 ops.outbox_events
       └─ 关键事件进程
            ├─ 按持久化启用时间和消费游标读取事件
            ├─ 写 message.event_consumptions
            ├─ 解析订阅、接收人、模板和偏好
            ├─ 写 message.notifications
            └─ 写 message.deliveries 并投递渠道任务
                 ├─ 站内渠道：关键事件进程内完成
                 ├─ 企微、短信、邮箱：外部投递进程
                 └─ 重试、补投、到期扫描：维护补偿进程
```

生产部署使用同一 `apps/worker` 代码和镜像，拆分以下角色：

| 进程角色 | 默认并发 | 数据库连接预算 | 责任 |
| --- | ---: | ---: | --- |
| `worker-health` | 1 | 0至1 | 既有健康任务 |
| `worker-message-critical` | 3 | 3 | 发件箱消费、订阅编排、站内通知 |
| `worker-message-integration` | 3 | 2 | 企微、短信、邮箱外部投递 |
| `worker-message-maintenance` | 1 | 2 | 补投、重试、提醒计划和清理 |

开发环境允许少进程运行，但必须保持队列、状态和代码边界隔离。

## 4. 启用时间、游标与事件消费

### 4.1 安全启用

- `MESSAGE_WORKER_ENABLED` 的代码默认值为 `false`。
- 生产环境完成迁移、种子数据、权限和自检后，在 `v3.env` 中显式设为 `true`。
- `MESSAGE_EVENT_CUTOVER_AT` 是平台首次启用时间，由升级或发布负责人一次性填写并持久保存。
- 后续重启、扩容和重新部署不得重新生成启用时间。

禁止使用“当前工作进程启动时间”过滤事件。该做法会跳过停机期间产生的事件，造成永久漏消息。

### 4.2 独立消费事实

消息平台新增 `message.event_consumptions`，对每个发件箱事件建立独立消费记录，不修改 `ops.outbox_events` 的状态约束。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | 主键 |
| source_event_id | uuid | `ops.outbox_events.id` |
| consumer_code | text | 固定为版本化消费者代码 |
| event_code | text | 稳定事件代码 |
| event_version | integer | 事件契约版本 |
| status_code | text | `pending`、`processing`、`retry_wait`、`succeeded`、`dead`、`cancelled` |
| attempt_count | integer | 已尝试次数 |
| locked_until | timestamptz | 消费锁到期时间 |
| next_retry_at | timestamptz | 下次重试时间 |
| last_error_code | text | 稳定中文错误码对应的程序代码 |
| last_error_message | text | 脱敏后的中文原因 |
| created_at | timestamptz | 创建时间 |
| updated_at | timestamptz | 更新时间 |
| finished_at | timestamptz | 最终完成时间 |

唯一约束：`(source_event_id, consumer_code)`。

领取时使用条件更新或 `FOR UPDATE SKIP LOCKED`，单批最多 100 条；锁定时间 120 秒，心跳每 30 秒续期。进程异常后，锁过期记录由维护进程重新领取。

| 规则管理 R1 | 扩展 `message.event_subscriptions` | 事件规则名称、保护级别、版本、接收人、渠道、合并窗口、生效状态和审计主体 |
| 规则管理 R2 | `message.reminder_rules` | 到期对象、到期字段、提前天数、工作日执行时点、接收人、渠道、版本和启停 |

`workflow_definitions` 和重复的业务线 `subscriptions` 暂不建设。出现不能由 `event_subscriptions` 表达的明确业务规则后，再单独评审。

### 5.3 站内通知

`message.notifications` 至少包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | 主键 |
| recipient_user_id | uuid | 接收人，引用 `iam.users` |
| source_event_id | uuid | 来源发件箱事件，可为空 |
| event_code | text | 事件代码 |
| category_code | text | `todo`、`business`、`system`、`security` |
| priority_code | text | `normal`、`strong`、`forced` |
| aggregate_type | text | 业务对象类型 |
| aggregate_id | uuid | 业务对象编号 |
| target_action | text | `view`、`process`、`approve` 等受控动作 |
| template_version | integer | 实际使用的模板版本 |
| title | text | 已脱敏标题 |
| body | text | 已脱敏正文 |
| status_code | text | `unread`、`read`、`archived` |
| payload_snapshot | jsonb | 最小化、脱敏后的渲染快照 |
| read_at | timestamptz | 已读时间 |
| archived_at | timestamptz | 归档时间 |
| expires_at | timestamptz | 可见截止时间 |
| created_at | timestamptz | 创建时间 |

建议索引：

- `(recipient_user_id, status_code, created_at DESC)`
- `(recipient_user_id, category_code, created_at DESC)`
- `(source_event_id)`

### 5.4 投递记录

`message.deliveries` 保存接收人、渠道、模板版本、语义去重键、状态、尝试次数、下次重试时间、供应商消息编号、回执、费用摘要和脱敏错误原因。

状态使用：`pending`、`sending`、`retry_wait`、`success`、`failed`、`cancelled`、`ignored`。`failed` 只表示永久失败或重试耗尽；可恢复失败必须进入 `retry_wait`。

### 5.5 联系方式保护

M2 如需在消息域保存完整手机号或邮箱，必须采用单独密钥加密，并保存不可逆摘要和脱敏显示值。完整值不进入投递记录、队列载荷、普通日志或页面列表。密钥不得进入数据库、代码仓库和升级包明文。

## 6. 事件契约与幂等

### 6.1 事件契约

每个事件必须在 `packages/contracts/src/message.ts` 声明：

- 稳定事件代码和版本。
- 生产者、业务对象类型和业务对象编号。
- 允许的载荷字段及敏感级别。
- 接收人解析所需的最小字段。
- 兼容窗口和废弃规则。

消费者不得依赖未声明的临时字段。

### 6.2 业务语义键

生产者或事件注册表先生成 `semantic_key`：

- 一次性业务事件：使用发件箱事件编号。
- 到期提醒：使用业务对象类型、业务对象编号、提醒类型和提醒日期。
- 合并摘要：使用摘要类别、组织范围和合并时间窗。

渠道投递去重键：

```text
sha256(semantic_key + recipient_user_id + channel)
```

模板版本不得进入去重键，否则模板更新后可能重复发送同一业务提醒。

## 7. 状态机

### 7.1 事件消费

```text
pending → processing → succeeded
                    ↘ retry_wait → processing
                    ↘ dead
pending / retry_wait → cancelled
```

### 7.2 渠道投递

```text
pending → sending → success
                 ↘ retry_wait → sending
                 ↘ failed
pending / retry_wait → cancelled / ignored
```

### 7.3 站内通知

```text
unread → read → archived
unread → archived
```

单条已读、全部已读和归档操作必须服务端持久化并保持幂等。

## 9. 重试、死信与补偿

| 错误类型 | 次数 | 退避 |
| --- | ---: | --- |
| 数据库、Redis 短暂失败 | 5 | 5秒、30秒、2分钟、10分钟、30分钟 |
| 数据库锁冲突 | 3 | 5秒、30秒、2分钟 |
| 企微、短信、邮件限流或网络失败 | 5 | 30秒、2分钟、10分钟、1小时、6小时 |
| 模板未发布、权限不足、数据非法 | 0 | 直接失败并记录中文原因 |
| 已退订、停用账号、失效身份 | 0 | 标记 `ignored` |

第三方返回明确重试时间时优先采用第三方返回值。重试耗尽后写 PostgreSQL 死信事实、审计和告警；强制提醒最终失败必须立即生成平台管理员待办。

## 10. 接口与权限

全部新接口使用 `/api/messages` 前缀。

### 10.1 用户接口

| 方法与路径 | 用途 | 关键约束 |
| --- | --- | --- |
| `GET /api/messages/notifications` | 当前用户通知列表 | 默认 20 条，最大 100 条；支持分类、状态和游标 |
| `GET /api/messages/notifications/unread-count` | 当前用户未读数 | 只返回本人汇总 |
| `PUT /api/messages/notifications/:id/read` | 单条已读 | 必须校验接收人为当前用户，幂等 |
| `PUT /api/messages/notifications/read-all` | 全部已读 | 只更新当前用户可见通知 |
| `PUT /api/messages/notifications/:id/archive` | 单条归档 | 已读或未读均可归档 |
| `GET /api/messages/preferences` | 当前用户偏好 | 只返回本人配置 |
| `PUT /api/messages/preferences` | 更新偏好 | 强制消息不能关闭 |

### 10.2 平台管理接口

模板、渠道配置、投递监控、人工重试和测试发送均放在 `/api/messages/platform/*` 下，并分别校验 `message.template.*`、`message.channel.*`、`message.delivery.*` 权限。人工重试必须重新校验账号状态、模板版本、渠道授权和业务对象权限。

### 10.3 提醒规则管理接口与权限

首期接口统一使用 `/api/messages/platform/rules`，只接受服务端 Cookie 会话中的 `superadmin`。读取、修改、启停、预览均写 `audit.audit_logs`；请求体、审计和日志不得记录手机号、邮箱、Webhook、模板明文或业务明细。

| 方法与路径 | 用途 | 强制约束 |
| --- | --- | --- |
| `GET /api/messages/platform/rules/catalog` | 读取受控事件、接收人策略和渠道目录 | 目录由代码定义，前端不可自造事件或策略 |
| `GET /api/messages/platform/rules` | 分页读取事件与到期规则 | 仅返回脱敏统计、版本和配置摘要 |
| `PUT /api/messages/platform/rules/:id` | 保存规则草稿或更新版本 | 必须携带当前版本；版本冲突返回 409，不覆盖他人修改 |
| `POST /api/messages/platform/rules/:id/enable` | 启用规则 | 必须二次确认，校验至少一个有效接收人和站内渠道 |
| `POST /api/messages/platform/rules/:id/disable` | 停用规则 | 系统保护规则拒绝停用；必须二次确认和填写操作原因 |
| `POST /api/messages/platform/rules/:id/preview` | 使用脱敏样例预览解析结果 | 不查询或泄露真实客户、合同、商机和联系方式 |

允许的接收人策略只有：当前负责人、创建人、当前审批人、平台管理员、指定用户、指定角色。指定用户和指定角色必须在服务端根据账号状态、组织、角色和业务数据范围再次筛选；无有效接收人时不允许启用。首期不开放协作人、任意部门群发和跨区域角色群发。

规则字段采用显式结构，禁止万能 JSON 解释器：事件规则维护启停、优先级、接收人策略、渠道、合并窗口、版本和生效时间；到期规则额外维护受控到期字段、提前天数集合和工作日 09:00 执行策略。30、7、1 天在同一业务对象规则内可独立勾选，且每个提前天数均进入独立语义去重键。

## 11. 正式页面与业务跳转

### 11.1 页面入口

| 用户端 | 顶栏入口 | 完整通知中心 |
| --- | --- | --- |
| 管理桌面端 | `admin.html` 顶栏铃铛 | `admin.html#/notifications` |
| 渠道桌面端 | `partner.html` 顶栏铃铛 | `partner.html#/notifications` |
| 管理移动端 | 首页未读卡片和消息入口 | `admin-mobile.html#/admin/notifications` |
| 渠道移动端 | 首页未读卡片和消息入口 | `partner-mobile.html#/partner/notifications` |

平台模板、渠道配置和投递监控只在管理桌面端开放。个人偏好在四套正式页面开放，但移动端首期只提供常用开关和免打扰设置。

桌面端铃铛抽屉标题必须显示当前账号未读总数，并保留“查看全部”入口，避免较长列表因抽屉可视高度而被误判为漏投。完整通知中心按当前账号、创建时间倒序展示全部可见记录。

订单、客户报备、报价、商机及到期提醒正文统一使用“渠道商【渠道商名称】、提报人【提报人】”前缀。字段由服务端受控查询并随投递快照固化；历史通知不回写，模板调整只作用于后续投递。

### 11.3 超管提醒规则管理视觉与交互

管理端新增 `admin.html#/message-rules`，沿用 V3 管理端卡片、标签、表格和抽屉样式。页面包含“业务事件”“到期提醒”两个页签：列表展示规则名称、状态、系统保护标记、接收人摘要、渠道、合并方式、最近修改人和版本；编辑抽屉按场景展示可选字段，并在保存前显示“仅影响后续事件”的提示。

系统保护规则以锁定标签和禁用操作呈现。到期提醒在同一规则内展示可独立勾选的 30、7、1 天，醒目显示工作日 09:00；渠道未完成试发或未启用时，规则可保存但不能启用外部渠道。页面必须提供加载、空状态、无权限、版本冲突和保存失败的中文反馈；不得展示其他用户的联系方式或业务数据。

已启用的系统业务事件规则均须提供“保存规则”入口，不能因其保护级别为“可配置”而只显示“停用该规则”。保存统一通过现有二次确认、规则版本和服务端白名单校验；客户报备审批待办额外保存限定的角色与指定用户范围，两类接收人取并集后再过滤停用账号。编辑时必须回显既有角色与指定用户；历史范围缺失时回退到区域管理员和超级管理员。业务事件始终保留站内提醒，以确保外部通道异常或未启用时不影响站内可见性。

### 11.2 业务目标解析

消息数据只保存受控的 `aggregate_type`、`aggregate_id` 和 `target_action`。前端根据当前角色和设备解析到正式页面内部路由。目标不在允许清单、业务对象不存在或当前用户无权访问时，显示“该记录不存在、已失效或当前账号无权访问”，不得泄露业务摘要。

具体视觉和交互见 `docs/operations/统一消息提醒平台前端UI设计.md`。

## 12. 偏好、免打扰与频控

### 12.1 默认策略

- 站内通知默认开启。
- 企微应用仅对重要和强制消息默认开启；普通消息默认关闭。
- 短信和邮箱默认关闭，必须由用户授权或强提醒规则显式启用。
- 企微群只发送脱敏汇总。
- 默认免打扰为 22:00 至次日 08:00。
- 普通消息延迟或合并；重要消息站内即时；强制消息可绕过免打扰但仍需去重和限频。

### 12.2 初始频控

| 维度 | 默认值 |
| --- | ---: |
| 同一业务对象、同一提醒窗口、同一渠道 | 1 次 |
| 普通企微消息 | 每用户每天 20 条 |
| 普通短信 | 每用户每天 3 条 |
| 普通邮件 | 每用户每天 5 封 |
| 企微群汇总 | 每群每小时 1 条 |
| 短信灰度期平台总量 | 每天 500 条 |
| 邮件灰度期平台总量 | 每天 2000 封 |

强制消息达到阈值后合并成异常摘要并告警，不得简单丢弃。

## 13. 数据保留与安全

| 数据 | 默认保留 |
| --- | ---: |
| 通知中心默认可见 | 180 天 |
| 站内通知归档后保留 | 365 天 |
| 投递状态与费用元数据 | 365 天 |
| 含敏感变量的投递快照 | 最多 30 天，之后清除或脱敏 |
| 普通失败堆栈摘要 | 90 天 |

| R2 | 到期规则迁移、报备/商机 30/7/1 独立勾选扫描、工作日时点、语义去重和补偿 | 多实例和重复扫描不重发；负责人变化按实际执行时身份重新校验 |
| R3 | 管理端规则页、视觉原型、脱敏预览、错误与冲突交互 | V3 统一登录后的超管可完整维护；普通用户不可见入口且接口拒绝 |
| R4 | 联调、压测、停机补投、回退、部署与验收记录 | 规则服务或外部渠道故障不影响订单、报备、商机等业务事务 |

## 16. 验收门禁

M1 至少满足：

1. 同一事件重复消费 10 次，只生成一条站内通知。
2. 工作进程停机 30 分钟后恢复，停机期间事件全部补投。
3. Redis 清空后可从 PostgreSQL 恢复未完成任务。
4. 事件到站内通知的百分之九十五耗时不超过 10 秒。
5. 通知列表在 50 并发下百分之九十五耗时不超过 500 毫秒。
6. 未读数接口在 50 并发下百分之九十五耗时不超过 200 毫秒。
7. 跨用户读取、已读、归档和业务目标跳转全部被拒绝。
8. 消息平台不可用时，原业务事务仍能成功。
9. 四套正式页面均完成铃铛、列表、已读、空状态、错误状态和权限回归。
10. `tests/smoke.sh`、接口测试、工作进程测试和浏览器测试全部通过。

提醒规则管理额外满足：

11. 同一规则版本的同一业务对象在同一提醒窗口内只产生一条通知；规则版本更新不使旧语义键失效。
12. 30、7、1 天可在到期规则中独立勾选或取消，非工作日不会生成 09:00 到期提醒；下一工作日补扫不重复。
13. 当前负责人、审批人、指定用户或角色失效、越权或无数据范围时被过滤并审计，不向替代人员静默扩散。
14. 规则的保存、启停、冲突、保护规则拒绝、回退和页面无权限均有自动化测试。

## 17. 发布与回退

发布顺序：数据库扩展迁移 → API 兼容发布 → UI 发布但隐藏入口 → 关键事件进程关闭状态部署 → 自检 → 写入持久化启用时间 → 显式开启站内渠道 → 灰度观察 → 全量开放。

生产回退顺序：关闭新入口和外部渠道 → 停止消息工作进程 → 保留 `message.*` 数据和迁移版本 → 回退兼容代码 → 完成未处理事件与失败记录核对。生产环境不得直接删除 `message` 架构。

规则管理回退优先将新增规则置为停用，并保留规则版本、审计和已生成提醒；不得通过删除规则表或已生成通知回退。

只有本地、测试或尚未产生任何真实消息的演练环境，才允许使用同名回退脚本删除新增结构。

## 18. 与既有通知的关系

- M1 不迁移、不删除 `ops.notifications`。
- 新事件写入 `message.notifications` 和 `message.deliveries`。
- 四套正式页面在灰度期分别读取新旧数据源并明确来源，禁止浏览器内静默双写已读状态。
- 历史通知迁移和旧表下线必须另立任务、迁移方案和验收，不包含在 M1。

## 19. 风险登记

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 启用时间随重启变化 | 停机期间消息永久遗漏 | 使用持久化启用时间和消费事实游标 |
| 多消费者争抢发件箱状态 | 其他集成消费者漏事件 | 使用独立 `event_consumptions`，不改写既有状态语义 |
| 任意业务链接 | 越权或跳向非正式页面 | 保存业务目标，由四套正式页面白名单解析 |
| 同一进程处理全部任务 | 外部渠道阻塞关键事件 | 按角色拆分进程和连接预算 |
| 去重键缺业务对象 | 多笔业务被错误合并 | 使用业务语义键、接收人和渠道组合 |
| 联系方式明文扩散 | 隐私泄露 | 加密、摘要、脱敏、权限和审计 |
| 生产回退删除架构 | 丢失投递和审计事实 | 生产只停用并保留数据 |
| 通知过多 | 用户忽略或关闭提醒 | 分类、合并、免打扰、频控和强制边界 |
| 超管误配接收人或渠道 | 无关人员收到提醒，或关键人员漏收 | 白名单策略、数据范围校验、系统保护规则、二次确认、版本并发和审计 |
| 规则变更导致补扫重复 | 同一到期事项重复提醒 | 提前天数独立语义键、规则版本不进入去重键、已投递计划不可重新生成 |
