# 阶段6 单机性能治理与资源分配

## 1. 生产约束

用户已确认首发生产目标按单机容器部署，资源约为 12 核心、32GB 内存。数据库使用 PostgreSQL，缓存和任务使用 Redis。暂不准备备用服务器，但架构必须预留后续备用服务器接管能力。

单机部署只能实现进程级和容器级恢复，不能消除整机、机房、磁盘和网络单点。上线前必须有异机备份、外部监控和恢复演练。

## 2. 资源分配建议

| 组件 | CPU预算 | 内存预算 | 关键限制 | 说明 |
| --- | ---: | ---: | --- | --- |
| PostgreSQL 16 | 5至6核 | 12至14GB | 连接数、查询超时、事务超时 | 核心业务数据优先保障 |
| Node 接口服务 | 3核 | 4至5GB | 请求体、响应行数、连接池 | 建议多进程，按接口负载调节 |
| Node 任务消费者 | 2核 | 3至4GB | 队列并发、数据库连接预算 | 与接口服务分容器或分进程 |
| Redis 状态实例 | 1核 | 3GB | `noeviction`、AOF | 会话、限流、队列 |
| Redis 缓存实例 | 0.5至1核 | 2GB | 过期、大小上限、淘汰策略 | 可与状态实例合并但不推荐 |
| Nginx | 0.5核 | 512MB至1GB | 连接数、限速、上传大小 | TLS、静态资源和入口保护 |
| 监控与日志采集 | 0.5至1核 | 1至2GB | 保留期、采样 | Prometheus、Loki 或轻量替代 |
| 操作系统和文件缓存 | 预留 | 5至7GB | 不得挤占 | 给内核、页缓存、备份和突发负载 |

资源分配初始值必须通过阶段6压力测试校准。导入、导出、统计刷新和迁移演练不能占满 PostgreSQL 连接池。

## 3. PostgreSQL 初始参数建议

以下是 12 核 32GB 单机的起始值，必须结合真实数据规模和执行计划调整。

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| `max_connections` | 120 | 应配合应用连接池，避免连接风暴 |
| `shared_buffers` | 8GB | 单机 32GB 的保守起点 |
| `effective_cache_size` | 20GB至24GB | 告诉优化器可用缓存规模 |
| `work_mem` | 16MB至64MB | 按慢查询和并发调节，避免排序耗尽内存 |
| `maintenance_work_mem` | 1GB | 索引维护和迁移演练使用 |
| `statement_timeout` | 接口 3至10秒，后台任务 1至30分钟 | 按任务类型区分 |
| `idle_in_transaction_session_timeout` | 30秒至120秒 | 防止空闲事务长期占锁 |
| `wal_compression` | 开启 | 降低备份和复制压力 |

连接池建议：

| 来源 | 连接预算 |
| --- | ---: |
| 接口服务总池 | 40至50 |
| 任务消费者总池 | 15至25 |
| 迁移演练和维护 | 5至10 |
| 管理和监控 | 5 |
| 预留 | 20以上 |

## 4. Redis 初始参数建议

状态 Redis：

```text
appendonly yes
appendfsync everysec
maxmemory 3gb
maxmemory-policy noeviction
timeout 0
tcp-keepalive 60
```

缓存 Redis：

```text
appendonly no
save 900 1
maxmemory 2gb
maxmemory-policy allkeys-lru
timeout 0
tcp-keepalive 60
```

如果只部署一个 Redis：

- 使用 `appendonly yes` 和 `noeviction`。
- 缓存写入失败必须被降级处理。
- 所有缓存必须有过期时间和大小上限。
- 队列和会话优先级高于缓存。

## 5. Node 服务治理

| 项目 | 建议 |
| --- | --- |
| 接口进程 | 按 2至4 个进程启动，先以 3 个为起点 |
| 任务进程 | 单独启动，按队列设置并发，不与接口共用全部连接 |
| 请求体限制 | 普通接口 1MB，导入上传按类型设置硬限制 |
| 响应限制 | 列表默认分页，最大页大小必须有限制 |
| 超时 | 接口请求整体超时 15秒以内，大任务只返回任务编号 |
| 连接池 | 接口和任务分池或分预算 |
| 日志 | 结构化日志，禁止记录密码、令牌和客户台账明文 |

## 6. Nginx 治理

| 项目 | 建议 |
| --- | --- |
| TLS | 统一在 Nginx 终止 |
| 静态资源 | 带摘要文件长期缓存，入口 HTML 短缓存 |
| 上传大小 | 按导入类型设置，不允许无限上传 |
| 代理超时 | 普通接口短超时，任务创建接口短返回 |
| 限速 | 登录、开放接口、导入上传单独限速 |
| 健康检查 | 分接口服务、任务服务、PostgreSQL、Redis |

## 7. 性能治理清单

阶段6必须逐项建立证据：

- 用户、渠道、报备、商机、报价、订单、产品树、审批、审计、开放接口的执行计划和索引证据。
- 核心列表必须服务端分页，不返回无界数组。
- 大导入和大导出必须任务化，不占用接口请求线程。
- 登录和通知列表不得触发到期提醒全量扫描。
- 看板统计只有在阶段7实测昂贵且高频时才做预计算。
- 缓存清单外的缓存不得上线。

## 8. 阶段6压力目标

| 场景 | 目标 |
| --- | --- |
| 基线 | 50 并发持续 15 分钟，无错误和资源异常 |
| 目标 | 500 活跃并发，持续请求量 300 次每秒，持续 30 分钟 |
| 峰值 | 600 次每秒持续 10 分钟，错误率低于 0.1% |
| 长稳 | 典型混合负载持续 8 小时，无持续内存增长和任务积压 |
| 导出并行 | 普通查询负载下同时执行受控大导出，页面目标不严重退化 |
| 队列积压 | 人为积压后恢复消费者，稳定清空且不压垮数据库 |
| 缓存失效 | Redis 清空后逐步恢复，无数据库雪崩 |

## 9. 当前风险结论

12 核 32GB 可以作为 V3 首发单机资源起点，但必须遵守连接、队列并发、导出并发和缓存大小上限。若真实客户量达到百万级、渠道达到数千级，性能瓶颈主要会出现在 PostgreSQL 查询设计、导出任务、统计刷新和权限范围过滤，不在 Redis 本身。
