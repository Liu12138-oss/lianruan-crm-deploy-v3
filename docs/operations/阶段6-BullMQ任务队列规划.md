# 阶段6 BullMQ任务队列规划

## 1. 总体原则

BullMQ 只负责排队、延迟、重试和消费者协作。任务事实、业务状态、结果文件、错误原因和审计记录必须落在 PostgreSQL。Redis 清空、队列丢失或消费者重启时，系统必须能从 PostgreSQL 找出未完成任务并补投。

所有任务必须满足：

- 先写任务事实，再提交队列。
- 使用任务事实编号作为 BullMQ `jobId`。
- 任务载荷只保存必要编号和参数摘要，不保存敏感明文。
- 每个任务有幂等键、检查点、中文错误码和可追踪请求编号。
- 可重试错误自动重试，业务校验失败不盲目重试。
- 人工重试、取消、补投和清理必须进入审计。

## 2. 队列总表

| 队列 | 任务类型 | 初始并发 | 数据库连接预算 | 重试 | 死信策略 | 说明 |
| --- | --- | ---: | ---: | --- | --- | --- |
| `import` | 导入预检、导入执行 | 1至2 | 2至4 | 网络、锁等待、临时数据库错误可重试 | 进入人工处理 | 防止导入占满数据库 |
| `export` | 列表导出、明细导出、失败文件生成 | 2 | 2至4 | 文件系统临时错误可重试 | 保留任务和临时文件摘要 | 使用游标和流式写文件 |
| `migration-drill` | 迁移演练、数据校验、数量守恒检查 | 1 | 2至3 | 环境类错误可重试 | 阻断阶段8 | 只在演练环境或受控窗口执行 |
| `notification` | 到期提醒扫描、通知生成 | 3至5 | 2至3 | 可重试 | 超限后人工处理并告警 | 使用业务对象、日期和提醒类型防重 |
| `stats-refresh` | 看板统计刷新、开放接口统计刷新 | 2至3 | 2至4 | 可重试 | 保留旧统计版本 | 不提前建设数据仓库 |
| `integration` | 外部接口补偿、开放接口异步审计聚合 | 3至5 | 1至3 | 按外部限流退避 | 人工处理 | 必须有外部超时和并发上限 |
| `maintenance` | 发件箱补投、临时文件清理、大键扫描 | 1 | 1至2 | 可重试 | 告警，不自动破坏数据 | 只能执行白名单维护动作 |

### 2.1 关键任务落地策略

| 任务 | `jobId` | 幂等依据 | 重试策略 | 死信策略 | 补偿策略 |
| --- | --- | --- | --- | --- | --- |
| 导入预检 | 预检任务事实编号 | 文件摘要、规则版本、创建人、导入类型 | 文件读取临时错误和数据库连接失败可重试 3 次 | 记录中文行级失败摘要，进入失败或人工处理 | 文件未变时可重新预检，新规则必须生成新预检 |
| 导入执行 | 导入执行任务事实编号 | 预检编号、业务唯一键、任务编号、批次检查点 | 锁等待、临时数据库错误可重试 3 至 5 次 | 重试耗尽进入人工处理，保留已完成批次 | 从最后成功检查点继续，已写批次靠唯一约束跳过 |
| 导出 | 导出任务事实编号 | 任务编号、查询条件摘要、数据范围快照 | 临时文件错误和数据库连接失败可重试 3 次 | 保留临时文件摘要和错误位置 | 文件缺失或摘要不一致时重新生成并替换有效结果 |
| 迁移演练 | 演练批次任务事实编号 | 演练批次号、源快照摘要、目标库标识 | 环境类错误可重试 2 至 3 次 | 阻断阶段8迁移准入，等待人工确认 | 清理演练目标库后重新开批次，不覆盖正式库 |
| 到期通知生成 | 通知扫描任务事实编号 | 业务对象编号、提醒类型、提醒日期 | 数据库临时错误可重试 3 次 | 超限后人工处理并告警 | 重扫时间槽，只补缺失通知 |
| 统计刷新 | 统计刷新任务事实编号 | 统计口径、时间范围、数据范围、版本 | 可重试 3 次，失败不影响上一成功版本 | 保留旧统计版本并告警 | 重新刷新新版本，成功后再切换可见指针 |
| 发件箱补投 | 发件箱维护任务事实编号 | 发件箱事件编号、消费者动作 | 外部限流按退避重试 3 至 8 次 | 进入人工处理，禁止静默丢弃 | 人工确认后按事件编号补投 |

### 2.2 BullMQ 初始参数建议

| 参数 | 建议 | 说明 |
| --- | --- | --- |
| `attempts` | 按任务类型设置 3 至 8 | 业务校验失败必须直接失败 |
| `backoff` | 指数退避加随机抖动 | 避免故障恢复时同时冲击数据库 |
| `removeOnComplete` | 保留有限数量或短期保留 | PostgreSQL 保存长期事实和审计 |
| `removeOnFail` | 不自动删除近期失败 | 失败定位和人工处理需要可查 |
| `limiter` | 对外部接口和高风险任务启用 | 避免突破外部额度和数据库预算 |
| `concurrency` | 使用队列表初始值 | 调整必须有压测证据 |
| `lockDuration` | 按批次处理时间设置 | 长任务必须有检查点，不靠长锁保活 |

BullMQ 失败队列只能作为短期排查入口，最终死信状态必须回写 PostgreSQL。任何只存在 Redis 中的失败记录，都不算阶段6验收证据。

## 3. 任务状态

| 状态 | 含义 | 允许进入方式 |
| --- | --- | --- |
| `待排队` | PostgreSQL 已创建任务事实，尚未成功投递 Redis | 接口创建、补投器创建 |
| `等待执行` | Redis 已接收任务，等待消费者 | 投递成功 |
| `运行中` | 消费者已占有并开始执行 | 消费者加锁成功 |
| `成功` | 业务处理完成，结果可查询 | 消费者提交结果 |
| `失败` | 不可重试失败或重试耗尽 | 消费者记录失败 |
| `等待人工处理` | 需要人工判断补偿或放弃 | 死信、数据异常、外部长期不可用 |
| `取消` | 未执行或允许取消的任务停止 | 管理员受控取消 |

状态更新必须带版本号。更新失败时消费者重新读取任务事实，不覆盖其他执行者结果。

## 4. 幂等策略

| 任务 | 幂等依据 | 防重复方式 | 补偿策略 |
| --- | --- | --- | --- |
| 导入预检 | 文件摘要、规则版本、创建人、导入类型 | 同一摘要和规则版本只保留一个有效预检结果 | 重新预检生成新版本 |
| 导入执行 | 预检编号、业务唯一键、任务编号 | PostgreSQL 唯一约束和批次检查点 | 未完成批次继续，已完成批次跳过 |
| 导出 | 任务编号、查询条件摘要、数据范围快照 | 同一任务只保留一个有效结果文件 | 文件缺失则重新生成并替换结果 |
| 迁移演练 | 演练批次号、源快照摘要、目标库标识 | 演练批次唯一 | 删除演练目标库或重新开新批次 |
| 通知生成 | 业务对象编号、提醒类型、提醒日期 | 唯一约束防重 | 重复执行只补缺失通知 |
| 统计刷新 | 统计口径、时间范围、数据范围、版本 | 新版本覆盖可见指针，旧版本保留短期回退 | 失败时继续使用上一成功版本 |
| 外部补偿 | 外部请求编号、业务编号、动作 | 发件箱事件编号幂等 | 超限后人工处理 |

## 5. 重试和退避

| 错误类型 | 示例 | 是否重试 | 建议次数 | 退避 |
| --- | --- | --- | ---: | --- |
| 临时基础设施错误 | Redis 短暂不可用、数据库连接获取失败 | 是 | 3至5 | 指数退避加随机抖动 |
| 数据库锁等待 | 更新冲突、短时间锁等待 | 是 | 3 | 5秒、30秒、2分钟 |
| 外部系统限流 | 企业查询、第三方接口限流 | 是 | 3至8 | 按外部返回时间或指数退避 |
| 文件系统临时错误 | 临时目录不可写、文件被占用 | 是 | 3 | 10秒、1分钟、5分钟 |
| 业务校验失败 | 字段非法、权限不足、状态不允许 | 否 | 0 | 直接失败并给中文原因 |
| 数据不一致 | 上级渠道断裂、未知状态 | 否 | 0 | 等待人工处理 |

重试不能绕过权限、状态机和数据范围。重试前必须重新检查账号状态和任务版本。

## 6. 死信和人工处理

阶段6不使用“静默丢弃”。达到重试上限后：

1. 更新 PostgreSQL 任务状态为 `等待人工处理` 或 `失败`。
2. 保存最后一次错误代码、中文原因、堆栈摘要、请求编号和业务编号。
3. 写入审计。
4. 触发告警。
5. 允许管理员只对可重试任务执行人工重试或取消。

禁止提供任意修改任务载荷、跳过权限、直接写业务结果的管理入口。

## 7. 补投流程

Redis 清空、队列异常或消费者长时间停止后，补投器按以下规则执行：

1. 从 PostgreSQL 查询 `待排队`、`等待执行`、`运行中且心跳超时` 的任务。
2. 按任务类型和创建时间分批补投。
3. 使用任务编号作为 `jobId`，重复投递必须幂等。
4. 补投前检查任务是否已成功或取消。
5. 补投结果进入审计和指标。

补投器属于 `maintenance` 队列，默认并发为 1。

补投器只能补投任务事实表中仍需执行的任务，不允许根据 Redis 历史记录反向创建业务事实。每次补投必须记录补投原因、补投人或系统进程、补投批次号和命中的任务数量。

## 8. 队列停机和恢复

计划维护时：

1. 停止入口新增高风险任务。
2. 暂停消费者接收新任务。
3. 等待运行中任务完成或到达检查点。
4. 记录队列等待数、运行数、失败数。
5. 维护后恢复消费者，并观察积压清理速度。

非计划故障时：

1. 先恢复 PostgreSQL 和 Redis。
2. 启动消费者，执行补投。
3. 检查死信和人工处理列表。
4. 对导入、导出、迁移演练任务做抽样结果校验。

## 9. 阶段6验收样本

| 验收项 | 样本 |
| --- | --- |
| 重复投递 | 同一导入执行任务重复投递 3 次，只生成一组业务结果 |
| 进程重启 | 导出进行中停止消费者，恢复后从检查点继续 |
| Redis 清空 | 清空队列 Redis 后，未完成任务从 PostgreSQL 补投 |
| 失败定位 | 失败任务能看到业务编号、请求编号、错误代码和中文原因 |
| 人工重试 | 只允许可重试任务重试，操作进入审计 |
| 积压恢复 | 人为积压 1 万任务，恢复消费者后稳定清空且接口不被拖垮 |

## 10. 上线前禁止项

- 禁止在接口请求内同步执行大导入、大导出、迁移演练和全量通知扫描。
- 禁止任务消费者与接口服务共享不受控的数据库连接池。
- 禁止人工入口修改任务载荷、跳过权限校验或直接写业务结果。
- 禁止把死信只留在 Redis，不回写 PostgreSQL 任务事实表。
- 禁止任务失败只记录英文堆栈，必须给业务和运维可理解的中文原因。
