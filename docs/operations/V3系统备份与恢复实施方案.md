# V3 系统备份与恢复实施方案

> 文档编号：KB-20260814-BAK-001  
> 文档状态：完整实施基线，尚未接入生产  
> 适用工程：`deploy/single-server`、`database/migrations`、`apps/api`、`apps/worker`  
> 关联总方案：[V3 业务平台底座与业务扩展实施交付方案](../V3业务平台底座与业务扩展实施交付方案.md) 第 18.6 节  
> 编制日期：2026-08-14  
> 文档版本：v1.1

## 1. 结论

当前 V3 是单机 Docker Compose 部署：PostgreSQL、两类 Redis、上传文件、导出文件和生产配置均依赖宿主机目录。现有 `backup.sh` 只能手工导出 PostgreSQL 逻辑备份并打包部分业务文件，备份仅保留在本机，不能应对整机、磁盘、机房或误删后的时间点恢复。

当前架构下最方便且满足专业恢复要求的方案为：

1. PostgreSQL 使用 `pgBackRest` 写入独立的 S3 兼容对象存储，启用持续 WAL 归档、每周全量、每日差异和定期增量备份，支持时间点恢复。
2. 上传文件、未过期导出、迁移材料、运行配置、密钥恢复材料、Compose 编排和发布清单使用 `restic` 加密备份到独立对象存储仓库。
3. 使用宿主机 `systemd timer` 调度备份、校验和恢复演练；不新增常驻备份容器，避免额外容器编排和生命周期管理。
4. 不把正在运行的 PostgreSQL 数据目录当普通文件复制；不把 Redis 当作业务唯一恢复来源；不将云盘或虚拟机快照当作唯一备份。
5. 整机恢复采用“离线运行时和镜像 + 受控配置与密钥恢复材料 + 数据库时间点恢复 + 文件恢复”的可移植重建方式，而不是绑定供应商的整机镜像。宿主机快照可以额外保留，但只作为加速手段。

该方案以现有单机目录结构为边界，不改变 V3 对外入口、业务接口或数据模型。接入后才可将“异机备份、恢复演练、五分钟恢复点”作为已实现能力对外说明。

## 2. 当前架构与保护对象

### 2.1 当前宿主机持久化目录

| 路径 | 内容 | 恢复优先级 | 恢复方式 |
| --- | --- | --- | --- |
| `data/postgres` | PostgreSQL 主数据、审计、任务事实和事件发件箱 | P0 | 仅通过 `pgBackRest` 恢复 |
| `data/uploads` | 业务上传附件 | P0 | `restic` 恢复并校验摘要 |
| `data/exports` | 未过期导出文件 | P1 | `restic` 按保留策略恢复 |
| `data/migration` | 迁移输入、核对结果和证据 | P1 | `restic` 恢复 |
| `data/redis-state` | 会话、队列状态和限流状态 | P2 | 默认重建；必要时恢复最近快照 |
| `data/redis-cache` | 缓存 | P3 | 不备份，启动后回源重建 |
| `config`、`secrets` | 环境变量、Nginx 配置、数据库和 Redis 密钥 | P0 | `restic` 加密恢复，密钥双人保管 |
| `compose`、`scripts`、`releases` | 编排、运行脚本、当前发布清单和离线包摘要 | P1 | `restic` 恢复，镜像从离线包或制品库加载 |

日志目录不进入长期业务备份。日志按现有轮转和审计留存规则独立处理；诊断包、导入错误报告等确需留存的证据应写入 `data/migration` 后再进入文件备份。

### 2.2 当前能力缺口

| 项目 | 当前状态 | 本方案收口方式 |
| --- | --- | --- |
| 数据库 | 手工 `pg_dump`，仅本机 | 持续归档、异机仓库、全量/差异/增量、时间点恢复 |
| 业务文件 | 手工 ZIP，仅上传和导出 | 加密异机备份、快照保留、摘要校验 |
| 配置和密钥 | 仅保存脱敏摘要，不能恢复 | 加密备份完整配置和密钥恢复材料 |
| 整机故障 | 文档预留，不能一键重建 | 固定恢复清单、自动化恢复脚本和演练证据 |
| 定时与告警 | 未落地 | `systemd timer`、备份结果、失败与恢复点告警 |

## 3. 技术选型

### 3.1 推荐组件

| 保护范围 | 推荐组件 | 选择原因 |
| --- | --- | --- |
| PostgreSQL | `pgBackRest` | 原生支持全量、差异、增量、WAL 归档、校验和时间点恢复；适合 PostgreSQL 16 和长期保留策略。 |
| 文件、配置、密钥恢复材料 | `restic` | 默认加密、去重、快照、保留和校验，适合宿主机目录与 S3 兼容对象存储。 |
| 异机存储 | 企业已有 S3 兼容对象存储 | 与机器解耦，可设置版本、不可变保留、独立访问凭据和生命周期策略。 |
| 调度 | `systemd timer` | 当前部署已依赖宿主机 Docker，定时器可明确记录执行、重试、日志和失败状态，无须再维护常驻备份容器。 |
| 告警 | 现有外部监控或消息平台 | 监控备份最后成功时间、WAL 归档延迟、仓库容量、校验和演练结果。 |

`pg_dump` 保留为发布前的小型逻辑快照和人工排障工具，但不得替代生产主备份链路。`wal-g` 也具备云端归档能力；为避免在当前单机 V3 中同时维护两套 PostgreSQL 归档工具，本方案统一采用 `pgBackRest`。

### 3.2 GitHub 参考

| 项目 | 参考地址 | 本方案采用的能力 |
| --- | --- | --- |
| pgBackRest | <https://github.com/pgbackrest/pgbackrest> | 并行全量、差异、增量备份，WAL 归档，校验与时间点恢复。 |
| restic | <https://github.com/restic/restic> | 加密快照、去重、仓库校验，以及 S3 兼容对象存储后端。 |
| WAL-G | <https://github.com/wal-g/wal-g> | 作为 PostgreSQL 云端归档的备选实现，本期不与 pgBackRest 并用。 |

上述仓库只作为技术实现参考，不直接复制其示例中的账号、路径、保留参数或容器镜像。生产依赖版本必须进入离线包清单，并与 V3 镜像一同校验。

## 4. 目标架构

```text
                   生产服务器
┌──────────────────────────────────────────────────────┐
│ Docker Compose                                        │
│  PostgreSQL ── pgBackRest / WAL 归档 ─────────────┐  │
│  API、Worker ── uploads / exports / migration      │  │
│                                                     │  │
│ systemd timer ── restic 加密快照 ──────────────────┼──┼────> 独立对象存储
│ systemd timer ── 备份校验与演练报告 ───────────────┘  │       数据库仓库
│                                                      │          文件配置仓库
│ 离线运行时、镜像摘要、Compose、配置和密钥恢复材料      │          只追加保留策略
└──────────────────────────────────────────────────────┘
                                                        │
                                                        └────> 隔离恢复环境
                                                               数据库恢复、文件校验、冒烟验证
```

数据库仓库和文件配置仓库必须使用不同的桶或前缀、不同的访问凭据和独立保留策略。对象存储账号仅允许对应仓库的最小读写权限，不允许读取业务生产环境的其他对象。

## 5. 备份策略

### 5.1 数据库策略

| 项目 | 基线 | 目的 |
| --- | --- | --- |
| WAL 归档 | 持续归档，归档延迟告警阈值 5 分钟 | 恢复点目标不超过 5 分钟 |
| 全量备份 | 每周日 02:00 | 提供完整恢复基线 |
| 差异备份 | 每日 02:20，跳过全量日 | 缩短日常恢复链路 |
| 增量备份 | 每 6 小时 | 降低恢复时需要回放的 WAL 量 |
| 全量保留 | 至少 4 份 | 形成至少 28 天的可恢复窗口 |
| WAL 保留 | 覆盖所有未过期全量链路 | 防止备份链路断裂 |
| 仓库校验 | 每日 | 发现归档、权限、校验和或容量异常 |
| 隔离恢复 | 每周至少一次 | 验证最近备份能实际启动和校验 |

为满足五分钟恢复点，PostgreSQL 必须启用 `archive_mode=on`，并以不大于 300 秒的归档切换策略保证低写入时也会产生可归档 WAL。`archive_command` 仅调用 PostgreSQL 容器内的 `pgbackrest archive-push`；因此 PostgreSQL 镜像必须以当前 `postgres:16.4-alpine` 为基础加入已锁定版本的 `pgBackRest`，不得在运行中的生产容器内临时安装。

数据库备份的仓库配置、S3 访问凭据和加密材料均通过受限文件挂载，不写入 `v3.env`、Compose 文件、日志或备份报告。备份报告只记录备份编号、时间、大小、校验结果和恢复点，不记录连接串、访问密钥或口令。

### 5.2 文件、配置与发布环境策略

| 对象 | 频率 | 保留 | 说明 |
| --- | --- | --- | --- |
| `data/uploads` | 每小时 | 30 个日快照、12 个周快照、12 个月快照 | 通过快照和摘要恢复业务附件。 |
| `data/exports` | 每小时 | 与导出文件业务保留期一致 | 已过期且无合规留存要求的文件可不恢复。 |
| `data/migration` | 每日及迁移前后 | 至少 12 个月 | 保留迁移证据、核对报告和回退依据。 |
| `config`、`secrets` | 每次发布或变更后立即执行，另每日一次 | 与对应发布包同生命周期，至少 12 个月 | 完整内容只进入加密仓库；恢复密钥双人保管。 |
| `compose`、`scripts`、`releases` | 每次发布后立即执行 | 永久保留发布记录，离线包按合规策略保留 | 支持在新服务器重建同版本环境。 |
| `data/redis-state` | 每日，可选 | 7 天 | 仅用于加速恢复；无法恢复时由 PostgreSQL 任务事实补投。 |

`data/redis-cache`、运行日志目录、Docker 临时层和 PostgreSQL 数据目录不得交给 `restic` 作为普通文件备份。前者可重建，后两者会造成不一致或无效恢复。

### 5.3 对象存储要求

1. 数据库仓库和文件配置仓库位于生产服务器以外的故障域。
2. 启用服务端加密、对象版本和不可变保留；不可变保留至少覆盖最近 14 天，以降低误删和勒索风险。
3. 备份访问凭据与应用凭据分离，备份写入账号不拥有删除整个仓库或修改保留规则的权限。
4. 恢复账号单独管理，只在演练或事故恢复时由两名授权人员启用。
5. 存储容量、对象存储服务等级、跨地域复制和合规保留期由运维与业务负责人在实施前确认。

## 6. 实施边界与交付物

### 6.1 需要新增的 V3 部署资产

| 资产 | 职责 |
| --- | --- |
| PostgreSQL 备份镜像构建文件 | 固定 `pgBackRest` 版本，提供归档和恢复命令。 |
| `config/backup.env.template` | 仅提供非敏感参数模板；真实访问凭据使用受限密钥文件。 |
| `scripts/backup-db.sh` | 执行全量、差异、增量或校验；输出脱敏报告。 |
| `scripts/backup-files.sh` | 使用 `restic` 备份规定目录，执行保留清理和仓库校验。 |
| `scripts/restore-db.sh` | 显式要求恢复目标、时间点和人工确认；默认只允许隔离环境恢复。 |
| `scripts/restore-system.sh` | 在新服务器恢复发布环境、文件、配置和数据库，不自动切换生产流量。 |
| `scripts/verify-backup.sh` | 检查最后成功时间、归档延迟、仓库校验和恢复演练证据。 |
| `systemd` 服务与定时器 | 调度数据库、文件、校验与演练任务，失败交给外部监控告警。 |
| 备份清单 | 记录镜像摘要、数据库备份编号、文件快照编号、配置版本和演练结果。 |

所有脚本必须使用严格错误处理、中文日志、非交互默认拒绝和明确的安装根目录。恢复脚本不得默认覆盖正在运行的生产数据库，也不得在未确认备份编号、恢复点和目标环境时执行。

### 6.2 发布联动

每次生产发布按以下顺序执行：

1. 运行数据库备份和文件配置快照，等待仓库校验成功。
2. 保存当前 Compose 解析结果、镜像摘要、数据库迁移版本、备份编号和文件快照编号。
3. 执行迁移与应用发布。
4. 发布成功后立即执行一次配置与发布清单快照。
5. 将本次备份和发布编号写入发布记录；数据库回退仍必须单独审批，不能由应用回退脚本自动执行。

### 6.3 超级管理员页面控制

系统健康时，在 `/workspace/admin/platform-admin/backups` 提供备份与恢复中心，覆盖状态总览、策略版本、手工备份、备份校验、隔离恢复演练、生产恢复计划和审计记录。详细页面、接口、权限、事实表、状态机和验收要求以主方案第 18.6.1 节为准。

页面控制采用“V3 控制面 + 宿主机受控执行器”结构：

1. V3 API 只校验身份、权限、二次认证、职责分离和结构化参数，并将任务写入运维事实表。
2. 宿主机执行器使用独立账号轮询白名单任务，只能调用已交付的固定备份或恢复脚本；不得接受任意命令或任意脚本路径。策略发布后由执行器校验版本并原子更新受控策略文件，固定短周期的 `systemd timer` 只负责唤醒调度器。
3. API、Worker 容器不得挂载 Docker 控制接口，不得持有对象存储恢复账号或备份加密恢复密钥。
4. 任务执行状态、备份编号、恢复点、校验结果和脱敏错误回写 V3，同时写入异机仓库中的签名清单，避免生产数据库故障后丢失唯一恢复证据。
5. 数据库或整机故障导致页面不可用时，授权人员改用离线恢复脚本；页面恢复后补录任务和审批证据。
6. 生产恢复批准后生成短时一次性签名执行凭证，并同步保存在宿主机受限目录和异机控制证据区；执行器不能只依赖待恢复数据库中的审批记录。

手工备份和隔离恢复可以由具备相应权限的超级管理员在二次认证后执行。生产恢复必须经过恢复计划预检、独立复核和限时批准，申请人、复核人和执行人遵守职责分离；页面不得提供备份文件、完整配置或密钥下载，也不得自动切换生产流量。

## 7. 恢复流程

### 7.1 恢复分级

| 事故 | 首选动作 | 是否恢复数据库 |
| --- | --- | --- |
| 单个 API、Worker 或 Nginx 容器故障 | 重启或回退应用镜像，执行健康检查 | 否 |
| 上传或导出文件误删 | 从最近文件快照恢复到隔离目录，校验后回填 | 否 |
| 业务数据误删、错误迁移或逻辑损坏 | 在隔离 PostgreSQL 恢复到指定时间点，核对后按批准方案切换 | 是，时间点恢复 |
| 主机或磁盘损坏 | 新服务器重建运行环境，恢复配置、文件和最近数据库备份 | 是 |
| Redis 丢失 | 重启 Redis，用户重新登录，按 PostgreSQL 任务事实补投 | 否，默认不恢复 |

### 7.2 整机重建顺序

1. 准备已加固的新服务器，安装经校验的 Docker、Docker Compose 和 V3 离线运行时。
2. 从受控仓库恢复指定版本的 Compose、脚本、发布清单、配置和密钥恢复材料，核对镜像摘要。
3. 加载对应 V3 镜像，先只启动 PostgreSQL 与必要维护容器。
4. 按最近可用备份或指定时间点恢复 PostgreSQL，执行数据库完整性、迁移版本、核心数量和抽样业务校验。
5. 恢复上传、导出和迁移材料到隔离目录；校验文件摘要、对象数量和数据库附件元数据，再切换到正式挂载目录。
6. 启动 Redis、API、Worker、Nginx；Redis 不能恢复时执行任务补投，不伪造旧会话。
7. 执行健康检查、登录、权限、核心业务、任务积压和附件下载冒烟。
8. 经业务与运维负责人批准后，才切换域名或入口流量；记录恢复点、恢复时长、数据损失范围和遗留项。

### 7.3 时间点恢复原则

1. 先冻结相关写入或将生产切至维护模式，保存事故发生时间、请求编号、操作者和影响对象。
2. 首先恢复到隔离数据库，目标时间取事故前最后确认无误的时间点。
3. 对比关键数量、金额、审批状态、任务事实、发件箱事件和附件引用；禁止只凭数据库启动成功即切换。
4. 数据库恢复后，消息和企微流程必须依据幂等键、外部流程绑定和投递记录去重，不得重新创建已成功的外部动作。
5. 只有获得业务负责人和运维负责人对恢复范围的书面确认，才可切换恢复后的数据库。

## 8. 校验、演练与告警

### 8.1 自动校验

| 校验项 | 频率 | 失败处理 |
| --- | --- | --- |
| 最近 WAL 归档时间不超过 5 分钟 | 持续监控 | 一级告警，立即检查数据库与对象存储链路。 |
| 最近数据库备份成功 | 每小时检查 | 超过 26 小时未出现成功全量或差异备份时二级告警。 |
| `pgBackRest` 仓库校验 | 每日 | 阻断下一次数据库结构变更。 |
| `restic` 快照与仓库校验 | 每日快照、每周完整校验 | 失败告警并保留最近成功快照，不自动清理。 |
| 配置与发布清单快照 | 每次发布后 | 缺失时发布验收不通过。 |
| 存储容量与不可变保留状态 | 每日 | 容量不足或保留策略失效时一级告警。 |

### 8.2 恢复演练

| 演练 | 频率 | 通过标准 |
| --- | --- | --- |
| PostgreSQL 最近备份恢复到隔离环境 | 每周 | 数据库可启动；迁移版本、约束、数量和抽样业务校验通过。 |
| 指定时间点恢复 | 每月 | 恢复至选定时间点，恢复点误差不超过 5 分钟。 |
| 文件、配置与密钥恢复 | 每月 | 文件摘要和对象数量一致；新服务器可读取配置但不泄露密钥。 |
| 单机整机重建 | 每季度 | 在目标恢复时间内完成启动、健康检查和核心业务冒烟。 |
| 备份仓库访问失效 | 每季度 | 告警及时触发，恢复账号与双人保管流程有效。 |

演练只能在隔离环境执行。演练报告至少包含：执行人、备份编号、恢复点、开始与结束时间、恢复命令版本、校验结果、失败项、修复负责人和证据位置。

## 9. 验收门禁

以下条件全部满足，才能将本方案标记为“已上线”：

1. PostgreSQL 的全量、差异、增量和 WAL 归档均已写入异机仓库，且最近恢复点不超过 5 分钟。
2. 上传文件、未过期导出、迁移材料、完整运行配置、密钥恢复材料和发布清单均已加密备份。
3. 数据库仓库与文件配置仓库的凭据、桶或前缀和删除权限相互隔离。
4. `systemd timer` 已启用，重启服务器后仍能自动恢复调度；备份失败、归档延迟、容量不足和校验失败均能告警。
5. 最近一次周度隔离恢复和月度文件配置恢复均有可复核报告。
6. 至少完成一次新服务器整机重建演练，且恢复前后主业务、权限、任务和附件校验通过。
7. 发布清单能追溯任一次生产发布对应的镜像摘要、数据库备份编号、文件快照编号和迁移版本。

## 10. 实施前需确认的生产决策

| 决策 | 推荐值 | 确认责任 |
| --- | --- | --- |
| 对象存储 | 企业内部 S3 兼容对象存储，数据库和文件配置分仓库 | 运维负责人 |
| 备份保留 | 数据库 4 个周全量链路；文件配置 30 日、12 周、12 月 | 运维与业务负责人 |
| 不可变保留 | 至少 14 天 | 安全负责人 |

| 整机恢复目标 | 30 分钟；无预置备用机时需书面接受例外 | 业务与运维负责人 |
| 备份加密密钥保管 | 两名不同角色的授权人员共同保管 | 安全负责人 |

## 11. 功能范围与角色边界

### 11.1 功能范围

本功能以“备份可见、任务可控、恢复可审、灾难可离线执行”为目标，首期完整范围如下：

1. 展示 PostgreSQL 恢复点、备份链、WAL 归档延迟、文件快照、对象存储容量和最近恢复演练。
2. 版本化管理数据库、文件、配置、校验、保留和演练策略。
3. 手工发起数据库备份、文件配置快照、备份校验和隔离恢复演练。
4. 创建、预检、提交、复核和执行生产恢复计划。
5. 记录宿主机执行器心跳、版本、任务进度、脱敏日志摘要和外部证据编号。
6. 对备份失败、WAL 延迟、容量不足、校验失败、执行器离线和演练超期告警。
7. 在 V3 控制面不可用时，通过离线脚本和异机证据完成整机恢复，恢复后回填审计。

首期不包含：浏览器下载数据库备份、浏览器查看完整配置或密钥、任意 Shell 命令、跨生产环境复制数据、自动切换域名、自动开放流量、移动端控制、渠道端控制，以及未经隔离验证直接覆盖生产数据库。

### 11.2 角色与职责分离

| 角色 | 职责 | 禁止事项 |
| --- | --- | --- |
| 备份查看人 | 查看状态、记录、报告和告警 | 不得发起或修改任何任务 |
| 备份操作人 | 手工备份、校验和隔离演练 | 不得执行生产恢复 |
| 备份策略管理员 | 保存、校验和发布策略版本 | 不得绕过版本发布直接改宿主机定时任务 |
| 恢复申请人 | 创建恢复计划、选择恢复点和提交审批 | 不得审批或执行自己的计划 |
| 恢复复核人 | 复核影响、目标、恢复点和预检报告 | 不得审批自己申请的计划 |
| 恢复执行人 | 执行已批准且未过期的恢复计划 | 不得修改已批准参数或跳过维护模式 |
| 审计查看人 | 查看操作、审批、任务和外部证据 | 不得查看密钥和备份内容 |

超级管理员身份不自动拥有全部动作权限。生产环境至少由两名不同账号完成“申请与复核”，执行权限建议再分配给运维值守账号；确需两人模式时，申请人和复核人仍必须分离，执行人可以是复核人，但必须再次认证并记录执行原因。

共享请求和响应类型由 `packages/contracts` 生成或导出，前端不得自行复制状态码、任务状态和权限代码。页面状态以接口事实为准，不根据按钮点击结果提前假设任务成功。

### 12.2 页面状态管理

1. 首屏并行加载总览、当前已发布策略和最近任务，单个区块失败不抹掉其他已成功数据。
2. 首期使用页面组合式函数管理状态，不为单页面新增全局状态库；只有跨页面通知或审批中心复用时才进入共享状态。
3. 对 `requested`、`running`、`verifying`、`executing` 状态按 5 秒间隔轮询；页面进入后台后降为 30 秒，任务结束后停止轮询。
4. 每次刷新取消前一请求，防止旧响应覆盖新状态；离开页面时清理轮询和请求。
5. 所有写请求生成 `Idempotency-Key`。网络超时后先查询原任务，不自动重复提交。
6. 页面只保存筛选条件和未提交的普通表单草稿，不保存二次认证凭据、审批凭据、备份编号之外的仓库引用或敏感错误详情。

### 12.3 前端权限守卫

| 页面或动作 | 前端要求 | 服务端要求 |
| --- | --- | --- |
| 进入页面 | 路由元信息要求 `system.backup.read` | 每个查询接口再次校验权限 |
| 修改策略 | 无权限时不渲染编辑控件 | 校验 `system.backup.policy.update` |
| 手工备份 | 显示权限、执行器在线且系统未在恢复中 | 校验 `system.backup.run`、二次认证和并发锁 |
| 校验备份 | 仅对可校验的成功备份显示 | 校验 `system.backup.verify` 和备份归属 |
| 创建恢复计划 | 仅允许选择服务端返回的恢复点和目标 | 校验 `system.restore.plan` |
| 审批 | 申请人不显示审批按钮 | 服务端强制职责分离和审批有效期 |
| 执行生产恢复 | 仅对已批准且预检未过期的计划显示 | 校验 `system.restore.execute`、维护模式和一次性凭证 |

前端隐藏按钮只改善体验，不构成安全控制。直接调用接口、篡改权限状态、修改恢复点或重放旧审批请求均由服务端拒绝。

### 12.4 错误处理

| 错误码 | 页面处理 |
| --- | --- |
| `SYSTEM_BACKUP_DISABLED` | 显示功能未启用状态，不展示操作按钮 |
| `SYSTEM_BACKUP_AGENT_OFFLINE` | 顶部显示红色状态条，禁止新任务，保留查询 |
| `SYSTEM_BACKUP_CONFLICT` | 提示已有互斥任务并跳转对应任务详情 |
| `SYSTEM_BACKUP_POLICY_STALE` | 提示策略已被他人更新，重新加载后再编辑 |
| `SYSTEM_BACKUP_REAUTH_REQUIRED` | 打开二次认证对话框，认证后重新发起原动作 |
| `SYSTEM_RESTORE_SELF_APPROVAL` | 明确提示申请人不能审批自己的恢复计划 |
| `SYSTEM_RESTORE_APPROVAL_EXPIRED` | 标记审批过期，要求重新预检和审批 |
| `SYSTEM_RESTORE_PRECHECK_CHANGED` | 展示变化项，禁止沿用旧批准结果 |
| `SYSTEM_RESTORE_MAINTENANCE_REQUIRED` | 禁止执行，显示当前维护模式状态 |
| `SYSTEM_BACKUP_SENSITIVE_DENIED` | 不回显敏感原因，只显示请求编号供审计查询 |

- 使用页内表单，不使用多层卡片。按数据库、文件配置、保留校验和恢复演练四个分组展示。

#### 备份记录

- 筛选项包括时间范围、备份范围、备份类型、触发来源、状态和校验结果。

- 失败任务允许在原因仍可恢复且无同类任务运行时重新发起；“重试”生成新任务并关联原任务，不修改原记录。

#### 恢复计划

- 列表展示计划编号、恢复范围、目标环境、恢复点、申请人、复核人、状态、审批有效期和操作。
- 新建恢复计划使用四步模态向导：选择恢复范围、选择服务端候选恢复点、选择已登记目标环境、执行预检并提交。
- 生产目标始终显示红色影响区域，列出预计停机、可能丢失的数据区间、外部消息去重和附件校验范围。
- 审批对话框展示不可编辑的参数摘要、预检报告和申请原因；执行对话框再次显示摘要，要求二次认证并输入计划编号确认。

#### 演练记录

- 展示演练类型、隔离环境、使用备份、目标恢复点、恢复耗时、校验项、结论和整改状态。
- 报告详情使用抽屉展示数据库约束、数量抽样、附件摘要、登录权限、任务补投和业务冒烟结果。
- 失败演练必须登记整改责任人和期限；未关闭阻断问题前，生产恢复执行入口保持关闭。

1. 本模块首期仅支持桌面端，不注册移动端路由，不在四套移动页面提供危险操作。

4. 模态框打开后锁定焦点，关闭后焦点返回触发按钮；异步进度使用可读状态文本，不反复抢占屏幕阅读器。
5. 时间同时显示绝对时间和时区；容量统一以可读单位显示，详情保留精确字节数。

## 14. 后端工程方案

### 14.1 模块边界

备份控制面使用独立模块，不继续扩展 `business-store.ts` 和 `business-routes.ts`：

```text
apps/api/src/system-backup/
├── routes.ts              # /api/platform 下的备份恢复接口
├── service.ts             # 权限、状态机、幂等和事务编排

├── reauth.ts              # 二次认证状态检查
├── execution-ticket.ts    # 一次性执行凭证摘要和签名校验边界
└── errors.ts              # 稳定中文错误码
```

`create-app.ts` 在 `/api/platform` 下挂载独立路由。共享契约进入 `packages/contracts`，配置项进入 `packages/config`；既有 V2 兼容路由、业务路由和正式四页面接口不读取新表，也不因备份模块关闭而失败。

### 14.2 请求处理顺序

所有写操作按以下固定顺序执行：

1. 读取当前 HttpOnly Cookie 会话并确认账号仍有效。
2. 从正式权限表计算动作权限，禁止仅根据用户名或角色字符串判断超管。
3. 校验来源、二次认证时间、请求频率和 `Idempotency-Key`。
4. 使用 Zod 校验结构化参数，并将目标环境、备份编号和恢复点解析为服务端正式记录。
5. 在数据库事务中锁定策略或恢复计划，校验行版本、状态机、职责分离和互斥任务。
6. 写任务事实、审批事件、审计日志和发件箱事件；事务提交后由宿主机执行器认领。
7. 返回 `202` 和任务编号，不等待备份或恢复在 HTTP 请求内完成。

查询接口必须分页、限定最大页大小并使用索引；脱敏错误详情只有 `system.restore.audit.read` 权限可见。接口响应继续使用 V3 统一成功/错误信封，包含 `requestId` 和构建信息。

### 14.3 二次认证

新增 `POST /api/auth/reauth`，要求当前用户再次提交受支持的认证因子。验证成功后只在服务端会话中写入 `reauth_at`、认证方式和认证强度，不向浏览器返回可长期保存的高权限令牌。

| 动作 | 二次认证有效期 |
| --- | ---: |
| 手工备份、校验 | 15 分钟 |
| 发布备份策略、隔离恢复演练 | 10 分钟 |
| 提交或审批生产恢复 | 5 分钟 |
| 执行生产恢复 | 必须当次重新认证 |

账号密码重置、角色变化、会话撤销、来源地址显著变化或风险事件发生后，已有二次认证状态立即失效。

### 14.4 任务与并发

备份和恢复任务事实存放在 PostgreSQL，不使用 Redis 作为唯一队列。宿主机执行器通过 `FOR UPDATE SKIP LOCKED` 或等价存储过程认领 `ops.system_maintenance_tasks`；Redis 清空不影响已提交任务。

互斥规则：

- 同一时刻只允许一个生产恢复任务。
- 生产恢复与所有备份、校验和演练互斥。
- PostgreSQL 全量、差异和增量备份互斥；持续 WAL 归档不受影响。
- 文件快照可与数据库备份并行，但同一文件范围只允许一个任务。
- 仓库完整校验与保留清理互斥；清理失败不得删除最近成功链路。
- 取消只对 `requested` 或执行器明确声明可取消的阶段开放。

### 14.5 审计与外部证据

每次读取敏感恢复详情、策略发布、手工备份、校验、预检、审批、执行、终止和证据回填都写入 `audit.audit_logs`。审计包含请求编号、用户、角色、权限、来源地址、对象、动作、结果、原因、参数摘要和前后状态，不包含备份内容、口令、访问密钥和恢复密钥。

生产恢复批准后生成一次性签名执行凭证。凭证只保存计划编号、备份编号、恢复点、目标环境、参数摘要、审批人、有效期和随机编号，并同步到宿主机受限目录及异机不可变证据区。恢复到旧时间点导致 V3 中审批事实消失时，执行器依靠该凭证继续完成已批准任务，恢复后再将外部执行日志回填。

## 16. 数据库设计

### 16.1 设计原则

1. 新表进入现有 `ops` 逻辑域，权限继续使用 `iam.permissions`，审计继续写 `audit.audit_logs`，不新增平行账号或审计体系。
2. 任务、备份、审批和恢复记录只追加或状态迁移，不物理删除；保留策略删除的是外部制品，数据库保留最小历史与删除证据。
3. 数据库只保存仓库别名、外部引用和摘要，不保存对象存储密钥、备份加密密钥、数据库口令、完整配置或恢复凭证明文。
4. 金额以外的容量使用 `bigint` 字节数；时间全部使用 `timestamptz`；状态使用稳定英文代码和数据库检查约束。
5. 所有可并发修改的策略和恢复计划使用 `row_version`；所有写接口使用现有 `ops.idempotency_keys`。

### 16.2 `ops.system_backup_policies`

| 字段 | 类型 | 约束与用途 |
| --- | --- | --- |
| `id` | `uuid` | 主键 |
| `policy_code` | `text` | 稳定策略编号 |
| `scope_code` | `text` | `database`、`files`、`config`、`verification`、`drill` |
| `version_no` | `integer` | 同一策略递增版本 |
| `status_code` | `text` | `draft`、`published`、`retired` |
| `schedule_json` | `jsonb` | 已校验的周期、时间和时区，不允许命令或路径 |
| `retention_json` | `jsonb` | 全量、差异、快照和不可变保留参数 |
| `settings_json` | `jsonb` | 仓库别名、校验级别和演练模板等非敏感设置 |
| `row_version` | `integer` | 乐观锁，从 1 递增 |
| `created_by_user_id` | `uuid` | 创建人，关联 `iam.users` |
| `published_by_user_id` | `uuid` | 发布人，可空 |
| `created_at`、`published_at` | `timestamptz` | 创建与发布时间 |

唯一约束为 `(policy_code, version_no)`；每个 `policy_code` 只允许一个 `published` 版本，使用部分唯一索引保证。

| 字段 | 类型 | 约束与用途 |

| `policy_id` | `uuid` | 关联实际执行的策略版本，可空表示人工兜底 |
| `scope_code` | `text` | `database`、`files`、`config`、`all` |
| `backup_type_code` | `text` | `full`、`diff`、`incr`、`snapshot`、`verify` |
| `trigger_code` | `text` | `schedule`、`manual`、`pre_release`、`drill` |
| `status_code` | `text` | 备份任务状态机 |
| `requested_by_user_id` | `uuid` | 定时任务可空，人工任务必填 |
| `agent_id` | `uuid` | 实际执行器 |
| `progress_percent` | `numeric(5,2)` | 0 至 100 |
| `recovery_point_at` | `timestamptz` | 可恢复时间点 |
| `recovery_lsn` | `pg_lsn` | PostgreSQL 恢复位置，可空 |
| `total_size_bytes` | `bigint` | 非负 |
| `error_code`、`error_summary` | `text` | 稳定错误码和脱敏摘要 |
| `summary_json` | `jsonb` | 数量、阶段耗时和校验摘要 |
| `created_at`、`started_at`、`finished_at` | `timestamptz` | 生命周期时间 |

索引覆盖 `(status_code, created_at)`、`(scope_code, created_at)`、`recovery_point_at` 和 `agent_id`。运行中互斥由事务锁和部分唯一索引共同保证。

### 16.4 `ops.system_backup_artifacts`

| 字段 | 类型 | 约束与用途 |
| --- | --- | --- |
| `id` | `uuid` | 主键 |
| `backup_run_id` | `uuid` | 关联备份任务，禁止级联删除 |
| `artifact_type_code` | `text` | `pgbackrest_set`、`wal_range`、`restic_snapshot`、`release_manifest`、`evidence` |
| `repository_code` | `text` | 仓库别名，不是真实凭据 |
| `external_ref` | `text` | 外部备份编号或快照编号 |

| `size_bytes` | `bigint` | 非负 |
| `verify_status_code` | `text` | `pending`、`passed`、`failed`、`expired` |
| `verified_at` | `timestamptz` | 最近校验时间 |
| `immutable_until`、`expires_at` | `timestamptz` | 不可变和保留到期时间 |
| `metadata_json` | `jsonb` | 非敏感版本、范围和数量摘要 |

`(repository_code, external_ref)` 唯一。到期清理完成后保留记录，将校验状态改为 `expired` 并写删除事件。

### 16.5 `ops.system_restore_plans`

| 字段 | 类型 | 约束与用途 |
| --- | --- | --- |
| `id`、`plan_no` | `uuid`、`text` | 主键和唯一计划编号 |
| `restore_scope_code` | `text` | `database`、`files`、`config`、`system` |
| `target_type_code` | `text` | `isolated`、`production` |
| `target_code` | `text` | 预登记目标别名 |
| `backup_run_id` | `uuid` | 主要数据库备份链 |
| `restore_point_at` | `timestamptz` | 目标恢复点 |
| `file_snapshot_ref` | `text` | 文件快照编号，可空 |
| `status_code` | `text` | 恢复计划状态机 |
| `reason`、`impact_summary` | `text` | 申请原因和影响评估 |
| `parameter_hash` | `text` | 预检、审批和执行参数一致性 |
| `precheck_status_code` | `text` | `pending`、`passed`、`failed`、`expired` |
| `precheck_json` | `jsonb` | 容量、链路、版本、附件和外部任务摘要 |
| `precheck_expires_at` | `timestamptz` | 预检有效期 |
| `row_version` | `integer` | 乐观锁 |
| `requested_by_user_id` | `uuid` | 申请人 |
| `created_at`、`updated_at` | `timestamptz` | 生命周期时间 |

生产计划的恢复点、目标、范围或文件快照变化后，必须清空原预检与审批并回到 `draft`。

恢复计划的 `target_code` 只能引用 `ops.system_restore_targets`。该表由部署或运维审批流程预登记，保存目标编号、目标类型、环境代码、主机别名、容量摘要、支持的恢复能力、状态、配置引用和最后校验时间；不保存主机登录口令、对象存储密钥或数据库连接凭据。生产目标不能由超管页面临时新建，目标地址变化必须走生产配置变更并重新校验。

### 16.6 审批、恢复运行和任务表

`ops.system_restore_approvals` 保存 `plan_id`、审批阶段、审批人、决定、意见、参数哈希、审批时间和有效期；唯一约束防止同一人在同一阶段重复有效审批。服务端和数据库触发器共同拒绝申请人批准自己的生产恢复计划。

`ops.system_restore_runs` 保存执行编号、计划、执行器、状态、阶段、进度、开始结束时间、外部签名凭证随机编号、恢复结果摘要、校验摘要、流量切换确认人和外部证据引用。生产恢复记录不得因计划删除而级联删除。

`ops.system_maintenance_tasks` 保存任务类型、目标事实编号、幂等编号、参数摘要、优先级、状态、可执行时间、认领执行器、租约到期时间、重试次数、脱敏错误和外部日志编号。只允许 `backup`、`verify`、`policy_sync`、`restore_precheck`、`restore_isolated`、`restore_production`、`restore_abort`、`evidence_reconcile` 白名单任务类型。

`ops.system_maintenance_agents` 保存执行器编号、主机别名、版本、能力列表、状态、当前任务、最后心跳、最后成功任务和证书指纹摘要。超过两个轮询周期无心跳标记为 `offline`，但历史任务仍保留原执行器引用。

### 16.7 状态事件

为备份任务和恢复计划分别新增只追加事件表 `ops.system_backup_run_events`、`ops.system_restore_plan_events`，记录事实编号、事件代码、前后状态、操作者、执行器、发生时间、原因、请求编号和脱敏扩展信息。列表页读主表当前状态，详情时间线读事件表，禁止从普通日志推算业务状态。

### 16.8 迁移与回退

迁移只新增表、索引、权限和状态约束，不修改现有业务表。上线前在同版本 PostgreSQL 16.4 执行空库、已有生产结构副本和回滚预演。功能尚未启用且没有任务事实时允许执行回滚脚本删除新增对象；一旦产生生产备份、审批或恢复事实，数据库对象不再物理回滚，只关闭功能开关并保留审计。

## 17. 宿主机执行器设计

### 17.1 运行形态

宿主机执行器位于 `deploy/single-server`，由 `systemd` 固定短周期唤醒，不开放网络监听端口，不通过 API 容器控制 Docker，也不依赖 BullMQ。

```text
deploy/single-server/
├── config/
│   └── backup-policy.env.example
├── scripts/
│   ├── backup-controller.sh
│   ├── backup-db.sh
│   ├── backup-files.sh
│   ├── verify-backup.sh
│   ├── restore-db.sh
│   ├── restore-system.sh
│   ├── reconcile-backup-evidence.sh
│   └── backup-status.sh
└── systemd/
    ├── lianruan-backup-controller.service
    └── lianruan-backup-controller.timer
```

执行脚本由 `root` 拥有且普通账号不可写。服务使用专用账号和最小文件权限；确需调用 Docker 的固定包装命令由受限提权规则执行。不得把专用账号直接加入可执行任意 Docker 命令的用户组。

### 17.2 调度与任务认领

1. 定时器每分钟唤醒一次控制器。
2. 控制器先读取已签名的本机策略文件，计算到期的定时备份；即使 API 临时不可用，已发布周期备份仍能继续。
3. 数据库可用时，通过固定存储过程认领一条白名单人工或恢复任务，使用租约避免重复执行。
4. 参数以固定列和枚举传递，不拼接任意命令；所有路径由安装根目录和服务端登记目标映射生成。
5. 每个阶段更新本地执行日志和异机证据；数据库可用时同步进度，数据库不可用时待恢复后补录。
6. 控制器退出前释放或续期租约；进程异常后，只有租约到期且外部证据确认未完成的任务才允许重新认领。

### 17.3 策略同步

页面发布策略只生成 `policy_sync` 任务。执行器校验策略版本、字段白名单、时间范围、保留下限和签名后，先写临时文件、设置权限、重新读取校验，再原子替换正式策略。失败时保留上一发布版本并回写失败原因；页面不能直接修改 `crontab`、`systemd` 文件或 Shell 脚本。

### 17.4 恢复执行安全

生产恢复开始前必须同时满足：执行凭证有效且未消费、参数哈希一致、目标是预登记生产主机、维护模式生效、最近隔离恢复通过、对象存储可读、目标磁盘容量足够、当前无互斥任务、外部流程和消息去重预案已确认。

执行器先保存当前环境清单和事故证据，再停止写流量与任务消费者，恢复数据库和文件，启动只读检查，执行自动校验。任何步骤失败均停留在维护模式，不自动切回旧库、不自动开放流量，并输出明确人工处理点。

## 18. 安全设计

### 18.1 密钥与凭据

- PostgreSQL 备份仓库、文件仓库、恢复账号和签名密钥使用不同凭据。
- 应用 API 只知道仓库别名和状态，不持有恢复账号、`restic` 仓库口令或对象存储删除权限。
- 凭据文件权限不高于 `600`，父目录不高于 `700`；配置备份进入 `restic` 加密仓库，恢复密钥离线双人保管。
- 页面、接口、审计、任务参数、错误、诊断包和通知中不得出现密钥或完整连接串。
- 对象存储启用版本、不可变保留和独立恢复账号，生产写入账号不得修改桶级保留策略。

### 18.2 Web 安全

- 复用当前 HttpOnly Cookie 会话，写接口校验来源和跨站请求防护；不接受 URL 中的凭据或操作令牌。
- 对策略发布、备份、校验、审批和执行分别限频；连续二次认证失败触发安全审计和会话风险处置。
- 生产恢复参数由服务端候选集合产生，防止路径穿越、服务器端请求伪造和任意命令注入。
- 恢复任务详情按字段脱敏；备份制品没有浏览器下载接口。
- 内容安全策略沿用 V3，不新增内联脚本、远程脚本或第三方管理页面嵌入。

### 18.3 供应链与离线部署

`pgBackRest`、`restic` 和新增 PostgreSQL 镜像必须锁定版本、保存来源、许可证、摘要和漏洞扫描结果。离线包包含二进制或镜像及 SHA-256 清单，目标服务器不在安装时联网下载。升级前验证工具版本与备份仓库格式兼容，禁止在生产容器内临时安装依赖。

## 19. 可观测性与告警

### 19.1 指标

| 指标 | 告警基线 |
| --- | --- |
| 最后成功 WAL 归档时间 | 超过 5 分钟一级告警 |
| 最后成功数据库备份时间 | 超过 26 小时二级告警 |
| 最后成功文件快照时间 | 超过 2 小时二级告警 |
| 仓库可用容量 | 低于 20% 二级、低于 10% 一级 |
| 执行器最后心跳 | 超过 3 分钟一级告警 |
| 最近仓库校验 | 超过 8 天二级告警 |
| 最近隔离恢复演练 | 超过 8 天二级告警 |
| 最近整机恢复演练 | 超过 100 天二级告警 |
| 失败任务数 | 任一生产恢复失败立即一级告警；普通备份连续两次失败一级告警 |

指标至少包含任务编号、仓库别名、主机别名和环境，不包含客户数据、路径、密钥和配置正文。告警进入统一消息平台时只发送影响、状态、请求编号和处置入口。

### 19.2 日志与报告

API、执行器和备份工具日志使用同一任务编号关联。执行器本地日志按大小轮转，异机仅保存脱敏执行报告和签名清单；`pgBackRest` 与 `restic` 原始日志限制为运维账号读取。页面展示阶段摘要，不直接展示原始命令输出。

## 20. 测试方案

### 20.1 前端测试

- 单元测试覆盖权限按钮、状态映射、轮询停止、幂等重试、审批过期、申请人不可审批和敏感字段不渲染。
- 接口模拟覆盖加载、空、部分失败、执行器离线、冲突、长任务、审批变化和恢复执行中状态。
- Playwright 覆盖 1440、1280、1024 像素桌面视口，检查无文本溢出、无控件重叠、表格可用、模态焦点正确和危险操作不可误触。
- 端到端覆盖手工备份、策略发布、隔离演练、恢复申请、他人审批、二次认证和执行监控。

### 20.2 后端与数据库测试

- 每个接口覆盖未登录、无权限、二次认证失效、参数错误、目标越权、状态冲突、幂等重放和并发提交。
- 状态机覆盖所有允许和拒绝迁移；申请人自审、审批过期、参数哈希变化和重复消费凭证必须失败。
- 事务测试验证任务、审批、审计和发件箱要么同时成功，要么同时回滚。
- 数据库迁移在空库、已有 V3 结构和大数据量副本上执行；验证约束、部分唯一索引、查询计划和回滚门禁。
- 执行器认领测试覆盖并发认领、租约过期、进程终止、数据库断开、Redis 清空和证据补录。

### 20.3 备份恢复集成测试

- 使用隔离 PostgreSQL 16.4 和测试 S3 兼容仓库验证全量、差异、增量、WAL、文件快照、保留清理和仓库校验。
- 在持续写入下执行备份，恢复后核对事务一致性、约束、业务数量、审计、任务事实和附件引用。
- 模拟删除业务记录，恢复到删除前时间点；误差不超过 5 分钟且不重复发送外部消息。
- 模拟数据库目录损坏、对象存储短时失败、磁盘不足、执行器重启、签名凭证篡改和旧审批重放。
- 新服务器整机恢复必须从离线包开始，不复用原服务器 Docker 层、环境目录和会话。

### 20.4 性能与稳定性

| 项目 | 验收值 |
| --- | --- |
| 备份总览接口 | 第 95 百分位不超过 500 毫秒 |
| 备份记录分页接口 | 第 95 百分位不超过 800 毫秒 |
| 页面首个可操作状态 | 内网第 75 百分位不超过 2 秒 |
| 备份期间常用 API 延迟增幅 | 不超过基线 20% |
| 连续运行 | 7 天无重复任务、无失联任务、无未解释的恢复点超标 |
| 恢复点 | 不超过 5 分钟 |
| 整机恢复 | 目标 30 分钟；无备用机时形成书面例外 |

## 21. 实施顺序与任务拆分

### 阶段 A：生产决策与备份引擎

确认对象存储、保留期、不可变策略、恢复目标、责任人和演练窗口；构建固定版本 PostgreSQL 备份镜像，落地 `pgBackRest`、`restic`、WAL 归档和离线脚本。先完成命令行备份与隔离恢复闭环，再开放任何页面入口。

退出条件：数据库和文件可异机备份，隔离恢复成功，密钥和仓库权限通过评审。

### 阶段 B：数据库事实与宿主机执行器

新增 `ops` 表、权限、事件和迁移；实现策略同步、定时调度、任务认领、租约、外部证据和状态回填。

退出条件：定时备份不依赖页面或 Redis，重复认领和进程重启不产生重复制品。

### 阶段 C：后端控制面

实现独立路由、契约、权限、二次认证、幂等、状态机、审批、审计和告警事件。生产恢复执行开关保持关闭。

退出条件：接口、数据库、并发和安全测试全部通过，可完整控制手工备份、校验和隔离演练。

### 阶段 D：前端与 UI

实现工程化工作区路由、超管入口、总览、策略、记录、恢复计划和演练页面，完成当前 V3 视觉一致性、响应式、可访问性和端到端测试。

退出条件：所有页面只显示真实接口数据，权限与服务端一致，危险动作没有绕过路径。

### 阶段 E：生产恢复与整机演练

实现一次性执行凭证、生产恢复执行、维护模式、外部证据回填和流量切换门禁；在新服务器完成整机恢复演练。

退出条件：业务、测试、安全和运维共同签署，才允许开启 `SYSTEM_RESTORE_EXECUTION_ENABLED`。

## 22. 功能开关、发布与回退

建议配置：

| 配置 | 默认值 | 作用 |
| --- | --- | --- |
| `SYSTEM_BACKUP_CONTROL_ENABLED` | `false` | 控制页面和控制面接口 |
| `SYSTEM_BACKUP_SCHEDULER_ENABLED` | `false` | 控制定时备份任务生成 |
| `SYSTEM_RESTORE_DRILL_ENABLED` | `false` | 控制隔离恢复演练 |
| `SYSTEM_RESTORE_EXECUTION_ENABLED` | `false` | 控制生产恢复执行，最后开启 |

发布顺序为备份仓库与密钥、备份镜像、宿主机脚本和定时器、数据库迁移、API、前端入口、隔离演练、生产恢复开关。任何阶段失败先关闭对应开关，不删除已产生的备份、任务、审批、审计或外部证据。

应用回退可以回退前端、API 和执行器版本，但必须保持对已创建任务与事件版本的兼容。数据库迁移产生生产事实后不删除新表；WAL 归档和已验证备份链不得因应用回退停止。生产恢复失败时保持维护模式和事故现场，不自动恢复旧数据目录，不使用未经批准的备份覆盖。

## 23. 完成定义

本功能只有同时满足以下条件才算完成：

1. 前端、后端、共享契约、数据库迁移、宿主机执行器、离线恢复脚本和文档均已进入 V3 正式交付包。
2. 超管页面与 V3 当前布局、色彩、组件密度、表格和模态框一致，桌面目标视口无重叠和溢出。
3. 页面可查看真实恢复点，执行手工备份、校验和隔离演练；生产恢复经过二次认证、独立复核和一次性凭证。
4. API 不持有 Docker 控制权限和恢复密钥，浏览器不能下载备份或完整配置。
5. PostgreSQL 恢复点不超过 5 分钟，备份和文件快照位于异机不可变仓库。
6. 新服务器整机恢复、附件一致性、权限抽样、任务补投、消息去重和核心业务冒烟全部通过。
7. 备份失败、执行器离线、容量不足、校验失败和演练超期均可观测并实际触发过告警。
8. 生产开关、发布记录、备份编号、文件快照、镜像摘要、迁移版本和恢复证据可相互追溯。
