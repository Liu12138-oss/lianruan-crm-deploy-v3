# 组织架构与账号管理整合落地方案

> 版本：v1.3
> 日期：2026-08-27
> 状态：四项反馈及发布/回退门禁已完成本地实现、自动化和真实浏览器验收；待真实 PostgreSQL 任务测试、测试环境部署、制包回退演练与真实账号验收；尚未部署或开启
> 适用范围：V3 管理端、V3 API、组织架构、账号管理、渠道商员工、企业管理员、角色权限和证书
> 不在本次范围：渠道端页面改版、单点登录协议改造、统一入口改造、移动端新功能、客户/报备/商机/报价/订单规则改造

## 1. 结论

本次采用“前端入口整合、后端领域分层”，不采用“账号数据并入组织表”。

1. 管理端日常账号操作并入“组织与账号”入口，取消独立“账号管理”日常菜单。
2. `iam.users`、密码凭据、外部身份、角色、权限、数据范围和会话仍属于身份权限域，不迁入 `org` 数据表。
3. 内部人员在组织架构中完成账号、部门、岗位和唯一有效任职维护；当前不支持一人多任职或跨部门任职，调岗直接调整原任职。
4. “企业管理员”保留为渠道成员职责，不再发展成独立主数据或第二套账号体系。
5. 组织架构、渠道商员工和企业管理员三个入口共用一份渠道成员档案；姓名、电话、邮箱、销售/技术业务角色和多份证书任一处修改后，其余入口刷新同步。
6. 企业管理员身份、系统权限、审批状态、账号状态、登录账号和 IAM/UniSDP 外部身份独立保存，不由统一成员档案编辑改变。
7. 实施期不改单点登录、登录响应、统一入口、角色编码和四套正式页面会话。

目标信息架构：

```text
组织与账号
├─ 组织与成员
│  ├─ 部门树
│  ├─ 人员账号概要
│  ├─ 岗位与任职
│  └─ 内部人员入职、调岗和停用
├─ 证书管理
├─ 角色管理
├─ 权限与范围
├─ 离职交接
└─ 企微组织同步
```

## 2. 目标、验收、回退和风险

### 2.1 目标

- 管理员在部门和人员上下文中完成常用账号操作，减少模块往返。
- 账号、组织任职、渠道成员、权限角色保持独立数据语义，降低后续维护成本。
- 渠道商管理页面、区域归属、渠道等级和员工管理保持现有使用方式。
- 渠道商员工和企业管理员继续保留现有入口与操作习惯，仅将共用资料、销售/技术角色和证书收口到同一事务和统一弹窗。
- 任何入口整合都不影响账号密码登录、IAM 单点登录、UniSDP 单点登录和统一入口分流。

### 2.2 验收方式

完成必须同时满足：

1. 超级管理员从“组织与账号”可完成内部账号查询、新建、资料维护、停启用、密码重置、任职和角色管理。
2. 渠道商管理页面的菜单、列表、详情、区域、等级、上下级和成员操作无变化。
3. `superadmin`、`admin`、`region_manager`、`partner_admin`、`staff` 现有角色编码不改名、不删除、不自动转换。
4. 账密登录、IAM 单点登录、UniSDP 接口单点登录、UniSDP 门户单点登录全部通过回归。
5. 管理员桌面端仍进入 `/admin.html`，管理员移动端仍进入 `/admin-mobile.html`，渠道桌面端仍进入 `/partner.html`，渠道移动端仍进入 `/partner-mobile.html`。
6. 旧链接 `#/account-manage` 在兼容期内可用，关闭新入口开关后可立即恢复旧菜单。
7. 无数据库表合并，无账号编号重编，无历史角色或外部身份迁移。
8. 三入口保存同一渠道成员后，姓名、电话、邮箱、销售/技术角色和有效证书一致；企业管理员身份、审批状态、账号状态和系统权限不变。
9. 内部人员仅一条有效任职；重复有效任职阻断迁移和新增，不能自动结束或删除历史任职。
10. 渠道成员“删除”按逻辑归档处理；角色、证书和历史业务保留，多渠道账号仅删除当前关系时保持启用。

### 2.3 回退方式

- 首选回退：关闭“账号入口整合”开关，恢复独立“账号管理”菜单。
- 次选回退：回退 Web/API 镜像到上一版；数据库新增列、固定角色、证书和归档历史保留，不做破坏性删除。
- 兼容回退：保留 `#/account-manage` 和 `#/partner-admin` 路由及组件至少两个正式发布版本，不在首次切换中删除。
- 数据回退：本次不设破坏性迁移；账号停用、角色变更等业务操作按原有审计和恢复流程处理，不通过代码回退撤销业务事实。

### 2.4 主要风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 统一资料修改了单点识别字段 | 渠道手机号改变后，IAM 或 UniSDP 可能无法按原手机号匹配 | 用户名和外部身份保持只读；渠道电话允许受控修改并写入 `iam.users.phone`，保存后必须回归新旧手机号识别、账号唯一匹配和四套页面落点，未通过前不得宣称登录无影响 |
| 普通资料保存夹带角色变更 | 登录落点、页面会话前缀和数据权限突变 | 基本资料与系统角色分开提交，角色变更单独二次确认 |
| 新旧入口并存期双写 | 账号与任职不一致 | 两个入口调用同一组后端服务，不复制数据或双写两套表 |
| 新建账号成功但新建任职失败 | 出现无归属内部账号 | 首期显式提示未归集账号；后续用单事务内部成员编排接口收口 |
| 停用或离职流程绕开交接 | 业务负责人、待办和审批断链 | “账号停用”和“离职交接”区分语义，存在业务引用时引导交接 |
| 隐藏旧菜单后能力不齐 | 管理员无法完成原操作 | 建立能力对照表，全量通过后才隐藏旧入口 |
| 三入口各自保存资料 | 姓名、角色或证书互相覆盖 | 三入口使用统一成员档案接口；旧渠道保存也在同一事务同步固定业务角色 |
| 删除渠道关系误删历史或停错账号 | 证书丢失、多渠道账号无法登录 | 只逻辑归档当前关系；有其他有效关系则保持账号启用并切换兼容渠道 |
| 迁移覆盖既有固定角色 | 正式角色被改名或重新启用 | 发现同编码语义冲突立即阻断，要求人工确认，不静默覆盖 |

## 3. 业务与数据边界

| 数据或动作 | 唯一权威领域 | 组织与账号页面中的呈现 | 是否影响登录或授权 |
| --- | --- | --- | --- |
| 账号、显示名、状态 | `iam.users` | 可查询；显示名可编辑；状态受控变更 | 状态会影响登录 |
| 本地密码 | `iam.password_credentials` | 只提供重置动作，不回显 | 影响账密登录，不改外部身份映射 |
| IAM、UniSDP 或企微外部身份 | `iam.external_identities` 及集成映射 | 只读显示来源和映射状态 | 会影响单点登录，本页不直接修改 |
| 内部部门、岗位、任职 | `org.org_units`、`org.positions`、`org.staff_assignments` | 组织页面维护 | 不直接授予系统权限 |
| 渠道商及渠道成员 | `channel.partners`、`channel.partner_members` | 渠道商主档仍在原页面；成员共用资料、销售/技术角色和证书可从三入口维护 | 渠道成员关系参与渠道身份识别 |
| 企业管理员 | `channel.partner_members.member_role_code` 与权限角色 | 身份与审批仍在原企业管理员流程；共用资料、销售/技术角色和证书走统一成员档案 | 会影响渠道端能力，统一资料保存不得改变该身份 |
| 系统角色和权限 | `iam.roles`、`iam.permissions`、`iam.user_roles`、`iam.role_permissions` | “角色管理”栏目独立维护 | 会影响入口、功能和数据权限 |
| 数据范围 | `iam.data_scope_bindings` | “权限与范围”栏目独立维护 | 接入运行时后影响数据可见性 |

### 3.1 不可混同的三类角色

| 类型 | 例子 | 用途 | 是否直接授权 |
| --- | --- | --- | --- |
| 岗位 | 销售经理、技术工程师 | 表示在组织中做什么 | 否 |
| 业务角色 | 销售、技术（二选一） | 表示承担什么业务职责 | 否 |
| 权限角色 | 超级管理员、区域管理员、受控自定义角色 | 决定能做什么及可见范围 | 是 |

组织页面不得根据部门名、岗位名或业务角色名静默授予权限角色。

### 3.2 历史账号总体处理原则

历史账号不做“从账号管理迁入组织架构”的复制迁移。新旧页面使用同一份账号主档，整合时仅增加组织归属和治理标记，不重建账号。

必须保留：

- `iam.users.id`、`v2_source_id`、`username`、创建时间和现有状态。
- `iam.password_credentials` 中的密码散列、算法和改密标记。
- `iam.external_identities` 中的 IAM、UniSDP 或其他外部主体映射。
- `iam.user_roles` 和已有角色历史。
- `channel.partner_members` 中的渠道成员归属。
- `org.staff_assignments` 中已建立的内部任职。
- `extra_json` 中现存历史字段，在兼容退场完成前不删除、不覆盖为空。
- 账号关联的业务记录、审批、消息、配置和审计日志。

禁止：

- 为了让账号出现在组织树中而新建同名账号。
- 重编历史用户名、替换用户主键或重置全部密码。
- 根据姓名、手机号或邮箱自动合并两个账号。
- 根据历史页面展示的角色名静默新增或删除系统角色。
- 将 `apps/web/public/*-app.js` 中的演示数组、静态兜底或样例账号直接导入生产数据库。

### 3.3 历史账号分类与页面落点

| 分类 | 判定条件 | 整合后处理 |
| --- | --- | --- |
| 有效内部人员 | 账号有有效 `org.staff_assignments` | 按唯一有效任职显示在组织树；调岗调整原任职 |
| 未归集内部管理账号 | 具有管理端角色，但无有效内部任职 | 进入“待归集账号”清单，人工选择部门和岗位后建立任职 |
| 渠道账号 | 有有效 `channel.partner_members` | 渠道归属和身份仍在原页面；统一资料、销售/技术角色和证书可在三入口维护 |
| 双重身份账号 | 同时有内部任职和渠道成员关系 | 保留一个 `iam.users` 账号，分别展示两类成员关系，不拆成两个账号 |
| 停用、锁定或已离职账号 | `status_code<>'active'` 或离职状态非正常 | 默认不出现在有效组织树，在“历史账号”可检索，不物理删除 |
| 无归属账号 | 无内部任职、无渠道成员关系，且非明确的平台应急账号 | 进入“待治理账号”，人工选择归集、保留、停用或发起交接 |
| 外部身份账号 | 存在外部身份或 `origin_code<>'local'` | 账号来源和外部编号只读，不在历史整理中自动换绑 |
| 紧急或服务账号 | 经明确标记的平台紧急账号或服务主体 | 不强制挂普通部门，进入单独受控清单并审计 |

### 3.4 字段权威级和历史兼容

历史数据中可能同时存在结构化字段和 `extra_json` 兼容字段。目标权威顺序为：

| 信息 | 目标权威来源 | 历史兼容来源 |
| --- | --- | --- |
| 用户名、显示名、状态、手机号、邮箱 | `iam.users` 结构化列 | `extra_json` 只用于比对和追溯 |
| 本地密码 | `iam.password_credentials` | 不允许从 `extra_json` 恢复明文密码 |
| 系统角色 | `iam.user_roles` 关联的有效角色 | `extra_json.role` 只作兼容观察 |
| 内部归属 | `org.staff_assignments` | `iam.users.org_unit_id` 及历史扩展字段用于对账 |
| 渠道归属 | `channel.partner_members` | `extra_json.partnerId/partnerName` 只作兼容观察 |
| 区域和数据范围 | 结构化区域关联及 `iam.data_scope_bindings` | 历史 `region`、`bigRegion` 字段用于对账 |

在认证与 V2 兼容路由仍使用 `extra_json` 兜底的窗口内，只建立“结构化值、兼容值、是否一致”对账报告，不立即删除兼容值。冲突记录必须人工确认，禁止批量以任一侧覆盖另一侧。

### 3.5 历史数据处理步骤

1. 发布前备份数据库，导出账号主档、密码凭据存在标记、外部身份、角色、任职和渠道成员关系只读快照。
2. 生成不写库的历史账号体检报告，按第 3.3 节分类，同时输出冲突与异常。
3. 先处理会影响单点登录的异常：用户名冲突、手机号冲突、外部主体重复映射和系统角色冲突。
4. 再处理组织归集：只对人工确认的内部账号建立任职，不根据区域名或角色名自动推断部门。
5. 对停用账号和无归属账号逐项确认保留、归集、停用或交接；任何删除都不得作为批量整理手段。
6. 处理后重新生成同口径对账报告，验证账号总数、各状态数量、角色数量、外部身份数量和渠道成员数量无静默变化。
7. 完成账密、IAM、UniSDP 和四套正式页面回归后，才允许进入菜单切换。

### 3.6 体检报告必须输出的异常

- 非空手机号规范化后重复。
- 同一外部主体映射到多个 V3 账号。
- `iam.user_roles` 与 `extra_json.role` 不一致。
- `iam.users.status_code` 与 `extra_json.status` 不一致。
- 结构化区域关联与历史 `region/bigRegion` 不一致。
- 结构化渠道成员关系与历史 `partnerId/partnerName` 不一致。
- 激活管理账号没有有效内部任职。
- 激活渠道角色没有有效渠道成员关系。
- 停用或已离职账号仍有有效任职、渠道成员关系或高权限角色。
- 账号无任何角色、无内部任职且无渠道成员关系。
- 存在角色但缺少本地密码凭据，且当前认证链路无法构建可登录用户。

## 4. 单点登录和统一会话保护线

### 4.1 禁止改动的登录链路

本次整合不修改以下文件的运行逻辑：

- `apps/api/src/auth-routes.ts`
- `apps/api/src/iam-sso.ts`
- `apps/api/src/unisdp-sso.ts`
- `apps/web/src/api/auth-client.ts`
- `apps/web/src/router/entry-target.ts`
- `apps/web/src/router/sso-entry.ts`

不修改以下契约：

- `/api/auth/login`
- `/api/auth/me`
- `/api/auth/logout`
- `/api/auth/sso/iam/config`
- `/api/auth/sso/iam/login`
- `/api/auth/sso/unisdp/login`
- `/app/sso.htm`
- HttpOnly Cookie 名称、签名、有效期、`SameSite` 和 `Secure` 策略
- `admin_*`、`partner_*` 本地页面会话键
- 根路径 `/` 和安全 `redirect` 分流规则

如实施中发现必须修改任一上述文件或契约，必须中止本次整合，单独立项、评审和授权，不得以“页面合并”名义顺带改动。

### 4.2 会影响单点登录的高风险字段

| 字段或关系 | 当前影响 | 整合后控制 |
| --- | --- | --- |
| 管理员用户名 | IAM、UniSDP 管理端优先按用户名匹配 | 已开通单点登录的管理员用户名只读 |
| 渠道账号手机号 | IAM、UniSDP 渠道端可能按规范化手机号匹配 | 三入口统一成员资料允许受控维护并写入 `iam.users.phone`；不改匹配算法，但字段变化可能改变匹配结果，部署验收必须验证新旧手机号、重复手机号和渠道页面落点 |
| `iam.user_roles` | 最高优先级角色决定管理端或渠道端落点 | 角色变更仅在“角色管理”提交，展示落点影响并二次确认 |
| 账号状态 | 停用后新登录和 `/api/auth/me` 应拒绝 | 单独动作、显示影响、要求原因和审计 |
| 外部身份映射 | 决定外部主体绑定哪个 V3 账号 | 本次只读，不提供解绑、换绑或自动合并 |

### 4.3 单点登录不受影响的判定标准

不以“页面能打开”作为不受影响的证明，必须验证：

1. 登录后同时写入 HttpOnly Cookie 和对应的页面会话。
2. 管理员和渠道账号在电脑端和移动端落点不变。
3. IAM 统一入口仍返回 `enabled:true`，且包含 `entries`、`requestIsaidByEntry`、`timeoutMs`。
4. UniSDP 门户用户名和渠道手机号识别规则不变。
5. 隐藏旧账号菜单后，不改变登录用户的 `defaultPath`、`allowedPaths`和页面角色。

## 5. 授权保护线

### 5.1 首期授权原则

- 首次整合仍只向超级管理员开放组织与账号管理，不因页面合并扩大区域管理员、企业管理员或普通员工的管理权。
- 后端继续以签名 Cookie 会话确认操作人，不使用本地存储角色、`operatorId`、兼容请求头或前端自报字段授权。
- 组织、账号、角色和数据范围四类写操作保持独立权限语义，不因同屏展示而共用一个粗粒度“管理”权限。
- 岗位、业务角色不直接代表运行时权限；用户角色变更仍通过 RBAC 接口处理。
- 数据范围未完成主业务运行时接管前，页面必须显示“未应用到主业务”，不得暗示配置已生效。

## 7. 后端落地

### 7.1 首次整合的最小改动

本轮在不合并账号表、不重编账号和不改登录匹配算法的前提下，增加向前兼容的组织数据结构与受控接口：

- 保留现有 `/api/v2/users`、`/api/v2/users/:id`、`/api/v2/users/:id/status`、`/api/v2/users/:id/password` 兼容接口。
- 保留 `/api/rbac/users/:userId/roles` 角色维护接口。
- 保留 `/api/org/staff/:userId/assignments` 和任职相关接口。
- 增加渠道成员统一资料、固定销售/技术业务角色、逻辑归档字段和一人一条有效任职约束；迁移必须按 `S10_009`、`S10_010` 顺序执行。
- 增加停用归档影响预览、交接单和独立任务进程，但执行开关默认关闭，不能随普通组织写入一起开启。
- 组织页面不新建第二套用户表、密码表或角色表。
- 对现有兼容接口的身份可信性问题不在页面整合中扩大；组织新入口的高风险操作优先走签名 Cookie 会话的受控路由。

### 7.2 维护性收口

在不改外部接口的前提下，将账号数据逻辑逐步抽取为一个内部账号服务：

```text
账号服务
├─ 账号查询
├─ 基本资料维护
├─ 账号状态变更
├─ 本地密码重置
├─ 外部身份只读概要
└─ 审计与授权版本更新
```

旧兼容路由和新组织页面路由共用该服务，不允许两份 SQL 分别维护。抽取时只做机械迁移和原行为回归，不同时改角色优先级、单点匹配或密码策略。

### 7.3 目标受控接口

待账号服务抽取和权限契约通过评审后，增加受签名 Cookie 会话保护的身份管理接口：

| 方法与路径 | 用途 | 目标权限 |
| --- | --- | --- |
| `GET /api/identity/users` | 账号列表与查询 | `identity.user.read` |
| `GET /api/identity/users/:id` | 账号与身份概要 | `identity.user.read` |
| `POST /api/identity/users` | 创建本地账号 | `identity.user.create` |
| `PUT /api/identity/users/:id/profile` | 修改可编辑资料 | `identity.user.update` |
| `PUT /api/identity/users/:id/status` | 变更账号状态 | `identity.user.status` |
| `POST /api/identity/users/:id/reset-password` | 重置本地密码 | `identity.credential.reset` |

接口规则：

- 列表、详情和写入都由服务端根据签名会话确认操作人。
- 写操作要求 `Idempotency-Key`、行版本、操作原因和审计。
- 创建账号不自动创建外部身份映射，不根据姓名、手机号或邮箱自动合并用户。
- 编辑资料不夹带角色、权限、范围或任职变更。
- 接口实现后，旧 `/api/v2/users*` 仍保留兼容窗口，四套正式页面回归通过前不得下线。

### 7.4 内部成员编排接口

待第 7.3 节稳定后，再建设“账号加主职”的单事务编排，不在首次菜单整合中强行合并后端事务。

```text
POST /api/org/internal-members
输入：新账号资料或已有 userId、orgUnitId、positionId、isPrimary、effectiveAt
事务：创建或锁定账号 → 校验组织和岗位 → 创建任职 → 审计 → 提交
禁止：自动绑定外部身份、自动授予高权限、自动扩大数据范围
```

退出条件：能力对照全部通过，新旧入口查询和修改结果一致，单点登录专项全部通过。

- 抽取账号服务，旧兼容路由和新受控路由共用。

退出条件：新旧账号接口契约对照通过，四套页面和三类登录主链回归通过。

### 8.5 阶段四：兼容清理

满足以下条件后才能评估删除旧菜单组件和冗余账号 SQL：

- 至少跨越两个正式发布版本。
- 旧路由访问无实际业务使用。
- 正式页面、导入导出、移动端和单点登录全量回归通过。
- 已有明确的 Web 镜像回退点和数据对账记录。

| 数据范围尚未运行时接管 | 页面清楚显示 `runtimeApplied=false` 对应中文提示 |

## 11. 发布、观察和回退演练

### 11.1 发布顺序

1. 发布前完成数据库备份、配置快照、镜像摘要和迁移账本核对；固定销售/技术角色不得有语义冲突，一人多条有效任职查询必须返回零行。
2. 依次执行 `20260827_S10_009_渠道成员统一业务角色`、`20260827_S10_010_任职编辑一致性修正`，再发布 Web、API 和 Worker；`S10_009` 必须先于 `S10_010`。
3. 首次验证保持组织总开关、组织写入、账号状态防护、停用归档交接和入口合并开关全部关闭，并核对 `/admin.html` 引用 `admin-app.js?v=159`、`style.css?v=16`。
4. 只开启组织总开关完成只读观察；数据对账通过后再开启普通组织写入，验证部门选择、弹层层级、统一成员资料、多证书和并发冲突。
5. 保持 `V3_ORGANIZATION_OFFBOARDING_ENABLED=false`，单独开启 `V3_AUTH_ACCOUNT_STATUS_CHECK_ENABLED=true`，验证有效账号无感、停用账号旧会话返回 401、状态查询异常返回 503。
6. 账密、IAM、UniSDP、四套正式页面和客户、报备、商机、报价、订单、渠道、账号主链全部通过后，才开放全部超管和入口合并开关。
7. 真实 PostgreSQL Worker 专项和安全回退演练签字后，才能单独评审停用归档交接；观察至少 7 天后再评估旧组件清理。

发布资产还必须满足以下硬门禁：

- SP-APP 和 SP-FULL 首次升级时，组织总开关、组织写入、企微目录同步、账号入口整合、账号状态防护、停用归档交接六个开关全部为 `false`。
- 制包必须显式传入版本和包编号，工作区存在未收口改动时拒绝制包；镜像归档必须与本地同标签镜像摘要一致。
- Nginx 镜像中的 `admin.html`、`admin-app.js`、`style.css`、组织入口、内嵌路由和组织工作区资源必须与当前 Web 构建产物名称及摘要一致。
- 发布后必须核对 `S10_009`、`S10_010` 迁移账本摘要、四个固定销售/技术业务角色、唯一有效任职约束和任职一致性函数。
- 应用回退前不仅检查配置文件，还要检查运行中主 Worker 的实际开关、未完成交接单和未终结扫描事件；已有停用归档账号时不得回退到缺少账号状态防护的版本。

### 11.2 观察指标

- 账密登录成功率和失败错误码。
- IAM 单点登录成功率、本地用户匹配方式和入口分布。
- UniSDP 接口和门户单点登录成功率。
- `/api/auth/me` 的 401 与异常增长。
- 组织与账号接口的 401、403、409 和 422。
- 新建账号后未生成有效主职的数量。
- 账号状态、角色变更和密码重置的审计数量。
- 旧 `#/account-manage` 和 `#/partner-admin` 路由的实际访问量。

### 11.3 必停条件

出现以下任一情况立即关闭整合开关并恢复旧菜单：

- IAM 或 UniSDP 单点登录成功率明显下降。
- 管理员落到渠道页面，或渠道账号落到管理员页面。
- 页面会话缺失、前缀错乱或登录后循环跳转。
- 角色或数据范围出现静默变更。
- 组织页面可修改外部身份映射、登录账号，或渠道电话修改后出现重复匹配、单点匹配失败、登录落点变化。
- 渠道商页面、区域筛选、区域价格或渠道员工操作出现回归故障。

## 12. 完成定义

只有同时满足以下条件，才可标记“账号管理已并入组织架构”：

1. 新入口能力对照全部通过，无孤儿账号和无归属写入。
2. 账号、任职、渠道成员、角色和数据范围仍为独立数据事实。
3. 单点登录和统一入口全矩阵回归通过。
4. 渠道商管理页面、区域使用和渠道端保持不变。
5. 高风险字段和动作有服务端允许清单、二次确认、原因和审计。
6. 旧入口回退演练成功，两个版本兼容窗口执行完成。
7. 文档、契约、测试、发布说明和运维验证脚本与实际实现一致。
8. 一人一条有效任职、销售/技术二选一、多证书和三入口一致性均通过真实数据库与浏览器验收。
9. 关闭组织写入和入口合并开关后，渠道商、企业管理员、账号、登录、客户、报备、商机、报价和订单主链路保持可用。
