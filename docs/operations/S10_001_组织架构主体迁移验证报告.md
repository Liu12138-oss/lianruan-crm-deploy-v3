## 修复的真实问题（dry-run 发现）

### Bug 1：视图引用不存在的字段
- **现象**：脚本最后 `CREATE VIEW v_org_units_active_tree` 时引用 `created_at, updated_at`，但 `org.org_units` 原表无此字段。
- **修复**：移除视图中这两个字段。
- **影响**：崩溃级，所有迁移都会失败。

### Bug 2：`assert_no_cycle` ltree `@>` 操作符语义反转
- **现象**：原实现用 `v_new_parent_path @> v_child_path` 判断成环，方向反了，导致：
  - 防环 T2（A → A1A）未拦住（应拦但放行）
  - 合法 T3/T4 可能被误拦
- **根因**：ltree `@>` 是"左操作数包含右操作数"（祖先关系）。新父是子的子孙 ⇔ 子是祖先 ⇔ `v_child_path @> v_new_parent_path`。
- **修复**：改为 `v_child_path @> v_new_parent_path`。
- **影响**：核心安全约束，**必须修**。

### Bug 3：path_code 回填漏父路径
- **现象**：原循环 UPDATE 只更新单层（`LIANRUAN-HQ.S-A` 没拿到父路径前缀）。
- **根因**：PG 在多轮 UPDATE 中**不能读到自己刚更新的同表数据**。
- **修复**：改用 `WITH RECURSIVE + 单条 UPDATE`，一次性构造 path。
- **影响**：迁移后所有 path_code 都不完整，防环函数失效。

### Bug 4：根节点 path_code 被错误回填
- **现象**：原循环把根节点 `LIANRUAN-HQ` 的 path_code 也填成了自己的 unit_code（nlevel=1 而非 0）。
- **根因**：WHERE `c.path_code = ''::ltree` 同时命中根和子节点。
- **修复**：CTE 种子查询用 `parent_unit_id IS NULL` 单独处理根（path 为空），子节点走递归拼接。
- **影响**：根节点语义错位，跨域判断受影响。

## dry-run 中暴露的非脚本 bug（仅测试用）

### Bug T：多行 INSERT 子查询看不到刚插入的行
- **现象**：`INSERT ... VALUES (...), ((SELECT id FROM ... WHERE unit_code='X-A'), ...), ...` 在同一 INSERT 中 Z-A1 的 parent_unit_id 实际为 NULL。
- **根因**：PG 多行 INSERT 的 VALUES 子查询对同语句中之前插入的行不可见。
- **修复**：测试用例改为多次独立 INSERT。
- **影响**：仅测试代码，迁移脚本不受影响（脚本只 ALTER，不 INSERT）。
