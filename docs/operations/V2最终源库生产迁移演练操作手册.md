## 1. 这份手册解决什么问题

这份手册用于“有一份新的 V2 数据库，要在 V3 测试服务器上完整演练一次迁移”。

演练目标：

- 从最终 V2 源库重新生成数量记录。
- 从最终 V2 源库只读导出迁移批次。
- 把导出批次装入 V3 PostgreSQL 暂存层。
- 核对 V2 源库、V2 导出、PostgreSQL 暂存层数量是否一致。
- 把暂存层落到 V3 正式业务表。
- 初始化迁移用户统一登录密码。
- 抽查登录和核心业务页面。

通过标准：

```text
V2源库数量 = V2导出数量 = PostgreSQL暂存数量
```

正式业务表重点核对：

```text
用户、渠道商、报备、商机、报价、订单必须能对上。
产品、工作量、开放接口、通知、审计必须能查到并可页面抽查。
迁移用户必须能用统一初始化密码登录。
```

## 3. 本地生成本次迁移批次

下面命令在本地电脑执行。

进入 V3 工程目录：

```bash
cd "/Users/liu/Documents/Codex/lianruan-crm-deploy-v3"
```

设置本次源库目录和批次号。只需要改第一行路径：

```bash
SOURCE_DIR="/Users/liu/Documents/Codex/v2-final-source-20260730/backend"
BATCH_CODE="S8-RUN-$(date +%Y%m%d-%H%M%S)"
RUN_DIR="tmp/stage8/${BATCH_CODE}"
SNAPSHOT_DIR="${RUN_DIR}/v2-snapshot"
EXPORT_DIR="${RUN_DIR}/v2-export"
STAGING_DIR="${RUN_DIR}/v2-postgres-staging"

echo "本次批次号：${BATCH_CODE}"
```

### 3.1 生成 V2 源库数量记录

```bash
node scripts/migration/生成V2快照实体数量记录.js \
  --crm-db "${SOURCE_DIR}/crm.db" \

  --output-dir "${SNAPSHOT_DIR}" \
  --label "生产迁移演练V2最终源库数量记录" \
  --expected-source-dir "${SOURCE_DIR}" \
  --record-doc "docs/stage-records/生产迁移演练-${BATCH_CODE}-V2源库实体数量记录.md"
```

看到这句才算第一步成功：


如果看到“阻断正式迁移”，先停下，不要继续导入。

查看数量文件：

```bash
sed -n '1,80p' "${SNAPSHOT_DIR}/entity-counts.csv"
```

### 3.2 只读导出 V2 迁移批次

```bash

  --crm-db "${SOURCE_DIR}/crm.db" \
  --audit-db "${SOURCE_DIR}/audit.db" \
```

### 3.3 生成 PostgreSQL 暂存装载包

```bash

  --export-manifest "${EXPORT_DIR}/manifest.json" \
  --output-dir "${STAGING_DIR}" \
  --batch-code "${BATCH_CODE}" \
```

## 8. 落到 V3 正式业务表

重要提醒：

- 如果这是测试服务器，并且你希望“用新源库覆盖旧测试数据”，建议先让技术人员备份后重置测试库。
- 如果直接在已有测试数据上重复落表，V3 会尽量更新同源数据，但旧源库里有、新源库里删除的数据可能还留在测试库里，导致正式表数量大于新源库数量。
- 正式生产迁移建议在空的 V3 正式业务库或已确认的迁移窗口内执行。


## 10. 核对正式业务表数量

服务器上执行，记得把第一行批次号改成本次的：

```bash
BATCH_CODE="S8-RUN-这里换成本次批次号"
cd /opt/lianruan-crm-v3/compose

sudo docker compose exec -T postgres psql -U lianruan_app -d lianruan_crm_v3 <<SQL
WITH expected AS (
  SELECT e.entity_name, e.expected_records
  FROM migration.v2_import_expected_counts e
  JOIN migration.migration_batches b ON b.id = e.batch_id
  WHERE b.batch_code = '${BATCH_CODE}'
),
formal AS (
  SELECT 'users' AS entity_name, COUNT(*) AS formal_records FROM iam.users WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'partners', COUNT(*) FROM channel.partners WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'registrations', COUNT(*) FROM crm.registrations WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'opportunities', COUNT(*) FROM crm.opportunities WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'quotes', COUNT(*) FROM crm.quotes WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'orders', COUNT(*) FROM crm.orders WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'categories', COUNT(*) FROM catalog.product_categories WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'modules', COUNT(*) FROM catalog.product_modules WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'features', COUNT(*) FROM catalog.product_features WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'hardwareProducts', COUNT(*) FROM catalog.hardware_products WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'packages', COUNT(*) FROM catalog.product_packages WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'implementationWorkloadClassifications', COUNT(*) FROM catalog.workload_classifications WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'implementationWorkloadMappings', COUNT(*) FROM catalog.workload_mappings WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'implementationWorkloadRules', COUNT(*) FROM catalog.workload_rules WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'implementationDeliveryWorkloadRules', COUNT(*) FROM catalog.delivery_workload_rules WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'openApiClients', COUNT(*) FROM integration.open_api_clients WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'pendingApprovals', COUNT(*) FROM ops.approvals WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'notifications', COUNT(*) FROM ops.notifications WHERE v2_source_id IS NOT NULL
  UNION ALL SELECT 'audit_logs', COUNT(*) FROM audit.audit_logs WHERE v2_source_id IS NOT NULL
)
SELECT
  e.entity_name AS "实体",
  e.expected_records AS "V2导出数量",
  COALESCE(f.formal_records, 0) AS "V3正式表数量",
  CASE
    WHEN e.expected_records = COALESCE(f.formal_records, 0) THEN '一致'
    WHEN e.expected_records < COALESCE(f.formal_records, 0) THEN 'V3更多，检查是否叠加旧测试数据或系统兜底数据'
    ELSE 'V3缺少，需要停止验收'
  END AS "结果"
FROM expected e
LEFT JOIN formal f ON f.entity_name = e.entity_name
ORDER BY e.entity_name;
SQL
```

重点通过标准：

```text
users、partners、registrations、opportunities、quotes、orders 必须一致。
features、hardwareProducts、packages、implementationWorkloadMappings、implementationWorkloadRules 必须可解释。
如果 V3 正式表数量比 V2 多，先确认是不是旧测试数据叠加，不能直接说通过。
```

## 13. 失败时怎么处理

如果暂存导入失败：

```text
不要落正式表。
保留日志。
把日志发给技术人员处理。
```

如果正式表数量少于 V2：

```text
停止验收。
不要让用户继续试用。
先查迁移异常表和落表日志。
```

如果只是 V3 数量多于 V2：

```text
先确认是不是旧测试数据叠加。
正式交付前建议恢复到干净 V3 数据库后重跑。
```

如果登录失败：

```bash
sudo INSTALL_ROOT=/opt/lianruan-crm-v3 \
  INIT_PASSWORD='LrCRM@2026!' \
  /opt/lianruan-crm-v3/scripts/init-migrated-user-passwords.sh --yes
```

然后重新测试登录。

## 14. 给产品负责人的一句话结论

你只需要记住三件事：

1. 新数据不要覆盖旧演练目录，每次都用新批次号。
2. 数量必须按“源库、导出、暂存、正式表”四层核对。
3. 正式表导入前必须先备份，失败就回滚，不带问题继续验收。
