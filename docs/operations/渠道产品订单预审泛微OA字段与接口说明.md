> 文档状态：已完成 V3 自动发起、泛微流程发起、报价单双附件和企微自动建群的独立任务实现；生产 OA 已完成单次人工联调验证。本轮未以 V3 任务进程调用真实泛微或企微，功能默认关闭，待测试环境参数、身份映射和区域映射就绪后联调。

>
> 适用范围：仅适用于泛微 OA／eteams 的“渠道产品订单预审”流程。

## 1. 使用边界

本流程用于 V3 向泛微 OA 发起“渠道产品订单预审”。V3 只负责文件上传、创建并发起流程、记录泛微受理编号；审批节点、审批人、审批结果、撤回和后续处理均由泛微 OA 管理。

不得将本说明复用于其他泛微流程。其他流程的模板编号、字段编号、必填规则、审批路径和附件规则均须单独读取并验证。

## 5. 附件规则

当前模板中两个附件字段均为主表必填附件。首期从报价明细生成一份受控报价单 PDF，并对泛微文件服务执行两次独立上传：第一次绑定“采购订单上传处”，第二次绑定“报价单／收益表上传处”。两次上传的文件内容相同，但必须分别保存各自返回的 `fileid`。

1. 将 V3 已完成权限校验的受控文件上传到泛微文件服务。
2. 上传成功后取得返回值中的 `fileid`。
3. 创建流程时，将第一次上传返回的 `fileid` 写入“采购订单上传处”的 `dataOptions[0].optionId`。
4. 将第二次上传返回的 `fileid` 写入“报价单／收益表上传处”的 `dataOptions[0].optionId`。
5. 发起成功后，通过 `getInfoByID` 只读回查两个附件字段均存在，且均对应当前订单的报价单 PDF。

文件上传接口：

```text
POST /api/file/v2/common/upload
Content-Type: multipart/form-data
```

上传参数至少包括：

| 参数           | 规则                                       |
| -------------- | ------------------------------------------ |
| `access_token` | 泛微访问令牌；只允许由服务端密钥引用提供。 |
| `userid`       | 当前流程发起人的泛微人员编号。             |
| `module`       | 固定为 `workflow`。                        |
| `file`         | 文件本体。                                 |
| `name`         | 文件名。                                   |
| `size`         | 文件字节数。                               |

创建流程时的附件字段结构如下。`optionId` 必须替换为对应上传返回的实际 `fileid`：

```json
{
  "fieldId": 4742314795739512449,
  "dataOptions": [
    {
      "optionId": 1234567890123456789,
      "optionObj": {
        "name": "采购订单.pdf",
        "extName": "pdf",
        "type": "application/pdf",
        "img": false
      }
    }
  ]
}
```

注意事项：

- 不得传 CRM 文件 URL、下载链接、文件名字符串或本地路径代替 `fileid`。
- 不得为这两个主表附件字段传 `dataIndex`；传递后 OA 会将字段判定为空。
- 首期允许两个附件字段使用内容相同的报价单 PDF，但必须是同一订单关联报价在本次发起时生成的受控文件；不得使用空白、占位、历史订单或其他订单文件。
- 文件上传成功不等于流程已受理。上传成功但流程创建失败时，应记录为未绑定文件，不得标记业务流程已发起。
- 不在日志、审计正文、前端响应或文档中记录访问令牌、文件下载链接或完整文件标识。

## 6. 创建并发起接口

已验证接口：

```text
POST /api/workflow/core/paService/v2/doCreateRequest?access_token=...
Content-Type: application/json
```

令牌必须位于 URL 查询参数；请求体必须是纯 JSON，不能把令牌与 JSON 混合成表单请求体。

关键请求参数：

| 参数                   | 已验证规则                                                              |
| ---------------------- | ----------------------------------------------------------------------- |
| `userid`               | 使用订单所属区管映射得到的泛微人员编号；联调编号不得写死进正式实现。    |
| `workflowId`           | 固定为 `7412314682719324051`。                                          |
| `requestname`          | 流程请求标题；OA 最终展示标题可能自动拼接合同对方、最终用户和订单编号。 |
| `isnextflow`           | 固定为数字 `1`，表示创建后立即流转。                                    |
| `isVerifyFormRequired` | 固定为布尔值 `true`，由 OA 校验必填字段。                               |
| `formData.formId`      | 固定为 `7412314682719324051`。                                          |
| `formData.module`      | 固定为字符串 `workflow`。                                               |
| `formData.dataDetails` | 按第 3 节字段编号和第 5 节附件结构传递。                                |

成功响应的 `message.requestId` 为泛微流程实例编号。V3 必须持久化该编号，并将“已受理”仅定义为泛微成功返回该编号；不得把它等同为审批通过。

## 7. 回查与状态规则

流程创建后，使用以下只读接口回查：

```text
GET /workflow/v2/getInfoByID
```

回查参数包括 `access_token`、`userid` 和流程实例编号 `id`。至少检查：

1. 返回 `message.errcode` 为 `0`。
2. `flowRequest.statusType` 为 `inProcess` 或对方定义的后续有效状态。
3. `flowRequest.currentNode` 有值。
4. `formData.dataDetails` 内的所属区域、订单编号、产品类型、采购内容与发起请求一致。
5. `formData.fileDownload_Urls` 中同时存在“采购订单上传处”和“报价单／收益表上传处”，并均对应本次生成的报价单 PDF。

网络超时或无法确认响应时，V3 必须标记为“待人工确认”，按订单编号和已记录的外部请求信息查询，不能直接重试创建，避免重复审批流程。

## 8. 开发与联调门禁

1. 仅服务端任务进程调用泛微接口，浏览器不得持有泛微凭据或直连泛微。
2. V3 必须仅在自动触发时点校验订单、发起人、数据范围、区域真实值、产品类型，以及同一报价单 PDF 的两次独立上传均成功：普通订单为区管确认后进入 `pending_superadmin_confirm`；调价订单为超管确认后进入 `confirmed`。区管调价本身不得调用泛微。
3. 同一订单、相同行为、相同模板版本必须使用稳定幂等键；已取得泛微流程编号时固定返回已有结果。
4. 对模板编号、字段编号、字段类型、必填规则、区域选项或产品类型规则发生变化时，立即停用该模板的新发起并告警。
5. 接口失败只记录脱敏摘要、错误码和请求编号；不记录令牌、附件链接或附件正文。
6. 测试流程一旦被泛微受理，撤回或删除必须遵从泛微 OA 的既有人工规则，V3 不自动处理。

## 10. V3 自动发起业务规则

1. 不提供人工“自动发起订单预审”按钮。订单状态机在满足下列条件时，于同一数据库事务写入一条预审发起记录和一条发件箱事件；浏览器不传入、覆盖或等待泛微字段。
   - 普通订单：订单由 `primary_confirmed`（等待区管确认）经区管确认进入 `pending_superadmin_confirm` 时自动触发。
   - 调价订单：区管调价进入 `pending_superadmin_confirm` 时只创建超管待办，绝不发起泛微；仅在超级管理员通过服务端确认后进入 `confirmed` 时自动触发，其他账号请求必须被拒绝。
2. 泛微流程发起人固定为订单所属区域的区管。普通订单使用完成区管确认的区管；调价订单使用已固化在订单上的该次调价区管。超管确认仅决定调价订单的触发时点，不替换泛微发起人。
3. 订单编号、合同对方、最终用户和所属区域均由服务端从订单关联数据读取；浏览器不得传入或覆盖这些值。
4. 报价单 PDF 必须由服务端根据该订单关联报价生成、留存，并分别上传到“采购订单上传处”和“报价单／收益表上传处”。
5. 同一订单只能创建一条“渠道产品订单预审”发起记录。只要记录已经存在，不论其为已受理、失败、已停止或待人工确认，都不得再次自动创建；页面固定提示“此订单需要人工操作发起或修改‘OA渠道订单预审’”。
6. 泛微返回流程实例编号且只读回查为有效流程后，立即创建订单预审企微群；不等待 OA 审批通过、驳回或结束。
7. 对方后续完成第二附件非必填调整并经一次不传第二附件的测试发起验证后，才可移除第二次上传；此前仍按本节双附件规则执行。

## 11. 区管泛微 `userid` 获取与维护规则

2026-08-27 对当前 V3 数据库的只读核查结果：23 个有效区管账号的手机号、邮箱均为空，且均未维护外部身份映射。泛微用户目录查询结果包含姓名、手机号、邮箱、部门和 `userid`，但不包含 V3 登录名。因此，不能将区管 V3 登录名自动可靠地匹配到泛微 `userid`；提供的示例脚本中的按姓名匹配只能用于人工辅助查找，不能用于正式发起。

正式实现必须在 `iam.external_identities` 中显式维护映射：`provider_code='eteams'`，`external_subject` 保存泛微 `userid`，`external_username` 保存对方用户名或姓名用于人工核验。发起前必须恰有一条有效映射；缺失或重复即拒绝发起并提示维护映射。

1. 泛微管理员通过用户目录接口或后台导出，提供“泛微 `userid`、姓名、手机号／邮箱、部门”的权威名单。
2. V3 超级管理员逐条核验后维护“V3 登录名、泛微 `userid`、核验人、核验时间”。
3. 不以姓名、部门、相似账号或猜测规则自动写入映射；后续区管变更时先更新映射再允许发起。

### 11.2 泛微 `userid` 只读查询方法

查询必须由服务端连接器或受控联调工具执行，不得由浏览器调用，也不得在前端、日志、审计正文或本文档记录访问令牌与应用密钥。当前已验证的获取顺序如下：

1. 调用 `GET /oauth2/authorize`，使用泛微企业标识取得一次性授权码 `code`。
2. 调用 `POST /oauth2/access_token`，提交应用标识、应用密钥、`grant_type=authorization_code` 和 `code`，仅在服务端内存中取得短期 `accessToken`。
3. 以 `GET /user/v3/findAllUsers?access_token=...&page=<页码>` 分页读取成员，直到返回空 `data` 数组。
4. 每页只读取 `userid`、`name`、`mobile`、`email`、`department` 与 `status`，以 V3 人员姓名、手机号或邮箱做人工核验；泛微接口不返回 V3 登录名。
5. 仅“泛微状态正常 + 唯一可核验”的人员可以转为正式映射；查询无结果、重名、多条记录或 V3 联系方式缺失时，保持待核验，不能自动选取。

参考伪代码如下。示例只表达调用顺序，正式实现必须使用部署密钥配置并进行脱敏审计：

```text
授权码 = GET /oauth2/authorize?corpid=<泛微企业标识>
访问令牌 = POST /oauth2/access_token
  app_key=<受控应用标识>
  app_secret=<受控应用密钥>
  grant_type=authorization_code
  code=<授权码>

for 页码 from 1:
  成员页 = GET /user/v3/findAllUsers?access_token=<访问令牌>&page=<页码>
  if 成员页.data 为空: break
  仅保留待核验人员的 userid、姓名、联系方式、部门和状态
```

### 11.3 已实现的组织架构维护能力

已新增迁移 `database/migrations/20260827_S10_012_泛微OA身份候选与确认.sql` 及其安全回退脚本。组织架构的账号抽屉已增加“泛微 OA 身份”区块；正式入口为 `/admin.html` 的组织架构，工程化工作区保留同等维护能力。超级管理员可查看该账号的正式映射、历史停用映射及候选记录，并可按受控步骤维护：录入或更正候选、确认候选、驳回候选、停用正式映射。

候选和正式映射严格分开保存：

- 待核验候选保存于 `iam.external_identity_candidates`，仅供超级管理员人工核验；候选不能被订单预审或任何 OA 发起链路读取。
- 正式映射保存于 `iam.external_identities`：`provider_code='eteams'`、`external_subject=<泛微 userid>`、`external_username=<泛微姓名或登录名>`、`status_code='active'`。只有该状态可作为后续 OA 发起人。
- 确认操作在一个数据库事务内完成：先校验当前 V3 用户没有其他有效泛微映射、该 `userid` 未绑定其他有效账号，再创建正式映射并将候选改为已确认；冲突拒绝覆盖。
- 停用不物理删除正式映射，保留历史与审计；之后必须重新录入候选并人工确认，才可恢复发起资格。
- 所有写操作要求超级管理员签名 Cookie 会话、组织写入开关、幂等键；更正、确认、驳回和停用还要求匹配行版本。

本轮没有执行数据库迁移，没有写入 11.1 节的任何候选，也没有写入任何正式映射；上表仍仅是人工核验清单，不代表系统中已录入数据。

## 12. V3 实现、开关与测试状态

已实现的独立任务入口为 `apps/worker/src/order-preapproval-worker.ts`，仅消费 `crm.order.preapproval.requested` 发件箱事件。它与既有健康任务、组织交接任务、消息任务和订单主业务进程分离；任务失败只写预审请求、调用记录、受控附件、群记录和审计事实，绝不回写订单状态。

单机部署使用 `order-preapproval` 独立 Profile。以下配置默认均为关闭或空值，未同时提供完整参数时任务不会启动：

```text
ORDER_PREAPPROVAL_WORKER_ENABLED=false
ORDER_PREAPPROVAL_EVENT_CUTOVER_AT=
ORDER_PREAPPROVAL_ETEAMS_ORIGIN=
ORDER_PREAPPROVAL_ETEAMS_CORP_ID=
ORDER_PREAPPROVAL_ETEAMS_APP_KEY=
ORDER_PREAPPROVAL_ETEAMS_APP_SECRET=
```
