# V3 生产升级包制作规范

编写日期：2026-07-31  
最近修订：2026-08-18（补充 KB-20260818-025 R1 至 R7 生产升级复盘）<br>
适用系统：联软 CRM V3  
适用环境：openEuler x86_64 单机 Docker Compose 部署  
适用目录：生产默认安装目录 `/opt/lianruan-crm-v3`  
包格式要求：只使用 ZIP，不使用 TAR、TGZ、7Z、RAR。生产执行只假设有 `bash`、`zip`、`unzip`、`cp`、`mkdir`、`sha256sum`、`docker`、`docker compose`、`curl` 等基础命令。KB 包内 Docker 镜像归档统一使用 `.docker-image` 后缀，通过 `docker load -i` 加载，不使用 `.tar` 文件名。

> SP 与 KB 的统一名称、包型分级、完全离线约束、差量镜像边界和失败回退门禁，以 [V3 SP 与 KB 离线升级包分级规则](./V3_SP与KB离线升级包分级规则.md) 为准。本文保留并细化目录、脚本、校验和生产执行要求。

## 一、核心原则

所有缺陷修复和新功能开发必须基于 V3 版本执行。

禁止把 V2 的升级方式继续用于 V3：

| 禁止行为 | 原因 |
| --- | --- |
| 直接替换 `backend/server.js` | 这是 V2 后端，不是 V3 主线 |
| 直接替换 `frontend/admin-app.js` 或 `frontend/partner-app.js` | 这是 V2 静态前端遗留 |
| 用 `pkill -f node.*server.js` 停服务 | V3 生产由 Docker Compose 管理 |
| 用 `tar.gz` 做生产升级包，或在 KB 包内放 `.tar` 镜像文件名 | 生产欧拉环境按 ZIP 和 unzip 约束处理，镜像归档使用 `.docker-image` 后缀 |
| 不备份直接覆盖生产配置或数据库 | V3 已使用 PostgreSQL，回退成本高 |
| 修改数据库但不提供迁移 SQL 和回退说明 | 会造成版本不可追溯 |

V3 生产升级必须围绕这些资产：

| 类型 | V3 位置 |
| --- | --- |
| 后端镜像 | `lianruan-crm-v3-api:<版本>` |
| 前端镜像 | `lianruan-crm-v3-nginx:<版本>` |
| 任务镜像 | `lianruan-crm-v3-worker:<版本>` |
| 生产编排 | `/opt/lianruan-crm-v3/compose/docker-compose.yml` |
| 生产环境变量 | `/opt/lianruan-crm-v3/config/v3.env` |
| 部署变量 | `/opt/lianruan-crm-v3/config/deploy.env`、`/opt/lianruan-crm-v3/compose/.env` |
| 数据库迁移 | `/opt/lianruan-crm-v3/database/migrations/` |
| 运维脚本 | `/opt/lianruan-crm-v3/scripts/` |
| 健康检查 | `/opt/lianruan-crm-v3/scripts/health-check.sh` |
| 备份脚本 | `/opt/lianruan-crm-v3/scripts/backup.sh` |
| 回退脚本 | `/opt/lianruan-crm-v3/scripts/rollback.sh` |

## 二、升级包类型

### 2.1 SP 服务包

SP 服务包用于完整应用版本交付、较大范围升级或新服务器安装，分为：

1. `SP-APP`：应用服务包，默认不携带未变更的 PostgreSQL、Redis、Docker 和 Docker Compose。
2. `SP-FULL`：完整离线服务包，携带应用、基础镜像、预先展开的运行时和全部部署资产。

现有完整离线发布脚本主要对应 `SP-FULL`，包内包含镜像、Compose、配置模板、迁移 SQL、运行时和部署脚本。

制作入口：

```bash
npm ci
npm run verify
deploy/single-server/scripts/download-runtime.sh
V3_IMAGE_TAG=目标版本 deploy/single-server/scripts/build-images.sh
V3_IMAGE_TAG=目标版本 V3_SKIP_PULL=1 deploy/single-server/scripts/save-images.sh
V3_IMAGE_TAG=目标版本 V3_PACKAGE_FORMAT=zip deploy/single-server/scripts/package-offline.sh
```

输出示例：

```text
tmp/phase7-package/lianruan-crm-v3-offline-目标版本.zip
tmp/phase7-package/lianruan-crm-v3-offline-目标版本.zip.sha256
```

`SP-FULL` 适用场景：

1. API、Web、Worker 都有较大变化。
2. 需要同步 Dockerfile、Compose、Nginx、运行时。
3. 首次部署或整包重装。
4. 需要给完全离线服务器交付完整资产。

### 2.2 补丁 KB／KB 升级包

KB 升级包用于生产缺陷热修复或小范围功能补丁。这里的 KB 指“一个可执行、可复核、可回退、可留痕的知识库式修复包”。每个 KB 对应一个问题或一组强相关问题。

KB 按交付方式分为 `KB-FILE`、`KB-LAYER`、`KB-IMAGE` 和 `KB-DB`。未受影响的组件不得为了方便默认加入 KB；具体选择条件以《V3 SP 与 KB 离线升级包分级规则》为准。

命名规则：

```text
lianruan-crm-v3-kb-YYYYMMDD-编号-简短问题名.zip
lianruan-crm-v3-kb-YYYYMMDD-编号-简短问题名.zip.sha256
```

示例：

```text
lianruan-crm-v3-kb-20260731-001-quote-workload-fix.zip
lianruan-crm-v3-kb-20260731-001-quote-workload-fix.zip.sha256
```

KB 包必须能自动完成：

1. 环境检查。
2. 包完整性校验。
3. 生产 V3 安装目录检查。
4. 升级前自动备份。
5. 按需停止相关服务。
6. 加载新镜像或复制补丁文件。
7. 执行数据库迁移或修复脚本。
8. 启动相关服务。
9. 执行健康检查。
10. 执行业务自检。
11. 生成升级日志。
12. 输出回退方式。

涉及 `psql -c`、命令替换或包含括号的 Shell 参数时，不能只执行 `bash -n`。必须以与脚本相同的引号形式执行最小等价命令，确认 SQL 整体作为一个 `-c` 参数传入；禁止在 Shell 脚本中把用于分组的双引号写成 `\"`。后者可能通过 `bash -n`，但会在运行时把 SQL 中的括号误解析为 Shell 语法。

## 三、KB 包目录规范

KB 包解压后必须是单一目录，不允许散落文件。

```text
lianruan-crm-v3-kb-YYYYMMDD-编号-简短问题名/
├── README.md
├── KB说明.md
├── manifest/
│   ├── KB元数据.env
│   ├── 文件清单.tsv
│   └── SHA256SUMS
├── scripts/
│   ├── precheck.sh
│   ├── upgrade.sh
│   ├── verify.sh
│   └── rollback.sh
├── images/
│   ├── lianruan-crm-v3-api-目标版本.docker-image
│   ├── lianruan-crm-v3-nginx-目标版本.docker-image
│   └── lianruan-crm-v3-worker-目标版本.docker-image
├── database/
│   └── migrations/
│       └── YYYYMMDD_KB_编号_说明.sql
├── files/
│   ├── compose/
│   ├── config/
│   ├── scripts/
│   └── patches/
└── tests/
    ├── smoke.sh
    └── 验证清单.md
```

目录说明：

| 目录 | 是否必须 | 说明 |
| --- | --- | --- |
| `README.md` | 必须 | 给运维看的最短执行说明 |
| `KB说明.md` | 必须 | 问题背景、影响范围、修复内容、验证方式、回退方式 |
| `manifest/KB元数据.env` | 必须 | KB 编号、包型、精确源版本、允许源版本清单、目标版本、影响服务 |
| `manifest/SHA256SUMS` | 必须 | 包内文件校验值 |
| `scripts/precheck.sh` | 必须 | 只检查，不改生产 |
| `scripts/upgrade.sh` | 必须 | 自动备份、停启、修复、健康检查 |
| `scripts/verify.sh` | 必须 | 升级后复核 |
| `scripts/rollback.sh` | 必须 | 最小回退动作 |
| `images/` | 按需 | 镜像升级时必须提供 |
| `database/migrations/` | 按需 | 数据库结构或数据修复时必须提供 |
| `files/` | 按需 | 仅限配置、脚本、补丁资源；不要放 V2 文件 |
| `tests/` | 推荐 | 自动冒烟脚本和人工验证清单 |

## 四、KB 元数据规范

`manifest/KB元数据.env` 示例：

```bash
KB_ID=KB-20260731-001
KB_NAME="报价工作量试算修复"
PACKAGE_FAMILY=KB
PACKAGE_MODE=KB-IMAGE
SOURCE_VERSION=3.0.0-stage9.20.20260729
ALLOWED_FROM_VERSIONS=3.0.0-stage9.20.20260729
TARGET_VERSION=3.0.0-stage9.23.20260731
PACKAGE_TYPE=hotfix
REQUIRES_DB_MIGRATION=true
REQUIRES_IMAGE_LOAD=true
AFFECTED_SERVICES=api-1,api-2,worker,nginx
DEFAULT_INSTALL_ROOT=/opt/lianruan-crm-v3
BUILD_COMMIT=kb-20260731-001-quote-workload-fix
BUILD_TIME=2026-07-31T00:00:00Z
```

元数据文件必须能被 `bash` 直接读取。凡是值中包含空格、中文说明、括号或其他特殊字符，必须使用双引号包裹，例如 `KB_NAME="UniSDP PC单点登录优化"`。交付前除了 `bash -n` 脚本语法检查外，还必须执行等价读取校验：

```bash
set -a
. manifest/KB元数据.env
set +a
```

该校验用于防止 `KB_NAME=UniSDP PC单点登录优化` 这类运行时拆词错误。

字段要求：

| 字段 | 说明 |
| --- | --- |
| `KB_ID` | 唯一编号，不可复用 |
| `PACKAGE_FAMILY` | 固定为 `KB` |
| `PACKAGE_MODE` | `KB-FILE`、`KB-LAYER`、`KB-IMAGE` 或 `KB-DB` |
| `SOURCE_VERSION` | 本包主要验证的精确源版本 |
| `ALLOWED_FROM_VERSIONS` | 已实际验证可升级的精确源版本清单，不允许用最低版本推断兼容范围 |
| `TARGET_VERSION` | 升级后的 V3 版本 |
| `REQUIRES_DB_MIGRATION` | 是否包含 SQL |
| `REQUIRES_IMAGE_LOAD` | 是否包含镜像 |
| `AFFECTED_SERVICES` | 受影响服务，必须精确 |
| `DEFAULT_INSTALL_ROOT` | 默认安装目录 |
| `BUILD_COMMIT` | 构建标识 |
| `BUILD_TIME` | 构建时间 |

## 五、KB 制作流程

### 5.1 开发前确认

每个 KB 制作前必须确认：

1. 该修复属于 V3 范围。
2. 修复位置在 `apps/`、`packages/`、`database/`、`deploy/single-server/` 或 V3 明确保留的 `apps/web/public/`。
3. 不是修改旧 `backend/`、旧 `frontend/`。
4. 已确认生产当前版本。
5. 已确认是否需要数据库迁移。
6. 已确认是否影响 V2 兼容接口。
7. 已确认回退方式。

### 5.2 代码修复和验证

本地至少执行：

```bash
npm run check
npm test
npm run build
```

涉及数据库、接口、生产包时执行完整门禁：

```bash
npm run verify
```

如果修复旧静态入口，还必须补充：

```bash
node --check apps/web/public/admin-app.js
node --check apps/web/public/partner-app.js
node --check apps/web/public/mobile-app.js
```

按实际修改文件选择执行，不需要无关文件全部检查。

### 5.3 构建镜像

镜像型 KB 必须重新构建受影响镜像。

```bash
V3_IMAGE_TAG=目标版本 deploy/single-server/scripts/build-images.sh
V3_IMAGE_TAG=目标版本 V3_SKIP_PULL=1 deploy/single-server/scripts/save-images.sh
```

如果只修 API，只允许包含 API 镜像；如果只修前端，只允许包含 Nginx Web 镜像；如果 Worker 未变化，不要把 Worker 镜像放入 KB 包。

### 5.4 准备 SQL

数据库迁移命名：

```text
YYYYMMDD_KB_编号_中文说明.sql
```

示例：

```text
20260731_KB_001_修复报价工作量历史映射.sql
```

SQL 要求：

1. 必须可重复执行。
2. 必须写入或兼容 `migration.schema_migrations`。
3. 不能直接删除生产数据。
4. 大批量修复必须分批或说明执行时间。
5. 金额、订单、审批、账号权限修复必须有业务验收样本。

### 5.5 生成 ZIP

制作 KB 包时只使用 ZIP。

```bash
cd tmp/kb-build
zip -qr -X lianruan-crm-v3-kb-YYYYMMDD-编号-简短问题名.zip lianruan-crm-v3-kb-YYYYMMDD-编号-简短问题名
sha256sum lianruan-crm-v3-kb-YYYYMMDD-编号-简短问题名.zip > lianruan-crm-v3-kb-YYYYMMDD-编号-简短问题名.zip.sha256
```

禁止使用：

```text
tar
tar.gz
tgz
*.tar
*.tar.gz
*.tgz
rar
7z
python 解压脚本作为唯一解压方案
```

## 六、生产升级执行规范

### 6.1 上传和解压

生产服务器执行：

```bash
cd /tmp
sha256sum -c lianruan-crm-v3-kb-YYYYMMDD-编号-简短问题名.zip.sha256
unzip -q lianruan-crm-v3-kb-YYYYMMDD-编号-简短问题名.zip
cd lianruan-crm-v3-kb-YYYYMMDD-编号-简短问题名
```

### 6.2 预检查

```bash
sudo bash scripts/precheck.sh /opt/lianruan-crm-v3
```

预检查必须只读，不允许修改生产。

检查项：

1. 当前用户是否 root 或 sudo。
2. 系统是否 openEuler 或 Euler 标识。
3. CPU 架构是否 `x86_64`。
4. 安装目录是否存在。
5. 是否为 V3 安装目录。
6. Docker 和 Docker Compose 是否可用。
7. 目标容器是否存在。
8. 当前版本是否与 `SOURCE_VERSION` 相同，或明确包含在 `ALLOWED_FROM_VERSIONS` 中。
9. 磁盘剩余空间是否足够。
10. 包内文件校验是否通过。

### 6.3 自动升级

```bash
sudo bash scripts/upgrade.sh /opt/lianruan-crm-v3
```

自动升级必须按这个顺序执行：

```mermaid
flowchart LR
  A["预检查"] --> B["生成升级日志目录"]
  B --> C["执行生产备份"]
  C --> D["保存当前版本快照"]
  D --> E["停止受影响服务"]
  E --> F["加载镜像或复制文件"]
  F --> G["同步版本变量"]
  G --> H["执行数据库迁移"]
  H --> I["启动服务"]
  I --> J["健康检查"]
  J --> K["业务冒烟"]
  K --> L["输出升级结果和回退命令"]
```

### 6.4 自动备份要求

KB 升级前必须执行自动备份，但不得默认调用服务器旧 `backup.sh`。如果旧脚本依赖 `tar`、`python`、`jq`、`rsync` 等未承诺命令，升级包会在生产环境失败。

推荐 KB 自带备份逻辑：

```bash
backup_dir="/opt/lianruan-crm-v3/backups/local/时间戳-KB编号-preupgrade"
mkdir -p "${backup_dir}"
cd /opt/lianruan-crm-v3/compose
docker compose exec -T postgres pg_dump -U lianruan_app -d lianruan_crm_v3 > "${backup_dir}/postgres.sql"
cd /opt/lianruan-crm-v3/data
zip -qr -X "${backup_dir}/uploads.zip" uploads
zip -qr -X "${backup_dir}/exports.zip" exports
```

同时 KB 脚本必须额外保存：

```text
/opt/lianruan-crm-v3/releases/升级前版本/
├── compose/docker-compose.yml
├── config/v3.env
├── config/deploy.env
├── config/nginx/default.conf
└── scripts/
```

注意：

1. 使用 KB 自带脚本备份数据库和业务文件，业务目录只使用 ZIP。
2. `releases/` 快照用于应用配置回退。
3. 数据库回退不应自动执行，必须人工确认恢复策略。

### 6.5 停启服务要求

只停受影响服务，减少影响范围。

| 影响范围 | 停止服务 |
| --- | --- |
| 只改前端静态资源或 Nginx 配置 | `nginx` |
| 只改 API | `nginx`、`api-1`、`api-2` |
| 改 Worker | `worker` |
| 改数据库迁移 | 通常停止 `nginx`、`api-1`、`api-2`、`worker`，保留 `postgres`、`redis-state` |
| 改 Compose 网络、PostgreSQL、Redis | 进入维护窗口，按完整停启处理 |

推荐命令：

```bash
cd /opt/lianruan-crm-v3/compose
docker compose stop nginx
docker compose stop api-1 api-2 worker
docker compose up -d api-1 api-2 worker nginx
```

不要使用：

```bash
pkill -f node
pkill -f server.js
```

### 6.6 健康检查要求

升级后必须执行：

```bash
/opt/lianruan-crm-v3/scripts/health-check.sh
```

还要直接检查：

```bash
curl -fsS http://127.0.0.1/health/live
curl -fsS http://127.0.0.1/health/ready
curl -fsS http://127.0.0.1/health/dependencies
```

如果 `/health/dependencies` 被 Nginx 来源限制拦截，应在服务器本机执行，或通过 Compose 直接访问 API 容器。

## 七、KB 脚本模板

以下模板只使用 openEuler 常见基础命令，不依赖 tar、jq、python、rsync。

模板脚本启用 `set -euo pipefail` 后，新增命令时必须避开会因管道提前关闭而误判失败的写法。尤其是校验目标镜像时，不得写 `docker compose config | grep -q 目标镜像`；必须先将 `docker compose config` 输出保存到变量或文件，再对保存内容做匹配。

目标镜像通过 `docker load -i` 加载后，不得将构建机上的 Docker 镜像 ID 作为生产端的强制相等断言。不同 Docker 引擎可能在加载时重算镜像配置摘要，即使根文件系统层和运行入口完全一致。升级前必须继续严格校验源镜像 ID；目标镜像应依次校验包内 `.docker-image` 的 SHA-256、目标标签存在、继承的源根文件系统层、健康接口以及本次修复对应的运行后断言。

目标服务启动后，健康检查必须在合理等待窗口内重试，不得将 Nginx 在 API 实例注册前返回的一次 `502` 直接判定为升级失败。自动回退后只能执行旧版本的存活和就绪检查，禁止复用要求“当前版本必须为目标版本”的升级后自检脚本。

多实例 API 切换后，必须先分别确认每个 API 容器达到 `healthy`，再通过 Nginx 执行 HTTP 自检。所有 HTTP 业务自检必须使用同一套重试机制，包括 `/health/live`、`/health/ready`、IAM 配置等接口；禁止仅对基础健康接口重试、随后对业务接口执行一次请求，因为上游注册和连接恢复仍可能存在短暂时间差。健康检查必须使用部署配置中的真实路由，并校验 JSON 业务字段，禁止只根据 HTTP `200` 判断成功，避免把前端兜底 HTML 当作 API 健康响应。

Shell 变量名必须符合 `[A-Za-z_][A-Za-z0-9_]*`，不得使用中文或其他非 ASCII 字符作为变量标识符。`bash -n` 可能把 `中文变量="值"` 解析为普通命令而不报语法错误，因此交付前必须扫描非 ASCII 变量赋值和变量展开，并使用与生产相同主版本的 Bash 实际执行关键脚本路径；只通过 `bash -n` 不视为脚本验证完成。

### 7.2 `scripts/upgrade.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

install_root="${1:-${INSTALL_ROOT:-/opt/lianruan-crm-v3}}"
script_dir="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
package_root="$(cd "${script_dir}/.." && pwd)"
meta_file="${package_root}/manifest/KB元数据.env"

if [ -f "${meta_file}" ]; then
  set -a
  # shellcheck disable=SC1090
  . "${meta_file}"
  set +a
fi

kb_id="${KB_ID:-KB-UNKNOWN}"
target_version="${TARGET_VERSION:-unknown}"
timestamp="$(date '+%Y%m%d-%H%M%S')"
log_dir="${install_root}/logs/install"
log_file="${log_dir}/${kb_id}-${timestamp}.log"
release_dir="${install_root}/releases/${target_version}-pre-${timestamp}"

mkdir -p "${log_dir}"
exec > >(tee -a "${log_file}") 2>&1

失败处理() {
  local exit_code="$1"
  echo "KB 升级失败，退出码：${exit_code}"
  echo "升级日志：${log_file}"
  echo "如需回退应用配置，可执行：bash ${script_dir}/rollback.sh ${install_root} ${release_dir}"
}
trap '失败处理 $?' ERR

echo "开始执行 ${kb_id}，目标版本：${target_version}"

bash "${script_dir}/precheck.sh" "${install_root}"

backup_dir="${install_root}/backups/local/${timestamp}-${kb_id}-preupgrade"
mkdir -p "${backup_dir}"

备份目录为zip() {
  local source_dir="$1"
  local output_file="$2"
  local parent_dir
  local source_name
  parent_dir="$(dirname "${source_dir}")"
  source_name="$(basename "${source_dir}")"
  [ -d "${source_dir}" ] || mkdir -p "${source_dir}"
  (cd "${parent_dir}" && zip -qr -X "${output_file}" "${source_name}")
}

echo "执行升级前 ZIP 备份：${backup_dir}"
cd "${install_root}/compose"
docker compose exec -T postgres pg_dump -U lianruan_app -d lianruan_crm_v3 > "${backup_dir}/postgres.sql"
备份目录为zip "${install_root}/data/uploads" "${backup_dir}/uploads.zip"
备份目录为zip "${install_root}/data/exports" "${backup_dir}/exports.zip"

echo "保存当前应用配置快照：${release_dir}"
mkdir -p "${release_dir}/compose" "${release_dir}/config" "${release_dir}/scripts"
cp "${install_root}/compose/docker-compose.yml" "${release_dir}/compose/docker-compose.yml"
cp "${install_root}/config/v3.env" "${release_dir}/config/v3.env"
[ -f "${install_root}/config/deploy.env" ] && cp "${install_root}/config/deploy.env" "${release_dir}/config/deploy.env"
[ -f "${install_root}/config/nginx/default.conf" ] && mkdir -p "${release_dir}/config/nginx" && cp "${install_root}/config/nginx/default.conf" "${release_dir}/config/nginx/default.conf"
cp "${install_root}/scripts/"*.sh "${release_dir}/scripts/" 2>/dev/null || true

cd "${install_root}/compose"

echo "停止受影响服务。"
docker compose stop nginx || true
docker compose stop api-1 api-2 worker || true

if [ -d "${package_root}/images" ] && ls "${package_root}/images/"*.docker-image >/dev/null 2>&1; then
  echo "加载 KB 镜像。"
  for image_file in "${package_root}/images/"*.docker-image; do
    docker load -i "${image_file}"
  done
fi

if [ -d "${package_root}/files/compose" ]; then
  echo "更新 Compose 文件。"
  cp "${package_root}/files/compose/docker-compose.yml" "${install_root}/compose/docker-compose.yml"
fi

if [ -d "${package_root}/files/config/nginx" ]; then
  echo "更新 Nginx 配置。"
  mkdir -p "${install_root}/config/nginx"
  cp "${package_root}/files/config/nginx/default.conf" "${install_root}/config/nginx/default.conf"
fi

if [ -d "${package_root}/files/scripts" ]; then
  echo "更新运维脚本。"
  cp "${package_root}/files/scripts/"*.sh "${install_root}/scripts/"
  chmod 750 "${install_root}/scripts/"*.sh
fi

if [ -d "${package_root}/database/migrations" ]; then
  echo "同步数据库迁移文件。"
  mkdir -p "${install_root}/database/migrations"
  cp "${package_root}/database/migrations/"*.sql "${install_root}/database/migrations/" 2>/dev/null || true
fi

if [ "${target_version}" != "unknown" ]; then
  echo "同步版本变量。"
  if grep -q '^V3_IMAGE_TAG=' "${install_root}/compose/.env"; then
    sed -i "s#^V3_IMAGE_TAG=.*#V3_IMAGE_TAG=${target_version}#" "${install_root}/compose/.env"
  else
    printf 'V3_IMAGE_TAG=%s\n' "${target_version}" >> "${install_root}/compose/.env"
  fi
  sed -i "s#^V3_BUILD_VERSION=.*#V3_BUILD_VERSION=${target_version}#" "${install_root}/config/v3.env"
fi

echo "执行数据库迁移。"
INSTALL_ROOT="${install_root}" "${install_root}/scripts/migrate-db.sh"

echo "启动服务。"
docker compose up -d api-1 api-2 worker nginx

echo "执行健康检查。"
INSTALL_ROOT="${install_root}" "${install_root}/scripts/health-check.sh"

if [ -x "${package_root}/tests/smoke.sh" ]; then
  echo "执行 KB 冒烟测试。"
  bash "${package_root}/tests/smoke.sh" "${install_root}"
fi

echo "KB 升级完成。"
echo "升级日志：${log_file}"
echo "升级前配置快照：${release_dir}"
```

自检脚本强制要求：

1. 断言必须来自本次修复后的真实接口响应和业务设计，不得复制旧包脚本后不复核。当前设计同时支持移动端 IAM、PC IAM 和 PC UniSDP，接口 `/api/auth/sso/iam/config` 应断言 `enabled:true`，不得依赖已废弃的 PC 独立开关字段。
2. 前端资源不得写死 Vite 构建后的哈希文件名，例如 `/assets/index-xxxx.js`、`SingleSignOnPage-xxxx.js`；应从 `/login` 或目标入口 HTML 动态提取实际资源路径，或检查 `admin-app.js`、`partner-app.js`、`mobile-app.js` 等稳定文件。
3. 写入 `tests/smoke.sh` 的每个关键字，都必须先用本地构建产物或目标环境接口响应验证存在；只凭代码印象写断言视为未通过出包检查。
4. 如果生产日志显示容器镜像、健康检查和业务主流程已经通过，仅自检脚本误判失败，应制作 R2 修正包并说明可直接运行 `verify.sh` 完成验收，不得要求用户回退健康服务。

## 十四、生产升级失败复盘与强制防复发规则

本章来源于 `KB-20260818-025` 区域管理员单点登录修复包 R1 至 R8 的实际生产升级过程。以下规则不是建议项，而是后续所有 SP、KB 出包的一票否决门禁。

### 14.1 R1 至 R8 复盘

| 阶段 | 生产现象 | 根因 | 后续强制规则 |
| --- | --- | --- | --- |
| R1 | 预检查直接拒绝升级 | 包内记录的源 API 镜像摘要来自本地旧基线，与生产 KB024 实际镜像不一致 | 出包前必须只读核对生产 `V3_IMAGE_TAG`、实际运行容器镜像和源镜像摘要；源镜像摘要必须严格相等，不得根据标签猜测 |
| R2 | 目标镜像加载成功后被摘要门禁拒绝 | 不同 Docker 引擎加载镜像归档时可能重算镜像配置摘要，生产目标镜像 ID 与构建机目标镜像 ID 不同 | 不得强制比较构建机与生产的目标镜像 ID；改为校验外层 ZIP、包内镜像归档、目标标签、源层继承、运行入口、运行用户和业务断言 |
| R3 | API 刚切换即收到一次 `502`，脚本自动回退 | 容器启动完成不等于两个 API 实例均已健康，也不等于 Nginx 上游连接已经恢复 | 必须先分别等待 API-1、API-2 达到 `healthy`，再通过 Nginx 自检；合理等待窗口内的瞬时 `502` 必须重试 |
| R4 | `/live`、`/ready` 重试后，IAM 配置接口一次 `502` 仍触发回退 | 只给基础健康接口增加重试，业务自检仍为单次请求 | 所有 HTTP 自检必须共用统一重试机制，不能遗漏 IAM 配置、登录配置或本次修复对应的业务接口 |
| R5 | 自检脚本第 38 行报“接口响应：未找到命令”，退出码 `127` | Bash 变量使用中文标识符；`bash -n` 将该行解析成普通命令，因此静态语法检查未发现 | Shell 变量名必须使用 ASCII 标识符；交付前必须扫描非 ASCII 变量赋值和展开，并实际执行关键脚本路径 |
| R5 深入核查 | `/live`、`/ready` 返回前端 HTML 且 HTTP 为 `200` | 正式 Nginx 健康路由是 `/health/live`、`/health/ready`，错误路径被前端兜底页面接管 | 健康路径必须来自当前部署配置；除了 HTTP 成功，还必须断言响应为 API JSON，并包含 `success:true`、`status:ok` 等稳定业务字段 |
| R6 | 修正后完成闭环验收 | 在隔离环境中执行了完整升级、再次复核、失败回退、瞬时 `502` 重试和 HTML 假健康拦截 | 最终包必须以同等深度执行运行级测试，并从最终 ZIP 重新解压验证，不能只验证打包前目录 |
| R7 出包前核查 | `.env`、构建版本和健康接口都显示 R6，但 API-1、API-2 实际仍运行 KB022 | 只验证了配置与接口中的环境变量，没有在升级成功前核对容器 `Config.Image` 和 `.Image`；执行终端残留的 `V3_IMAGE_TAG` 还可能覆盖 Compose `.env` | 版本判定必须同时核对配置版本、Compose 展开镜像、容器声明镜像和容器实际镜像摘要；Compose 调用必须隔离外部覆盖变量；回退必须恢复升级前真实运行镜像 |
| R7 在 SP002 环境执行 | 源版本门禁拒绝从 SP002 执行仅允许 R6 的 R7 包 | 目标环境已经包含 R7 制包基线之后的 SP002 变更，旧包若仅放宽版本校验，会以 R6 产物覆盖 SP002 并造成功能降级 | 源基线不一致时必须停止；只读取得目标环境实际镜像并确认后续差异，基于该实际镜像重制新修订包；禁止放宽旧包门禁跨基线升级 |
| R8 | 基于生产 SP002 实际镜像重制并完成闭环验收 | 目标镜像完整继承 SP002 根文件系统层，只叠加本次认证修复，并对 SP002 独有配置文件做哈希保护 | 跨分支补丁必须继承目标环境真实基线、保护已知后续修复，并重新执行升级、复核、回退和最终 ZIP 反向验收 |

### 14.2 生产只读核对基线

制作任何绑定精确生产基线的 KB 前，必须在不修改生产文件、配置、数据和服务的前提下记录：

1. `/opt/lianruan-crm-v3/compose/.env` 中的 `V3_IMAGE_TAG`。
2. `/opt/lianruan-crm-v3/config/v3.env` 中的构建版本和构建提交。
3. `docker compose config --images` 显示的 Compose 展开镜像，执行时必须清除可能残留的外部覆盖变量。
4. `docker inspect` 显示的容器 `Config.Image`、`.Image` 实际镜像摘要和健康状态，不能只看 Compose 解析标签。
5. API、Nginx、Worker 的实际运行版本是否与 Compose 标签别名一致。
6. 本次升级依赖的真实接口路径、状态码、内容类型和稳定响应字段。

配置中的 `V3_IMAGE_TAG`、`V3_BUILD_VERSION` 和健康接口返回的构建版本都可能只来自环境变量，不能单独证明容器已使用目标镜像。升级成功门禁必须同时满足：

1. Compose 展开镜像为目标标签。
2. API-1、API-2 的 `Config.Image` 均为目标标签。
3. API-1、API-2 的 `.Image` 均等于当前 Docker 中目标标签对应的实际镜像摘要。
4. 两个容器内都能验证本次修复的精确代码或资源断言。

Compose 调用必须显式使用安装目录的 `docker-compose.yml` 和 `.env`，并在命令环境中清除 `V3_IMAGE_TAG`、`COMPOSE_FILE`、`COMPOSE_PROJECT_NAME` 等可能从执行终端继承的覆盖值。需要切换目标镜像时，必须在已清理的命令环境中显式传入目标 `V3_IMAGE_TAG`，并使用 `--force-recreate` 后再执行上述四项硬校验。

诊断生产失败时只允许读取日志、版本、容器状态、镜像元数据和接口响应。没有单独授权时，不得为了验证猜测而修改生产文件、重启服务、运行迁移或写入数据。

发现目标环境配置版本、实际运行镜像或镜像摘要与制包源基线不一致时，必须遵守以下规则：

1. 立即停止升级，保留严格源版本门禁；不得直接修改旧包的 `SOURCE_VERSION`、允许版本列表或镜像摘要后继续执行。
2. 只读确认目标环境是否已经包含原补丁或其他后续修复，不能只根据版本字符串推断新旧关系。
3. 确需补丁时，从目标环境只读取得实际运行镜像，以其为新基线制作新的修订包；目标镜像必须完整继承新基线，并仅叠加本次必要变更。
4. 对新基线独有的关键运行文件、配置能力或业务修复增加精确断言，证明新包没有回退或覆盖后续能力。
5. 新修订包必须使用新的目标版本和包编号，重新完成镜像构建、运行级测试、回退测试、清单生成和最终 ZIP 反向验收，禁止沿用旧包的测试结论。

### 14.3 镜像校验边界

源镜像和目标镜像采用不同校验策略：

- 源镜像是升级安全基线，必须校验生产实际镜像 ID 与元数据记录严格一致。
- 目标镜像不能要求生产加载后的镜像 ID 与构建机相同。
- 目标镜像必须校验 `.docker-image` 文件 SHA-256、目标标签存在、源根文件系统层完整继承、`User`、`WorkingDir`、`Entrypoint`、`Cmd` 和版本标签。
- 必须在镜像内部检查本次修复对应的精确代码或资源断言；只搜索可能在旧版本其他位置已经存在的宽泛关键字不合格。
- 交付前必须删除本地目标标签，再仅使用包内 `.docker-image` 执行 `docker load -i`，证明镜像归档可以独立恢复。

### 14.4 健康检查与业务自检

API 双实例升级后的强制顺序为：

1. 等待 API-1 容器达到 `healthy`。
2. 等待 API-2 容器达到 `healthy`。
3. 重试 `/health/live`，并校验 API JSON。
4. 重试 `/health/ready`，并校验 API JSON。
5. 重试本次变更涉及的业务接口。
6. 在两个目标容器内分别验证本次修复断言。

禁止以下做法：

- 使用 `/live`、`/ready` 等未经部署配置确认的路径。
- 只检查 HTTP `200`，不检查内容类型和业务字段。
- 基础健康接口重试，但 IAM 配置等业务接口只请求一次。
- 写死 Vite 构建哈希文件名。
- 复制旧包的 `enabled:false`、已删除字段或其他过时断言。

IAM 统一单点登录当前正确断言为：`enabled:true`，并包含 `entries`、`requestIsaidByEntry`、`timeoutMs`。每个字段必须独立检查，不得依赖 JSON 字段顺序。

### 14.5 Shell 脚本运行级门禁

`bash -n` 只能证明脚本语法可解析，不能证明命令语义正确。以下问题都可能通过 `bash -n`：

- 中文变量赋值被解析为命令。
- `set -o pipefail` 下游 `grep -q` 提前关闭管道导致上游非零退出。
- GNU 与 BSD 命令参数差异。
- 错误 URL 返回前端 HTML `200`。
- 命令替换、引号或 SQL 参数在运行时被拆分。

出包前必须同时执行：

1. 所有脚本 `bash -n`。
2. Shell 变量赋值和 `${变量}` 展开的非 ASCII 标识符扫描。
3. 与生产相同 Bash 主版本和 GNU 基础命令语义的运行级测试。
4. `upgrade.sh` 从允许源版本到目标版本的完整演练。
5. `verify.sh` 在目标版本上的重复复核。
6. `rollback.sh` 恢复源版本并检查旧服务健康。
7. 至少一次瞬时 `502` 后重试成功的故障注入。
8. 至少一次 HTTP `200` 但返回前端 HTML 的假健康拦截测试。

### 14.6 自动回退边界

不含数据库变更的 API 镜像 KB 可以在应用切换失败时自动恢复旧镜像引用和配置，但必须遵守：

- 回退只恢复应用镜像引用、配置和受控文件，不自动恢复数据库。
- 回退快照必须同时记录配置版本、容器 `Config.Image` 和容器 `.Image` 摘要；当三者不一致时，必须恢复升级前容器真实使用的镜像，禁止只根据 `.env` 推测回退标签。
- 回退后只检查旧版本 `/health/live`、`/health/ready` 和必要的旧业务查询。
- 回退后禁止复用要求当前版本等于目标版本的 `smoke.sh`。
- 日志必须明确记录失败步骤、退出码、回退动作、回退后版本和配置快照目录。
- 如果目标服务真实健康且仅自检断言错误，不得机械回退，应停止切换并进入人工复核。
- 升级失败后必须立即核对 `V3_IMAGE_TAG`、API 双实例实际镜像和接口构建版本，确认目标版本仍在运行还是已经回退；目标版本已回退时，旧业务现象继续存在是预期结果，不能据此判断业务修复代码无效。
- 如果目标版本仍健康运行且仅自检误判，可制作只修正验证脚本的后续修订包，并允许单独执行 `verify.sh`；如果目标版本已经回退，后续修订包必须重新执行完整升级，不能只运行验证脚本。
- 升级成功和自动回退完成后，都必须输出当前版本、实际运行镜像和双实例健康状态，不能只输出“完成”文字。

### 14.7 最终交付物反向验收

最终 ZIP 生成后，必须在独立空目录中重新完成：

1. 同名 `.zip.sha256` 校验。
2. `unzip -t` 和实际 `unzip` 解压。
3. 包内 `manifest/SHA256SUMS` 校验。
4. 解压后所有脚本 `bash -n`。
5. 非 ASCII Shell 变量扫描。
6. `tar`、`gzip`、`jq`、`python`、`rsync` 等禁止依赖扫描。
7. 镜像重新加载、层继承、入口和业务修复断言。
8. 从解压后的脚本重新执行关键运行级自检。

任何一项未执行或失败，都不得把包交付生产。

## 十五、建议后续补充的自动制包脚本

建议后续新增：

```text
scripts/kb/create-kb-package.sh
```

脚本目标：

1. 读取 KB 元数据。
2. 自动创建标准目录。
3. 自动复制脚本模板。
