# 阶段3认证权限审计底座落地方案

生成日期：2026-07-23

## 1. 交付边界

本文件依据 `docs/V3总体改造与实施方案/13-阶段3-认证权限审计底座.md`、阶段0基线资料和当前工作区事实编写。

当前阶段1、阶段2尚未合入，因此本次只交付可审查、可合并的权限底座设计与静态校验资产，不修改后端、前端、数据库、样本库、日志、备份包和客户台账。

阶段3真正编码落地时，任何新迁移接口必须满足以下原则：

- 身份只来自服务端会话、统一身份认证映射、真实客户关系管理系统映射或受控开放接口令牌。
- 不信任前端传入的 `operatorId`、`operatorRole`、`userId`、`role`、`region`、`partnerId` 等授权字段。
- 超级管理员也必须通过显式权限授权，不使用隐藏全局绕过。
- 数据范围必须转化为数据库查询条件，不允许先读全量数据再在内存中过滤。
- 敏感操作必须先具备可写审计能力，审计不可用时按风险等级阻断。

## 2. 阶段0基线结论

| 项目 | 阶段0事实 | 阶段3落地要求 |
| --- | --- | --- |
| 当前角色 | `superadmin`、`admin`、`partner_admin`、`staff` | 建立显式角色、权限、数据范围绑定 |
| 历史角色 | 阶段0矩阵未发现其他样本角色，页面清单标记历史角色待确认 | 未确认角色不自动授权，不自动提升为管理员 |
| 身份风险 | 部分接口读取前端操作者、角色、区域、渠道或用户编号 | 迁移接口统一从会话注入操作者 |
| 密码风险 | 样本账号存在疑似明文密码 | 本地凭据统一迁移为 `scrypt` 散列 |
| 数据范围来源 | `region`、`bigRegion`、`partnerId`、`parentPartnerId`、`createdBy`、`owner`、`assignedStaffId` | 统一沉淀为组织、渠道关系和本人关系策略 |
| 审计现状 | 已有独立 SQLite 审计库 | V3 统一写入 PostgreSQL 审计事件表，敏感字段脱敏 |

## 3. 服务端统一身份模型

### 3.1 身份来源优先级

| 优先级 | 来源 | 使用范围 | 授权原则 |
| ---: | --- | --- | --- |
| 1 | 统一身份认证 | 正式组织账号首选入口 | 外部主体必须映射到一个有效本地用户 |
| 2 | 真实客户关系管理系统登录 | 已确认兼容入口 | 只接受显式映射，不按姓名或用户名模糊绑定 |
| 3 | 本地应急管理员 | 外部身份系统故障和紧急运维 | 默认关闭，独立账号，双人保管，来源地址白名单，全量审计 |
| 4 | 测试模拟登录 | 开发和测试构建 | 不进入生产镜像，不允许环境变量误开启 |

多个外部来源可以映射到同一个 `iam_users` 用户，但每个外部来源加外部主体只能对应一个有效本地用户。外部登录成功但本地映射缺失时，返回中文错误并写入安全审计，不自动创建高权限账号。

### 3.2 用户表模型

| 表或模型 | 关键字段 | 落地约束 |
| --- | --- | --- |
| `iam_users` | 用户编号、用户名规范化值、姓名、手机号摘要、邮箱摘要、账号状态、授权版本、身份类型、创建时间、更新时间 | 用户名规范化后唯一；状态变化必须记录原因、操作者和审计事件 |
| `iam_credentials` | 用户编号、算法、算法版本、盐、散列值、参数、是否当前凭据、首次登录强制修改标记 | 本地密码使用 Node.js 内置 `scrypt`；不保存明文；常量时间比较 |
| `iam_external_identities` | 用户编号、来源、外部主体、外部显示名、绑定状态、最后验证时间 | 来源加外部主体唯一；冲突映射拒绝；禁止模糊匹配 |
| `iam_user_status_logs` | 用户编号、原状态、新状态、原因、操作者、请求编号 | 停用、锁定、拒绝、恢复均可追溯 |

### 3.3 账号状态语义

| 状态 | 中文含义 | 登录策略 | 会话策略 |
| --- | --- | --- | --- |
| `active` | 正常 | 允许登录 | 允许继续使用 |
| `pending` | 待审核 | 拒绝登录 | 不创建会话 |
| `rejected` | 已拒绝 | 拒绝登录 | 不创建会话 |
| `disabled` | 已停用 | 拒绝登录 | 立即撤销既有会话 |
| `locked` | 安全锁定 | 拒绝登录，按锁定策略提示 | 保持撤销或强制重新验证 |
| `password_reset_required` | 必须修改密码 | 只允许进入改密流程 | 改密成功后重新签发会话 |
| `deleted` | 逻辑删除 | 拒绝登录 | 立即撤销既有会话 |

状态检查必须在登录前、登录后和每次受保护请求时执行。状态变化必须提升用户授权版本，使旧会话无法继续执行敏感动作。

## 4. 统一会话模型

| 组件 | 作用 | 关键规则 |
| --- | --- | --- |
| 浏览器安全 Cookie | 保存会话令牌 | 设置 `HttpOnly`、`Secure`、合适的 `SameSite`，不暴露给业务前端 |
| Redis 会话内容 | 保存热会话 | 包含用户编号、授权版本、登录来源、创建时间、最后活动时间、过期时间、设备摘要、来源地址摘要 |
| PostgreSQL 会话摘要 | 保存可撤销事实 | 保存令牌摘要、会话来源、设备、撤销原因、撤销操作者、撤销时间 |
| 授权版本 | 快速失效旧会话 | 密码修改、账号停用、角色权限变化、应急操作后递增 |

建议默认策略待产品确认，阶段0已有默认建议为闲置2小时、最长12小时、并发设备数按角色控制。

受保护请求的会话校验顺序：

1. 读取安全 Cookie 或受控开放接口令牌。
2. 校验令牌摘要和 Redis 会话存在性。
3. 校验 PostgreSQL 会话未撤销。
4. 校验账号状态为可用状态。
5. 校验会话授权版本与用户当前授权版本一致。
6. 注入服务端操作者快照，后续授权只读该快照。

## 5. 角色权限模型

权限代码统一使用“模块.资源.动作”格式，例如 `identity.user.read`、`crm.registration.approve`、`audit.event.export`。

| 模型 | 关键规则 |
| --- | --- |
| `iam_roles` | 保存角色代码、中文名称、角色类型、是否系统内置、是否启用 |
| `iam_permissions` | 保存权限代码、中文名称、模块、资源、动作、风险等级 |
| `iam_role_permissions` | 保存角色和权限绑定，变更后提升授权版本 |
| `iam_user_roles` | 保存用户角色绑定、生效时间、失效时间、绑定原因 |
| `iam_data_scopes` | 保存用户或角色的数据范围绑定，不直接读取请求参数 |

常规角色仅包括阶段0确认出现的四类：

| 角色代码 | 中文名称 | 默认数据范围 | 说明 |
| --- | --- | --- | --- |
| `superadmin` | 超级管理员 | 总部范围 | 具备显式系统管理和全局业务权限，不作为隐藏绕过 |
| `admin` | 区域管理员 | 区域或大区范围 | 管理绑定区域内渠道、账号、审批和业务数据 |
| `partner_admin` | 渠道管理员 | 一级渠道或二级渠道范围 | 管理本渠道及经确认下级渠道范围内业务和员工 |
| `staff` | 渠道员工 | 本人范围 | 只能处理本人创建、负责或被指派的数据 |

历史角色处理原则：

- 阶段0矩阵未发现除四类常规角色之外的样本用户角色。
- `partner`、`secondary_partner` 当前更像审批类型或渠道层级，不自动进入角色表。
- 中文旧称“企业管理员”映射到 `partner_admin`，中文旧称“企业用户”或“渠道员工”映射到 `staff`。
- 任何未知角色迁移时进入问题清单，默认不授权，不提升为 `admin` 或 `superadmin`。

详细矩阵见 `docs/stage-records/阶段3-角色权限矩阵落地版.md`。

## 6. 数据范围规则

### 6.1 范围类型

| 范围 | 范围代码 | 服务端来源 | 查询策略 |
| --- | --- | --- | --- |
| 总部 | `hq_all` | 内置总部组织绑定或超级管理员显式权限 | 可访问全部已授权资源，但仍需功能权限 |
| 大区 | `big_region` | `org_units` 大区绑定和区域归属 | 转化为大区下所有区域或渠道的数据库条件 |
| 区域 | `region` | `org_units` 区域绑定、用户区域绑定 | 使用标准区域代码过滤，不使用前端传入区域 |
| 一级渠道 | `primary_partner_tree` | `partner_partners`、`partner_relationships`、`partner_members` | 包含本一级渠道和已确认下级渠道树 |
| 二级渠道 | `secondary_partner` | 渠道成员关系和有效渠道层级 | 仅本二级渠道，不自动上溯读取一级渠道全部数据 |
| 本人范围 | `self` | 用户编号和业务责任关系 | 使用创建人、负责人、被指派人、审批人等标准关系字段 |

### 6.2 组合与拒绝规则

- 功能权限和数据范围必须同时满足。
- 一个用户有多个数据范围时，按同一资源的可组合条件求并集；跨资源不得互相借用范围。
- 无组织绑定、渠道关系断裂、区域标准化失败或范围冲突时保护性拒绝并告警。
- 列表、详情、更新、删除、审批、导出、下载和异步任务必须复用同一范围策略。
- 导出和异步任务创建时保存服务端确认的数据范围快照，执行和下载时再次校验当前权限。

## 7. 字段允许清单和服务端事实

每个写接口必须定义严格字段允许清单。未知字段默认拒绝，历史操作者字段只允许作为审计对比值，不参与授权。

| 字段类别 | 处理方式 |
| --- | --- |
| 创建人、更新人、审批人 | 由服务端会话写入 |
| 角色、区域、渠道归属 | 由组织、渠道和角色绑定计算 |
| 状态、金额、价格、折扣 | 由服务端状态机和计算规则写入 |
| 操作者相关历史字段 | 可记录“客户端自报值”和“服务端事实值”差异 |
| 密码、令牌、密钥、完整 Cookie | 禁止写入响应、普通日志和审计明细 |

## 8. 统一审计模型

审计事件模型、敏感操作清单和保留建议见 `docs/stage-records/阶段3-审计事件与敏感操作清单.md`。

阶段3统一审计的最低要求：

- 每个审计事件包含请求编号、服务端操作者、登录来源、模块、资源、动作、目标、结果、来源地址、用户代理和必要前后值。
- 密码、令牌、密钥、完整 Cookie、证书私钥和开放接口密钥只记录摘要或掩码。
- 登录、账号、权限、数据范围、应急管理员、密钥、导入、导出、审批、价格和恢复操作属于高风险审计。
- 高风险动作审计不可用时阻断；普通失败可进入可靠补偿队列。
- 审计查询本身必须受权限和脱敏约束，审计导出也必须写审计。

## 9. 本地应急管理员机制

### 9.1 设计目标

本地应急管理员只用于统一身份认证和真实客户关系管理系统登录不可用时的紧急运维，不替代日常超级管理员，不用于普通业务办理。

### 9.2 落地规则

| 控制点 | 规则 |
| --- | --- |
| 默认状态 | 默认关闭，生产配置必须显式设置启用，未启用时登录入口直接拒绝 |
| 独立账号 | 使用独立本地账号，身份类型标记为 `emergency_local`，不复用普通 `superadmin` 账号 |
| 双人保管 | 初始一次性密码或恢复密钥拆分为两份，由产品负责人和运维负责人分别保管 |
| 启用审批 | 每次启用必须填写故障原因、批准人、启用时段、来源地址范围和处置单编号 |
| 来源地址白名单 | 仅允许白名单来源地址或网段，白名单为空时不得启用 |
| 首次使用 | 首次登录强制修改密码，修改后撤销旧会话 |
| 会话限制 | 会话时长短于普通账号，建议最长不超过2小时，禁止长期保持 |
| 权限限制 | 只开放恢复、账号解锁、会话撤销、配置复核、审计查询和必要的权限恢复；业务数据写入默认禁止 |
| 全量审计 | 登录、失败、启用、禁用、每个操作、审计查询和导出全部按最高风险记录 |
| 告警 | 登录成功、登录失败、来源不符、越权尝试、禁用失败立即告警 |
| 退出复核 | 外部身份系统恢复后立即禁用，应急会话全部撤销，并输出操作报告 |

### 9.3 应急启停流程

1. 运维确认统一身份认证或真实客户关系管理系统登录不可用，并创建处置单。
2. 产品负责人和运维负责人共同批准启用时间、来源地址白名单和操作边界。
3. 两名保管人分别提供密钥片段或密码片段，合成后由应急管理员登录。
4. 登录后系统立即告警并写入高风险审计。
5. 故障处理期间，每个请求写入完整审计事件，不允许关闭审计。
6. 外部身份系统恢复后禁用应急入口、撤销会话、导出应急审计报告。
7. 产品负责人、运维负责人和安全负责人复核报告，确认是否需要补充整改。

## 10. 接口落地顺序建议

阶段1、阶段2合入后，阶段3编码建议按以下顺序推进：

1. 先建立身份、角色、权限、数据范围和审计表结构。
2. 实现密码散列、外部身份映射和账号状态服务。
3. 实现 Redis 共享会话和 PostgreSQL 会话摘要。
4. 实现权限声明、数据范围策略和审计写入服务。
5. 建立旧 `/api` 兼容认证层，只保护高风险旧接口，不重写业务逻辑。
6. 最后接入前端登录、会话接口和无权限处理。

| 门槛 | 验收证据 |
