## 1. 结论

阶段9已经完成 V3 架构、部署、迁移、接口和主业务闭环，但当前界面属于“新架构业务可用版”，不是“V2用户体感还原版”。阶段9.10的目标是保留 V3 后端、PostgreSQL、Redis、Docker Compose、迁移和接口能力，只改造前端界面体感，让 V2 用户切换到 V3 后菜单找得到、字段看得懂、流程走得通、页面密度和操作习惯基本一致。

本阶段不新增公海池等新功能，不维护 V2，不修改 V2 源码。所有远端调试和验证只允许使用 HexHub 资产「渠道CRM（新架构）」，不得操作其他 HexHub 资产。

## 3. 差距来源判定

| 项目 | V2现状 | V3现状 | 阶段9.10处理 |
| --- | --- | --- | --- |
| 页面壳层 | 深色固定侧边栏、顶部面包屑、右上通知和帮助 | 浅色侧栏、按钮式菜单、没有 V2 顶部结构 | 还原 V2 桌面壳 |

| 表格体感 | 高密度表格、状态标签、金额、行操作明确 | 通用列较少，信息不够 V2 | 逐页还原列和操作 |

## 4. 总体策略

阶段9.10采用“V2体感基线 + V3技术承载”的策略。

保留内容：

1. 保留 V3 Vue 3、路由、接口客户端、认证、权限、迁移和部署架构。
2. 保留 V3 PostgreSQL 正式业务表和 Redis 任务化基础。
3. 保留阶段9已经跑通的报备、商机、报价、订单接口。
4. 保留单机 Docker Compose 和 HexHub部署验证方式。

还原内容：

1. 还原 V2 管理端深色侧边栏、菜单分组、顶部面包屑和账号区。
2. 还原 V2 筛选工具条、表格密度、状态标签、金额展示、行操作。
3. 还原客户报备、商机、报价、订单、渠道商、产品、审核、账号、OpenAPI、工作量等页面的字段和流程。
4. 还原手机一期的移动端查询、待办、列表、详情和轻量操作体感。
5. 保留 V2 用户熟悉的页面名称和业务文案，避免无意义改名。

不做内容：

1. 不把 V2 的 `admin-app.js` 整个复制进 V3 长期运行。
2. 不继续读 SQLite。
3. 不恢复 V2 密码和旧 OpenAPI 密钥。
4. 不新增公海池、线索池等 V2 不存在的新功能。
5. 不操作 HexHub 其他资产。

## 12. HexHub使用规则

1. 只允许使用 HexHub 资产「渠道CRM（新架构）」。
2. 不允许操作既往 V2 生产或其他测试资产。
3. 远端调试前必须先本地通过 `npm run verify`。
4. 远端部署必须保留安装日志、健康检查日志、页面巡检结果和截图。
5. 调试期间可以重复部署测试包，但每次必须记录版本、时间、改动范围和回退方式。
6. 不在 HexHub 上直接手改容器内代码，所有改动必须回到本地工程形成可复现提交或补丁。
7. 自动化业务闭环会产生测试数据，执行前必须使用“阶段9.10验收”命名，便于后续识别。

## 14. 风险和处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 直接复制 V2 大文件 | 破坏 V3架构，后续难维护 | 只提取 V2视觉和交互规范，V3组件化实现 |
| 字段不足 | 页面像 V2 但信息不完整 | 先列字段差距，再补接口和数据库映射 |
| 渠道权限不足 | 渠道端可能越权或看不到数据 | 菜单、接口、数据范围一起验收 |
| 手机端被桌面表格污染 | 手机上难操作 | 手机一期单独组件，不压缩桌面表格 |
| 导入导出拖慢主链路 | 延误第一闭环 | 先还原入口和任务结果，再补完整导入导出 |
| OpenAPI和工作量复杂 | 后台验收延期 | 归入 P2，不能影响报备到订单主链路 |
| 截图差异争议 | 无法判断是否通过 | 建立差异说明和产品签收表 |
| HexHub调试污染数据 | 测试数据混入业务数据 | 用阶段9.10命名并记录测试批次 |
