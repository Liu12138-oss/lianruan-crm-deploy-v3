# 阶段9业务可用迁移实施方案

生成日期：2026-07-27  
负责人角色：产品交付总监、架构师、前后端负责人、数据迁移负责人、测试负责人  
目标：在V3架构上恢复V2已有业务能力，并让用户体感变化最小

## 1. 执行结论

阶段9采用“V2体验基线 + V3架构承载”的迁移策略。

本阶段只迁移V2已有功能，不引入公海池、线索池等新功能。PC端保持菜单、字段、流程一致，视觉允许轻微现代化。手机端以V2一期为准。OpenAPI、工作量配置、导入导出等V2已有能力纳入阶段9首批范围，但按后台页面和风险批次分步交付。

阶段9第一验收闭环为：

```text
客户报备 -> 商机 -> 报价 -> 订单
```

## 4. 首批最高优先级

阶段9不得先做边缘页面，必须先恢复业务闭环。

第一优先级：

1. 账号、角色、渠道商正式可用。
2. 客户报备列表、新建、审核。
3. 商机列表、新建、跟进。
4. 产品目录和工作量配置。
5. 报价列表、新建、编辑、服务端试算。
6. 订单列表、转单、一级确认、调价、履约。
7. 审计日志追踪。

第二优先级：

1. 导入导出。
2. OpenAPI。
3. 经营报表。
4. 手机一期完整覆盖。

## 5. 技术落地要求

### 5.1 前端

1. 以V2菜单和页面为基线。
2. 不直接复制V2大文件作为长期代码。
3. 按业务模块拆成Vue页面和组件。
4. PC后台和PC渠道端尽量复用业务组件。
5. 手机一期单独适配，不复用PC表格。
6. 页面级开关必须存在。

### 5.2 后端

1. 保留V2旧接口路径兼容层。
2. 控制器调用V3服务，不读SQLite。
3. 所有列表接口服务端分页。
4. 所有写操作服务端鉴权、审计、幂等。
5. 报价和订单金额以服务端计算为准。
6. 导入导出进入Redis任务队列。

### 5.3 数据

1. 页面只读正式业务表。
2. 不允许页面直接读取 `migration.*` 暂存表。
3. 密码统一初始化，不恢复V2密码。
4. OpenAPI密钥重新签发。
5. 历史数据和新增数据必须可区分迁移批次。

## 8. 仍需控制的风险

| 风险 | 处理 |
| --- | --- |
| 阶段8.4未完成，页面无真实业务数据 | 阶段9业务页面启动前必须完成正式落表 |
| 用户体感变化过大 | 以V2截图逐页对照验收 |
| V2接口返回字段复杂 | 先兼容字段，再逐步整理V3标准契约 |
| 大数据量列表慢 | 强制服务端分页、索引和筛选 |
| 密码和密钥不可恢复 | 初始化密码、OpenAPI重新签发 |
| 金额计算风险 | 固定样本逐分校验 |

## 9. 可开始条件

根据用户确认，阶段9业务口径已经明确，可以进入阶段9.0和阶段8.4并行准备。

建议下一步执行：

1. 启动阶段8.4正式业务表迁移方案和脚本。
2. 启动阶段9.0 V2体验基线冻结。
3. 将PC后台24个页面、PC渠道12个页面、手机一期19个页面拆成任务卡。
4. 优先安排第一闭环页面和接口。
