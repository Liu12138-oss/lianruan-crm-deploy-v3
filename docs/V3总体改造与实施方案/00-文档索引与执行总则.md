# V3 总体改造与实施方案文档索引

## 1. 文档目的

本套文档用于指导联软渠道管理平台 V3 在不增加新业务功能的前提下，完成工程化、模块化、关系型数据建模、认证授权、性能、稳定性、可观测性、容器化部署和 V2 数据迁移改造。

文档不是方向性建议，而是项目执行基线。项目负责人可以按阶段和任务编号拆分工作，开发、测试、运维可以按验收条件提交证据，任何偏离必须记录到决策日志。

## 2. 已确认决策

| 决策项 | 已确认结论 |
| --- | --- |
| 服务范围 | 只服务联软总部及其渠道体系，不建设面向多家厂商的软件即服务多租户平台 |
| 当前业务范围 | 只迁移和改造现有功能，不新增公海池及其他新功能 |
| V2 处理方式 | 不继续维护；V3 完成后一次性迁移 V2 数据 |
| 业务数据库 | PostgreSQL 16 或同主版本的受控补丁版本 |
| 缓存、会话和任务 | Redis 7，任务队列使用 BullMQ |
| 生产部署 | 优先支持一台服务器容器化部署，架构保留多机扩展能力 |
| 可用性目标 | 月度可用性目标不低于 99.9% |
| 数据恢复点目标 | 业务数据最多丢失 5 分钟 |
| 故障恢复时间目标 | 重大故障 30 分钟内恢复；单机整机损坏场景受备用机器到位时间影响 |
| 登录方式 | 统一身份认证优先，本地应急管理员作为受控补充 |
| 数据迁移窗口 | 允许停止 V2 业务 5 至 8 小时完成最终迁移和切换 |

## 3. 必须先理解的限制

一台物理服务器可以通过双应用实例、进程自恢复、健康检查、数据库持续归档和异地备份提高稳定性，但无法消除服务器硬件、操作系统、机房网络和电源故障形成的单点。

因此本方案把部署分为两级：

1. 首发单机版：符合当前部署偏好，具备进程级冗余、数据恢复和横向扩展接口。
2. 完整高可用版：应用、数据库、Redis 和入口均跨机器部署，用于真正保障机器级故障下的 99.9% 可用性和 30 分钟恢复目标。

单机版上线前必须具备异机或对象存储备份、外部存活监控和备用服务器恢复预案，否则不得对外承诺机器级高可用。

## 5. 执行顺序

阶段 0 至阶段 3 必须顺序执行。阶段 4 的接口契约稳定后，阶段 5 可以与阶段 4 后半程并行。阶段 6 依赖相关业务模块完成关系型数据迁移。阶段 7 可以提前准备环境，但必须在阶段 6 完成后进行完整验收。阶段 8 只能在前七个阶段全部通过退出门槛后启动。

不得因为进度压力跳过阶段 0、阶段 2、阶段 3、阶段 7 或阶段 8 的演练。

## 6. 当前系统基线事实

| 项目 | 当前事实 |
| --- | --- |
| 后端主程序 | `backend/server.js`，约 18123 行 |
| 管理端主程序 | `frontend/admin-app.js`，约 16798 行 |
| 渠道端主程序 | `frontend/partner-app.js`，约 9240 行 |
| 接口规模 | 后端约 248 个路由 |
| 业务存储 | SQLite 通用 `entities` 表，业务记录以 JSON 保存 |
| 审计存储 | 独立 SQLite `audit_logs` 表 |
| 认证风险 | 部分接口信任前端传入的操作人、角色、区域或用户编号 |
| 密码风险 | 现有本地账号存在明文密码存储和比较 |
| 运行方式 | 单进程 Node.js、静态文件服务、缺少完整生产编排 |
| 本地 V3 环境 | 已准备 PostgreSQL 和 Redis 容器 |

## 7. 项目完成定义

只有同时满足以下条件，V3 基础改造才算完成：

- 当前确认保留的页面、接口和业务流程全部通过回归，不增加未经确认的新功能。
- 所有在线业务数据进入 PostgreSQL 关系表，运行时不再依赖 SQLite 和全量内存对象。
- 所有受保护接口只信任服务端会话身份，并执行角色、权限和数据范围校验。
- 密码不以明文存储，令牌、密钥和敏感信息不进入前端静态文件和普通日志。
- 列表使用服务端分页，导入导出和长任务使用任务队列，写入具备事务、幂等和审计。
- 单机生产版完成压力、长稳、故障、备份和恢复演练，并保留可复核证据。
- 至少完成三次 V2 全量迁移演练，最终迁移在 5 至 8 小时窗口内完成。
- 上线回退条件、回退负责人、回退数据处理方式已经书面确认。
