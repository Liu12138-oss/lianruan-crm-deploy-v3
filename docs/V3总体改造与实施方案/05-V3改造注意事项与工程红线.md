# V3 改造注意事项与工程红线

## 1. 文档定位

本文件是所有阶段共同遵守的停止线。任何任务即使功能测试通过，只要违反本文件中的工程红线，也不得合并、发布或进入下一阶段。

## 2. 范围红线

- 本次只改造当前已有功能，不新增公海池及其他业务功能。
- 不因技术改造顺便改变审批流程、角色职责、价格规则、状态名称和页面口径。
- 新发现的业务需求进入独立清单，由产品负责人确认后另行排期。
- V2 不再开发和修改；发现 V2 缺陷时记录为迁移兼容问题，不直接修补 V2。
- 不为未来可能出现的需求建立大量空模块、空表和通用规则引擎。

## 3. 现有行为保护

- 阶段 0 未形成接口、页面、角色和数据基线前，不开始批量重构。
- 每个迁移模块必须先写当前行为测试，再替换实现。
- 兼容层负责旧字段和旧响应转换，领域服务不得长期携带多套字段语义。
- 不以页面能打开代替业务回归；必须验证查询范围、状态变化、金额和审计。
- 发现现有行为互相矛盾时立即形成产品决策单，不自行选择看起来合理的一种。

## 4. 代码修改红线

- 不在现有 `server.js`、`admin-app.js` 和 `partner-app.js` 中继续堆叠 V3 新架构代码。
- 不在一次提交中同时做目录迁移、格式化、依赖升级和业务修改。
- 不进行与当前任务无关的全局重命名、样式重做和抽象层增加。
- 控制器不得直接执行 SQL，不得包含大段业务规则。
- 数据访问层不得决定用户权限；权限和数据范围由服务策略明确传入。
- 不允许吞掉异常后返回成功，不允许数据库写入失败后继续使用内存假成功。
- 不允许使用定时全量保存、进程内全局业务对象或本地会话集合。
- 不允许在生产路径保留模拟接口、演示账号、默认密码和调试后门。

## 5. 数据库红线

- 生产环境禁止应用启动时自动建表或修改表。
- 禁止无备份执行删除列、改类型、全表更新和大表索引创建。
- 禁止通过禁用外键或约束长期绕过脏数据问题。
- 禁止使用浮点数保存和计算最终金额。
- 禁止在大表接口中读取全表后由 JavaScript 过滤、排序或分页。
- 禁止字符串拼接 SQL 值、排序字段和表名。
- 禁止把 Redis 或应用日志当作业务数据恢复来源。
- 所有正式迁移脚本必须可重复并产生中文执行报告。

## 6. 认证和权限红线

- 接口不得信任请求体或查询参数中的 `operatorId`、`operatorRole`、`operatedBy`、`userId`、`region` 等字段决定身份和授权。
- 前端隐藏按钮不是权限控制，列表、详情、写入、导出和文件下载都要服务端鉴权。
- 账号停用、密码修改和权限变化后，旧会话必须按策略失效。
- 不允许明文或可逆方式存储本地密码。
- 不允许在浏览器本地存储生产长期令牌和密钥。
- 应急管理员不得作为日常账号使用，不得绕过审计和来源限制。
- 超级管理员也不能绕过业务状态机和幂等校验。

## 7. 接口红线

- 所有新接口必须有请求校验、响应契约、权限策略、数据范围、错误代码和测试。
- 未知字段默认拒绝，涉及服务端事实的字段必须从允许清单移除。
- 写接口必须有明确事务边界；高风险创建和状态推进必须幂等。
- 第三方调用必须设置连接和响应超时，不允许无限等待。
- 不能直接把第三方错误、数据库错误或堆栈返回给用户。
- 不得无限制返回列表，单页上限必须由服务端固定。
- 兼容接口的弃用必须有调用统计、调用方确认和下线日期。

## 8. Redis 和任务红线

- Redis 不保存不可重建的订单、报价、报备审批等唯一业务事实。
- 任务必须先在 PostgreSQL 建立事实记录，再进入队列。
- 任务重试必须幂等，不得因超时重试重复转单、重复导入或重复通知。
- 不允许后台任务使用创建任务时已过期的前端身份；数据范围要保存受控快照并在执行时复核账号状态。
- 队列积压、失败和死信必须可见、可告警、可人工处理。
- 缓存没有明确失效策略时不得上线。

## 9. 前端红线

- 不把生产接口地址、令牌、应用密钥和第三方密钥写入构建产物。
- 不在前端计算最终可信价格、权限范围和状态合法性。
- 不把百万级列表全部拉到浏览器分页。
- 不在 Pinia 或浏览器存储中长期保存完整敏感业务记录。
- 不用静默刷新掩盖并发冲突；必须提示记录已变化并让用户重新确认。
- 不在工程化迁移阶段同时重做视觉系统和业务交互。
- 移动端和桌面端不能各自维护一套状态代码和价格逻辑。

## 10. 日志、审计和隐私红线

- 密码、会话令牌、开放接口密钥、完整 Cookie 和数据库连接串不得进入日志。
- 手机号、邮箱、联系人、身份证明和完整客户敏感资料按角色和场景脱敏。
- 审计记录不存储无必要的整份请求体和第三方原始响应。
- 高风险写入必须记录操作者、目标、结果、原因、请求编号和必要前后值。
- 审计失败不能悄悄忽略；根据动作风险选择阻断或写入可靠发件箱。
- 生产错误信息使用中文说明，不暴露表名、SQL、文件路径和堆栈。

## 11. 部署和运维红线

- 生产不得使用 Python 简易静态服务器或直接暴露 Node.js 接口端口。
- 生产必须使用 HTTPS，后端、数据库和 Redis 只在内网或容器内部访问。
- 禁止直接在生产服务器修改源代码和安装临时依赖。
- 同一构建产物必须先经过测试再晋级生产。
- 镜像、数据库迁移和配置必须有明确版本，禁止不可追溯覆盖。
- 没有成功备份和回退确认不得发布数据库变更。
- 单机生产的备份不得只保存在本机或同一物理磁盘。
- 监控部署在本机时，必须有外部存活监控补充整机故障告警。

## 12. 测试红线

- 权限改造必须覆盖允许和拒绝两类测试，不能只测管理员成功路径。
- 数据迁移必须校验数量、关联、金额、状态和权限，不只比较总记录数。
- 并发领取虽不在本轮功能范围，但当前转单、审批、状态推进和导入必须做并发测试。
- 性能测试必须使用接近目标规模的数据分布，不能使用几十条演示数据得出结论。
- 备份脚本必须通过真实恢复验证。
- 故障测试必须包含接口实例、Redis、PostgreSQL、磁盘和外部依赖异常。
- 关键回归失败、数据不一致或越权问题不得以“后续修复”方式带入下一阶段。

## 13. 数据迁移红线

- 正式迁移必须先停止 V2 写入并验证停止成功。
- SQLite 复制必须使用一致性备份方式，不能在运行写入时直接复制单个数据库文件。
- 源快照、导出文件和迁移报告必须计算摘要并留存。
- 未知状态、未知角色、断裂关联和金额不一致不得自动猜测修复。
- 迁移脚本不得修改 V2 源库。
- 未完成三次全量演练不得进入正式切换。
- V3 开放写入后回退到 V2 必须评估 V3 新增数据，禁止直接丢弃。

## 14. 单机部署特别注意事项

- 两个接口容器部署在同一台服务器，只能处理进程故障，不能处理整机故障。
- PostgreSQL 和备份在同一台服务器不满足恢复要求，必须异机存储。
- 本机监控无法报告本机掉电，必须外部探测。
- 数据盘没有冗余时，恢复时间高度依赖备份下载和备用磁盘速度。
- 如果 99.9% 和 30 分钟恢复属于对外承诺，应至少准备可在 30 分钟内接管的备用服务器。

## 15. 必须暂停并上报的情形

出现以下任一情况，立即停止当前任务或发布：

1. 现有业务规则无法确定，且不同选择会改变数据或权限。
2. 发现 V2 数据存在无法自动判断的角色、区域、渠道关系或金额异常。
3. 迁移或发布步骤不可回退，且没有经过批准的前进修复方案。
4. 发现可利用的越权、明文密码、密钥泄露或任意文件访问问题。
5. 压力测试出现持续错误、数据库锁死、内存持续增长或数据不一致。
6. 备份无法恢复、恢复点超过目标或异机备份不可用。
7. 需求范围从技术改造扩展为新业务功能。
8. 生产环境条件与文档假设不一致，足以改变部署和恢复方案。

## 16. 每次提交自检

- 本次改动是否只对应一个明确任务编号。
- 是否改变了现有业务语义、字段或权限。
- 是否新增或修改数据库结构，迁移和回退是否齐全。
- 是否处理身份、数据范围、幂等、事务和审计。
- 是否有中文错误说明且没有泄露敏感信息。
- 是否有自动测试和人工验证证据。
- 是否影响性能、备份、监控和部署。
- 是否需要更新接口契约、迁移映射或运维手册。
