# V3 部署、高可用、稳定性与安全架构

## 1. 部署结论

首发使用一台生产服务器和 Docker Compose 部署，满足当前成本和运维偏好。应用使用两个无状态接口实例，Nginx 统一入口，PostgreSQL 单实例，Redis 单实例，任务进程独立运行，并部署监控、日志和备份组件。

必须明确：该方案具备进程级和容器级恢复能力，不具备物理服务器级高可用。要让整机故障也满足 99.9% 和 30 分钟恢复目标，至少需要一台备用服务器和可直接获取的异机备份；要做到自动故障切换，需要进入多服务器部署形态。

## 2. 单服务器推荐配置

### 2.1 推荐生产规格

| 资源 | 推荐值 | 最低可验收值 |
| --- | --- | --- |
| 处理器 | 16 核 | 8 核，仅适合较低并发首发 |
| 内存 | 64 GB | 32 GB |
| 数据盘 | 1 TB 企业级 NVMe，RAID1 | 500 GB 企业级固态盘，必须有异机备份 |
| 系统盘 | 与数据盘分离 | 可同盘，但风险必须登记 |
| 网络 | 千兆及以上稳定内网 | 千兆 |
| 操作系统 | 受支持的欧拉或 Ubuntu 长期支持版 | 经完整兼容验证的 Linux |
| 时间同步 | 两个以上时间源 | 一个可靠时间源 |
| 异机备份 | 必须 | 必须 |

如果实际配置低于最低值，必须重新执行容量和压力测试，不得沿用推荐配置下的验收结论。

### 2.2 初始资源预算

| 容器 | 数量 | 处理器建议 | 内存建议 |
| --- | ---: | ---: | ---: |
| Nginx | 1 | 1 核 | 512 MB |
| 接口服务 | 2 | 每个 2 核 | 每个 3 GB |
| 任务进程 | 1 | 2 核 | 4 GB |
| PostgreSQL | 1 | 6 核 | 24 GB |
| Redis | 1 | 2 核 | 4 GB |
| 数据库连接池代理 | 1 | 1 核 | 512 MB |
| 监控、日志和告警 | 一组 | 2 核 | 8 GB |
| 操作系统和缓存余量 | - | 保留 | 至少 10 GB |

资源限制是初始值，阶段 7 根据真实压力报告调整。禁止把容器内存限制设置为服务器全部内存，必须为操作系统页缓存和故障处理留余量。

## 3. 单机容器拓扑

```text
公网或内网用户
      |
      v
Nginx：443
  |       |
  v       v
接口一   接口二
  |       |
  +---+---+
      |
连接池代理
      |
PostgreSQL <---- pgBackRest ----> 异机备份存储
      |
任务进程 <---- Redis

Prometheus <---- 所有组件指标
Loki       <---- 所有组件结构化日志
Alertmanager ----> 外部告警接收端
```

## 4. 网络隔离

- 外部只开放 Nginx 的 443 端口，80 端口只用于跳转到 443。
- 接口、PostgreSQL、Redis、监控后台和容器管理端口不对公网开放。
- PostgreSQL 和 Redis 只加入内部容器网络，运维访问通过受控管理通道。
- 管理后台和渠道端使用同源接口，减少跨域和令牌暴露。
- 开放接口可使用独立 Nginx 路径、来源地址允许清单和单独限流。
- 生产服务器禁止运行开发静态服务器、数据库图形管理工具和临时调试端口。

## 5. 容器和镜像要求

- 镜像使用不可变版本和摘要，禁止生产长期使用 `latest`。
- 接口和任务镜像使用非特权用户，删除编译依赖，根文件系统尽量只读。
- 只有日志缓冲、临时文件和业务文件目录允许写入明确卷。
- 容器设置健康检查、优雅停止时间、重启策略和资源上限。
- 生产配置和密钥不写入镜像，通过受控环境文件或密钥挂载提供。
- 环境文件权限仅允许部署账号读取，不进入交付压缩包和代码仓库。
- 基础镜像和依赖在发布前生成组件清单并完成漏洞检查。

## 6. 应用高可用和优雅发布

- Nginx 后端配置两个接口实例，单个实例失效时停止转发。
- 存活检查只判断进程是否正常；就绪检查验证数据库、必要配置和迁移版本。
- 发布时逐个替换接口实例，先启动新实例、通过就绪检查、再停止旧实例。
- 接口进程收到停止信号后停止接收新请求，等待正在处理的请求完成，并在时限后退出。
- 任务进程停止前暂停领取新任务，正在执行的任务提交检查点或安全失败重试。
- 所有接口实例无本地会话依赖，本地临时文件不得成为业务唯一数据。

## 7. PostgreSQL 稳定性

### 7.1 运行要求

- 数据目录使用独立持久卷和高性能磁盘。
- 开启校验和、慢查询记录、锁等待记录和必要的统计扩展。
- 初始 `shared_buffers` 约为数据库可用内存的四分之一，其他参数根据压力测试调整。
- 所有应用连接通过受控连接池，总连接数符合预算。
- 自动清理、统计信息和表膨胀必须监控，不能长期关闭。
- 数据库迁移使用专用账号，运行时账号不得拥有建表和删表权限。
- 备份账号、只读监控账号和应用账号分离。

### 7.2 备份策略

使用 pgBackRest，建议：

| 类型 | 频率 | 保留建议 | 存储位置 |
| --- | --- | --- | --- |
| 持续归档日志 | 持续，归档延迟不超过 5 分钟 | 覆盖全部保留备份 | 异机存储 |
| 增量备份 | 每日 | 14 天 | 异机存储 |
| 全量备份 | 每周 | 4 至 8 周 | 异机存储 |
| 月度归档 | 每月 | 按合规要求 | 独立归档介质 |

备份必须加密、校验摘要、限制读取权限，并监控最后成功时间、归档延迟和存储余量。

### 7.3 恢复演练

- 每月至少自动恢复一次到隔离环境并执行数据库完整性检查。
- 每季度至少进行一次完整业务恢复演练，包含应用启动和抽样业务校验。
- 恢复报告记录备份编号、目标时间点、实际恢复点、实际耗时、数据校验和问题。
- 没有成功恢复记录的备份策略视为未完成。

## 8. Redis 稳定性和降级

- 开启 AOF，每秒刷盘，并保留适当快照。
- 设置最大内存和明确淘汰策略，业务队列键不得因缓存淘汰策略被意外清除。
- 会话、缓存、限流和队列使用独立前缀，条件允许时使用独立逻辑库或独立实例。
- Redis 故障时禁止创建新的异步任务；已有业务事实保留在 PostgreSQL 中。
- 缓存失效时允许回源 PostgreSQL，但必须使用请求合并、短期限流或逐步恢复防止雪崩。
- 会话存储不可用时保护性拒绝登录和敏感写入，不使用前端自报身份降级。
- Redis 恢复后根据 PostgreSQL任务表和事件发件箱补投未完成任务。

## 9. 文件和磁盘治理

- 导入原文件、导出结果、迁移包和临时文件分目录管理。
- 文件记录保存创建人、数据范围、摘要、大小、内容类型、状态和过期时间。
- 下载必须重新鉴权，禁止使用永久公开地址。
- 临时文件达到保留期后由任务进程清理，清理结果可审计。
- 设置磁盘 70%、80%、90% 三级告警；达到 90% 时暂停大导出和非必要任务。
- 业务文件和数据库备份不得只保存在同一物理磁盘。

## 10. 可观测性和告警

### 10.1 核心告警

| 级别 | 场景 | 初始触发建议 |
| --- | --- | --- |
| 一级 | 服务不可访问、数据库不可用、磁盘即将写满、备份连续失败 | 立即通知并启动故障流程 |
| 二级 | 错误率升高、接口延迟严重、锁等待、队列持续积压 | 5 分钟内持续触发 |
| 三级 | 缓存命中下降、单任务失败、容量趋势异常 | 工作时间处理 |

### 10.2 必备看板

- 总体请求量、成功率、延迟和版本。
- 登录成功失败、会话数量和越权拒绝。
- 各业务模块读写量、错误代码和慢接口。
- PostgreSQL 连接、事务、慢查询、锁、表增长和备份。
- Redis 内存、命中、连接、AOF 和队列。
- Node.js 内存、事件循环延迟、进程重启和资源使用。
- 任务等待、运行、成功、失败和重试。

### 10.3 外部监控

监控系统和业务系统都在同一服务器时，整机故障会同时失去告警能力。因此必须从另一台机器或外部监控服务定时访问公开健康地址，并向独立通知渠道发送告警。

## 11. 安全架构

### 11.1 入口安全

- 生产强制 HTTPS，证书自动续期并监控到期时间。
- 设置内容安全策略、防嵌入、内容类型、引用来源和权限策略响应头。
- 登录、开放接口和大文件接口使用独立限流。
- 限制请求体大小、上传类型和解压后大小，防止压缩炸弹和磁盘耗尽。

### 11.2 主机安全

- 部署账号、运行账号和数据库账号分离。
- 禁止密码直接远程登录，使用密钥和来源地址限制。
- 最小化安装软件，关闭不需要的端口和服务。
- 系统补丁、容器运行时和基础镜像有固定更新周期。
- 生产操作通过审计命令或受控脚本，禁止长期使用最高权限运行应用。

### 11.3 应用安全

- 所有输入使用结构校验和字段允许清单。
- 所有 SQL 参数化；排序和列名只能从服务端映射表选择。
- 输出按上下文编码，前端禁止直接渲染未经处理的富文本。
- 上传文件使用随机内部名称，不使用用户文件名作为路径。
- 日志、审计和错误中统一屏蔽密码、令牌、密钥和个人敏感信息。
- 高风险操作要求重新认证或二次确认，并记录前后值和原因。

## 12. 外部依赖降级

真实客户关系管理系统、统一身份认证、企业信息查询等外部系统异常时：

- 已建立的有效本地会话在授权有效期内可以继续使用，具体策略由阶段 3 确认。
- 新统一身份认证登录返回明确中文故障信息，不回退为伪造身份。
- 企业信息查询失败不阻塞手工录入已有字段。
- 开放接口依赖失败使用超时、有限重试和熔断，禁止无限等待。
- 第三方故障不回滚已经成功提交的本地业务事务；后续动作通过任务补偿。

## 13. 多服务器扩展形态

当单机资源达到持续 60%、计划维护无法接受或整机风险需要消除时，按以下顺序扩展：

1. 将接口实例部署到至少两台应用服务器，前置受管负载均衡。
2. PostgreSQL 建立同城热备和自动或受控故障切换，持续归档保留。
3. Redis 建立主副本和三个哨兵节点，或使用受管高可用服务。
4. 任务进程按队列并发扩展，所有任务保持幂等。
5. 监控和备份控制面独立于业务服务器。

多服务器不是改写应用的前提。只要阶段 1 至阶段 6 正确完成无状态和共享存储设计，扩展主要是部署变化。

## 14. 故障等级和恢复动作

| 故障 | 首要动作 | 数据原则 |
| --- | --- | --- |
| 单接口实例崩溃 | Nginx 摘除，容器重启 | 不涉及数据恢复 |
| 任务进程崩溃 | 暂停领取，重启后按任务状态续跑 | 不重复执行业务写入 |
| Redis 故障 | 限制登录和任务，修复后补投 | PostgreSQL业务数据不回退 |
| PostgreSQL 进程故障 | 停止写流量，重启并检查恢复 | 禁止切换到内存写入 |
| 数据误操作 | 立即冻结相关写入，评估时间点恢复或逻辑修复 | 先保全证据，不直接覆盖当前库 |
| 整机故障 | 启用备用服务器，从异机备份恢复 | 按恢复点和业务校验决定开放 |
| 外部身份系统故障 | 保留受控已有会话，暂停新外部登录 | 不降低认证强度 |

## 15. 上线门槛

- HTTPS、网络隔离、安全头和端口扫描通过。
- 两个接口实例能独立摘除、重启和恢复。
- PostgreSQL 连续归档和全量备份成功，并完成隔离恢复。
- Redis 重启、数据恢复和任务补投验证通过。
- 主机、应用、数据库、Redis、磁盘、备份和外部存活告警实际触发过。
- 压力测试、8 小时长稳测试和故障测试达到阶段 7 标准。
- 生产部署、发布、回退、备份和恢复命令全部脚本化并由非编写者复核。
