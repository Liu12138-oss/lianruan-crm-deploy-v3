# 阶段 0：现状冻结与基线建立

## 1. 阶段目标

在修改核心代码前，把当前 V3 复制目录所代表的 V2 行为、数据、接口、页面、角色、外部依赖和运行性能变成可查、可测、可比较的基线。阶段结束后，开发团队必须知道“哪些行为必须保留、哪些是已知问题、哪些需要产品确认、如何判断改造没有破坏现有业务”。

本阶段不重构业务代码，不调整数据库，不优化页面，不修复非阻断缺陷。

## 2. 计划周期和角色

建议周期：2 周。

| 角色 | 主要责任 |
| --- | --- |
| 产品负责人 | 冻结现有功能范围、状态语义、角色职责和已知例外 |
| 架构负责人 | 建立系统、接口、数据和依赖清单，形成决策记录 |
| 后端负责人 | 提取接口和核心业务规则，记录当前鉴权及数据读写方式 |
| 前端负责人 | 建立页面、入口、菜单、接口依赖和设备清单 |
| 测试负责人 | 建立核心回归、权限回归、数据样本和缺陷基线 |
| 运维负责人 | 核对生产环境、网络、部署、备份、监控和恢复现状 |

## 3. 输入

- V3 当前目录中的 `backend`、`frontend`、`scripts`、`docs` 和数据库样本。
- V2 生产部署信息、生产版本、运行配置和数据统计。
- 《统一管理中心完整产品与架构设计方案》作为后续产品参考，不把其中未上线的新功能计入当前改造。
- 已确认的六项架构决策。

## 4. 任务清单

### S0-01 建立独立版本管理基线

责任人：架构负责人。

执行内容：

1. 确认 V3 目录与 V2 生产目录完全独立。
2. 在 V3 目录建立 Git 仓库和默认分支，首个基线版本不得包含数据库、日志、备份包、临时文件和生产密钥。
3. 建立忽略清单，至少覆盖 `node_modules`、数据库文件、日志、备份、上传、导出、环境文件和系统临时文件。
4. 对保留的旧源码、脚本和文档建立基线标签，例如 `v3-legacy-baseline`。
5. 记录当前后端、前端和数据库文件摘要，防止后续无法确认原始来源。

交付物：

- `docs/baseline/版本与文件基线.md`
- `docs/baseline/基线文件摘要.txt`
- 版本管理初始化记录

验收：从全新目录检出后可以还原源码和文档，但不会带出业务数据库、日志和密钥。

### S0-02 建立功能和页面清单

责任人：产品负责人、前端负责人、测试负责人。

执行内容：

1. 逐一登记统一登录、管理端、渠道电脑版、渠道移动端、管理员移动端和开放接口管理入口。
2. 每个页面登记入口地址、菜单路径、允许角色、主要操作、关联接口、关键字段和当前状态。
3. 区分“生产正在使用”“代码存在但未确认使用”“演示或模拟”“已废弃候选”。
4. 对照现有 87 页设计方案，只把当前实际存在的页面标记为本轮改造范围；公海等未上线页面标记为未来需求。
5. 记录各端相同业务的字段、状态和操作差异。

交付物：

- `docs/baseline/现有功能范围清单.xlsx`
- `docs/baseline/页面与接口依赖清单.xlsx`
- `docs/baseline/本轮明确不做清单.md`

验收：所有可访问入口都能在清单中找到，且每个纳入改造的页面都有责任模块和回归用例编号。

### S0-03 建立接口契约基线

责任人：后端负责人、测试负责人。

执行内容：

1. 提取约 248 个 Express 路由，记录方法、路径、请求字段、响应字段、状态码和调用页面。
2. 记录每个接口当前读取的操作者、角色、区域、渠道和用户参数。
3. 标记鉴权缺失、信任前端身份、无分页、全量内存扫描、同步大任务和敏感数据返回风险。
4. 对已发布开放接口单独登记调用方、权限、版本和兼容承诺。
5. 为每个接口分配稳定编号和目标模块。
6. 用自动化脚本生成机器可读快照，后续每次改造比较契约差异。

交付物：

- `docs/baseline/接口契约基线.yaml`
- `docs/baseline/接口风险与迁移归属.xlsx`
- `scripts/baseline/生成接口清单脚本`

验收：路由源码数量与清单数量一致；找不到页面调用方的接口必须标记为待确认，不能直接删除。

### S0-04 冻结角色和权限现状

责任人：产品负责人、后端负责人、测试负责人。

执行内容：

1. 登记超级管理员、区域管理员、渠道管理员、渠道员工及其他历史角色代码。
2. 建立“角色 × 页面 × 接口动作 × 数据范围”矩阵。
3. 分别验证列表、详情、创建、修改、删除、审批、导入、导出和下载。
4. 标记当前由前端隐藏、前端传角色或后端真实校验实现的权限。
5. 对超级管理员现有业务能力和系统管理能力分别记录，不默认所有未来角色继承全部权限。
6. 记录区域、大区、渠道、上级渠道和本人范围的实际来源字段。

交付物：

- `docs/baseline/现有角色权限矩阵.xlsx`
- `docs/baseline/数据范围来源与异常清单.md`

验收：每个核心接口至少有一个允许样本和一个拒绝样本；无法解释的数据范围进入产品决策清单。

### S0-05 冻结业务状态和规则

责任人：产品负责人、业务代表、测试负责人。

执行内容：

1. 登记账号、渠道、报备、商机、报价、订单、审批和发布状态代码及中文名称。
2. 记录合法状态迁移、触发角色、必填条件、拒绝原因和产生的后续动作。
3. 记录报价计算、渠道等级价格、区域覆盖、工作量、订单转化和一级确认规则。
4. 对代码中存在但文档未说明的例外形成产品决策单。
5. 为金额和状态准备固定输入输出样本，后续用于新旧实现对比。

交付物：

- `docs/baseline/现有业务状态机.md`
- `docs/baseline/价格与工作量计算样本.json`
- `docs/decisions/待确认业务决策.md`

验收：任何核心状态更新都能在状态机中找到合法来源和目标；固定价格样本由业务负责人确认。

### S0-06 建立数据字典和质量报告

责任人：数据负责人、后端负责人。

执行内容：

1. 从 SQLite 通用实体表提取所有实体、记录数、字段、类型、空值比例和样本。
2. 建立实体之间基于编号和字段的实际关联图。
3. 统计重复用户名、重复业务编号、缺失渠道、断裂上级渠道、未知状态、未知角色、无效时间和金额异常。
4. 区分源数据真实缺失、旧逻辑默认值和代码初始化数据。
5. 对审计库统计时间范围、模块、动作、结果和增长量。
6. 不修改源库，所有分析基于只读一致性快照。

交付物：

- `docs/baseline/V2数据字典.xlsx`
- `docs/baseline/V2数据质量报告.md`
- `docs/baseline/V2实体关系图.md`

验收：所有 `ENTITY_NAMES` 实体和审计表均有统计；异常数据有原始编号和建议处理责任人。

### S0-07 建立外部依赖清单

责任人：后端负责人、运维负责人。

执行内容：

1. 登记真实客户关系管理系统登录、统一身份认证、企业信息查询、开放接口调用方和其他第三方。
2. 记录生产地址来源、认证方式、超时、重试、来源地址限制、证书、负责人和测试环境。
3. 检查密钥是否进入代码、静态文件、日志或历史交付包。
4. 为每个依赖定义不可用时的当前表现和 V3 目标降级行为。
5. 无法获得测试环境的依赖必须提供可验证模拟服务，但模拟服务不得进入生产镜像。

交付物：

- `docs/baseline/外部依赖与集成清单.xlsx`
- `docs/baseline/外部依赖降级基线.md`

验收：每个外部请求都有负责人、超时上限和故障处理方式。

### S0-08 建立可执行回归基线

责任人：测试负责人、前后端负责人。

执行内容：

1. 建立接口冒烟测试，覆盖登录、账号、渠道、报备、商机、报价、订单、产品和开放接口。
2. 建立浏览器核心流程脚本，覆盖管理端、渠道端和移动端。
3. 建立固定数据库快照和脱敏测试账号。
4. 测试结果区分当前已通过、当前已失败和环境不可测，不能把既有失败算作改造回归。
5. 对金额、权限和状态场景优先自动化。

交付物：

- `tests/legacy-contract/`
- `tests/legacy-browser/`
- `docs/baseline/现有系统回归结果.md`

验收：在固定环境重复执行两次结果一致；既有失败有独立缺陷编号。

### S0-09 建立性能和资源基线

责任人：测试负责人、运维负责人。

执行内容：

1. 在隔离环境记录当前启动时间、内存、处理器、接口延迟、错误率和数据库大小。
2. 选取登录、渠道列表、报备列表、商机列表、产品树、报价预览、订单列表和导出作为基线场景。
3. 记录单用户、20 并发和 100 并发表现，不对当前系统做破坏性极限压力。
4. 保存慢接口、全量内存扫描和同步写入证据。
5. 明确该基线只用于新旧比较，不代表 V3 目标容量。

交付物：

- `docs/baseline/现有系统性能与资源基线.md`
- `tests/performance/legacy-baseline.js`

验收：报告包含硬件、数据量、并发、持续时间和原始结果，不能只写平均值。

### S0-10 核对生产条件和迁移窗口

责任人：运维负责人、产品负责人。

执行内容：

1. 确认生产操作系统、处理器架构、处理器、内存、磁盘、网络、域名、证书和容器版本。
2. 确认异机备份位置、容量、带宽、访问方式和负责人。
3. 确认是否有可在 30 分钟内接管的备用服务器；没有则登记可用性例外。
4. 确认 5 至 8 小时停机窗口的日期选择、审批人、通知范围和业务联系人。
5. 确认 V2 停写方式、数据库一致性快照方式和重新开放方式。

交付物：

- `docs/baseline/生产环境确认单.md`
- `docs/baseline/迁移窗口与联系人清单.md`

验收：环境信息由运维负责人签字；未知项有明确完成日期，不能使用“与现有相同”代替参数。

## 5. 阶段质量门槛

- 功能、页面、接口、角色、状态、数据和外部依赖清单完整。
- 当前 248 个路由全部有迁移归属或书面废弃候选结论。
- 核心回归能够在固定环境重复执行。
- 所有待确认业务差异已经由产品负责人决定或明确阻断后续模块。
- V2 数据质量问题有处理分类：自动映射、业务补录、隔离、阻断迁移。
- 生产基础条件和异机备份责任人明确。

## 6. 阶段退出会议

参会人逐项确认：本轮功能范围、角色权限、状态和金额规则、迁移数据边界、生产条件、已知缺陷和不做事项。会议结论进入决策记录并建立阶段基线标签。

## 7. 回退

本阶段不改变业务运行代码。若基线采集脚本影响现有环境，立即停止脚本并使用只读快照重新执行。任何测试数据不得写入 V2 生产库。

## 8. 本阶段需要负责人确认的事项

- 生产真实硬件和是否准备备用服务器。
- 浏览器会话闲置时间和最长登录时间。
- 审计、访问日志、导入文件和导出文件保留期限。
- 应急管理员启用流程、允许来源和双人保管责任人。
- 已发布开放接口的实际调用方和兼容期限。
