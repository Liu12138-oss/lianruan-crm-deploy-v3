# V3 总体改造策略

## 1. 改造结论

V3 不采用一次性推翻全部业务逻辑的重写方式，也不继续在现有两个超长主文件上叠加代码。推荐采用“独立 V3 工作区内的渐进替换”策略：先冻结 V2 行为，在 V3 中建立新工程和关系型数据底座，再按模块迁移现有接口和页面，最后完成 V2 数据迁移和生产切换。

目标架构是一个模块化单体，而不是微服务。一个接口进程、一个任务进程、一套 PostgreSQL、一套 Redis 和一个工程化前端即可覆盖当前阶段。模块边界、数据库约束和内部事件先建立清楚，未来只有在真实容量或团队边界证明需要时才拆分服务。

## 2. 为什么必须先改底座

当前系统在小数据量下可以运行，但以下结构不能支撑目标规模和高可用要求：

| 当前结构 | 规模化后果 | V3 处理方式 |
| --- | --- | --- |
| 单个后端文件承载全部业务 | 修改相互影响，测试和发布风险持续增大 | 按业务领域拆分路由、服务和数据访问 |
| 业务数据启动时全部加载到内存 | 多实例数据不一致，容量受单进程内存限制 | PostgreSQL 作为唯一事实来源，按需查询 |
| 通用实体表保存 JSON | 无法可靠使用外键、唯一约束和高效组合索引 | 按领域建立关系表和数据库约束 |
| 每次保存同步全量实体 | 写入放大，并发覆盖风险高 | 只更新发生变化的记录，使用事务和版本号 |
| 部分接口信任前端角色和用户编号 | 可伪造身份或跨范围操作 | 身份只来自服务端会话，数据范围服务端计算 |
| 本地密码明文保存 | 账号泄露风险不可接受 | 使用 `scrypt` 加盐散列，迁移时立即转换 |
| 单进程会话和任务状态 | 重启丢失，多实例不一致 | Redis 共享会话和任务，PostgreSQL保存任务事实 |
| 同步导入、导出和大查询 | 请求超时并拖慢正常业务 | 任务化执行、分批处理和下载结果管理 |
| 静态脚本式前端 | 无模块边界、无构建检查、回归困难 | Vue 3 工程化、路由分包、统一接口契约 |

## 3. 改造范围

### 3.1 纳入改造的现有能力

- 本地登录、真实客户关系管理系统登录、统一身份认证登录和退出。
- 超级管理员、区域管理员、渠道管理员、渠道员工等现有账号和数据范围。
- 用户、渠道商、渠道员工、渠道层级、渠道档案、渠道目标和渠道拜访。
- 客户报备、审批、查重、商机、跟进、报价、工作量计算、订单和履约状态。
- 产品分类、模块、功能、硬件、套餐、产品和价格相关配置。
- 通知、待审批、审计、导入、导出、企业信息查询和开放接口。
- 管理端、渠道电脑版、移动端和统一登录入口。

### 3.2 本轮明确不做

- 不开发公海池、客户领取、自动回收等新业务功能。
- 不新增渠道健康度、复杂规则引擎、工作流设计器等未上线能力。
- 不建设软件即服务多租户体系。
- 不拆微服务，不引入 Kafka、Elasticsearch、Kubernetes 等当前不必要的基础设施。
- 不在改造过程中顺手重做业务规则、视觉风格或产品流程。
- 不修改 V2 生产代码；V2 只作为行为参考和最终数据来源。

## 4. 目标规模

架构和测试以以下设计容量为基线，实际承载能力以指定生产硬件上的压力测试结果为准：

| 指标 | 设计基线 |
| --- | --- |
| 注册账号 | 5 万 |
| 同时在线账号 | 3000 |
| 活跃并发请求 | 500 |
| 渠道商 | 1 万家 |
| 客户数据 | 200 万条，为后续客户资产能力预留 |
| 报备记录 | 500 万条 |
| 商机记录 | 300 万条 |
| 报价和订单 | 各 200 万条 |
| 审计及业务事件 | 1 亿条，按月分区并按策略归档 |
| 持续接口吞吐 | 单机推荐配置下 300 次请求每秒 |
| 短时峰值 | 单机推荐配置下 600 次请求每秒，持续 10 分钟 |

这些数值是设计和验收目标，不等于在任何服务器配置上自动达到。阶段 7 必须使用接近生产的数据分布进行实测。

## 5. 非功能目标

| 维度 | 目标 |
| --- | --- |
| 可用性 | 月度目标 99.9% |
| 恢复点 | PostgreSQL 数据恢复点不超过 5 分钟 |
| 恢复时间 | 应用或容器故障 10 分钟内恢复；重大故障目标 30 分钟 |
| 接口性能 | 常用读接口第 95 百分位不超过 500 毫秒，常用写接口不超过 800 毫秒 |
| 页面性能 | 常用列表首屏 2 秒内可用，核心看板 3 秒内可用 |
| 错误率 | 压力测试稳定阶段服务端错误率低于 0.1% |
| 数据一致性 | 核心业务写入使用事务；不得出现重复转单、越权写入和无审计高风险操作 |
| 可追溯性 | 每个请求、任务、审计记录和关键状态变化可通过请求编号关联 |
| 可恢复性 | 备份必须定期做恢复演练，只有备份文件不算完成 |

## 6. 目标系统形态

```text
用户浏览器
    |
    v
Nginx 统一入口与静态资源
    |
    +---> 接口实例一 ----+
    |                   |
    +---> 接口实例二 ----+----> PostgreSQL
                        |
                        +----> Redis
                        |
任务执行进程 -----------+
    |
    +----> 本地受控文件目录或兼容对象存储

监控组件 <---- 指标、日志、健康检查
异机存储 <---- PostgreSQL 持续归档、全量备份、配置和文件备份
```

首发可以全部部署在一台服务器上。接口双实例只能抵御单进程崩溃，不能抵御整机故障。未来扩展时，接口实例保持无状态，可直接分布到多台机器；PostgreSQL 增加热备，Redis 增加副本和哨兵，入口切换到多机负载均衡。

## 7. 业务模块边界

| 模块 | 当前职责 | 主要数据 |
| --- | --- | --- |
| 认证账号 | 登录、会话、密码、账号状态、应急管理员 | 用户、凭据、会话 |
| 组织权限 | 总部、区域、渠道、角色、权限、数据范围 | 组织、角色、授权、范围 |
| 渠道管理 | 渠道主档、层级、档案、成员、目标、拜访 | 渠道、成员、画像、目标、拜访 |
| 报备管理 | 报备创建、查重、审核、修改和状态历史 | 报备、审核、状态事件 |
| 商机管理 | 商机创建、阶段变化和跟进 | 商机、跟进、阶段事件 |
| 报价管理 | 报价、产品明细、价格和工作量快照 | 报价、明细、价格快照 |
| 订单管理 | 转单、一级确认、价格调整、状态和履约 | 订单、明细、状态事件 |
| 产品价格 | 分类、模块、功能、硬件、套餐、产品和工作量 | 产品目录、价格和映射 |
| 通知审批 | 站内通知、待审批和已读状态 | 通知、审批任务 |
| 集成开放 | 企业信息查询、统一身份认证、开放接口 | 客户端、令牌摘要、访问日志 |
| 导入导出 | 模板、预检、执行、下载和失败明细 | 任务、文件、错误行 |
| 审计运维 | 操作审计、健康检查、配置和运行记录 | 审计、配置、运行事件 |

模块之间只能通过公开服务接口或明确的数据查询接口协作，不允许跨模块直接修改对方表。当前阶段不建设复杂内部总线，跨模块可靠动作使用同库事务和事件发件箱。

## 8. 渐进替换策略

### 8.1 双轨目录

改造期间保留现有 `backend` 和 `frontend` 目录作为旧实现参考，在新目录建立 V3 工程。旧页面和旧接口不立即删除。

### 8.2 契约先行

阶段 0 先记录当前 248 个接口、字段、状态码、权限和页面依赖。新接口内部可以改造，但兼容入口必须保证当前页面需要的字段和语义，直到全部前端完成迁移。

### 8.3 按领域迁移

迁移顺序遵循“低风险只读配置 → 账号和渠道 → 报备 → 商机 → 报价 → 订单 → 导入导出与开放接口”。每个领域完成后单独回归，不等待全部模块一起测试。

### 8.4 数据单一写入

V3 独立开发期间不与 V2 做实时双写。开发和演练使用 V2 脱敏快照。正式切换时停止 V2 写入，完成最终全量迁移。这样可以避免两个系统互相覆盖和长期维护双写逻辑。

### 8.5 兼容层有退出期限

旧路径、旧字段和旧响应由兼容层转换，不把兼容逻辑散落进领域服务。全部 V3 前端和已确认外部调用方迁移后，兼容层才能按清单下线。

## 9. 数据策略

- PostgreSQL 是业务唯一事实来源，Redis 不保存不可重建的唯一业务数据。
- 每个核心表使用稳定主键、创建时间、更新时间和乐观锁版本号。
- 金额使用 `numeric`，不得使用浮点数；时间统一保存为带时区时间。
- 当前字符串区域、角色和状态通过映射表归一化，历史原值保留用于追溯。
- 高风险状态变化保留事件历史，不只覆盖当前状态。
- 审计、访问日志和任务记录按增长速度设置分区和保留策略。
- 深分页使用游标或基于稳定排序键的翻页，不允许无限制偏移扫描。
- 导出必须复用服务端数据范围，严禁通过导出绕过页面权限。

## 10. 安全策略

- 浏览器会话优先使用安全、仅服务端可读、同站点限制的 Cookie。
- 移动端和开放接口使用可撤销的不透明令牌，服务端只保存令牌摘要。
- 本地密码使用 Node.js 内置 `scrypt` 加盐散列，迁移过程不落明文。
- 应急管理员默认禁用或限制来源地址，启用、使用和关闭均审计。
- 所有详情、列表、写入、导出和下载均重新验证数据范围。
- 创建人、审批人、区域、渠道、金额和状态等服务端字段拒绝前端伪造。
- 登录、导入、导出、密钥重置和高风险写入设置分级限流。
- 生产密钥只来自环境变量或密钥文件，不进入代码仓库和镜像。

## 11. 发布策略

每次发布只包含一个可回退的改造批次。数据库迁移遵循先扩展、再切换、最后清理：先添加兼容结构，再发布读取和写入切换，稳定后才删除旧结构。代码回退不得自动回退已提交的业务数据。

生产发布需要满足：构建通过、自动测试通过、迁移预检通过、备份成功、回退命令验证、负责人在线、监控和告警可用。

## 12. 组织和管理机制

- 产品负责人负责冻结现有业务语义和确认差异，不在改造中临时改变流程。
- 架构负责人维护模块边界、接口契约、数据模型和决策记录。
- 开发负责人按任务编号提交代码、测试和迁移说明。
- 测试负责人维护现状回归、权限矩阵、数据校验和性能基线。
- 运维负责人负责生产参数、备份、监控、恢复和发布证据。
- 任何人发现数据丢失、越权、明文密钥、不可回退迁移或范围扩大时，有权立即停止发布。

## 13. 总体成功标准

V3 基础改造成功不以“代码换了框架”为标准，而以以下结果为标准：现有业务无损迁移，权限可信，数据可约束，系统可扩容，故障可定位，数据可恢复，发布可回退，最终迁移可在批准窗口内完成。
