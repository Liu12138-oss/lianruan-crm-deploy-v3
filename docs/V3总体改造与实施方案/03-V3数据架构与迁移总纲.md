# V3 数据架构与迁移总纲

## 1. 目标

把当前“内存全量对象 + SQLite 通用实体表 + JSON 记录”改造为以 PostgreSQL 为唯一事实来源的关系型数据架构，在不改变现有业务语义的前提下获得以下能力：

- 支持百万级业务数据的索引查询、服务端分页和批处理。
- 使用外键、唯一约束、检查约束、事务和版本号保证一致性。
- 支持多个接口实例和任务进程同时读写。
- 支持连续备份、按时间点恢复、慢查询分析和容量治理。
- 支持 V2 全量数据可重复迁移、校验和回退。

## 2. 核心原则

1. PostgreSQL 是业务唯一事实来源，应用内存和 Redis 不保存不可重建的唯一数据。
2. 关系模型表达稳定业务事实，可变扩展属性才允许使用 `jsonb`。
3. 数据库约束负责守住最终一致性，应用校验负责提供友好中文错误。
4. 所有结构变化必须通过版本化迁移执行，生产禁止自动同步结构。
5. 数据迁移必须可重复、可中断恢复、可校验，禁止人工直接修改生产表凑结果。
6. 不为未确认的新功能提前创建空业务表；只保留明确的扩展边界和命名规范。
7. 历史数据不因新字典发布而被覆盖，必要时保存原值、标准值和规则版本。

## 3. 数据库逻辑分区

V3 使用一个 PostgreSQL 数据库。当前不拆库，使用清晰表名前缀区分责任边界：

| 前缀 | 责任边界 |
| --- | --- |
| `iam_` | 账号、凭据、会话摘要、角色、权限和数据范围 |
| `org_` | 总部、区域、渠道组织绑定和组织层级 |
| `partner_` | 渠道主档、成员、层级、档案和能力资料 |
| `channel_` | 渠道目标、拜访及现有运营数据 |
| `registration_` | 报备主记录、审核和状态历史 |
| `opportunity_` | 商机、跟进和阶段历史 |
| `quote_` | 报价、明细、价格和工作量快照 |
| `order_` | 订单、明细、确认、调价和履约历史 |
| `catalog_` | 分类、模块、功能、硬件、套餐和产品 |
| `pricing_` | 价格规则、区域覆盖和发布版本 |
| `workload_` | 实施工作量分类、映射和规则 |
| `notify_` | 通知、已读状态和投递记录 |
| `approval_` | 当前已有待审批事项 |
| `integration_` | 外部集成、开放接口客户端和访问记录 |
| `io_` | 导入、导出、文件和失败明细 |
| `system_` | 字典、配置、功能开关、幂等记录和任务事实 |
| `audit_` | 操作审计和高风险事件 |

本轮不建立公海池、客户领取、保护权益等新功能数据表。未来批准相关功能后，在独立阶段新增，不混入本次底座改造。

## 4. 通用字段规范

核心业务表统一考虑以下字段，按实际需要使用，不机械复制无意义字段：

| 字段 | 类型建议 | 规则 |
| --- | --- | --- |
| `id` | `uuid` | 内部主键，应用生成时间有序 UUID |
| `business_no` | `varchar` | 用户可见业务编号，按业务建立唯一约束 |
| `legacy_id` | `varchar` | V2 原始编号，迁移记录唯一，非迁移数据可为空 |
| `created_at` | `timestamptz` | 服务端或数据库生成，统一时区语义 |
| `created_by` | `uuid` | 服务端会话身份，不信任前端传入 |
| `updated_at` | `timestamptz` | 每次更新维护 |
| `updated_by` | `uuid` | 服务端会话身份 |
| `version` | `integer` | 乐观锁版本，从 1 开始 |
| `deleted_at` | `timestamptz` | 仅确有恢复和历史需要时软删除 |

规则：

- 金额使用 `numeric(18,2)` 或经业务确认的更高精度，禁止 `float` 和 `double precision`。
- 比例使用明确精度的 `numeric`，数据库保存真实比例，不混用“15”和“0.15”。
- 日期使用 `date`，时间点使用 `timestamptz`，禁止无时区时间表达跨系统事件。
- 状态使用稳定代码和检查约束，中文名称在字典或前端展示。
- 手机号、邮箱等可以保留原值，但查询和展示遵循脱敏策略。
- 可变第三方原始响应可以进入受控 `jsonb`，但常用筛选、关联和约束字段必须独立成列。

## 5. 主键和编号策略

- 内部主键使用时间有序 UUID，避免依赖单机自增和暴露数据量。
- 用户可见编号保持现有格式或经产品确认后使用新编号规则。
- V2 迁移数据保存 `legacy_id`，兼容层通过 `legacy_id` 查找新主键。
- 外部开放接口在兼容期可以继续接收旧编号，但内部服务统一使用新主键。
- 编号生成器不得依赖 Redis 作为唯一事实；需要严格连续时使用 PostgreSQL 序列，需要高吞吐且无需连续时使用日期加随机段。

## 6. 关系模型清单

### 6.1 认证、组织和权限

| 表 | 主要内容 | 关键约束 |
| --- | --- | --- |
| `iam_users` | 账号基础资料和状态 | 用户名规范化后唯一 |
| `iam_credentials` | 本地密码散列和算法版本 | 一个用户一个当前本地凭据 |
| `iam_external_identities` | 真实客户关系管理系统、统一身份认证映射 | 来源与外部主体唯一 |
| `iam_sessions` | 会话摘要、来源、授权版本和撤销记录 | 令牌摘要唯一，不保存令牌明文 |
| `iam_roles` | 功能角色 | 角色代码唯一 |
| `iam_permissions` | 模块、资源、动作权限 | 权限代码唯一 |
| `iam_user_roles` | 用户角色绑定 | 用户、角色、有效期组合唯一 |
| `iam_role_permissions` | 角色权限绑定 | 角色、权限组合唯一 |
| `iam_data_scopes` | 用户或角色的数据范围绑定 | 范围类型和目标必须合法 |
| `org_units` | 总部、区域等内部组织 | 同级代码唯一，禁止环形层级 |

### 6.2 渠道

| 表 | 主要内容 | 关键约束 |
| --- | --- | --- |
| `partner_partners` | 渠道商主档 | 渠道编号唯一；信用代码存在时条件唯一 |
| `partner_relationships` | 一级、二级等渠道关系 | 同一子渠道同一时点仅一条有效上级关系 |
| `partner_members` | 渠道和账号的成员关系 | 渠道、用户、成员身份组合唯一 |
| `partner_profiles` | 渠道画像及稳定扩展资料 | 一个渠道一个当前画像版本 |
| `partner_profile_products` | 渠道产品能力 | 渠道和产品组合唯一 |
| `channel_targets` | 现有渠道目标 | 渠道、目标周期、目标类型唯一 |
| `channel_visits` | 现有渠道拜访记录 | 关联渠道和责任人必须存在 |

### 6.3 报备、商机、报价和订单

| 表 | 主要内容 | 关键约束 |
| --- | --- | --- |
| `registration_records` | 报备当前事实 | 报备编号唯一，渠道和创建人必填 |
| `registration_reviews` | 报备审核记录 | 每次审核追加，不覆盖历史 |
| `registration_status_events` | 状态变化历史 | 旧状态、新状态、操作人和时间完整 |
| `opportunity_records` | 商机当前事实 | 商机编号唯一，关联报备可空但存在时有效 |
| `opportunity_followups` | 商机跟进 | 只追加；更正需留痕 |
| `opportunity_stage_events` | 阶段变化 | 记录版本和变化原因 |
| `quote_records` | 报价头和当前状态 | 报价编号唯一，金额非负 |
| `quote_items` | 报价产品明细 | 数量正数，金额定点保存 |
| `quote_snapshots` | 价格、产品、工作量和折扣快照 | 报价版本唯一，不受后续配置变化影响 |
| `quote_status_events` | 报价状态变化 | 状态机约束和操作人完整 |
| `order_records` | 订单头和当前状态 | 订单编号唯一；来源报价转单唯一 |
| `order_items` | 订单产品明细 | 从确认快照复制，不回读当前价格 |
| `order_status_events` | 确认、驳回、调价和履约历史 | 只追加，关键金额保留前后值 |

### 6.4 产品、工作量和系统治理

| 表组 | 迁移来源 | 关键约束 |
| --- | --- | --- |
| 产品目录表 | `categories`、`modules`、`features`、`hardwareProducts`、`packages`、`products` | 编码唯一、层级引用有效、发布状态受控 |
| 工作量表 | 三类工作量实体 | 规则版本化，映射目标有效 |
| 通知和审批表 | `notifications`、`pendingApprovals` | 接收人有效，已读和处理状态可追溯 |
| 开放接口表 | `openApiClients` 和访问记录 | 密钥摘要唯一、权限范围明确 |
| 审计表 | `audit_logs` | 追加写入，按月分区，禁止普通业务修改 |
| 任务和文件表 | 新技术底座 | 任务事实持久化，文件有摘要和过期时间 |
| 事件发件箱 | 新技术底座 | 事件编号唯一，发布状态可重试 |
| 幂等记录 | 新技术底座 | 作用域、幂等键唯一，并保存结果摘要 |

## 7. 状态机和历史

报备、商机、报价、订单、账号、渠道关系和审批必须有服务端状态机。状态更新至少检查：当前状态、目标状态、操作者权限、数据范围、记录版本和必填业务证据。

状态主表保存当前值，事件表保存完整历史。禁止通过直接更新主表绕过事件记录。数据迁移无法还原完整历史时，创建“历史迁移”事件并标注来源，不伪造具体操作人和时间。

## 8. 索引策略

### 8.1 必备索引

- 主键、业务编号和 V2 原始编号唯一索引。
- 用户名、外部身份、渠道编号、信用代码等业务唯一索引。
- 高频列表的“数据范围字段 + 状态 + 时间 + 主键”组合索引。
- 外键列索引，尤其是渠道、用户、报备、商机、报价和订单关联。
- 任务的状态、计划时间和主键组合索引。
- 审计和访问日志按时间分区，分区内建立用户、模块和目标索引。

### 8.2 禁止事项

- 不为每个字段都建索引。
- 不在高频更新表上创建大量重叠索引。
- 不允许以 `%关键词%` 模糊查询直接扫描百万级表。
- 不允许没有稳定排序的分页。
- 不允许在接口中先读取全部记录再使用 JavaScript 筛选。

### 8.3 模糊检索

当前先使用 PostgreSQL `pg_trgm` 和规范化检索列。公司名称等字段保存规范化值并建立三元组索引。只有阶段 7 的百万级检索实测不达标，才提交引入专用搜索服务的架构决策。

## 9. 分区和保留

- `audit_logs`、开放接口访问日志和高增长业务事件按月分区。
- 业务主表初期不分区，避免无证据的复杂化。
- 单表超过 3000 万行、维护窗口持续超标或查询无法通过索引治理时，再评估业务表分区。
- 审计在线保留期、归档期和销毁期由合规负责人确认；未确认前不得自动删除。
- 任务日志和临时文件按明确保留期清理，清理任务自身也要有执行记录。

## 10. 事务和并发

- 创建或更新核心业务记录时，主记录、明细、状态事件、审计必要上下文和事件发件箱在一个事务中提交。
- 外部接口调用不放在数据库事务内；先提交待执行事件，再由任务进程调用并记录结果。
- 乐观并发使用 `version` 条件更新；资源争抢场景使用数据库行锁和唯一约束。
- 死锁和序列化失败可以有限重试，重试次数和原因必须记录。
- 报价转订单通过来源报价唯一约束防止重复转单。
- 幂等记录需要保存请求摘要，使用同一幂等键但请求内容不同必须拒绝。

## 11. 连接管理

首发单机版初始预算：

| 来源 | 实例数 | 每实例连接上限 | 总预算 |
| --- | ---: | ---: | ---: |
| 接口服务 | 2 | 20 | 40 |
| 任务进程 | 1 | 15 | 15 |
| 迁移和运维 | 受控 | 10 | 10 |
| 监控和备用 | - | 10 | 10 |
| 合计 | - | - | 75 |

PostgreSQL 初始最大连接数可设置为 150，并保留系统和应急空间。连接池参数必须经压力测试调整，不得通过无限增加连接掩盖慢查询。

## 12. V2 到 V3 数据迁移结构

迁移分四层：

```text
V2 SQLite 一致性快照
    |
    v
原始导出文件：逐实体、逐记录、带摘要
    |
    v
PostgreSQL 临时迁移表：保留原始 JSON 和批次号
    |
    v
清洗映射层：状态、角色、区域、关联和金额校验
    |
    v
V3 正式关系表
```

这样可以把“源数据是什么”和“转换后是什么”分开，失败时可以定位具体记录，不需要反复读取生产 SQLite。

## 13. 迁移批次和可重复性

每次迁移生成唯一批次号，记录源文件摘要、源库表统计、实体统计、开始结束时间、脚本版本、执行人、成功数、跳过数、失败数和校验结论。

迁移脚本必须满足：

- 同一源快照和同一脚本重复执行得到相同结果。
- 写入通过 `legacy_id` 或迁移映射表防止重复。
- 每个实体分批提交，失败可以从检查点继续。
- 失败记录进入错误表和中文报告，不因少量脏数据静默跳过。
- 迁移完成后不自动删除临时表和原始导出文件。

## 14. 映射规则

| 数据类型 | 处理原则 |
| --- | --- |
| 用户和密码 | 用户名规范化；明文密码直接转换为 `scrypt` 散列，不写入正式表明文字段 |
| 角色 | 按确认矩阵映射；未知角色停止迁移，不自动提升权限 |
| 区域和大区 | 原值保留，映射到标准组织；无法映射进入问题清单 |
| 渠道层级 | 校验上级存在、禁止自关联和环形；异常关系不自动猜测 |
| 业务关联 | 优先通过原始编号映射；缺失父记录的子记录进入隔离清单 |
| 状态 | 使用明确映射表；未知值停止该记录并报告 |
| 时间 | 标明源时区，转换为带时区时间；无效时间不使用当前时间代替 |
| 金额和比例 | 按现有真实语义转换，转换前后抽样重算 |
| 空值和缺失字段 | 区分未知、空字符串和真正无值，不擅自补业务默认值 |

## 15. 校验规则

### 15.1 全量校验

- 每个实体源数量、成功数量、隔离数量和失败数量守恒。
- 主键、业务编号和 V2 原始编号无重复。
- 外键孤儿数量为零，或全部进入经批准的隔离清单。
- 状态、角色、区域和渠道层级值全部合法。
- 报价、订单总金额与明细重算结果一致。
- 来源报价和订单转化关系唯一。
- 账号数量、有效状态和权限映射与批准清单一致。

### 15.2 抽样校验

每类业务至少抽取高金额、旧记录、新记录、异常状态、跨区域、一级渠道和二级渠道样本。抽样不得只选正常记录。关键金额和权限样本由业务负责人签字确认。

## 16. 迁移演练要求

正式上线前至少完成三次全量演练：

1. 首次演练发现字段、状态和关联问题，不考核最终耗时。
2. 第二次演练使用修正脚本，要求全量校验通过并测量完整耗时。
3. 第三次演练模拟生产停机窗口、人员、命令、备份、切换和回退，必须在 5 至 8 小时内完成。

每次演练必须使用新生成的数据快照，不得只重复使用第一次快照掩盖新增数据问题。

## 17. 回退数据原则

- 正式开放 V3 用户前发生失败：停止 V3，恢复 V2 写入，V3 迁移库保留用于分析。
- V3 已开放但尚处于受控验证期：立即停止 V3 写入，导出增量操作清单，由业务确认回退或修复前进。
- V3 已大范围产生新业务数据：不得直接切回 V2 造成新数据丢失，必须进入重大故障决策流程。
- 数据库结构回退不等于业务数据回退。任何不可逆迁移必须采用先扩展、后切换策略。

## 18. 数据架构验收

- 应用启动不再把所有业务记录加载到内存。
- 两个接口实例同时写入不会互相覆盖。
- 关键唯一性在并发测试下由数据库约束守住。
- 百万级测试数据下核心列表使用预期索引，不出现全表扫描和无界返回。
- 数据库备份能够恢复到隔离环境，并通过数量和业务抽样校验。
- 迁移报告能定位到源实体、原始编号、目标表和中文失败原因。
