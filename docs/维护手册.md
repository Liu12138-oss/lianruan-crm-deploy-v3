## 二、数据存储说明

### 2.1 数据存储位置

所有业务数据存储在单一文件：
```
backend/data.json
```

该文件包含：
- 用户账号（users）
- 渠道商（partners）
- 商机（opportunities）
- 报价单（quotes）
- 订单（orders）
- 客户报备（registrations）

### 2.2 数据版本

| 层级 | 版本定义位置 | 当前值 |
|------|------------|--------|
| 应用版本 | `docs/CHANGELOG.md` | v2.2.0 |
| 数据版本 | `frontend/data-migration.js` | 2 |
| 后端版本 | `backend/package.json` | 1.0.0 |

### 2.3 阿里云市场工商信息查询接口

后端提供阿里云市场企业工商模糊查询 API 代理接口，用于客户报备表单自动回填工商信息。

| 接口 | 说明 |
|------|------|
| `GET /api/company-search?keyword=xxx` | 搜索企业列表，返回公司名称、统一社会信用代码、法人、注册日期等 |

**配置**：在启动后端时设置环境变量 `COMPANY_API_KEY=你的AppCode`，例如：
```bash
COMPANY_API_KEY=8785eb7b1e854819867bc497405bb2cc node server.js
```

**认证方式**：`Authorization: APPCODE {AppCode}`（Header 中）

**返回字段**：companyName（企业名称）、creditNo（统一社会信用代码）、legalPerson（法人）、establishDate（注册日期）、companyStatus（企业状态）、companyCode（注册号）

**降级机制**：API 接口失败时自动降级返回本地历史报备数据，功能不中断。

### 2.4 迁移机制

项目支持前端 localStorage 数据迁移，但后端 `data.json` 升级需要手动处理：

- **无结构变更**：直接替换文件即可
- **有结构变更**：需要运行迁移脚本或手动修改 data.json

### 3.4 渠道商等级体系说明

| 等级 | 说明 | 价格政策 |
|------|------|---------|
| 一级渠道商 (primary) | 可发展二级渠道商，享受最优价格 | 使用 `priceForPrimary` |
| 二级渠道商 (secondary) | 绑定一个或多个上级渠道商，价格上浮10% | 使用 `priceForSecondary` |
| 无等级 (none) | 默认状态 | 使用标准价格 |

**二级渠道商绑定规则**：
- 可绑定多个一级渠道商（`parentPartnerIds` 数组）
- 报价转订单时可任选一个已绑定的上级渠道商提交
- 订单审批流程：`pending → primary_confirmed → processing → shipped → completed`

**维保产品计价规则**：
- 标准维保服务：价格 = 其他软硬件总价 × 15% + 防病毒模块总价 × 25%
- 原厂现场人工服务：按阶梯定价不变

## 五、数据变更处理

### 5.1 变更类型判断

| 变更类型 | 说明 | 处理方式 |
|---------|------|---------|
| **纯前端变更** | HTML/CSS/JS 界面调整 | 替换 frontend/ 即可 |
| **纯后端变更** | server.js 逻辑调整 | 替换 server.js，重启 |
| **前端数据结构** | localStorage 字段增删 | 前端自动迁移（data-migration.js） |
| **后端数据结构** | data.json 字段增删 | 需编写迁移脚本 |

### 5.2 后端数据变更处理流程

#### 场景一：添加新字段（不删除旧字段）

**最安全的方式，向后兼容。**

```javascript
// 在 data.json 中，新字段设为默认值
// 例如：添加 "priority" 字段
opportunities: [
  {
    id: "OPP001",
    name: "客户A项目",
    // 新增字段，旧数据没有，自动使用默认值
    priority: "normal"  // 需要手动补充或写脚本迁移
  }
]
```

**处理方式：**
1. 升级代码
2. 用户首次访问时，代码自动补充默认值
3. 无需手动迁移

#### 场景二：字段重命名

```javascript
// 将 "customer" 重命名为 "clientName"
// 旧代码: { id: "001", customer: "XX公司" }
// 新代码: { id: "001", clientName: "XX公司" }
```

**处理方式：**

```bash
# 创建迁移脚本 migrate_field.js
node << 'EOF'
const fs = require('fs');
const data = JSON.parse(fs.readFileSync('data.json', 'utf8'));

// 执行迁移
data.opportunities = data.opportunities.map(item => ({
  ...item,
  clientName: item.clientName || item.customer,  // 新字段从旧字段取值
  // 删除旧字段：delete item.customer;
}));

// 保存
fs.writeFileSync('data.json', JSON.stringify(data, null, 2));
console.log('迁移完成');
EOF
```

#### 场景三：新增数据表/集合

**最简单，只需确保代码正确处理空值。**

```javascript
// 新增 "feedbacks" 集合
data.feedbacks = data.feedbacks || [];  // 确保存在
```

## 七、故障排查

### 7.1 常见问题

#### 问题1：服务启动失败

```bash
# 查看详细日志

cat /opt/lianruan-crm/scripts/logs/frontend.log

# 3. 依赖未安装

```

#### 问题2：用户无法登录

```bash
# 检查后端 API
curl http://localhost:3000/api/users

# 检查 data.json 是否损坏
python3 -c "import json; json.load(open('/opt/lianruan-crm/backend/data.json'))"
```

#### 问题3：data.json 被清空后数据"复活"

**现象**：手动清空了 data.json 中的业务数据，但重启服务后数据又出现了。

**原因**：后端服务运行时修改 data.json 无效。`saveData()` 会将**内存中的数据**定期写回磁盘，覆盖文件修改。

**处理方式**：
1. 停止后端服务：`bash start.sh stop`（或 `pkill node`）
2. 确认 node 进程已停止：`ps aux | grep node`
3. 再修改 data.json
4. 重启服务

#### 问题4：数据丢失

```bash
# 检查备份
ls -la /opt/lianruan-crm-backup-*/

# 从备份恢复
cp /opt/lianruan-crm-backup-*/backend/data.json /opt/lianruan-crm/backend/data.json
bash /opt/lianruan-crm/scripts/start.sh restart
```

## 八、安全建议

### 8.1 密码安全

⚠️ **当前所有账号密码均为 `123456`，强烈建议上线前修改！**

```bash
# 使用管理后台修改（推荐）

# 或直接编辑 data.json（需重启服务）
vim /opt/lianruan-crm/backend/data.json
```

### 8.2 重要：修改 data.json 前必须停服务

⚠️ **后端服务运行时修改 data.json 无效！**

后端服务（`node server.js`）启动时将 data.json 加载到**内存**，并通过 `saveData()` **定时自动保存**（每约30秒或每次数据变更时）。

**错误流程（数据会"复活"）**：
1. 修改 data.json（清空/编辑）
2. 服务仍在运行
3. 下一次 `saveData()` 执行 → **内存数据覆盖文件修改**

**正确流程**：
1. `bash start.sh stop`（停止服务）
2. 修改 data.json
3. `bash start.sh start`（重启服务）

本地开发时同理：先停 node 进程，再改文件。

### 8.3 app.js 硬编码示例数据说明

`frontend/app.js` 的 `store` 对象中硬编码了以下示例数据：
- 商机：5条（OPP-001 ~ OPP-005）
- 报备：8条（REG-2026-001 ~ REG-2026-008）
- 报价：3条
- 订单：2条
- 渠道商：5个（含员工账号）

这些数据用于**主登录页（login.html）仪表盘**展示，通过 `loadRealData()` 合并逻辑加载（保留无 `createdBy` 字段的记录 + 后端数据）。

**清理步骤**（如需完全清空）：
1. 停止后端服务
2. 修改 `backend/data.json` 清空业务数据
3. 同时修改 `frontend/app.js`，将 `store` 中的示例数据数组改为 `[]`
4. 重启服务

## 九、业务逻辑说明

本章节详细介绍系统的核心业务逻辑，包括角色体系、渠道商等级、核心流程、状态机和数据权限。

### 9.1 角色体系

系统采用四级角色体系，权限从高到低依次为：

| 角色 | 说明 | 权限范围 |
|------|------|---------|
| superadmin | 超级管理员 | 全系统最高权限，管理所有区域、渠道商和业务数据 |
| admin | 区域管理员 | 管理本区域的渠道商、订单、报备等业务数据 |
| staff | 渠道商员工 | 仅可操作所属渠道商的数据，如商机、报价、订单 |
| partner_admin | 渠道商管理员 | 渠道商内部管理员，可管理本渠道商员工账号 |

**账号与角色关系**：
- 每个渠道商账号下可创建多个员工账号（`partnerId` 关联）
- 员工账号的 `role` 为 `staff`
- 渠道商自身的管理员账号（如 `partnership_admin`）也是 `staff`，但权限更大
- 区域管理员的账号 `role` 为 `admin`，且无 `partnerId`
- 超级管理员账号 `role` 为 `superadmin`

**账号字段说明**：
```javascript
{
  id: "USER001",
  username: "xxx",
  role: "staff",        // superadmin / admin / staff
  partnerId: "P001",    // 渠道商ID，admin/superadmin 无此字段
  region: "ah",         // 所属区域
  // ...
}
```

### 9.2 渠道商等级体系

渠道商分为三个等级，通过 `partnerLevel` 字段标识：

| 等级 | partnerLevel 值 | 说明 | 价格政策 |
|------|----------------|------|---------|
| 一级渠道商 | `primary` | 可发展二级渠道商，享受最优价格 | 使用 `priceForPrimary` |
| 二级渠道商 | `secondary` | 绑定一个或多个上级渠道商，价格上浮10% | 使用 `priceForSecondary` |
| 无等级 | `none` | 默认状态 | 使用标准 `price` |

**二级渠道商绑定规则**：
- `parentPartnerIds`：数组类型，可绑定多个一级渠道商
- `parentPartnerId`：兼容旧数据，取 `parentPartnerIds[0]`
- 二级渠道商在**报价转订单**时可任选一个已绑定的上级渠道商提交

**订单审批流程差异**：
- 一级/无等级渠道商：`pending → processing → shipped → completed`
- 二级渠道商：`pending → primary_confirmed → processing → shipped → completed`

### 9.3 核心业务流程

系统围绕四大核心模块展开：客户报备 → 商机 → 报价 → 订单。

```
客户报备
   │
   ▼
  商机（关联报备ID）
   │
   ├── 报备通过后，渠道商录入商机
   │
   ▼
  报价单（强制关联至少一个商机，支持关联多个）
   │
   ├── 渠道商提交报价
   ├── 超级管理员/区域管理员审核
   │
   ▼
  订单（从报价单转换而来）
   │
   ├── 渠道商提交订单
   ├── 二级渠道商需上级一级渠道商确认
   ├── 超级管理员/区域管理员审核
   │
   ▼
  完成
```

**关键规则**：
1. **报备有效期**：默认30天，可续期（`extendExpiry` 接口）
2. **商机强制关联**：报价单必须关联至少一个商机（`oppIds` 数组，不能为空）
3. **报价单审核**：区域管理员/超级管理员审核通过后，渠道商方可转订单
4. **订单金额计算**：基于渠道商等级应用不同价格系数

### 9.5 维保产品计价规则

产品目录中有"维保产品模块"（`CAT-MAINTENANCE`），其中：

**标准维保服务**（`FEAT-MOD-MAINTENANCE-01-01`）采用百分比计价：

```
标准维保价格 = 其他软硬件总价 × 15% + 防病毒模块总价 × 25%
```

- **其他软硬件**：所有非标准维保服务的功能（不含防病毒模块）
- **防病毒模块**：`FEAT-MOD-LEP-03-01`
- 百分比基于实际成交价（考虑渠道商等级折扣后）
- 该功能的数据结构中保留了阶梯定价字段，但**实际计价时使用百分比计算**

**原厂现场人工服务**（`FEAT-MOD-MAINTENANCE-01-02`）：按阶梯定价不变。

**防病毒模块**（`FEAT-MOD-LEP-03-01`）：按阶梯定价不变。

### 9.7 审核中心说明

审核中心统一处理各类待审核事项，按类型分为：

| 类型 | 说明 | 审核人 |
|------|------|--------|
| partner | 渠道商账号注册 | 超级管理员 |
| staff | 渠道商员工账号申请 | 超级管理员/区域管理员 |
| partner_admin | 渠道商管理员申请 | 超级管理员/区域管理员 |
| secondary_partner | 二级渠道商绑定上级 | 一级渠道商确认 + 管理员审核 |

审核流程：
1. 申请人提交账号注册/申请
2. 生成 `pendingApproval` 记录
3. 管理员在审核中心查看并处理
4. 通过：更新账号状态 → 删除待审记录
5. 驳回：更新账号状态为 rejected → 删除待审记录

### 9.8 产品价格体系

产品有三层价格，针对不同渠道商等级：

| 字段 | 适用对象 |
|------|---------|
| `price` | 无等级渠道商（默认价格） |
| `priceForPrimary` | 一级渠道商（最优价格） |
| `priceForSecondary` | 二级渠道商（上浮10%） |

价格计算逻辑（`calcFeatureTotal` 函数）：
1. 根据渠道商 `partnerLevel` 确定使用哪层价格
2. 如果指定等级的价格为空，降级使用下层价格
3. 按数量和阶梯数量计算最终价格
