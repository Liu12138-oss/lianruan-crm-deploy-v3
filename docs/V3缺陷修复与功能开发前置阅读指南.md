# V3 缺陷修复与功能开发前置阅读指南

编写日期：2026-07-31  
适用项目：联软 CRM V3  
适用对象：后续接手缺陷修复、功能开发、测试复核、上线发布的开发和运维人员。  
核心目的：让接手人员先掌握必要上下文，再改代码，避免误把 V2 遗留文件当成 V3 主线入口。

## 一、先读结论

本项目不是单纯的新系统，也不是纯 V2 维护项目。当前真实形态是：

```text
V3 工程化代码 + PostgreSQL 数据底座 + V2 兼容接口 + V2 静态页面遗留资产
```

修复缺陷或开发功能时，必须先判断问题属于哪一类：

| 问题类型 | 优先查看位置 | 说明 |
| --- | --- | --- |
| V3 工程化页面问题 | `apps/web/src` | Vue 3、路由、布局、统一业务工作台 |
| V2 体感旧入口页面问题 | `apps/web/public` | 旧静态页面和脚本，当前仍可能被部署入口使用 |
| 后端业务接口问题 | `apps/api/src` | Express 5、PostgreSQL 查询、V2 兼容路由 |
| 任务或队列问题 | `apps/worker/src` | 当前主要是 BullMQ 健康任务底座 |
| 数据结构或迁移问题 | `database/migrations`、`scripts/migration` | PostgreSQL 结构、V2 数据迁移和校验 |
| 部署、健康检查、备份问题 | `deploy/single-server` | 单机离线部署、脚本、镜像、环境模板 |
| 旧系统参考问题 | `backend`、`frontend` | V2 旧代码，只读参考，不应作为 V3 主开发入口 |

最容易踩坑的地方：

1. 根目录 `README.md` 仍是 V2.2.0 说明，不能作为 V3 开发和部署依据。
2. `backend/` 和 `frontend/` 是 V2 旧系统目录，除非明确修旧入口，否则不要在这里做 V3 新功能。
3. `apps/web/public/` 仍包含旧静态页面，部分部署入口会跳到这些页面，修页面问题前必须确认用户实际访问的是 Vue 路由还是旧静态页。
4. 版本号存在历史交付不一致，发布前必须核对源码版本、镜像标签、离线包和部署模板。
5. 修改数据库、账号、权限、金额、报价、订单状态前，必须先确认业务规则和备份状态。

## 三、开发前必须弄清楚的问题

每个缺陷或新功能开始前，先回答下面问题。

| 问题 | 为什么重要 |
| --- | --- |
| 用户实际访问的是 `/admin`、`/admin.html`、`/partner`、`/partner.html` 还是 `/mobile` | 不同入口可能走不同前端实现 |
| 问题发生在测试环境、生产环境、本地环境还是离线包安装环境 | 环境不同，配置、版本、数据状态可能不同 |
| 当前部署版本是多少 | 仓库、离线包、服务器版本可能不一致 |
| 后端接口实际请求路径是什么 | V3 标准接口和 V2 兼容接口并存 |
| 数据来自 PostgreSQL 正式表、迁移暂存表，还是旧 SQLite | 决定修复位置和风险 |
| 是否涉及账号、角色、区域、渠道数据范围 | 这类问题容易变成越权缺陷 |
| 是否涉及报价金额、工作量、订单状态 | 这类问题必须有业务样本和回归用例 |
| 是否涉及数据库结构变更 | 涉及迁移、备份、回退和发布窗口 |
| 是否会影响旧入口或外部调用方 | V2 兼容层不能随便删改 |

建议在缺陷单或开发记录里写清楚：

```text
问题入口：
登录账号：
复现路径：
实际请求接口：
当前版本：
涉及数据表：
是否影响 V2 兼容入口：
是否需要数据库迁移：
验证用例：
回退方式：
```

## 四、源码入口速查

### 4.1 后端接口

| 文件 | 作用 |
| --- | --- |
| `apps/api/src/create-app.ts` | 后端应用创建、路由挂载、中间件、错误处理 |
| `apps/api/src/server.ts` | API 服务启动和优雅停止 |
| `apps/api/src/auth-routes.ts` | 登录、当前用户、退出、密码散列校验 |
| `apps/api/src/business-routes.ts` | V3 主业务接口路由 |
| `apps/api/src/business-store.ts` | 主业务数据服务，包含内存兜底和 PostgreSQL 实现 |
| `apps/api/src/v2-compat-routes.ts` | V2 兼容接口、旧导入导出、旧路径适配 |
| `apps/api/src/health-routes.ts` | 存活、就绪、依赖检查 |
| `apps/api/src/dependencies.ts` | PostgreSQL、Redis、迁移状态检查 |
| `apps/api/src/ipg-pricing.ts` | 报价参考价相关逻辑 |

后端定位顺序：

1. 先看浏览器或接口日志里的请求路径。
2. `/api/auth/*` 看 `auth-routes.ts`。
3. `/api/v2/*` 或旧前端调用，看 `v2-compat-routes.ts`。
4. `/api/registrations`、`/api/opportunities`、`/api/quotes`、`/api/orders` 等，看 `business-routes.ts` 和 `business-store.ts`。
5. 健康检查失败，看 `health-routes.ts` 和 `dependencies.ts`。

### 4.2 前端工程化页面

| 文件 | 作用 |
| --- | --- |

| `apps/web/src/pages/LoginPage.vue` | V3 登录页 |

4. 如果接口字段不对，先看 `business-client.ts` 再看后端响应。

## 五、按缺陷类型的定位清单

### 5.1 登录失败

先查：

1. 用户访问入口是 `/login` 还是 `/login.html`。
2. 请求是否到 `/api/auth/login`。
3. 生产配置是否启用 `V3_DELIVERY_AUTH_ENABLED`。
4. 数据库 `iam.users` 和 `iam.password_credentials` 是否有该用户。
5. Cookie 是否写入，跨域和安全属性是否正确。
6. 用户默认路径和允许路径是否匹配角色。

优先源码：

1. `apps/api/src/auth-routes.ts`
2. `apps/web/src/pages/LoginPage.vue`
3. `apps/web/src/stores/session.ts`
4. `apps/web/public/login.html`
5. `apps/web/public/api-client.js`

### 5.2 页面显示异常

先查：

1. 当前访问的是工程化路由还是旧 `.html` 页面。
2. 页面控制台是否有报错。
3. 对应接口是否返回 `success: true`。
4. 前端字段是否和后端响应一致。
5. 是否只在移动端或窄屏复现。

优先源码：

1. `apps/web/src/router/index.ts`
2. `apps/web/src/pages/BusinessWorkspacePage.vue`
3. `apps/web/src/layouts`
4. `apps/web/src/styles/theme.css`
5. `apps/web/public/*-app.js`

### 5.3 列表数据不对

先查：

1. 请求路径是 `/api/stage9/:module`、业务标准路径，还是 `/api/v2/*`。
2. 查询参数中的 `page`、`pageSize`、`keyword`、`status` 是否正确。
3. 当前用户角色和数据范围是否限制了结果。
4. PostgreSQL 正式表数量是否符合预期。
5. 旧入口是否期待 V2 字段名。

优先源码：

1. `apps/api/src/business-routes.ts`
2. `apps/api/src/business-store.ts`
3. `apps/api/src/v2-compat-routes.ts`
4. `apps/web/src/api/business-client.ts`

### 5.4 报价金额或工作量不对

先查：

1. 产品、硬件、套餐 ID 是否正确。
2. 端点数是否正确。
3. 工作量映射是否命中。
4. 工作量规则是否启用。
5. 是否走了兜底公式。
6. V2 样本期望值是什么。

优先源码和资料：

1. `apps/api/src/business-store.ts`
2. `apps/api/src/ipg-pricing.ts`
3. `database/migrations/20260728_S9_013_工作量映射维护.sql`
4. `docs/baseline/价格与工作量计算样本.json`
5. `docs/产品价格比例功能设计方案.md`

### 5.5 订单状态或审批异常

先查：

1. 报价是否已满足转订单条件。
2. 订单是否已有重复转单记录。
3. 一级确认、驳回、区域审批的状态码是否一致。
4. `ops.approvals` 和业务主表状态是否同步。
5. 是否需要写状态历史和审计日志。

优先源码：

1. `apps/api/src/business-store.ts`
2. `apps/api/src/business-routes.ts`
3. `apps/api/src/v2-compat-routes.ts`
4. `docs/baseline/现有业务状态机.md`

### 5.6 导入导出异常

先查：

1. 是 V2 兼容导入，还是 V3 任务查询。
2. 上传文件大小是否超过限制。
3. 模板列名是否匹配。
4. 错误行是否被记录。
5. 是否需要异步任务。

优先源码：

1. `apps/api/src/v2-compat-routes.ts`
2. `apps/api/src/business-store.ts`
3. `ops.import_export_tasks`
4. `apps/worker/src`

### 5.7 数据迁移异常

先查：

1. V2 源库快照是否一致。
2. 导出数量是否守恒。
3. 暂存装载是否成功。
4. `migration.validation_results` 是否有失败。
5. 正式落表迁移是否重复执行。
6. 是否出现未知角色、未知区域、未知状态、金额不一致。

优先资料和源码：

1. `docs/migration/V2导出操作手册.md`
2. `docs/migration/PostgreSQL暂存装载操作手册.md`
3. `database/mapping/data-quality-rules.yaml`
4. `scripts/migration`
5. `deploy/single-server/scripts/migrate-db.sh`

### 5.8 部署或健康检查失败

先查：

1. 容器是否都启动。
2. `/health/live` 是否通过。
3. `/health/ready` 是否显示 PostgreSQL、Redis、迁移失败。
4. `v3.env` 是否有数据库、Redis、会话密钥。
5. `migration.schema_migrations` 是否有迁移记录。
6. Nginx 代理是否能连到两个 API 实例。

优先文件：

1. `deploy/single-server/compose/docker-compose.yml`
2. `deploy/single-server/config/v3.env.template`
3. `deploy/single-server/config/nginx/default.conf`
4. `apps/api/src/dependencies.ts`
5. `deploy/single-server/scripts/health-check.sh`

## 六、开发新功能前的判断标准

### 6.1 必须确认是否属于当前阶段范围

当前阶段原则是“只迁移和修复 V2 已有能力”。如果需求属于以下类型，需要先走产品确认：

1. 公海池。
2. 新工作流引擎。
3. 多租户。
4. 微服务拆分。
5. 新外部系统双向同步。
6. 新支付、短信、地图服务。
7. 大范围重做页面交互。
8. 修改核心报价和订单规则。

### 6.2 优先复用现有模式

新增功能时优先使用：

1. 后端标准响应：`packages/shared/src/index.ts`。
2. 配置读取：`packages/config/src/index.ts`。
3. 前端请求封装：`apps/web/src/api/client.ts`。
4. 业务列表标准字段：`阶段9记录`。
5. 现有路由元信息和 `BusinessWorkspacePage.vue`。
6. 现有数据库 schema 和迁移命名规则。
7. 现有测试组织方式。

### 6.3 不要轻易做的事

1. 不要直接删除 V2 兼容接口。
2. 不要把新业务写进 `backend/server.js`。
3. 不要在生产代码里写死真实密码、密钥、服务器地址。
4. 不要绕过服务端权限只靠前端隐藏按钮。
5. 不要用浮点数决定金额。
6. 不要无迁移文件直接改生产表结构。
7. 不要让 Redis 成为唯一业务数据来源。
8. 不要为了修一个页面问题重构整个工作台。

## 七、修改前检查表

开始编码前，至少完成下面检查：

| 检查项 | 是否必须 |

```bash

```

并人工复核：

2. `migration.schema_migrations` 记录正确。
3. 正式业务表数量符合预期。
4. 失败记录和校验结果可解释。

### 8.7 修复问题全面性检查

缺陷修复不能只处理截图表象，必须把同一业务动作的状态语义、刷新链路和相邻入口一起核对。

修复前必须确认：

1. 用户实际点的是哪个入口、哪个按钮、哪个接口。
2. 该动作是新增、编辑、禁用、启用、删除、归档还是审批拒绝，不能把不同语义混成同一个状态。
3. 数据是否来自正式表、兼容字段、旧静态页面缓存或浏览器本地状态。
4. 列表页、详情页、弹窗页、右侧汇总区是否使用同一份数据。
5. 同一对象是否还有管理端、渠道端、手机端、导入导出、审批页、登录页等相邻入口。

修复时必须做到：

1. 优先修后端真实语义，前端只做展示和缓存同步。
2. 删除类动作刷新后不得再返回被删除对象；禁用类动作可以保留灰色或停用状态，但必须可重新启用。
3. 涉及账号、权限、渠道成员、审批、订单和报价时，必须检查历史引用是否需要保留，不能随意物理删除主数据。
4. 前端删除成功后，要同步当前详情、列表缓存和汇总计数，避免不刷新时仍显示旧数据。
5. 每个缺陷至少补一个能复现失败场景的回归测试；状态类缺陷要同时覆盖相邻状态，例如禁用和删除。

修复后必须验证：

1. 刚修复的接口直接调用正常。
2. 页面操作后立即显示正常。
3. 刷新页面后仍正常。
4. 重新登录或换角色后仍符合权限预期。
5. 远端环境 `/health/live` 的版本、容器镜像标签和业务字段确实是新版本。

### 8.8 升级包制作强制规则

V3 热修复升级包必须遵守生产 ZIP 约束，不能再沿用 V2 或历史离线包的做法。

强制规则：

1. 对外交付文件只允许 ZIP 包和 `.zip.sha256`，不允许 TAR、TGZ、7Z、RAR。
2. KB 包内不使用 `.tar` 文件名；Docker 镜像归档统一使用 `.docker-image` 后缀，并通过 `docker load -i 文件名` 加载。
3. 生产脚本不得调用 `tar`、`jq`、`python`、`rsync`、`expect` 等未承诺命令。
4. KB 脚本不得直接复用服务器旧 `backup.sh`，除非已确认该脚本不依赖禁用命令；更推荐在 KB 内自带 `pg_dump` 加 `zip` 的备份逻辑。
5. 升级脚本必须同步 `V3_IMAGE_TAG`、`V3_BUILD_VERSION`、`V3_BUILD_COMMIT`、`V3_BUILD_TIME`。
6. 升级后必须强制校验容器实际镜像、`/health/live` 目标版本、前端静态资源关键修复片段和业务接口关键字段。
7. 如果任何一项没有切到目标版本，升级脚本必须失败退出，不能只因为健康接口可访问就提示成功。
8. 包内 `manifest/SHA256SUMS`、外层 `.zip.sha256`、解压后脚本语法检查必须全部通过后才能交付。
9. README 必须写清楚执行顺序、影响服务、成功标准、日志路径和回退命令。
10. 只包含受影响镜像和脚本；未修改 Worker、数据库或配置时，不得把它们放进 KB 扩大影响面。

## 十二、当前已知前置风险

| 风险 | 对修复和开发的影响 |
| --- | --- |
| 根 `README.md` 仍是 V2 文档 | 新人容易按旧方式启动和部署 |

| V2 密码不恢复 | 登录类问题要区分迁移用户和交付账号 |
